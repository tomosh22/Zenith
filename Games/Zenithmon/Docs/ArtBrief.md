# Zenithmon -- Art Brief (Hand-Authored Asset Wishlist)

**Document purpose:** the list of assets a human artist would be commissioned to
make, ordered by how far the procedural generators fall short of them, each with
a short prompt that can be handed to an artist or a generative tool as a starting
description.

**★★ THIS DOCUMENT DOES NOT CHANGE POLICY, AND IT CONTRADICTS ONE.**
`AssetManifest.md` section 0.1 is explicit: *"Every asset is procedurally
generated and baked to disk by ZENITH_TOOLS builds ... There is no artist, no
outsourcing, no import pipeline -- the 'asset team' is generator/authoring
code."* That is still the operating rule and nothing below is scheduled,
budgeted or approved. This is a **wishlist**: what to buy first IF art budget
ever exists, written down while the gaps are freshly measured rather than
recalled later.

**★ AND ADOPTING ANY ROW HAS A COST THAT IS NOT THE ARTIST'S FEE.** Three
properties this game currently relies on would break the day a hand-made asset
lands, and they are load-bearing rather than incidental:

* **The bake is DETERMINISTIC and gitignored.** Every generated byte is a pure
  function of an id, which is what lets a fresh clone regenerate everything and
  what the whole determinism test layer asserts. An imported asset is a binary
  that must be committed, versioned and diffed -- see `CIPolicy.md` for why CI
  currently never sees these files at all.
* **There is no import pipeline.** `AssetManifest.md` says so and it is true:
  the engine has `ZenithTools` exporters, but Zenithmon has no route from a DCC
  file to a `.zmesh`/`.ztxtr`, and no place to put source art.
* **The generators are the fallback.** `ZM_GreyboxVisual`, `ZM_BuildingFacade`,
  `ZM_InteriorShell` and `ZM_InteriorFurniture` all degrade to "nothing renders"
  on a clone with no bake. A mixed library needs a rule for what happens when
  half of it is present.

So a row being high on this list means "this is where the generator hurts most",
never "this is next".

**Companion docs:** `AssetManifest.md` (what the generators actually produce, and
the rule above), `GameDesignDocument.md` (what the assets depict),
`Scope.md` (the binding in/out list -- nothing here is in it),
`Shortfalls.md` (known gaps), `MapLayoutPlaybook.md` (why building and prop
footprints are constrained).

**Last updated:** 2026-08-30, written immediately after the Dawnmere building and
interior overhaul (ZM-D-219/220/221), which is what makes the gaps below measured
rather than guessed: buildings, rooms, props, humans and creatures all now carry
four-map PBR sets, so what remains missing is FORM, not material.

## 0. The tick-off protocol

Every commissionable item below is a checkbox row, in the same shape
`Roadmap.md` uses. The convention there is ZM-D-162: **where a document and a
checkbox disagree, the checkbox wins, and it is scored against its LITERAL
TEXT.** That applies here too.

### 0.1 The row format

```
- [ ] `AB-PROP-01` **Bed** -- 2.0 x 1.2 x 0.7 m -- <prompt>
```

and once the asset is in the game:

```
- [x] `AB-PROP-01` **Bed** -- 2.0 x 1.2 x 0.7 m -- <prompt> -- source: `Games/Zenithmon/Art/Props/Bed.gltf`
```

* **The id is stable and never reused.** It is what a ticket, a commit message
  or an invoice references. Ids are `AB-<FAMILY>-<NN>`; append, never renumber.
* **A ticked row MUST carry a `source:` path**, and that path must exist.
* **An unticked row must NOT carry one.** A half-delivered asset is unticked
  with its state in section 9, not ticked with a caveat.

### 0.2 What a tick asserts -- three things, all of them checkable

A tick means **the game loads this asset instead of the generated one**. Not
"the artist has delivered", not "it is in the repo". Specifically:

1. the `source:` file exists at the path the row names;
2. the import produces the same file set the generator produced, so every
   consumer keeps working (`AssetManifest.md` owns those file sets);
3. the generated fallback still exists and still works, because a clone with no
   art must still boot -- see the third bullet at the top of this page.

**★★ THE FIRST OF THOSE IS ENFORCED, THE OTHER TWO ARE NOT.** `doc_lint.ps1`
check **C8** reads every row on this page and fails if a ticked row names no
source, if a ticked row's source is not on disk, if an UNticked row names one,
or if two rows share an id. The other two conditions are judgement and are the
reviewer's job. **Do not read a green C8 as "the asset ships correctly"** -- it
only means the row is not lying about a file.

That asymmetry is deliberate and is the same one `Status.md`'s LIVE PIN block
lives with: a machine can reconcile a claim against an artefact, and cannot
reconcile it against an intention.

### 0.3 Why there is no separate status file

The obvious design is a `ArtAssets.json` beside this page with a state per id,
reconciled the way `Tools/unit_baselines.json` is reconciled against
`Status.md`. It was rejected: a pin is a NUMBER that several gates read, so it
needs a machine-readable home, whereas an art row is read by people and by one
lint check. **A second home would be a second thing to keep in step**, and this
repo has paid for that before -- the unit baseline was duplicated across four
files until it was given exactly one. The checkbox IS the record.

### 0.4 Every asset is itemised -- there are no batch rows

**One asset, one row, one prompt, one checkbox.** Every commissionable thing in
this game has its own line, including all 152 creature models, all 152 creature
cries, all 35 humans and all 30 buildings. Nothing is tracked as "0 of N".

**★ AN EARLIER DRAFT BATCHED THE BIG FAMILIES, AND IT WAS WRONG.** It grouped
creatures by archetype and generic humans into one row, arguing that a hundred
and fifty-two checkboxes are a worse tracker than a number. That reasoning is
comfortable and does not survive contact with the actual job: a batch row cannot
be TICKED until the whole batch ships, so it reads as untouched through the
entire commission, and the count beside it is a hand-maintained number nothing
reconciles -- exactly the stale-duplicate shape this repo keeps paying for.
**A per-asset row is the only granularity at which a tick means anything**,
because it is the granularity at which the work is actually commissioned,
delivered, reviewed and invoiced.

It also makes the page mechanically countable: `doc_lint` check C8 reports
"X of Y ticked" on every run, so progress is a measured number rather than a
narrated one.

**★ THE ROWS ARE GENERATED FROM THE ROSTERS, NOT TYPED.** The creature, cry and
human rows were emitted from `Source/Data/ZM_SpeciesData.cpp` and
`Source/Data/ZM_HumanData.cpp` -- name, element pair, archetype, evolution
stage, rarity, build, outfit and attachment all read from the tables rather than
recalled. **Regenerate them the same way when a roster changes**, and keep the
ids: an id is stable even if the species it names is later retyped.

### 0.5 Adding a row

Append it to the right family with the next free id, unticked, with a prompt.
Do not renumber, do not reuse an id from a deleted row, and do not tick a row in
the same change that adds it -- a row that arrives already ticked has never been
read by anyone as a claim.

### 0.6 Prompts, and the numbers in them

Each row carries a **prompt** -- one or two sentences that describe the asset
well enough to brief it. They are deliberately short and deliberately name the
constraint that matters, because the constraints here are unusual: this game's
assets are sized against compiled constants that tests measure.

**★ EVERY PROMPT THAT NAMES A DIMENSION IS QUOTING A COMPILED CONSTANT.** They
are not stylistic suggestions. A prop wider than its slot, a building deeper than
its blockout or a human taller than `fZM_HUMAN_BODY_HALF_HEIGHT` does not look
slightly wrong -- it fails a unit, or walks through a wall. Where a number
appears, the header that owns it is named beside it.

Priority is **P1** (the generator cannot reach this at all), **P2** (the
generator reaches it but the result reads as generated), **P3** (the generator is
adequate; art would be polish).

## 1. Props -- 28 sets  *(P2, and the clearest single win)*

**The gap, measured.** Props are box compositions with a palette. Since ZM-D-221
they carry a full four-map PBR set -- normal, roughness/metallic, occlusion --
so they are lit, weathered and materialled like everything around them. What did
not change is the FORM: a bed is a recognisably generated arrangement of boxes.
This is the one family where a modest amount of art would change the most,
because the interiors put furniture at conversation distance in a lit room.

Roster and sizes: `Source/Data/ZM_PropData.cpp` (`m_fWidth / m_fDepth /
m_fHeight`).

### 1.1 Interior furniture -- highest value, seen closest

- [ ] `AB-PROP-02` **Table** -- 1.4 x 0.9 x 0.9 m -- A plain four-legged kitchen table in stained timber, scuffed along one edge. Nothing on it; props are placed separately.

**★ THE FOOTPRINT IS A HARD CONSTRAINT, NOT A GUIDE.** Interior furniture carries
an AABB static collider sized from its own mesh bounds

collider in a corridor the automated walk driver has no way around

## 2. Creature species -- 152  *(P1, and by far the largest single commission)*

**The gap.** Creatures are lofted from eight archetypes with per-species
proportions, a type palette and a shiny hue rotation. Every species is
recognisably its archetype with the numbers changed. **This is the only family
where the generated result cannot approach the goal**: a monster-collecting game
is about the individual identity of 152 characters, and a parametric loft cannot
give 152 silhouettes anyone would tell apart.

It is also the least likely thing on this page to be commissioned, at 152 rigged
and animated models. Recorded at its true size rather than a comfortable one.

**Prompt (per species):** *An original creature of the [TYPE] element in the
[ARCHETYPE] body plan, readable in silhouette at 64 px, with one memorable
identifying feature. Rigged to the shared [ARCHETYPE] skeleton and animated for

changes HUE ONLY -- the mesh must not move, because both variants share one
relief set.*

## 5. Interiors  *(P3 -- the generator is good here)*

floor, walls, ceiling, trim -- on a [W] x [D] m footprint with [H] m walls and an
entrance gap of [Aw] x [Ah] m centred on the +Z wall. Furniture is placed
separately and must not be modelled in.*
