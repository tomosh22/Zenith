## Goal
`Status.md` R1 slice table, **R1-6**: author the two Route 1 trainers (the Rambler and the Forager, rows and appearances from R1-5 / ZM-23) into `Route1.zscen` as NPC entities carrying `ZM_Interactable` with `ConfigureTrainerSight`, at the two trainer stations `Source/World/ZM_Route1Placement.h` already declares with FROZEN ground columns and a sight-cone justification. Do not re-derive or move the stations: the header's banner explains why a trainer more than 4 m off the walked lane can never be triggered in any playthrough while every check stays green.

**Why this needs a GPU, stated correctly.** Not the `.zscen` publish guard (ZEN-6 removed it 2026-08-26). Zenithmon itself defers scene authoring on a Null backend (`sceneAuthoring=DEFERRED`, `Zenithmon.cpp`), so re-authoring `Route1.zscen` follows the ZM-D-190 order: build both configs, authoring boot on `Vulkan_vs2022_Debug_Win64_True` with `--skip-unit-tests`, `git status` the whole `Assets/` tree (a Vulkan boot authors every scene), a second boot proving byte-identity, then the gate on the `Null_` exe.

**Hazards this slice owns (ZM-D-196 ruling 3):** every armed trainer is a trap for every other Route 1 test. The between-tests hook clears `ZM_TrainerEngagementLatch`, so each trainer is RE-ARMED per test and distance is the only guard (8 m, cos30 cone). Pin the minimum clearance from BOTH gate approaches and from the walked lane's drive legs as boot units against the placement header, the way `ZM_DawnmereDressing.h`'s leg table does for Dawnmere. Both trainers are flagged (per-trainer defeat flag), so a lost battle and a return must NOT re-engage: extend `Tests/ZM_AutoTests_TrainerBattle.cpp` with a Route 1 arm or add a sibling test that drives the sighting on the real scene. The committed-bytes needle in `Tests/ZM_Tests_CommittedSceneBytes.cpp` must see both NPC payloads exactly once (strictly-more form for any name that collides with a component type name, ZM-D-197).
