**Why this needs a GPU, stated correctly.** ZEN-6 (2026-08-26) removed the engine's `.zscen` publish guard, so "a headless run may create but never change a scene" is no longer true and must not be repeated. What is still true is Zenithmon's own choice: `Zenithmon.cpp` defers every scene-authoring step on a Null backend (`sceneAuthoring=DEFERRED` in the `[ZM Terrain] Batch result` line) because the terrain bake needs a device. So the ZM-D-190 order applies: build `Null_` and `Vulkan_vs2022_Debug_Win64_True`; run the authoring boot on the Vulkan `_True` exe with `--skip-unit-tests` (the RED-BY-DESIGN needles from ZM-73 would otherwise abort the boot before authoring); `git status` the WHOLE `Assets/` tree; a second boot proving byte-identity; only THEN the gate on the `Null_` exe.

**What the door authors.** Two entities appended to Thornacre after `ThornacreSouthGate` (ZM-D-148 dense indices: append, never insert): a `"FromGym"` `ZM_SpawnPoint` and a `ZM_WarpTrigger` to build index 42 asking for tag `"Door"`. Entity count 5 to 7. Naming: U14 clause (6) forbids any entity name containing an offered tag or a tag the town's edges ask for, so `ThornacreFromGymSpawn` and anything containing `Door` are illegal. The gym-door column is placed per ZM-72 ruling 2 and its ground is FROZEN from a real downward raycast (the `Tests/ZM_AutoTests_RouteGround.cpp` oracle), never derived from a neighbour (ZM-D-203 §5, ZM-D-206).

A windowed `_True` boot authors before it tests. Expect exactly `Gym1.zscen` (new) and `Thornacre.zscen` in `git status`; Dawnmere and Route1 must come back byte-identical. Two consecutive boots must agree before anything is committed, and the committed-asset table in `Docs/Status.md` gains a `Gym1.zscen` row (bytes and SHA256) in the same commit.
