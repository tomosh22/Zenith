## Goal

`zagent board status --project ZM` reports one drift row, and has since the
check existed:

```
missing-issue   ZM-2       named in Roadmap.md but no such issue
```

**The documents are right and the board is wrong.** Two living docs name
`ZM-2`, and neither is a stale citation:

- `Games/Zenithmon/Docs/Roadmap.md` — `## [ZM-2] S1 -- Data core (M) -- parallel with S3/S4`,
  a section whose every item is `[x]` and whose gate reads *"MET 2026-07-10 -- 102
  `ZM_*` `ZM_Data` unit tests"*.
- `Games/Zenithmon/Docs/Board.md` §2 — the stage-epic table maps `S1` to `ZM-2`
  directly, and states the intent out loud: *"S0-S7 are on the board as Done
  epics, not omitted. They are the audit trail the board is supposed to be, and
  an epic tree starting at S8 would make this project look like it began in
  August."*

Every other stage resolves: S0 is `ZM-1`, S2 is `ZM-3`, on through S12 as
`ZM-13`. ZM issue numbers run 1..63 with exactly one gap, at 2. S1 is the sole
stage with no epic, and the roadmap section proves the work itself shipped —
so this is a hole in the audit trail, not an unbuilt stage.

**The key has to be `ZM-2` specifically.** Filing a new epic will not fix this:
`packages/agent/src/board.ts` allocates `number: COALESCE(MAX(number), 0) + 1`,
so a `zagent create` today produces `ZM-64`. Accepting `ZM-64` would mean
editing both documents and leaving S1 as the one stage outside an otherwise
exact S0->`ZM-1` .. S12->`ZM-13` mapping — trading a board defect for a
permanent documentation wart.

**Why this is labelled `windowed`.** Restoring a specific issue number needs an
explicit-number insert on the board, and no `zagent` verb offers one — `create`
can only ever append. A loop worker has neither shell nor board access, so it
cannot do this at all, and the gates that would notice are all green already.
