## Goal

**ZM-D-183 has recurred on `Dawnmere.zscen`, and the value is NOT Vesper's
facing.** `Games/Zenithmon/CLAUDE.md` carries a warning for exactly this — *"IF
THIS BREAKS A THIRD TIME, DO NOT ASSUME IT IS THE SERIALIZER"* — and this is the
third time.

MEASURED on ZEN-91 (2026-09-21), same 76-entity / 85199-byte scene, three
MUTUALLY DISTINCT byte states:

| state | differs from committed |
|---|---|
| committed on `master` | — |
| `Vulkan_vs2022_Debug_Win64_True` boot (×4, all byte-identical to each other) | 15 bytes |
| `Vulkan_vs2022_Release_Win64_True` boot | 6 bytes |

Debug and Release differ from **each other** by 9 bytes. Every boot re-authors
the scene deterministically *within* its configuration — four Debug boots agreed
bit-for-bit — so from inside either config this is indistinguishable from a
stale committed artifact. ZEN-91 nearly re-published it on that reading and was
stopped by a cross-configuration boot, which is the only test that separates the
two.

The drift is roughly **2 ULP**, in five groups of three consecutive identical
floats, near a stored `1.0f`. That is the same magnitude and the same mechanism
`ZM-D-183` records for MSVC Debug vs Release codegen disagreeing on
`std::atan2` fed to `glm::angleAxis`.

**But ZM-D-183's fix froze `ZM_DawnmereVesperFacing()` specifically, as four
`std::bit_cast` constants authored via `AddStep_SetTransformRotationQuat`, and
this is not that value:** a quaternion is four components and these are vec3s
(three identical floats per group, five groups). So a DIFFERENT authored value
in Dawnmere is still derived from runtime float math rather than a frozen
constant, and it ping-pongs the committed file between configurations exactly as
the rival's facing used to.

Find that value and freeze it the way ZM-D-183 froze the facing. Then re-publish
`Dawnmere.zscen` once, from any configuration, and confirm a boot under BOTH
`Debug` and `Release` leaves it byte-identical.

**Do not re-publish the scene before the value is frozen.** ZEN-91 deliberately
left `Dawnmere.zscen` uncommitted-to for this reason, and recorded in
`Games/Zenithmon/CLAUDE.md` that a dirty `git status` after a Dawnmere-authoring
boot is EXPECTED until this lands. Re-publishing first just moves the ping-pong's
starting point and hides the defect again.

Useful starting points, none of them confirmed:

- The differing floats sit near offsets 82850, 83013, 83176, 83339 and 83496 in
  the committed file, each group being three identical values with a `1.0f`
  immediately before — consistent with a colour, a uniform scale, or a
  normalised vec3 on five similar entities.
- `Zenith_TransformComponent`'s serialization was already hardened once by
  ZM-D-179; this is a different field.
- The two committed-vs-config deltas differ in SIZE (15 bytes vs 6), so the
  committed bytes are themselves a third state — probably authored by an older
  build or a third configuration — which means whatever is chosen as the frozen
  value should be derived deliberately, not taken from whichever boot happens to
  run first.
