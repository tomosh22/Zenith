## Goal
`Roadmap.md` S9: *"`ZM_UI_Box`, the storage screen. RE-DEFERRED HERE FROM S7 on 2026-07-29 (ZM-D-165, Q-2026-07-29-001)."* The storage MODEL is not outstanding: `ZM_SaveSchema` has persisted boxes 16x30 since S7 item 1 (ZM-D-136) in `Source/Party/ZM_BoxStorage.h`, deterministic and transactional. What is missing is a PRESENTER, in the S6 `Source/UI/ZM_UI_*` by-value idiom: no schema change, no new ECS order, no serialization bump.

It belongs at S9 because a box is only functional once the player can exceed a full party, which needs S9 routes and encounter tables (ZM-31, ZM-32 block this). Built earlier, its only reachable state is empty, which cannot be play-tested. **Do not let this deferral expire unremarked a second time.**

Scope: a Box screen reachable from a Care Center PC interactable (an `ZM_NpcData` role or an interactable prop; the Care Center interior template ZM-75 places it) with a box selector (16), a 6x5 grid per box on `Zenith_UIGridLayoutGroup` (E4), party strip, deposit / withdraw / move / release, and the full-party and last-monster refusals. Two engine rules from S6 apply verbatim (Shortfalls §1.6): never bake `SetNavigation` links into a widget pool whose members are shown or hidden at runtime (paged grids break on partial pages; use the spatial fallback), and a windowed UI test must drive REAL arrow-key edges and poll the focused element's name with a deadline, never park focus programmatically. A catch that overflows the party (`ZM_BattleWriteBack`) already lands in box storage; surface it with a line naming the box.
