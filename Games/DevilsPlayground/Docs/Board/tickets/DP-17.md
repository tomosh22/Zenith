## Goal
MvpRoadmap MVP-4.1.3 (*"Re-bake .zscen; no standalone CI step yet"*) and Shortfalls §3.4 and §5.3 (*"No CI for .zscen re-baking; content drift between authoring code and baked assets is a constant low-grade risk"*). ProcLevel is generated at runtime, but `ProcLevel.zscen` and `FrontEnd.zscen` are still authored by the tools boot, and the parity program recorded that the DP suite DIRTIES `ProcLevel.zscen` on every run, which is exactly the drift.

Make the DP scene authoring deterministic and prove it the way ZM does: two consecutive tools boots produce byte-identical `ProcLevel.zscen` and `FrontEnd.zscen`, a boot unit reads the committed bytes and reds on drift (the `ZM_Tests_CommittedSceneBytes` shape), and the test suite leaves `git status` clean after a full headless run. Find why the suite writes the scene (a save on teardown, an authoring step that runs per test) and fix it at the source. The CI step itself is a human task once the check exists. DP gates: `zenith build DevilsPlayground --headless`, the D3D12 link proof and `zenith test DevilsPlayground --headless`; the DP suite has no pinned unit-count row, so no pin bump applies unless `Zenith/**` is touched.

## Definition of Done
- [ ] Two consecutive tools boots produce byte-identical DP scenes and a boot unit guards the committed bytes
- [ ] A full headless `zenith test DevilsPlayground` leaves `git status` clean
- [ ] `Shortfalls.md` §3.4 and §5.3 and `MvpRoadmap.md` MVP-4.1.3 reflect the shipped state
