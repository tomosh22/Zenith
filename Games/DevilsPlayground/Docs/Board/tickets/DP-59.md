## Goal
ZEN-84 made `RenderTestTennis::Integration{LoadWiring,BlackboardPublish}` self-sufficient and added `Tools/check_boot_unit_assets.ps1`, a lint for the same shape. On its first real run that lint found the **identical defect in DevilsPlayground**, and the mechanism is confirmed, not inferred:

- `Games/DevilsPlayground/Tests/Test_DPGraphNodeWorldPins.cpp:124` calls `AddGraphByAssetPath("game:Graphs/DP_Door.bgraph")`.
- `Games/DevilsPlayground/Tests/Test_DoubleDoorAndForge.cpp:135` does the same for `game:Graphs/DP_DoubleDoor.bgraph`.
- **Zero `.bgraph` files are tracked anywhere in this repo** (`git ls-files '*.bgraph'` returns nothing); `**/Assets/**` is gitignored.
- Both assets are written only by `Games/DevilsPlayground/DevilsPlayground.cpp:2431`'s `xAuto.AddStep_GraphBuild(...)`, which merely QUEUES a `GRAPH_BUILD` action.
- A unit-gate boot never drains the editor-automation queue: units run at `Zenith_Engine.cpp:971`, `Project_RegisterEditorAutomationSteps()` only at `:993`, and `--exit-after-unit-tests` exits at `Zenith_Main.cpp:187` before the main loop.

So these tests can only be reading what an earlier tools boot left on disk: green on a warm tree, red on a fresh clone or straight after a clean, and the gate's `ran == baseline` pin counts it either way.

**What has NOT been verified**: nobody has run a cold DevilsPlayground gate. The mechanism is established; the symptom is not. Confirm it before fixing, and say what you observed.

`RenderTest_Tennis.Tests.inl`'s `EnsureTennisBrainGraphAssetAuthored()` is the worked example to copy, including the two defects review found in it: mirror `Zenith_EditorAutomation.cpp:3480-3495` (a failed `Build()` REMOVES the stale asset and writes nothing, because `ZENITH_ASSERT_TRUE` is record-and-continue and will not stop a bad write), and evict the registry cache after the save or the next read returns the prior load rather than the bytes just written.
