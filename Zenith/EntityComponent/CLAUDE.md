# EntityComponent — concrete components + ECS↔engine glue

This directory holds the **engine-side** half of the entity-component system: the
concrete built-in components and the glue that wires the generic ECS to the rest
of the engine. Everything here compiles into the aggregate **`Zenith`** engine lib
(NOT the leaf), because these files name concrete component / Flux / Physics /
editor types.

> The **generic ECS machinery** — entities, scenes, queries, events, the
> component-meta registry, the entity store — is the **`ZenithECS` leaf library**,
> physically located in [../ZenithECS/](../ZenithECS/CLAUDE.md). Read that doc for
> the ECS core (`Zenith_SceneSystem`, `Zenith_Entity`, `Zenith_Query`,
> `Zenith_EventDispatcher`, `Zenith_ComponentMeta` machinery, component pools,
> scene loading, lifecycle). This doc covers only what stays engine-side.

## Files

### `Components/` — the concrete built-in components
Each component lives in `Components/Zenith_*Component.{h,cpp}` and self-registers
via `ZENITH_REGISTER_COMPONENT` semantics (the explicit set + order is installed by
`Zenith_ComponentMeta_Registration.cpp`, below):

| Component | Purpose |
|---|---|
| `Zenith_TransformComponent` | Position, rotation, scale, model matrix; reads ECS slot hierarchy for parenting |
| `Zenith_CameraComponent` | View/projection matrices |
| `Zenith_ModelComponent` | Renderable mesh with material |
| `Zenith_LightComponent` | Dynamic lights |
| `Zenith_SunComponent` | Scene-authored solar direction/time-of-day authority; no colour or radiance fields |
| `Zenith_AtmosphereComponent` | Scene-authored physical atmosphere medium (Rayleigh/Mie density scales, Mie-G, both scale heights, capture ground albedo); co-authored with `Zenith_SunComponent` on one environment entity and resolved together through `Zenith_EnvironmentAuthorityData` (replaces the old `Zenith_SunAuthorityData` Sun-only gather). With `BlendRadius > 0` it is instead a **local blend volume** that lerps the medium over the global one at the view position — see `Components/CLAUDE.md` |
| `Zenith_ColliderComponent` | Physics collision shapes (Jolt) |
| `Zenith_TerrainComponent` | Heightmap-based terrain |
| `Zenith_InstancedMeshComponent` | GPU-instanced mesh rendering |
| `Zenith_ParticleEmitterComponent` | Particle effect emitters |
| `Zenith_GraphComponent` | Behaviour Graph host (designer-authored .bgraph logic; see below) |
| `Zenith_UIComponent` | UI element support |
| `Zenith_AnimatorComponent` | Skeletal animation state machine (separate from ModelComponent). Records the `.zanimctrl` `LoadControllerAsset` was last given — normalized, serialized (schema 2), readable via `GetControllerAssetPath()`, and recorded on an INCOMPLETE build too (the bool is the completeness verdict; the getter is not). It is what the anim-state-machine editor matches the selected entity against to decide whether to highlight from that entity's live controller instead of its own preview — so a weaker match (a layer count, a state name) is not an option here |
| `Zenith_TweenComponent` | Property tweening |
| `Zenith_AttachmentComponent` | Reusable bone-attachment for held objects (e.g. weapons, rackets); follows a named bone on a different entity each frame in OnLateUpdate |
| `Zenith_NavMeshComponent` | Baked-navmesh holder: carries a `.znavmesh` asset ref, loads it in `OnStart`, and OWNS the mesh for its own lifetime (see below) |

These name Flux / Physics types and so cannot live in the leaf. The leaf stores and
dispatches them generically through `Zenith_ComponentMeta` without naming a concrete
type.

### ECS↔engine glue (the wiring the leaf cannot contain)
- **`Zenith_ComponentMeta_Registration.cpp`** — defines `Zenith_RegisterEngineComponents()`, which calls `RegisterComponent<T>(name, order)` for the built-ins (Transform=0, Model=10, Tween=12, Animator=15, Camera=20, Light=25, Sun=26, Terrain=40, Collider=50, Graph=60, UI=70, InstancedMesh=80, ParticleEmitter=85, Attachment=95, NavMesh=96) then `Zenith_AI_RegisterComponents()` (AIAgent=90). In `ZENITH_TOOLS` builds it also mirrors the set into the editor "Add Component" registry. `Zenith_Engine::Initialise` installs this via `SetComponentRegistrar(&Zenith_RegisterEngineComponents)` then `EnsureInitialized()`. **Orders are centralised here.**
- **`Zenith_CameraResolve.h/cpp`** — the engine-side main-camera resolver. The leaf exposes only `FindMainCameraEntityAcrossScenes()` / `GetMainCameraEntity()` (EntityID-only); `Zenith_GetMainCamera(pxSceneData)` here wraps that and resolves to a `Zenith_CameraComponent&` (naming the concrete type, hence engine-side); `Zenith_GetMainCameraAcrossScenes()` returns a `Zenith_CameraComponent*` (pointer, nullptr if no loaded scene has a resolvable main camera).
- **`Zenith_ComponentEditorRegistry.h/cpp`** — the editor "Add Component" registry (display name + has/render/add callbacks per component type). Consumed by the editor property/hierarchy panels.
- **`Zenith_GraphNode_Registration.cpp`** — `Zenith_RegisterEngineGraphNodes()`, the engine Behaviour-Graph node library (**141 nodes** — this figure was stale at 128 for five node families, so count it with `rg -c "RegisterNodeType<" Zenith/EntityComponent/Zenith_GraphNode_Registration*.cpp` rather than trusting the line). The core TU holds events (12 sources incl. Timer/OnCustomEvent/OnGraphCall), blackboard scalar ops (retrofits: CompareBlackboardFloat var-vs-var, AddBlackboardFloat Delta input + dt-scale, Wait Seconds input, Loop Count input, LoadSceneByIndex loadMode), transform/entity actions (entity-targeted via `m_strTargetVar`), FireCustomEvent (+target/+payload)/BroadcastCustomEvent, and Wait/Branch/Gate/Once/Loop; domain families live in sibling sub-registrar TUs it calls — `_Input.cpp` (two layers: DEVICE — key/mouse/touch sources + queries incl. ReadMousePickRay, sim-aware — and ACTION — `OnActionPressed`/`OnActionReleased`/`OnActionHeld`/`ReadActionAxis1D`/`ReadActionAxis2D`, which name an action string resolved once per node instance against `g_xEngine.Actions()`, cached until the property changes, inert + one logged error when nothing matches), `_Flow.cpp` (SwitchOnInt/String, StateMachine, Selector, **Sequence** — the Blueprint-style exec FAN-OUT, 1–64 independent branch pins, RUNNING while any branch is suspended and never FAILURE;   - **The Blackboard family gained its READ half: `GetVariable` (B-3).** `SetBlackboard*` write a named variable; `GetVariable` is the one node that turns a declared variable into a **WIRE**, and it is the only node in the library whose output type comes from the GRAPH rather than from its own class or instance — `ZENITH_GRAPH_PIN_OUTPUT_FROM_VARIABLE(Value, "m_strVariable")` types the Value pin as the **declared** type of whatever `m_strVariable` names, so there is no `GetVariableFloat`/`GetVariableInt` family to keep in step. It is **PURE**: no exec pins at all, evaluated on demand inside whichever consumer gathers its wire and memoised for that gather. Three contracts worth knowing before wiring one. (1) A **missing** variable is `FAILURE` and nothing else — the consumer takes its own pin default plus one `[GraphPin] STATUS` line; it never writes a fabricated zero, which the consumer could not tell from a variable that really held zero. (2) It compares the live value's TAG to its own resolved slot type **itself** and FAILS on disagreement, rather than letting `SetOutput` refuse the write — a refusal would leave the stamped zero SET and the node would report SUCCESS while the consumer silently read 0. (3) The from-variable descriptor binds NOTHING (no var-name, no const, no fallback), so reading a variable can never register this node as an annotated **writer** of it; the blackboard read itself is the `SELECTOR_READ` pin beside it, which is what declare-or-error reports. Full rationale: `../Scripting/CLAUDE.md` § *Validation*.

  ### Historical B6/B7 migration record (superseded for authoring)

  The following per-TU B6/B7 narrative records the pre-C1 migration. It is not
  current authoring guidance where it describes INPUT/OUTPUT name properties,
  fallback reads, dual writes, counters, or pre-C1 factory forms. The final C1
  contract below governs current engine node work.
  - **Pin descriptor tables (the graph validator's view of these nodes).** Every node class in the swept registration TUs that declares a blackboard-variable-NAME property (`m_str…Var…`, which includes `m_strVariable`) now carries a `ZENITH_GRAPH_PINS_BEGIN … END` table beside its property table, saying for each such name which DIRECTION the value flows, what TYPE it is, and which property carries the name; `Zenith_GraphDefinitionValidator` reads those tables and nothing else, so **a node with no table is OPAQUE** — it contributes no writer and performs no read that any check can see. The role rulings are binding and live in ONE place, `../Scripting/CLAUDE.md` § *Validation* (with the macro list in `../Scripting/Zenith_GraphPinTable.h`): read them before annotating a new node, because the role follows what `Execute` DOES with the name, never the name's spelling — `WaitForCondition.m_strConditionVar` is `SELECTOR_READWRITE` (it consumes the flag) while `Branch.m_strConditionVar` is a read-only `INPUT`. Two mechanical traps: tables **inherit** like property tables, so the collision-source family is annotated on `Zenith_GraphNode_CollisionSourceBase` ONLY (a `PINS_BEGIN` in a derived class SHADOWS the base's rather than extending it), and a pin NAME is a bare identifier that is token-pasted, with a duplicate within one table asserting at static init. A string property that is not a blackboard name is not a pin (`m_strEventName`, `m_strScenePath`, `m_strAction`, `m_strElement`, `m_strCases`, …), and a constant with no var partner is not a pin either — `INPUT_CONST` is only for the `SetBlackboard*` value. Each TU's `.Tests.inl` carries a `GraphPinTable` **totality** test that runs THAT TU's registrar into a swapped-and-RAII-restored registry and fails any type with a variable-name property no descriptor covers (shared harness: `Zenith_GraphPinTotality.TestHarness.inl`), plus a role spot check — so the coverage is total by construction and a node added tomorrow needs no list updated.
  - **★ THE MATHS/BLACKBOARD TU'S PINS ARE LIVE (B-6.1) — `_Math.cpp` is the first node TU where a wire actually carries a value.** All 16 nodes read their INPUT descriptors through `Zenith_GraphNode::GetInput` / `GetInputPackedEntityID` / `TryGetInput` and write their OUTPUT descriptors through `SetOutput`, so a data edge into or out of any of them works. An **UNCONNECTED** node is byte-for-byte what it was, which is the whole proof: the transitional var-name fallback IS the old `var.empty() ? const : bb->GetX(var, const)` read, and `SetOutput`'s dual-write IS the old `SetValue` — the 18 pre-existing op tests are unchanged, and so are the totality and role spot checks. Four things to know before migrating another TU the same way. (1) **Each node declares `static constexpr u_int uPIN_<Name>` immediately before its `ZENITH_GRAPH_PINS_BEGIN`** — in the `public:` section the property block opens (`PINS_BEGIN`'s own `public:` comes AFTER the constants; `PINS_END` restores `private:`), because the pin INDEX is what every accessor addresses — table order is the contract, and `GraphPinTable.MathPinIndicesMatchTables` asserts the name, the role AND the pin count per class so an INSERTED pin fails rather than silently re-pointing every constant. A `static_assert` is impossible: the tables are filled at static init. (2) **A `GetInput` call must sit in EXACTLY the branch its blackboard read occupied** — `Lerp*`'s `T` only inside the mode-0 else, or a rate-mode node logs a census line for a pin it does not use and (in a graph) pulls its producer. (3) **Selectors, LIST names and the comma-list exemption stay DIRECT**: `MathBlackboard*.m_strVar` (`SELECTOR_READ`), the `Add*`/`Lerp*`/`Clamp*` `SELECTOR_READWRITE` variables — read AND written back directly, since a READWRITE reference is never a wire — and `LogicBlackboardBool.m_strVars`, which is N names in one string. The in-place maths write is NOT one of these: it is the Result pin's FALLBACK, so the `m_strResultVar.empty() ? m_strVar : m_strResultVar` ternary disappears from `Execute` and the dual-write lands exactly where it used to. (4) **`MathBlackboardVector3`'s Result slot is stamped from `GetPinType` once, at bind time**, so ops 4/5 write a FLOAT into a FLOAT slot — and changing `m_iOp` on a live instance does NOT re-stamp it (the next mismatching write is refused with one `OUTMISMATCH` line; use a fresh node per op). **The one deliberate divergence:** an OUTPUT whose var name and fallback both read EMPTY no longer creates a blackboard variable literally named `""`, which today's unconditional `SetValue` did — unobservable given the non-empty var-name defaults every shipped node carries (an author who blanks BOTH names on an attached graph would move that slot's serialised blackboard, i.e. `.zscen` bytes — no shipped content does) and pinned by `MathPinRuntime.EmptyOutputVarNameCreatesNoBlackboardEntry`. **The ~14 direct-construction tests in this TU** (a node on the stack, a bare context, results read off the blackboard) work because the accessors SELF-BIND — see `../Scripting/CLAUDE.md` § *Pin runtime* → *Self-binding*; they depend on the two transitional paths and are rewritten onto `SetInputForTest`/`GetOutputForTest` in B-7.6, before C-1 deletes those paths. The sibling `_Registration.Tests.inl` carries ~14 more of the same shape.
  - **★ THE ENTITY/CAMERA/TRANSFORM TU'S PINS ARE LIVE TOO (B-6.2) — `_Entity.cpp`, on exactly the `_Math.cpp` pattern above.** All 15 nodes read their INPUT descriptors through `Zenith_GraphNode::GetInput` and write their OUTPUT descriptors through `SetOutput`; the `uPIN_<Name>` constants, the "read in exactly its old branch" rule and the table-order contract (`GraphPinTable.EntityPinIndicesMatchTables`, which asserts the pin COUNT of every one of the 15 classes because the TARGET and LIST pins occupy indices without owning a constant) are all as B-6.1 established them. Three things are specific to this TU. (1) **TARGET_ENTITY and TARGET_POSITION pins stay DIRECT** — `Zenith_GraphContext::ResolveTargetEntity` and `Zenith_GraphNode_ResolvePositionRef`, because a target *reference* is never a wire — and so does `FindEntitiesInRadius`'s LIST name. There is no `READWRITE`, no `SELECTOR_READ` and no in-place aliasing here, and `GetInputPackedEntityID` is never reached: every entity reference in this TU is a `TARGET_REF`. ENTITY_ID **outputs** (`SpawnPrefab`/`FindEntityByName`/`FindNearestEntity` `Result`) go through the NON-template `SetOutput` with a `SetPackedEntityID`-stamped value, since `Zenith_PropertyTraits` has no `u_int64` specialisation. (2) **NINE OUTPUT WRITES USED TO SIT INSIDE `if (!m_strXVar.empty())` AND NO LONGER DO** — `FindEntitiesInRadius.Count`, `SpawnPrefab.Result`, `FindNearestEntity.Distance`, `ReadCameraBasis`'s four, `ReadEntityRotation`'s two — and neither do the computations that fed them (`GetUpDir()`, the camera `GetPosition()`, `glm::eulerAngles`, the `std::sqrt`, all cheap and total). These are **PARITY** rows, not divergences: the guard's observable — an empty name creates no blackboard variable — is `SetOutput`'s own dual-write rule, so the blackboard sees exactly what it saw. What is new is that the SLOT always latches, which is the only reason a wire can come off an `Up`, a `Position`, a `Euler` or a `Distance` whose author never named a variable. The other six writers (`ReadEntityPosition`/`QueryEntityValid`/`ComputeDistance`/`ComputeDirection`/`FindEntityByName` `Result`, `FindNearestEntity.Result`) were always unconditional and take B-6.1's `""` divergence, pinned by `EntityPinRuntime.Output_ReadEntityPositionEmptyResultVarCreatesNoBlackboardEntry`. Because a typed OUTPUT slot starts *SET* at its stamped zero, every `Output_*` row asserts the slot's VALUE against a fixture distinguishable from zero — "latched" alone is unfalsifiable. (3) **`ComputeDirection.m_strResultVar` and `RotateTowardDirection.m_strDirectionVar` BOTH default to `"dir"`**, so two placed nodes communicate today through that shared default and nothing else; after C-1 deletes the dual-write and the var-name fallback, such a pair must carry a WIRE. `RotateTowardDirection.Direction` is the TU's one plain INPUT with no const twin, so its pin default is the VECTOR3 zero — identical to the old `GetVector3(var)` for a missing, wrongly-tagged or unnamed variable, and a zero direction is the node's own FAILURE. The strongest cross-checks that an unconnected node is unchanged are not in this TU at all: `GraphComponent.EntityNodeFamilyRemainderExecution` drives nine of the OUTPUT writes through real graph instances (including a `ReadCameraBasis` whose `Up`/`Position` names are empty) and `GraphComponent.EntityTargetingActsOnOtherEntity` the targeting convention — both stay green unchanged. **B-7.6 ledger: `_Entity`: 0 → 11 direct-construction rows** (it had none before; the new ones stand nodes on the stack with `m_strTargetVar = ""` and `m_xSelf` pointing at a `Zenith_TempScene` entity, which self-binding makes legal, and depend on the two transitional paths for their blackboard-side assertions).
  - **★ THE PHYSICS TU'S PINS ARE LIVE (B-6.3).** The six nodes in `_Physics.cpp` that carry an INPUT or OUTPUT descriptor read it through `Zenith_GraphNode::GetInput` and write it through `SetOutput` (the other four carry only reference pins), on B-6.1's rules (public `static constexpr u_int uPIN_<Name>` immediately before `ZENITH_GRAPH_PINS_BEGIN`; every read in EXACTLY the branch its blackboard read occupied; `GraphPinTable.PhysicsPinIndicesMatchTables` asserting name + role + count for all ten classes). Unconnected behaviour is byte-for-byte today's, with one deliberate divergence. Five things this TU adds to the Math bullet above. (1) **Every input read sits AFTER its target/body guard**, so a missing / bodyless / dead target FAILURES before reading anything — the fallback count for a var-bound pin is 0 on a failed execute, which `PhysicsPinRuntime.Fallback_GuardedFailureDoesNotReadInputs` pins with a positive control. `SetVelocity`'s read stays **above** the per-axis-preserve branch: the flags overwrite components of the value, they do not decide whether it is fetched. (2) **`Raycast` is the exception, and deliberately:** `Direction` is read after the origin resolve but **BEFORE** the zero-direction and NO-HIT exits, because that is where its blackboard read has always been — so a miss or a zero direction has already read the pin and, in a graph, already pulled Direction's producer. (3) **A Raycast MISS touches no slot**: it returns FAILURE, the four hit outputs keep whatever they last held (their stamped zeros on a fresh instance, the PREVIOUS hit on a re-cast), and a wire off any of them must be gated on SUCCESS — which is what Raycast's FAILURE exec pin is for. A HIT latches all four unconditionally: the four `!m_strHitXVar.empty()` guards are gone and the dual-write's own non-empty rule reproduces exactly which reach the blackboard (`hitEntity`/`hitPoint` by default, `hitNormal`/`hitDistance` only when named). `ReadVelocity` has the same FAILURE shape — its guard is above the write. (4) **★ An `ENTITY_ID` slot's stamped zero is packed `0` = `{index 0, generation 0}`, a LEGAL entity id and NOT `INVALID_ENTITY_ID`** (index `0xFFFFFFFF`) — a pre-existing B-2 property that first MATTERS here, because `Raycast.HitEntity` is the first wirable ENTITY_ID output: an ungated consumer reads a plausible entity, not an obviously invalid one. (5) **`ReadVelocity.Result` is pin index 1**, not 0 — `Target` is declared first, and a `SetOutput` aimed at a `TARGET_REF` pin is a silent no-op, so the index test asserts that constant by value as well as by name. **The one deliberate divergence** lives on `ReadVelocity` (the TU's only unguarded writer): an empty `m_strResultVar` no longer creates a blackboard variable literally named `""`. `LockRotation`/`SetGravityEnabled`/`SetSensor`/`SetEntityPosition` declare **no** `uPIN_` constant at all — their only pins are references, resolved directly, and their `Execute` addresses none. The strongest cross-check is `GraphComponent.PhysicsNodeFamilyExecution`, whose Apply\*/Set\* instances bind no var (the const path) and whose `vel`/`vel2`/`hitEntity`/`hitDist` all arrive through the dual-write.
  - **★ THE ANIMATION/TWEEN/PARTICLE TU'S PINS ARE LIVE (B-6.4).** All 14 nodes in `_Animation.cpp` read their INPUT descriptors through `Zenith_GraphNode::GetInput` and write their OUTPUT descriptors through `SetOutput`, on B-6.1's rules (public `static constexpr u_int uPIN_<Name>` immediately before `ZENITH_GRAPH_PINS_BEGIN`; every read in EXACTLY the branch its blackboard read occupied — here, after the `ResolveTargetAnimator` / `ResolveOrAddTween` guard and, for the three tween starters, after the `ValidEasing` guard as well). Six things to know. (1) **All four `ReadAnimatorState` writes left their `!m_strXVar.empty()` guards**, and the shared `Zenith_PropertyValue` scratch and the `t - floor(t)` computation came out with them. These are **PARITY** rows, not divergences: the guard's observable — an empty name creates no blackboard variable — is `SetOutput`'s own dual-write rule, so the blackboard sees exactly what it saw (`animState`/`animTime` by default, `Transitioning`/`HasLooped` only when the author names them). What is new is that all four SLOTS latch on every SUCCESS, which is the only reason a wire can come off an unnamed output. **This TU therefore takes NO `""` divergence at all** — every OUTPUT in it was already guarded. (2) **The FAILURE shape:** `ReadAnimatorState`'s resolver guard is above every read and every write, and its only accessor is `SetOutput`, so a failed execution writes nothing, latches nothing and — on a DIRECTLY-CONSTRUCTED instance that has never succeeded — has not even built pin state (`GetOutputForTest` answers `nullptr`, because `EnsurePinState` runs only from the three Execute-time accessors); a GRAPH instance's four slots are stamped at instantiation, so a failed run leaves them at their zeros and an ungated consumer reads `""`/0/false, not "nothing". A re-execution that fails leaves the PREVIOUS values in the slots. The node has **no failure exec pin**, so a consumer wire off any of its four outputs must be gated on SUCCESS. (3) **Seven of the fourteen classes declare no `uPIN_` constant at all** — `SetAnimatorTrigger`, `CrossFadeAnimation`, `WaitForTween`, `StopTweens`, `EmitParticles`, `SetParticleEmitting`, `SetParticleEmitPosition`: their only pins are references, resolved directly. `GraphPinTable.AnimationPinIndicesMatchTables` still asserts name + role + pin COUNT for all fourteen, which is what would notice a value pin being added to one of them without its `Execute` being migrated. Note `ReadAnimatorState`'s `Target` is the LAST pin (index 4), the opposite of `ReadVelocity`'s — and a wrong-role `SetOutput` is a silent no-op. (4) **`StateName` is the library's first STRING output** and uses the template `SetOutput<std::string>` (`Zenith_PropertyTraits<std::string>` exists, unlike the `u_int64` the ENTITY_ID outputs in `_Entity`/`_Physics` needed the non-template form for). (5) **A clip-less synthetic state reports `NormalizedTime` 0 and `HasLooped` false** — `Flux_AnimationStateMachine::GetCurrentStateInfo` fills both only inside `if (pxBlendTree)` and `AddState` leaves no blend tree — so those two pins are covered by the APPEARANCE of their dual-write (an entry that did not exist before the Execute and is typed after it), never by a distinguishing value; a true `HasLooped` and a non-zero `NormalizedTime` need a clip-backed blend tree and are NOT covered. `Transitioning` IS value-distinguishable: `CrossFade` allocates the transition immediately, and mid-fade `StateName` is still the SOURCE state (the current state advances only at `CompleteTransition`). Pre-existing and preserved: `ResolveOrAddTween` ADDS the tween component BEFORE `ValidEasing` can fail the node, and `WaitForTween`/`StopTweens` call `ResolveTargetEntity` directly rather than through it. The strongest cross-check is `GraphComponent.AnimatorTweenParticleNodesExecution`, whose `SetAnimator*`/`Tween*` instances bind no var (the const path) and whose `animState`/`animTrans` arrive through the dual-write. **B-7.6 ledger: `_Animation`: 0 → 13 direct-construction rows.**
  - **★ THE AI TU'S PINS ARE LIVE (B-6.5).** All 13 nodes in `_AI.cpp` read their INPUT descriptors through `Zenith_GraphNode::GetInput` and write their OUTPUT descriptors through `SetOutput`, on B-6.1's rules (public `static constexpr u_int uPIN_<Name>` immediately before `ZENITH_GRAPH_PINS_BEGIN`; every read in EXACTLY the branch its blackboard read occupied; `GraphPinTable.AIPinIndicesMatchTables` asserting name + role + count). Six things. ## Gameplay logic: Behaviour Graphs + game components
The old C++ script-behaviour system was fully removed. Gameplay logic now has
two homes:

1. **Behaviour Graphs** (`Zenith_GraphComponent` + `.bgraph` assets) — designer-authored,
   hot-reloadable node graphs interpreted by `Zenith/Scripting/`. Slots hold
   `{asset path, graph instance, blackboard overrides}`; attach via the editor panel,
   content-browser drag-drop, `Zenith_EditorAutomation::AddStep_AttachGraph("game:Graphs/Foo.bgraph")`
   (authored entities), or `AddGraphByAssetPath` (runtime-spawned entities).
2. **Game ECS components** (systems-tier C++) — plain classes registered with
   `ZENITH_REGISTER_COMPONENT(Type, "Name", order)` from the game's main .cpp; the
   meta registry concept-detects the lifecycle hooks (`OnAwake`/`OnStart`/`OnUpdate`/
   `OnCollisionEnter`/...). Per-entity tuning uses `ZENITH_PROPERTY`.

Doctrine: systems are ECS components (C++); gameplay logic is graphs.

### Zenith_GraphComponent essentials
- **Slots:** `Zenith_GraphSlot { asset path, Zenith_BehaviourGraph* (null = unresolved), pending override bytes (+ format flag), removal flag }`. An unresolvable asset keeps its path + override bytes verbatim so a save round-trips unchanged (the unresolved-slot contract). Serialization v2 (accepts v1): length-framed per-slot blobs at meta order 60 ("Graph"); v2 override blobs append the blackboard's LIST section (v1 = values only — the slot's `m_bOverridesIncludeLists` records which format its pending bytes use, stamped from the component stream version).
- **Lifecycle dispatch:** the component's concept-detected hooks fire the matching `GraphEventType` on every slot (`OnDestroy` in reverse slot order; `OnUpdate` also drives Timer sources). Hardened-dispatch discipline: snapshot heap-stable graph pointers before invoking user logic, file-scope dispatch-depth counter, slot removal deferred until the outermost dispatch unwinds (`IsDispatchInProgress`).
- **Custom events:** `FireCustomEvent(szName, pxPayload = nullptr)` is the C++→graph plumbing seam — a shim/system fires a named event at exactly the point the old C++ call sat; `OnCustomEvent` source nodes stash the optional `Zenith_PropertyValue` payload into a blackboard variable (default `"payload"`; packed EntityIDs and dt-floats are the common payloads). Multi-field payloads go through `FireCustomEventWithArgs(name, args, count)` — every named `Zenith_GraphEventArg` is stashed verbatim under its own name (arg 0 doubles as the legacy payload). `static BroadcastCustomEvent(name, payload)` fires on every GraphComponent across loaded scenes (also the engine's `m_pfnSceneLoaded` hook target: `"__SceneLoaded"` + canonical path). Cross-entity delivery = the FireCustomEvent NODE's `m_strTargetVar`; dispatch depth is capped at 16 (event ping-pong protection, error-logged).
- **Hot reload:** `ReloadSlotsForAsset` (TOOLS) re-instantiates matching slots with name+type-matched blackboard migration; only ever called from `Zenith_GraphReload::Update()` at the safe point.

For the conversion playbook (decisions → graphs, systems → C++ shims, characterization tests) and per-game node libraries, see `Zenith/Scripting/CLAUDE.md`.

## Static-init dead-strip pitfall
`ZENITH_REGISTER_COMPONENT` does not fire if the component's `.obj` is never
referenced (MSVC dead-strips it). Engine components are safe (the registrar names
them explicitly); a game component that is only added at runtime can hit this —
add it from code (`AddComponent<T>()` in `OnAwake`) rather than relying on the
static registrar.

## C1 graph-pin contract

Graph INPUT and OUTPUT values are wire-only: `GetInput`/`TryGetInput` use an
override, resolved producer, current const default, or typed unconnected default, while `SetOutput`
publishes only its slot. Preserve accessor positions, type checks, pure pulls,
typed-zero/ANY-UNSET behavior, failure retention, and self-binding.

`GetVariable.m_strVariable` remains its selector and type source. Permanent
names also remain for SELECTOR_READ/WRITE/READWRITE, TARGET_REF, LIST, event
stashes, and configuration. They are not INPUT/OUTPUT bindings. In particular,
Branch, Gate, SwitchOnInt/String, StateMachine, Compare, and list value/result
pins carry values by wire or their allowed const/type default; do not recreate
their removed name properties.

Use final factory forms or an equivalent raw node with only permanent parameters.
Raw definitions remain required where node IDs, property order, or delayed data
edge insertion are serialized. Existing serialized unknown properties continue
through normal property loading. `GetListElement` and `ListRemoveAt` retain both
factory forms, `(list, index)` and `(list, index, wire)`.
