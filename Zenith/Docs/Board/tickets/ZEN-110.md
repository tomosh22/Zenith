## Goal

`CaptureDir()` — the helper that derives a harness's capture destination — now
exists as **nine near-identical copies**: one from ZEN-92
(`Test_MaterialEditorLivePreview.cpp`), three in Zenithmon
(`ZM_AnimEditorShowcase.cpp`, `ZM_AutoTests_GroundItemPropCapture.cpp`,
`ZM_AutoTests_ImportedPropShowcase.cpp`) and eight added by ZEN-105 across
DevilsPlayground and RenderTest. Each is ~20 lines with its comment block, and
they are the bulk of ZEN-105's +321/−26.

ZEN-105 duplicated them deliberately rather than invent a shared location
mid-ticket. That was the right call for one ticket and is the wrong steady
state, because **three separate defects are now nine-site fixes**, all found by
one review of one copy:

1. **`weakly_canonical`'s `std::error_code` is discarded** in every copy. On
   failure `xRepoRoot` is empty and the capture directory becomes a
   CWD-relative `Build/artifacts/...`, which `create_directories` happily
   creates — so the "fails loudly" guard PASSES while captures land outside the
   repo's artifact tree. Cannot fire on win64 today, where `GAME_ASSETS_DIR` is
   a compile-time absolute path, but it is the same root as the Android
   divergence in ZEN-109.
2. **The `--capture-tag` value is not sanitised.** `--capture-tag
   ../../../Windows/System32` escapes `Build/artifacts/` at all nine sites, and
   in `Test_DPFogPass_VisualOutput` the escaped path is then handed to
   `std::remove`. The right home for the guard is the engine-owned
   `Zenith_CommandLine::GetCaptureTag()` (`Zenith/Core/Zenith_CommandLine.cpp:284`),
   which covers every current and future caller at once.
3. **Directory creation is checked; the capture LANDING is not.**
   `Flux_Screenshot::RequestDump` only queues (`Zenith/Flux/Flux_Screenshot.cpp:26-34`).
   So a read-only or full artifact tree passes the directory check, writes
   nothing, and every affected harness still reports PASSED — a narrower version
   of the exact fail-open ZEN-92 and ZEN-105 removed. The in-repo precedent for
   the fix already exists: `RT_PhotoTour`'s `Verify` calls `file_size` on every
   requested path, and `Games/RenderTest/CLAUDE.md` states the reasoning —
   *"the shot counter proves the tour ASKED for N captures, never that N
   landed."*

A shared helper is reachable: `Zenith/Core` is linked by every game, and
`--capture-tag` already lives there, so the tag half of the mechanism is
engine-owned while the path half is copy-pasted per harness. Consolidating puts
both on the same side of the seam.

Two smaller inherited items worth folding in, both from ZEN-92's original and
faithfully copied nine times:

- **`SetShotPath` truncates silently.** A path at or over the buffer length
  writes an empty string and does NOT clear the harness's OK flag, so the test
  proceeds and dies later at the TGA load with a misleading message.
- **`Test_DPFogPass_VisualOutput`'s `Step` does not gate on
  `g_bVisualSetupOk`**, so when `Setup` bails on directory creation the test
  still runs its frames, calls `RequestDump("")` twice (a silent no-op) and
  reports *"setup failed (no orbit camera found?)"* — the real cause was logged
  165 frames earlier at `Zenith_Log` rather than `Zenith_Error` severity.

## Definition of Done

- [ ] One shared capture-path helper exists and the nine copies are gone, with
      each harness naming only its own game and area
- [ ] `weakly_canonical`'s error is handled rather than discarded, and a
      failure to resolve the repo root does not silently produce a
      CWD-relative destination
- [ ] A `--capture-tag` that would escape `Build/artifacts/` is refused, with
      the guard in one place rather than per call site, and a test pins it
- [ ] At least one harness verifies its captures LANDED rather than only that
      the directory was created, following `RT_PhotoTour`'s `file_size`
      precedent
- [ ] A truncated capture path fails the harness rather than proceeding with an
      empty string
- [ ] At least one affected harness is run windowed and its captures confirmed
      on disk, from an OBSERVED run — no gate executes any of this code
      (`ZEN-D-003`), so a green gate is not evidence
- [ ] Every affected game's pinned baseline bumped from an OBSERVED run, if the
      change adds or removes a unit
