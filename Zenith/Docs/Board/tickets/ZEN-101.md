## Goal

`AssetHandling` and `Flux` form a genuine header cycle: 23 include edges
`Flux -> AssetHandling` against 11 files reaching the other way. The engine
library split declared the heavier direction (`ZenithFlux` depends on
`ZenithAssetHandling`) and let the reverse references resolve at the executable
link, which works but leaves the cycle in place.

The reverse edges are not forward-declarable — the asset classes own Flux types
**by value**. A narrower fix was considered and rejected during the split:
moving `Flux_AnimatorControllerDef.h` and `Flux_GrassTypeTable.h` across looks
like moving leaf data, but they pull in `Flux_AnimationStateMachineDef.h`,
`Flux_AnimationLayer.h` and `Flux_GrassTypes.h` respectively, so the move either
drags three more files across or leaves the edge exactly where it was.

The real fix is a design change: split `AssetHandling` into a handle/registry
half (identifiers, lookup, lifetime — no Flux types) and a GPU-resource half
(the classes that own Flux types by value). The registry half then sits cleanly
below Flux and the cycle disappears rather than being declared around.

Measure the full include closure first and let it decide the split line, rather
than starting from the two files named above.

## Definition of Done

- [ ] `AssetHandling` is split so that no header in the lower half includes a Flux type, measured and recorded
- [ ] The Flux library no longer participates in a declared module cycle with the asset registry half
- [ ] Each half is its own static library, globbed by exactly one project, and the project-membership invariant check still passes with zero findings
- [ ] The engine and every game build green on Vulkan, Null, D3D12 and AGDE
- [ ] Every affected game's pinned unit baseline is bumped from an OBSERVED run, or confirmed unchanged
