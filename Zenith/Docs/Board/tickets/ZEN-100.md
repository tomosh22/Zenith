## Goal

`Zenith.h` is the precompiled-header master header: every engine `.cpp` begins
`#include "Zenith.h"`. Its transitive closure is **219 headers, of which 202 are
glm** — so every translation unit in the engine, and every one of the 13 binary
`.pch` files the library split now produces, pays for the entire glm surface
whether it does maths or not.

The cost is measurable. A win64 `Zenith.pch` is 119 MB in `Debug_True` and
192 MB in `Release_True`. The library split deliberately withheld a PCH from
every library under 4 translation units precisely because a 1-TU library with a
PCH parses glm twice instead of once — a rule that exists only to work around
this header's weight.

Introduce a forward-declaration header (`Zenith_MathsFwd.h` or similar) carrying
the `Zenith_Maths::` type names without the glm definitions, and move `Zenith.h`
onto it. Translation units that genuinely need the full glm surface include the
heavy header explicitly, the way `Flux_BackendTypes.h` is the explicit heavy
seam beside the light `Flux_Fwd.h`. This is the real fix that the >=4-TU PCH
rule is only a mitigation for.

Measure before and after: the header count in `Zenith.h`'s closure, the size of
one representative `.pch`, and a cold build of one game in
`Vulkan_vs2022_Debug_Win64_True`.

## Definition of Done

- [ ] `Zenith.h`'s transitive closure no longer pulls the full glm surface, and the measured header count is recorded in the commit message
- [ ] Every translation unit that needs full glm types includes the heavy header explicitly rather than relying on the precompiled header
- [ ] A representative `Zenith.pch` is measurably smaller, with the before/after figures recorded
- [ ] The engine and every game build green on Vulkan, Null, D3D12 and AGDE
- [ ] Every affected game's pinned unit baseline is bumped from an OBSERVED run, or confirmed unchanged

Filing (2) before (1) is measured would repeat this ticket's own defect.

**Deviations / follow-ups**

**Why this is a SCOPE block and not a failure.** Nothing went red. The ticket is buildable as filed — and that is the problem. Its third DoD box asks only that a representative `Zenith.pch` be *measurably smaller*, which a change that makes every build *slower* would satisfy. The measurement below says that is the likely outcome, so shipping it would put a pessimisation on `master` with every gate green.

**The measurements, all taken on `master` before dispatch.** The ticket's own central claim is CONFIRMED exactly: `Zenith.h` → `Maths/Zenith_Maths.h` → 4 glm includes whose resolved closure is **202 glm headers** (203 total). `glm/fwd.hpp`'s closure is **5**, so the PCH-size prize is real and large.

What the ticket did not establish:

- `glm/glm.hpp` **alone pulls 152 of the 202**, so there is no cheap subset to drop. Trimming the three `gtx`/`gtc` includes reaches 152 and stops, and `glm::quat` — aliased as `Zenith_Maths::Quat` — keeps `gtc/quaternion` mandatory regardless.
- `Zenith_Maths::Vector3` and friends are `using` **aliases** of glm types, not opaque wrappers. Anything holding one by value — a struct member, a by-value parameter, a return — needs the complete type, so forward declaration helps only declaration-only consumers.
- **587 of 1593 `.cpp` (37%) reference `Zenith_Maths::` or `glm::` directly; so do 261 `.h` and 176 `.inl`.** The 261 headers are the multiplier: a header with a `Vector3` member must include the heavy maths header itself, so every TU that includes it re-parses the 202 headers. The true reach is far larger than the 587 direct TUs.

**So the trade is 13 parses for 600-1000+.** Today glm is parsed once per PCH-creating library — 13, under the ≥4-TU rule established by the library split. After the flip it is parsed once per consuming TU. The PCH shrinks (119 MB Debug_True / 192 MB Release_True each, and `Build/obj` with them) and compile time for roughly half the tree gets worse. **That is the opposite of the motivation the ticket was filed under**, which described the change as "the real fix" for PCH weight.

**The ruling nobody has made** is whether that disk-for-time trade is wanted. It is not computable from the ticket, it is not a user preference I can invent, and no gate in the Engine list measures build time — so the loop cannot settle it and would not notice getting it wrong.

**What I did NOT do, deliberately.** I did not dispatch a worker to discover this expensively; the protocol is explicit that a scope problem is resolved before dispatch, not encoded into a worker prompt as a stop condition. I did not rescope the DoD in place either: the honest successor is two tickets with a decision point between them, not a reworded version of this one, and re-filing is a judgement for a human who wants the disk back.

**Suggested successors** (not filed — see below): (1) add `Maths/Zenith_MathsFwd.h` and adopt it in declaration-only consumers, which is cheap, reversible and valuable on its own; (2) prototype repointing `Zenith.h` at it and **accept or reject on measured cold AND incremental build time**, not on PCH size. Slice 2 is only worth filing if slice 1's measurement says the trade is favourable.

I have not filed those successors, because filing a ticket whose acceptance criterion is a number nobody has measured yet would repeat this ticket's own defect. Slice 1 is the thing to file first, and it wants a human to confirm the disk pressure is still worth chasing at all — `Build/obj` was ~7.9 GB before the library split and the ≥4-TU PCH rule was chosen specifically to keep it near 2.5× rather than 6×.
