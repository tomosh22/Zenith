## Goal

Three DevilsPlayground tests that PASSED on Android now FAIL there, for a
reason unrelated to what they assert. Introduced by ZEN-105, found by review,
shipped deliberately because the correct fix is a design decision that ticket
did not contain. Full analysis in `ZEN-D-038`.

**The chain, verified at three sites on 2026-09-21:**

1. `Zenith/Core/Zenith.h:361` defines `ZENITH_INPUT_SIMULATOR`
   **unconditionally** — no platform or tools guard.
2. `Games/DevilsPlayground/DevilsPlayground.zproj` declares `"android": true`
   and `Build/Sharpmake_Games.cs` gives the game an `agde` target with no
   source excludes for `Tests/`.
3. `Build/Sharpmake_Games.cs:119` — on `agde`, `GAME_ASSETS_DIR=""`,
   deliberately, because `AAssetManager` wants APK-relative paths.

So four test TUs guarded by `#ifdef ZENITH_INPUT_SIMULATOR` alone ship in the
Android `.so`: `Test_DPCamera_ModeTransition`, `Test_DP_LiminalHub_Spend`,
`Test_DP_Minimap_RevealAndTracking`, `Test_DPFogPass_VisualOutput`. (The two
`ZENITH_TOOLS`-guarded files in the same directory correctly drop out.)

ZEN-105 gave each of them the repo's capture-path idiom:

```cpp
weakly_canonical(std::filesystem::path(GAME_ASSETS_DIR) / ".." / ".." / "..")
```

which is the repo root on win64 and, from `""`, resolves CWD-relatively — on a
device, `/`. So the capture directory becomes `/Build/artifacts/...`,
`create_directories` returns `EACCES`, `Zenith_IsNullRenderer()` is false on
agde, and the fail-loudly branch ZEN-105 added executes.

**Three of the four fail in the FALSE direction.** Their subjects are a camera
-mode transition, a hub spend and a minimap reveal; the capture is incidental
diagnostic output. Before ZEN-105 they passed on Android while their `C:/tmp`
writes silently went nowhere — vacuous, which is the fail-open ZEN-105 existed
to remove — and now they fail for a reason that says nothing about the contract
they test. `Test_DPFogPass_VisualOutput` is the exception: it loads its own TGAs
back in `Verify`, so the capture IS its deliverable and failing is correct.

**The question this ticket has to answer**, which ZEN-105's Definition of Done
answered one way and Android makes contentious: *should a capture-directory
failure fail a test whose SUBJECT is not the capture?* DoD 3 said "each fails
loudly", and on win64 that is right. Candidate shapes, not a prescription:
distinguish harnesses whose capture is the deliverable from those where it is
diagnostic and let only the former fail; or treat an unaddressable artifact tree
(empty `GAME_ASSETS_DIR`) as a documented capture-skip rather than a failure; or
exclude these TUs from the agde target so the question does not arise.

Whatever is chosen, **do not restore a silent write-to-nowhere** — that is the
defect ZEN-92 and ZEN-105 removed, and "it passed on Android" was only ever true
because nothing checked.

Nothing runs DevilsPlayground tests on Android today: CI builds `Vulkan_` win64
only, `push` is false, and no gate line targets `agde`. So the practical blast
radius is zero right now, which is why this is filed rather than hot-fixed — but
it is a live trap for the first person who runs the suite on a device.

## Definition of Done

- [ ] The three tests whose subject is not the capture reach their normal
      verdict on a build where the artifact tree is not addressable, instead of
      failing on directory creation
- [ ] `Test_DPFogPass_VisualOutput` still fails when it cannot write the TGAs it
      later reads back — the correct behaviour is not lost in the fix
- [ ] The rule chosen is stated at the capture helper, so the next harness
      author does not have to re-derive it
- [ ] The `Vulkan_arm64_v8a_vs2022_Debug_Agde_False` DevilsPlayground build
      compiles, from an OBSERVED run
- [ ] The win64 behaviour ZEN-105 verified is unchanged, from an OBSERVED
      windowed run of at least one affected harness with its captures landing
      under `Build/artifacts/`
- [ ] Every affected game's pinned baseline bumped from an OBSERVED run, if the
      change adds or removes a unit
