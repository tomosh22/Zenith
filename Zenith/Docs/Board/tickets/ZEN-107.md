## Goal

A standalone tool that links `zenith.lib` has **no supported way to allocate
the engine's runtime services**, so it faults on its first engine call. ZEN-103
repaired `TilePuzzleLevelGen` and `TilePuzzleRegistryViewer` against the
current engine API and made `tilepuzzle_win64.sln` build whole with zero
errors — and both exes then crash. Measured 2026-09-21, immediately after
`Zenith_MemoryManagement::Initialise()`:

```
tilepuzzlelevelgen.exe --validate-registry --validate-max-states 2000 -> 0xC0000005
tilepuzzleregistryviewer.exe                                          -> 0xC0000005
```

**The mechanism (verified, see `ZEN-D-036`).** `Zenith_Engine`'s
`m_pxThreading` / `m_pxTasks` / `m_pxProfiling` are private members
(`Zenith/Core/Zenith_Engine.h:235-237`) allocated only inside
`InitialiseRuntimeServices()`, which is **private**
(`Zenith/Core/Zenith_Engine.h:211`). The only public entry is `Initialise()`
(`:101`) — the full boot including renderer, physics, ECS and editor, which a
CLI tool cannot run. So `g_xEngine.Threading()` in a tool dereferences null.

**And it faults instead of reporting.** `Threading`, `Tasks` and `Profiling`
are declared with `ZENITH_ENGINE_ACCESSOR_HOTPATH`
(`Zenith/EngineComposition/Zenith_Engine.cpp:221-223`), defined at `:217` with
**no null assert** — deliberate and documented at `:203-206`, because these are
reached from worker threads every frame. The sibling `ZENITH_ENGINE_ACCESSOR`
at `:210` does assert. Sound for the hot path; it leaves use-before-init
undiagnosable for every other caller.

**This is broader than two TilePuzzle tools.** De-globalisation (commit
`9e4253ca`) turned "call a static" into "reach through a singleton something
else must have allocated". Every caller that is not the game loop — asset
tools, validators, importers, any future CLI — inherits a precondition it
cannot satisfy. `FluxCompiler` is the one tool that survives, and only by
avoidance: it never touches Threading/Tasks/Profiling, defining the eight
`Project_*` stubs purely to satisfy the linker. A tool that genuinely needs
task parallelism cannot copy it.

The decision this ticket must make, and which ZEN-103 deliberately did NOT make
unilaterally: **how does a standalone tool obtain runtime services?** Candidate
shapes, not a prescription — a public tool-mode entry point that runs only the
runtime-services phase; a scoped RAII helper owning the three subsystems; or a
documented ruling that tools must not use them at all, in which case the two
TilePuzzle tools need their parallel validation rewritten serially.

Whatever is chosen, the assert-free accessors deserve a look in the same
breath: a tool getting a clear "called before Initialise()" message instead of
an access violation is most of the value, and the hot-path argument does not
obviously apply to a build that is not the game loop.

      reports a result, instead of exiting `0xC0000005` — from an OBSERVED run,

      from an OBSERVED run
