## Goal

`Build/Sharpmake_TilePuzzleLevelGen.cs` **never defines `ZENITH_TOOLS`**, in
either `ToolsEnabled` configuration — unlike every sibling project:

| File | Defines `ZENITH_TOOLS` |
|---|---|
| `Build/Sharpmake_TilePuzzleRegistryViewer.cs:86` | yes |
| `Build/Sharpmake_Games.cs:138` | yes |
| `Build/Sharpmake_TilePuzzleLevelGen.cs` | **no** |

So `TilePuzzleLevelGen.cpp` and `zenith.lib` (compiled WITH `ZENITH_TOOLS` in a
`_True` config) disagree about the layout of `Zenith_Engine` — an ODR violation.

**It is harmless today, and only by luck.** `m_pxThreading` / `m_pxTasks` /
`m_pxProfiling` are declared before every `#ifdef ZENITH_TOOLS`-gated member
(`Zenith/Core/Zenith_Engine.h:287-353`), so their offsets do not shift. ZEN-107's
new inline `HasRuntimeServices()` reads exactly those three, and is currently only
called from inside `Zenith_Engine.cpp` — never from the tool's own TU.

**Why it matters now rather than whenever.** ZEN-107 made "a tool reaches into
`g_xEngine` through an inline header accessor" the idiomatic pattern. The next
inline member added above those three, or the first tool that calls
`g_xEngine.HasRuntimeServices()` from its own TU, turns a latent mismatch into a
wrong offset — and the symptom will be a corrupt read or a crash a long way from
the cause, on one tool only.

Found by the ZEN-107 review; verified independently. Out of scope there because
the Sharpmake file was not in that ticket's file list.
