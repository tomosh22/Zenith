## Goal
`Zenith_AssetRegistry::Get<T>(path)` **does not exist**. The registry's static read API is `GetView<T>` (declared `Zenith/AssetHandling/Zenith_AssetRegistry.h:146`, defined `:410`) and the owning form is `Acquire<T>`. There is no `Get<T>` member and there are **zero call sites** in any `.cpp` or `.inl` — every occurrence is documentation, so nothing compile-checks it and it has drifted unnoticed.

Found while adding `Tools/check_boot_unit_assets.ps1` (ZEN-84): the lint's reader list was nearly given a phantom entry on the strength of these docs, and the worker caught it only by grepping for call sites and finding none.

Known occurrences:

- `Zenith/AssetHandling/Zenith_AssetRegistry.h:51` — ★ the registry's OWN header comment: *"The static API (Get<T>(path) / Create<T>() / Save / UnloadUnused / ...)"*
- `Zenith/AssetHandling/CLAUDE.md:176`, `:183`, `:851` — `:183` documents it as a named alternative to `Resolve()`
- `Zenith/AssetHandling/Zenith_MeshGeometryAsset.h:21` — usage example
- `Zenith/Core/CLAUDE.md:235` — cites it as the *canonical* access path
- `Zenith/Prefab/CLAUDE.md:28`
- `Games/DevilsPlayground/Docs/AssetTestPlan.md:40`, `:106`, `:179`

This is worse than a typo because `Core/CLAUDE.md` presents the spelling as canonical and `AssetHandling/CLAUDE.md` contrasts it with `Resolve()` — a reader has no reason to doubt it, and the compiler never sees a comment.

Decide and apply ONE of: correct every reference to the real name, or add a `Get<T>` alias for `GetView<T>` so the documented API exists. Prefer correcting the docs unless there is a reason to want the shorter name — an alias adds a second spelling of one operation, which is how this class of drift starts.
