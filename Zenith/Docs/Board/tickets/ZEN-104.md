## Goal

`Tools/Vault/scripts/adopt-stale-knowledge-rows.mjs` landed on ZEN-90 and moved
four stranded decision rows correctly. Its review surfaced two gaps that were
deliberately left open as out of that ticket's scope. Both are about what the
script would do on a DIFFERENT checkout or a future run, not about the migration
it already performed.

### 1. Nothing guards the DIRECTION of the move

The destination is whatever `databaseModel` (`Tools/Vault/cli/queries.mjs`)
resolves, which is deliberate — a second resolution of "which database is live"
is the exact defect ZEN-90 existed to remove. But that resolver is
`preferred ?? populated ?? databases[0]`, and `orgSlug` falls back to a hardcoded
`'pink-goat'` because this checkout's `vault.config.json` carries no
`policy.orgSlug`.

On a checkout whose `policy.orgSlug` named the other organisation, or one where
`notion.projects` / `public.organizations` were absent so the `populated`
fallback decided, a single `--apply` would sweep all 37 live decision rows the
other way. Nothing becomes unreadable (the move stays consistent with whatever
the reader resolves), so no check fails — but it is a 37-row rewrite of the live
board that nobody asked for.

There is no `--max-moves`, no "refuse when the destination is empty and the
source is large", and the plan does not print which organisation each side
belongs to. The dry-run default is the only thing standing in front of it, and a
dry run only helps if someone reads it.

Related, same root: two same-titled databases in the SAME organisation would be
silently MERGED. Title is the only discriminator.

### 2. The SELECT code path has zero test coverage

`labelOf` and `cellFor` map a SELECT cell's option id to its label and back to
the destination's own option id, falling through to the raw label when the
destination offers no match. That path RAN against live data on ZEN-90 —
Category, Repo and Reversibility are all SELECT — and it is exercised by no test.
The fixture in `Tools/Vault/test/decide-reference.test.mjs` defines only TEXT
properties.

The ZEN-90 migration's SELECT handling was verified empirically after the fact
(all four rows re-read with 9/9 fields populated), so this is a gap for FUTURE
runs rather than a doubt about the rows already moved. A fixture SELECT property
whose option ids differ between the two databases would close it the way the TEXT
remap is already closed.

Worth covering in the same test: three of the four migrated rows carry Category
`"Testing"`, an option defined in NEITHER database, which survived verbatim
through `cellFor`'s raw-label fall-through. Identical orphans (`Testing`,
`Tooling`) already existed in pre-migration live rows, so the behaviour is
correct — but it is unpinned.

## The ruling this ticket had to be read against

`ZEN-D-029` corollary 3 says *"Re-deriving the organisation inside the migration
would be a second answer to the question ZEN-90 exists to have exactly one answer
to."* Read carelessly that forbids DoD 1 outright. I drew the line as
**displaying vs deciding** — reading the organisation to PRINT it is allowed;
letting it RE-DECIDE which database is live is not — and asked the review to
check that I had drawn it correctly rather than assuming. It confirmed it:
`planFor` still takes `target` from `databaseModel` and nothing else, and
`organisationOf` feeds only the display array and a refusal. A refusal never
redirects a move; it stops one. Corollary 3's own premise is "a human reading
the plan", which presupposes the plan carries what they need.

Per `ZEN-D-007`, all three refusals throw from `planFor`, which runs for the
preview and again inside `prepare` against a `fresh` index — so a refusal leaves
the vault byte-identical with no journal and no commit.

## The review found three real defects, all of them mine to have caught

Risk MEDIUM put this in `reviewOn`. I asked explicitly for my own README to be
reviewed alongside the worker's code, and that was justified — one of the three
findings was in my prose.

1. **The same-organisation guard was narrower than its own comment claimed.** It
   compared each source against the DESTINATION only, never sources against each
   other. Three databases — one under `pink-goat` (the destination) and **two**
   under `acme-corp` — defeat it: every comparison is `acme-corp !== pink-goat`,
   nothing fires, and both acme databases merge into the destination. That is
   exactly the merge DoD 3 exists to prevent. Both the worker's header comment
   and **my README** stated the broader guarantee as fact. Fixed: the check is
   pairwise over `[destination, ...sources]`.
2. **The comparison was case-sensitive where `databaseModel` lower-cases**
   (`cli/queries.mjs:493`). With `{slug: "pink-goat"}` and `{slug: "Pink-Goat"}`
   the resolver treats both as the configured organisation and picks whichever
   comes first, while the guard saw two different organisations and stayed
   silent — **failing OPEN in the exact ambiguity it guards.** Fixed.
3. **The DoD-3 test's byte-identity assertion could not fail.** Its fixture had
   no movable rows, so with the guard removed `planFor` returned `moves: []` and
   the early return meant no operation was ever opened — the assertion passed
   either way. Fixed by giving the duplicate database a property set and a row.

A fourth finding was prose only: the code and README both called the
empty-destination condition *"the shape a resolver inversion actually takes"*. It
is **one** shape. `databaseModel` is `preferred ?? populated ?? databases[0]` and
the `populated` branch is defined as the first database already holding rows, so
an inversion landing there has a non-empty destination by construction and the
size guard is structurally dead on that path. Corrected in both places, naming
the branch it misses.
