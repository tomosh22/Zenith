## Goal

ZEN-44's review (2026-09-23) found that `Zenith_Pathfinding::FindPath`'s equal-cost behaviour is unpinned. `AStarNode::operator>` compares `m_fFCost` only, so equal-f-cost nodes are a real, reachable state (symmetric navmesh geometry), and which of two equal-cost routes `FindPath` returns depends on the open list's internal sift order. ZEN-44 moved that open list from `std::priority_queue` onto `Zenith_PriorityQueue`; the ordering KEY is identical but the tie-break is not provably so, and no unit in `Zenith/AI/Navigation/Zenith_Pathfinding.Tests.inl` asserts an exact route — every assertion checks status, waypoint-count bounds or duplicate waypoints. So an NPC's chosen route could change with every gate green.

Scope: headless units in `Zenith_Pathfinding.Tests.inl` that build a small navmesh with two equal-cost routes between a start and a goal and (a) assert `FindPath` returns the same route on repeated calls (determinism) and (b) pin WHICH route it returns today, with a comment saying the pin records current behaviour so a future open-list change that flips it is a deliberate, visible decision. Build the navmesh with whatever test helper the existing units use. No change to `Zenith_Pathfinding.cpp` or `Zenith_PriorityQueue.h`.

## Definition of Done

- [ ] A unit proves `FindPath` is deterministic over an equal-cost pair of routes, and another pins which route it returns, with an anti-vacuity note naming the change that would flip it
- [ ] `Zenith_Pathfinding.cpp` and `Zenith/Collections/Zenith_PriorityQueue.h` are unchanged
- [ ] Every game's pinned baseline bumped from an OBSERVED run
