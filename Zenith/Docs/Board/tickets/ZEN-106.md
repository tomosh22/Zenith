## Goal

ZEN-93 pinned the *decision* to refuse an unregistered `--automated-test` name.
It did not, and could not, pin the *enforcement*.

`BuildSingleTestResolution` (`Zenith/EngineComposition/Zenith_AutomatedTest.cpp`)
now returns a plain struct — `m_bFound`, `m_iExitCode`, `m_acMessage` — and seven
units assert its contents. That closes the gap ZEN-93 was filed over, where the
only existing unit pinned `FindNodeByName` returning null and would have passed
with the refusal deleted entirely.

**But the call site is still untestable**, and a review of ZEN-93 named the
consequence precisely:

> A future edit that broke *only* the wiring (e.g. forgot the `ExitHarness`
> call, or inverted the `!xResolution.m_bFound` check) would still pass every
> new unit while reproducing the exact symptom ZEN-93 was filed over.

The three lines in question are, in `BuildHarnessExecutionList`:

```cpp
const SingleTestResolution xResolution = BuildSingleTestResolution(s_xRunner.m_szRequestedName, pxNode);
if (!xResolution.m_bFound)
{
    std::printf("%s", xResolution.m_acMessage);
    ExitHarness(xResolution.m_iExitCode);
}
```

`ExitHarness` is `[[noreturn]]` and calls `Zenith_Core::Zenith_FullShutdown()`
then `std::exit`, so no in-process unit can ever reach it. The only thing that
can observe this wiring is a PROCESS: run a game exe with a name nobody
registers and assert the exit code.

That check is cheap and would be genuinely end-to-end — it is the literal
command from ZEN-93's own Goal:

```
<game>.exe --automated-test Zenith_NoSuchAutomatedTest_ZZZ --skip-unit-tests
  expect: exit 2, stdout contains "not found in registry"
```

It needs to run somewhere, and that is the part a loop cannot do alone: adding a
gate line means editing `zagent.project.json`, which is a `protectedPaths` entry
that `zagent guard` refuses. **So this ticket is deliberately split**: the script
is ordinary unprotected work, and wiring it into a gate list is a one-line human
edit.

Suggested shape, matching the repo's existing assert-script convention
(`Tools/Test_TickGates.ps1`, `Tools/Test_UnitBaselineManifest.ps1`,
`Tools/zagent/Test-ZagentClient.ps1` — each prints its own count and exits
non-zero on failure):

- a `Tools/Test_UnmatchedTestNameRefusal.ps1` that takes a `-Exe`, runs it with a
  deliberately unregistered name, and asserts BOTH the exit code is 2 AND the
  output names the token. Asserting only the exit code would pass if the message
  were dropped; asserting only the message would pass if the exit were dropped.
- an anti-vacuity arm: run the same exe with a name that IS registered and assert
  it does NOT produce the refusal, so the script cannot pass by always seeing a
  failure.

★ **Do not assert the exact full message text.** ZEN-93 added "Did you mean"
suggestions that appear only when the registry holds a close name, so the exact
output is registry-dependent. Assert on the stable fragment
(`not found in registry`) and the exit code.

## Definition of Done

- [ ] A script asserts, against a real built exe, that an unregistered
      `--automated-test` name exits 2 AND prints a message naming the token
- [ ] It carries an anti-vacuity arm proving it does not pass unconditionally
- [ ] It exits non-zero on failure and prints its own assertion count, matching
      the existing `Tools/Test_*.ps1` convention
- [ ] The residual-gap note in `Zenith_AutomatedTest.cpp` is updated to point at
      the script rather than describing the gap as open
- [ ] Every affected game's pinned baseline bumped from an OBSERVED run, if the
      change adds or removes a unit

## Not in this ticket

Wiring the script into a category's gate list edits `zagent.project.json`, a
protected path. File that as a human task once the script exists and passes.
