## Goal

`Games/TilePuzzle/tilepuzzle_win64.sln` is the ONE solution in the repo that
fails a whole-solution build. Measured on ZEN-85 (2026-09-21,
`Vulkan_vs2022_Debug_Win64_True`): exit 1, 27 error lines. Every other solution
measured — `Build/zenith_engine_win64.sln` in both `_True` and `_False`, and
`Games/Combat/combat_win64.sln` in `_True` — builds whole with zero errors.

Neither failing project is an aux tool. Both are TilePuzzle's own bespoke
tooling, and both have bit-rotted because nothing ever builds them:

- **`TilePuzzleLevelGen`** — 21 compile errors in `TilePuzzleLevelGen.cpp`. It
  calls engine APIs that no longer exist: `Zenith_TaskSystem::Inititalise`
  (the historical typo, now gone), an undeclared `Zenith_TaskArray`, a
  `Zenith_Profiling::Initialise` that no longer takes 0 arguments, a
  no-longer-static `Zenith_Multithreading::RegisterThread`, and an undeclared
  `ZENITH_PROFILE_INDEX__SCENE_UPDATE`.
- **`TilePuzzleRegistryViewer`** — compiles, then fails to link with 6 errors
  (`LNK2019`/`LNK2001`/`LNK1120`). It links `zenith.lib`, which requires the
  composition-root symbols every game supplies —
  `Project_SetGraphicsOptions`, `Project_RegisterGameComponents`,
  `Project_Shutdown` — and the viewer supplies none.

`zenith build TilePuzzle` is unaffected and stays green: it passes
`/t:TilePuzzle`, so it never builds either project. That is exactly why the rot
went unnoticed — no gate line, and no `zenith` command, builds these two
projects at all.

Either repair both projects against the current engine API, or retire whichever
is genuinely dead. Both are defensible; deciding which is part of the ticket.
Whichever way it goes, the outcome to aim at is that a whole-solution build of
`tilepuzzle_win64.sln` in `Vulkan_vs2022_Debug_Win64_True` is green, so the
"whole solutions build" statement ZEN-85 put into `Docs/BuildSystem.md` has no
remaining exception.

If a project is retired rather than repaired, remove it from the Sharpmake
project set and its solution the way the build system already expresses
membership — target declaration plus solution membership, never a
per-configuration source exclude (root `CLAUDE.md`, "The library structure's
invariant").

## ★★ BUILDING IS NOT RUNNING — both tools still crash, and I am not claiming otherwise

The DoD is a build outcome and it is met. It would have been easy to stop
there, so I ran the exes. **Both fault immediately:**

```
tilepuzzlelevelgen.exe --validate-registry --validate-max-states 2000 -> 0xC0000005
tilepuzzleregistryviewer.exe                                          -> 0xC0000005
```

A first run of `levelgen --help` printed clean usage and exited 1, which
**proved nothing** — argument parsing returns before the engine boot at
`:1582`. Only `--validate-registry` reaches it.

Cause, verified in the engine source: `m_pxThreading` / `m_pxTasks` /
`m_pxProfiling` are private members allocated only in the **private**
`InitialiseRuntimeServices()`; the sole public entry is `Initialise()`, the
full boot a CLI tool cannot run. So `g_xEngine.Threading()` dereferences null —
and because all three accessors use `ZENITH_ENGINE_ACCESSOR_HOTPATH`, which
carries **no null assert** (deliberate, documented, hot-path), it faults
instead of reporting.

**Neither tool regressed**, and the two need separate arguments:
RegistryViewer already spelled its boot the modern way and already
dereferenced the same nulls — it simply could not be observed while it failed
to LINK. LevelGen's crashing lines ARE lines this ticket wrote, but it produced
no exe beforehand and its pre-diff `g_xEngine.Profiling().Initialise()` would
have faulted identically had it compiled. `9e4253ca` (de-globalisation) is what
half-migrated both files.

I shipped anyway: the DoD is literally and measurably met, the API repair is
genuinely done, and "how does a standalone tool obtain runtime services" is an
engine design decision this ticket does not contain. Filed as **ZEN-107**
(COMPLEX/MEDIUM, opus, review required), linked `relates` to this one, and
documented loudly in `Docs/BuildSystem.md` plus the root `CLAUDE.md` so no
reader infers the tools work.

## The review caught two blocking defects I had missed

**1. The tree would not have stayed clean.** These two tools live at the
**repo root**, so neither `Games/*/build/` nor `**/Build/output` reaches their
`output/` dirs — and `.gitignore:48-50` already covers their `obj/` half with a
comment naming them by name. Someone fixed the `obj` half and not the `output`
half **because the output half could not exist**: neither project built. This
ticket is what makes those directories exist. Left alone, the next tick's
precondition (`git status --porcelain` empty) would have refused a ticket over
two untracked build trees, and `branching: "direct"` means it cannot stash
around it. Fixed next to the `ZenithHub/output/` one-off that has exactly this
shape. Scoped LevelGen's rule to `output/win64/` specifically, because
`output/` itself holds **1324 tracked files**.

**2. Root `CLAUDE.md` would have asserted a measured falsehood.** It and
`Docs/GameProjects.md` both still said TilePuzzle fails whole, both citing
`Docs/BuildSystem.md` §9 — the section this ticket inverted. `CLAUDE.md` is
loaded into every session and every worker prompt in this repo, so that is the
bad kind of doc drift: not stale-and-ignored but stale-and-authoritative and
self-contradicting. Both corrected. DoD 3 named only `BuildSystem.md`; the
other two were not in my file list and I had not looked.

**The review also corrected my own reasoning.** I told the worker to put
`RegisterThread` before `Profiling().Initialise()` because "RegisterThread
transitively calls `Zenith_Profiling::RegisterThread`". The ORDER is right but
that reason only argues the object must EXIST. The load-bearing reason is
`m_uMainThreadID = xThreading.GetMainThreadID()` at `Zenith_Profiling.cpp:666`
— `~0u` until `RegisterThread(true)` sets it, and `Initialise` self-guards on
`m_bInitialised` so a later call cannot repair it. Comment corrected to say the
real constraint.

That in turn exposed a **second, independent latent defect**:
RegistryViewer had the two calls in the opposite order, so it would have
recorded no main thread at all — silently, and masked today by the crash.
One-line swap, fixed here since the file was already open.

## Durable findings

- **`ZEN-D-036`** — a standalone tool linking `zenith.lib` cannot obtain the
  engine's runtime services, and the three accessors it needs carry no null
  assert, so the failure is an access violation with no diagnostic. Broader
  than TilePuzzle: every non-game-loop caller inherits a precondition it has no
  public way to satisfy. Records the second defect (the profiler ordering
  constraint) and why `FluxCompiler` survives only by avoidance.
