## Goal

`Games/TilePuzzle/tilepuzzle_win64.sln` is the ONE solution in the repo that
fails a whole-solution build. Measured on ZEN-85 (2026-09-21,
`Vulkan_vs2022_Debug_Win64_True`): exit 1, 27 error lines. Every other solution
measured — `Build/zenith_engine_win64.sln` in both `_True` and `_False`, and
`Games/Combat/combat_win64.sln` in `_True` — builds whole with zero errors.

Neither failing project is an aux tool. Both are TilePuzzle's own bespoke
tooling, and both have bit-rotted because nothing ever builds them:

- **`TilePuzzleLevelGen`** — 21 compile errors in `TilePuzzleLevelGen.cpp`. It
  calls engine APIs that no longer exist: `Zenith_TaskSystem::Inititalise`
  (the historical typo, now gone), an undeclared `Zenith_TaskArray`, a
  `Zenith_Profiling::Initialise` that no longer takes 0 arguments, a
  no-longer-static `Zenith_Multithreading::RegisterThread`, and an undeclared
  `ZENITH_PROFILE_INDEX__SCENE_UPDATE`.
- **`TilePuzzleRegistryViewer`** — compiles, then fails to link with 6 errors
  (`LNK2019`/`LNK2001`/`LNK1120`). It links `zenith.lib`, which requires the
  composition-root symbols every game supplies —
  `Project_SetGraphicsOptions`, `Project_RegisterGameComponents`,
  `Project_Shutdown` — and the viewer supplies none.

`zenith build TilePuzzle` is unaffected and stays green: it passes
`/t:TilePuzzle`, so it never builds either project. That is exactly why the rot
went unnoticed — no gate line, and no `zenith` command, builds these two
projects at all.

Either repair both projects against the current engine API, or retire whichever
is genuinely dead. Both are defensible; deciding which is part of the ticket.
Whichever way it goes, the outcome to aim at is that a whole-solution build of
`tilepuzzle_win64.sln` in `Vulkan_vs2022_Debug_Win64_True` is green, so the
"whole solutions build" statement ZEN-85 put into `Docs/BuildSystem.md` has no
remaining exception.

If a project is retired rather than repaired, remove it from the Sharpmake
project set and its solution the way the build system already expresses
membership — target declaration plus solution membership, never a
per-configuration source exclude (root `CLAUDE.md`, "The library structure's
invariant").
