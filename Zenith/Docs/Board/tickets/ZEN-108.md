## Goal

`Tools/Vault/scripts/adopt-stale-knowledge-rows.mjs` refuses during the **dry
run**, which is the one mode its organisation summary exists to make
informative. ZEN-104 added three guards on top of the dry-run default:

- the plan names the organisation each database belongs to (so a human can see
  a direction inversion before anything moves),
- a move into a destination holding none of its own rows is refused past
  `--max-moves`,
- two same-titled databases in one organisation are refused as unmergeable.

All three live in `planFor`, which is correct for atomicity (`ZEN-D-007`: a
refusal thrown there leaves the vault byte-identical with no journal and no
commit). But `planFor` also runs for the **preview**, so a refusal aborts the
dry run itself.

**The consequence is backwards.** In exactly the configuration the size guard
flags as a suspected resolver inversion, the human is denied the organisation
listing that was added for them to judge that inversion by. A dry run writes
nothing; refusing to SHOW a plan because the plan looks dangerous is the
opposite of what a dry run is for.

Two further edges, both observed on ZEN-104:

- In a five-database sweep (the default — omitting `--database` plans over all
  five), one key's refusal discards the organisation summary for **all five**,
  including keys already computed.
- The remedy a user reaches for is `--max-moves N`, and the refusal message
  names the exact number to pass. That is the same flag which authorises the
  apply, so "raise the threshold" becomes the natural first gesture rather than
  the last — the guard teaches the bypass.

The refusal text does carry the essential facts (the two database ids and the
shared slug for the collision; the row counts and the destination id for the
size guard), so nothing is unrecoverable. What is lost is the per-database
summary, which is the part that answers "is the direction right".

This is a design question about what a dry run should do when the plan looks
dangerous, deliberately left out of ZEN-104's scope rather than decided
unilaterally by a ticket whose DoD did not contain it. Candidate shapes, not a
prescription: gate the refusals on `apply === true` so a dry run always prints
and only an apply refuses; or have the dry run return the plan WITH a
`refusals` array rather than throwing; or compute all keys and aggregate the
refusals so one key cannot blank the other four.

Whichever is chosen, the atomicity property must survive: a refusal on the
`--apply` path must still be thrown from inside `planFor`/`prepare` before the
change set is built, per `ZEN-D-007`. Splitting "what the dry run reports" from
"what the apply refuses" must not become two divergent answers to the same
question — that is the defect `ZEN-D-029` corollary 3 warns about in a
different guise.

## Definition of Done

- [ ] A dry run against a vault that trips the size guard prints the
      organisation summary rather than aborting, from an OBSERVED run with the
      output quoted
- [ ] A dry run against a vault with two same-titled databases in one
      organisation does the same
- [ ] An `--apply` against either still refuses, and the vault is byte-identical
      afterwards
- [ ] In a multi-database sweep, one database's refusal does not suppress the
      other databases' reporting
- [ ] Every new or changed branch is covered by a test, and each guard's test is
      shown to be load-bearing by a mutation probe (see `ZEN-D-037`)
- [ ] `Tools/Vault/README.md` describes the resulting dry-run contract
- [ ] Every affected game's pinned baseline bumped from an OBSERVED run, if the
      change adds or removes a unit
