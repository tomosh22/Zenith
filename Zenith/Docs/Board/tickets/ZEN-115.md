## Goal
`zagent version create` writes a row that the board's own `version list` can never return.

The write side: `Tools/Vault/cli/write.mjs:1485` builds the new row as `{ id, name, description, status: 'UNRELEASED', position }`. It has no `project_id` and no other project field.

The read side: `version list` attributes a row to a project only through `project`, `project_key`, `projectKey`, or `project_id` looked up in `jira.projects` (`versionProject`, `Tools/Vault/cli/queries.mjs:434-436`). A row with none of these comes out as `String(undefined).toUpperCase()`, which is `"UNDEFINED"`, so `queries.mjs:446` filters it out of every project.

Measured on 2026-10-16 at `268b8ef6`:
- `zagent version list --project HE --json` and `zagent version list --project UV --json` both return `[]`.
- `Games/Hearth/Docs/Board/versions.md` holds 3 CLI-created rows (MVP, v1.0, Retail 1.0), and `Games/Undervault/Docs/Board/versions.md` holds 4.
- 37 HE tickets and 52 UV tickets name those versions in `fixVersions`.
- The FD and ZM rows were written with `project_id` by the migration, and they list correctly.

No existing test round-trips a create into a list. `Tools/Vault/test/write-branches.test.mjs:547-` and `Tools/Vault/test/mutations.test.mjs:336` assert only the create result.

The versions catalog is already per project: `version create` resolves it by board root (`configRecord(fresh, project, 'versions')`, `write.mjs:1480`). The preferred fix has two parts:
- When a row carries no project field, attribute it to the board whose catalog file holds it. This lists the existing HE and UV rows without editing any board file.
- Stamp the project onto newly created rows as well.
