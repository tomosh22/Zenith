## Goal

Found in the first lane test run (2026-09-23): `zagent queue` run from a registered lane lists the CHECKOUT DEFAULT project's queue (ZEN), not the lane's own, so `zagent queue` in `C:\dev\Zenith-lanes\ZM` shows ZEN tickets. It is read-only and harmless, but it is the one board read in a lane session that ignores the lane: `lane which`, `next` and `claim` are all lane-scoped already (a lane's bare `next` is scoped to its project through `index.lane`).

`dispatchQueue` (`Tools/Vault/cli/read.js`) picks its project with `projectSelection(index, argv)`, which falls back to the checkout default when no `--project` is given. In lane mode the Vault client sets `index.lane = { project, repoRoot }` (`Tools/Vault/cli/client.mjs`, `dynamicDispatcher`); outside lane mode `index.lane` is undefined.

Scope: in lane mode, a bare `zagent queue` (no `--project`) defaults to `index.lane.project`. An explicit `--project X` still wins, including another project's key — `queue` is a read, and reading another board from a lane is legitimate (unlike `claim`/`next`, which stay refused). Outside lane mode nothing changes. Add Vitest coverage next to the existing lane tests (`Tools/Vault/test/lanes*.test.mjs`, `cli-queue.test.mjs`): a lane-mode bare queue lists only the lane project's To Do tickets; an explicit `--project` from a lane lists that project; main mode is unchanged.
