## Goal
Root `CLAUDE.md:724` says: *"Completing a milestone sprint is REFUSED while that gate is unmet, and `--force` does not reach the check."* The code has no such check.

`sprint complete` (`Tools/Vault/cli/write.mjs:1393-1421`) refuses in only two cases: the sprint is not ACTIVE, or it has unfinished members and neither `--force` nor `--destination-sprint` was given. It never reads the sprint's `gate`. As a result, an ACTIVE milestone sprint whose gate ticket is still To Do completes with `--force`, and the gate ticket itself is carried to the backlog.

The human ruled on 2026-10-16 (Zenith2 open question Q6, option (b)) that the Vault enforces this. Completing a sprint is refused while its designated gate ticket is not in a DONE-category status, and `--force` does not bypass the refusal.

The gate is already resolved for reads. `sprint list` reports `gate: {key, title, status, unmet}` through `gateForSprint` (`Tools/Vault/cli/queries.mjs:375-390`), which handles both the frontmatter `gate:` key and the migrated `gate_issue_id`. Use that same resolution for the refusal, so `sprint list` showing `unmet: true` and `sprint complete` refusing can never disagree.

Current data: 21 of the 31 sprint files carry a gate. The one ACTIVE sprint, `Games/Zenithmon/Docs/Board/sprints/zm-g59n0dtrphhiop35dtrj6kcg.md`, is gated on ZM-30, which is To Do.

`sprint gate` (`write.mjs:1433-1438`) checks only that the ticket exists. `CLAUDE.md:724` describes the gate as *"an ordinary member of the sprint, never an EPIC"*. An EPIC's status does not track its children, so an EPIC gate would make this refusal meaningless. `sprint gate` should refuse an EPIC, and a ticket from another project.

The same `CLAUDE.md:724` sentence also says *"`--force` with unfinished work and NO designated gate is also a refusal"*. Here the doc is wrong and the code is right:
- `Tools/Vault/test/write-branches.test.mjs:536-545` pins `--force` carrying unfinished work to the backlog for an ungated sprint.
- `Tools/Vault/spec/command-matrix.md:210` specifies the same behaviour.

Keep that behaviour and correct the sentence.

## Definition of Done
- [ ] `zagent sprint complete <NAME>` on an ACTIVE sprint whose gate ticket is not in a DONE-category status exits 4, names the gate key and its status, and writes nothing
- [ ] The same refusal happens with `--force`. It also happens when the write path is given a destination sprint (`--destination-sprint`, which the tests pass directly because the CLI flag vocabulary does not accept it)
- [ ] Once the gate ticket is Done, the sprint completes, and `--force` still carries any other unfinished members to the backlog
- [ ] A sprint with no designated gate behaves as it does today: it is refused while it has unfinished members, unless `--force` is given, which carries them to the backlog
- [ ] `zagent sprint gate <NAME> <KEY>` exits 4 for an EPIC and for a ticket of another project
