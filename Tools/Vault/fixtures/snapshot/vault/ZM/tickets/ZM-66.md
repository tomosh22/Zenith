## Goal

Route 1 still cannot emit a wild encounter in a real boot. `ZM-22` (R1-4) landed the data and
the proof — the retuned rate via a Route-1-specific constant, the id-tagged biome table, and a
bake-independent synthetic roll-seam proof — but deliberately did **not** land the half that
makes encounters actually fire, because that half needs scene content and R1-4 was scoped
"re-authors: none".

`ZM_TallGrassSystem` is registered (ECS order 109) and, per its own header, *"Shares its entity
with the terrain component"*. Every place it is attached anywhere in the codebase is
tools-only scene authoring — the editor-automation step list plus a scene save — and there is
no production code path that attaches it. `Route1.zscen` is already committed, so attaching it
is a **change** to a committed asset, not a create.

**This is the gap R1-4's own slice row could not close.** The R1 slice table budgets R1-4 as
re-authoring nothing, while Status.md's structural fact #2 says the system is *"attached to NO
authored scene, so no shipped scene can emit a wild encounter ... Route 1 is where it comes
alive."* Those two statements cannot both be satisfied by one pure slice. The ticket is the
resolution: do the authoring half on its own, where the windowed boot it needs is expected
rather than a surprise.

**A workaround was considered and rejected, and should stay rejected.** ZM-22's worker weighed a
runtime hook — on scene load, if the scene is a ROUTE and its terrain entity lacks the
component, add it — and declined: it invents an unreviewed architectural pattern for a
component whose header says it owns nothing but the transition, and it lands in
`OnAwake`-not-firing-on-runtime-`AddComponent` territory that this project's decision log has
already been burned by. Author the scene; do not add a hook.

## Definition of Done

- [ ] Route 1's committed scene bytes are re-authored from a windowed boot, proven by two
