# ONLINE — identity, account changes, entitlements and achievements

## Scope of this file

This file is part of the ONLINE design family; the entry document is `Zenith2/Docs/Design/ONLINE.md`. It specifies the identity model, the session state machine, sign-in, account-change detection, identity verification after a resume, the rebind sequence that moves saves and entitlements to a new account mid-session, the cross-account isolation guarantees and their tests, generation fencing, entitlements (including the package entitlement query of Stage 6), achievements, the processing of script requests, notifications to worlds, replay mode and OS session signals. Every type named here is declared in `Zenith2/Docs/Design/ONLINE/PublicAPI.md`; every byte layout is in `Zenith2/Docs/Design/ONLINE/Formats.md`. The cloud-save model is `Zenith2/Docs/Design/ONLINE/CloudSave.md`.

## Identity model

### Account identifiers and keys

<!-- elaboration -->
- An account is identified by a `Zenith_OnlineAccountID`, the string `<prefix>:<native>`: `steam:` and the 64-bit SteamID in decimal; `gpgs:` and the Play Games player ID; `offline:` and the offline account name. The prefix keeps the identifiers of two backends disjoint, so a game that moves from the offline backend to Steam never maps an offline account onto a Steam account's saves. Inside the session every account comparison (stale, duplicate and changed signals; the bound account against `GetIdentity()`) compares the full account IDs byte for byte, never their keys, so a key collision can never skip a rebind.
- The account key `Zenith_OnlineAccountKey` is the value the session posts as `m_ulAccountKey` of PLAT's account signals (`Zenith2/Docs/Design/PLAT/Platform.md` → "Account signal sources"). PLAT records the account event's payload struct, key included, in every replay log: [Z2-N-ARCH-791] zeroes only the platform-scoped window IDs, device IDs and text-arena offsets of a recorded platform event, not its account key (`Zenith2/Docs/Design/PLAT.md` → "Threading lifetime and error contract", platform events in simulation step 1). The key is therefore **keyed with a per-install secret** so that it cannot be inverted: `Zenith_OnlineAccountKeyFromHash(LE64(the first 8 bytes of Zenith_Sha256Digest(S ‖ account ID bytes)))`, where S is the 32-byte install secret of the device record (`Zenith2/Docs/Design/ONLINE/Formats.md` → "Device record") and `Zenith_OnlineAccountKeyFromHash` maps 0 to 1 and every other value to itself (0 is reserved for "no account"). An unkeyed hash of a Steam account would invert by enumeration in minutes (the account number is 32 bits); the keyed one cannot be inverted without S, which never leaves the device: it is never logged, never counted, never published to a world, never written into a replay log, a save or a cloud object, and the device record is excluded from Android device backup and transfer (cross-area row ON18 (d)). The key is compared only within one process (R2 of § "Rebind steps", and replay ignores live events), so nothing depends on its value across installs or processes. It is never shown to a script: `Platform.AccountChanged` carries only the signal's kind and source (`Zenith2/Docs/Design/PLAT/SimulationInput.md` → "Script-facing input API").
- The save profile of an account is `Zenith_MakeSaveProfileKey(account ID)` (`Zenith2/Docs/Design/SAVE/PublicAPI.md` → "Zenith_SaveTypes header"), 16 hexadecimal digits of SHA-256, with two exceptions: signed out, and the offline account `offline:local`, both map to `Zenith_GetLocalSaveProfileKey()`. So a game that ships only the offline backend keeps its saves in `saves/local/`, exactly where SAVE puts them without the Online module, and adding a store backend afterwards moves each signed-in player to their own profile. The profile key is deliberately not keyed: another device must recognise the same account's cloud copies (envelope rule 9, `Zenith2/Docs/Design/ONLINE/Formats.md` → "Cloud envelope"), so it is a deterministic identity of the account, and it is stored only in that account's own data (its save directory and save metadata, its sync manifest's path, its cloud envelopes and index). ONLINE never writes it into a log line, a counter, a crash annotation, the overlay or a replay log; SAVE's own log line of a profile switch is the subject of cross-area row ON16 (c).
- Logs, the overlay, the console and crash annotations identify an account by the bind generation and the **account ordinal**: a session-local number, 1 for the first distinct account bound in the process, 2 for the next, and so on (the session keeps the last 16 bound account IDs and their ordinals in memory only; an account not among them receives the next number), printed `#<n>`, with the local profile printed `local`. An ordinal is meaningless outside its process.
- The display name is a `Zenith_OnlineDisplayName` (64 bytes UTF-8, sanitised). It is presentation data: the editor panel, the overlay and the console show it; a world sees it only when `online.exposeDisplayName` is true and the process is not recording a replay (§ "Display name exposure").

### Display name exposure

`Zenith_Module_Online_Start` reads `Zenith_ModuleStartContext::IsRecordingReplay()` (MAIN_THREAD, valid during `Start`; true when the process runs `--record`; `Zenith2/Docs/Design/MOD/RuntimeSeams.md` → "Start context members for ONLINE and PACK", row ON18 (c), landed).

When `online.exposeDisplayName` is true and `IsRecordingReplay()` is true, the module logs `online: online.exposeDisplayName ignored while recording a replay` once and starts the session with `m_bExposeDisplayName` false, so a display name never enters a replay log: every `Online.IdentityChanged` of the recorded run carries an empty `DisplayName`, and the replay reproduces exactly that. When the key is true outside recording, the module logs `online: online.exposeDisplayName is on; display names reach worlds` once at start.

### Backend identity snapshot

A backend reports its identity in two ways: `GetIdentity()` returns the current `Zenith_OnlineIdentitySnapshot` at any time on the main thread, and `Pump` calls `OnIdentityChanged` whenever the state, the account or the display name changes. The session treats `GetIdentity()` as the truth and `OnIdentityChanged` as a trigger: whenever the two disagree (a newer change queued behind the one delivered), the session acts on `GetIdentity()`. A sink callback only records that the identity may have changed (§ "Account change detection"); the session acts on it after the backend's `Pump` returns, because the sink's contract forbids calling `Submit` from inside `Pump` (`Zenith2/Docs/Design/ONLINE/PublicAPI.md` → "Zenith_OnlineServices header", `Zenith_OnlineEventSink`).

### Session state machine

<!-- elaboration -->
`Zenith_OnlineSessionState` × event → next state and action. "Bound account" is the account the session is bound to (empty when signed out), "target account" the account of `GetIdentity()` (empty unless SIGNED_IN); both are compared as full account IDs. REBINDING has two sub-states held in the session: `AWAITING_SIGNAL` (fenced, the account signal posted, the account consumer not yet called) and `AWAITING_PROFILE` (the consumer ran, SAVE's profile switch not yet accepted). "Queue" means appending to a world's notification queue; parking (allocating a completion ID and parking the payload) happens only at the end of `Pump` (§ "Notifications" step 3).

| State | Event | Next state | Action |
|---|---|---|---|
| (Create, `m_bReplay`) | — | REPLAY | § "Replay mode" |
| (Create) | — | STARTING | load the device record; bound account empty; generation 0 |
| STARTING | `Start`'s Session step, backend SIGNED_IN at creation (Steam; offline with auto sign-in) and `SetActiveProfile` accepted | SIGNED_IN | § "Bind at start": R4 … R6 in `Start`, no signal, no fence, generation 0 → 2 |
| STARTING | account consumer (an OS-sourced account event delivered before the first `Pump`) | STARTING | the event is deferred: kept, and handled as R1 … R6 at the end of the first `Pump`, after the STARTING row that `Pump` takes (bound account still empty) |
| STARTING | first `Pump`, backend SIGNED_IN (the bind at start did not happen: SAVE was busy, or the identity settled after creation) | REBINDING (`AWAITING_SIGNAL`) | § "Account change detection" with kind `ACCOUNT_SIGNAL_SIGNED_IN` |
| STARTING | first `Pump`, backend SIGNING_IN (Play's automatic sign-in in progress) | SIGNING_IN | submit nothing; wait for the identity to settle (the backend's own request completes it) |
| STARTING | first `Pump`, backend SIGNED_OUT, auto sign-in on (offline `online.offline.autoSignIn`; Steam and Play always) | SIGNING_IN | submit `ONLINE_REQUEST_SIGN_IN_SILENT` |
| STARTING | first `Pump`, backend SIGNED_OUT, auto sign-in off | SIGNED_OUT | queue IDENTITY_CHANGED with reason signed out (no sign-in was attempted) |
| SIGNING_IN | identity settled SIGNED_IN | REBINDING (`AWAITING_SIGNAL`) | detection, kind SIGNED_IN |
| SIGNING_IN | sign-in completion not OK | SIGNED_OUT | § "Sign-in" step 4 |
| SIGNING_IN | backend reports SIGNED_OUT before the sign-in request completes | SIGNED_OUT | § "Sign-in" step 4, as a failed sign-in; the outstanding sign-in request's later completion is consumed and changes nothing |
| SIGNED_OUT | target account non-empty (identity event or poll) | REBINDING (`AWAITING_SIGNAL`) | detection, kind SIGNED_IN |
| SIGNED_IN | backend SIGNING_IN (an unverified identity, Play on resume) | VERIFYING | § "Identity verification" step 1 |
| VERIFYING | backend SIGNED_IN, target account = bound account | SIGNED_IN | § "Identity verification" step 3 |
| VERIFYING | backend SIGNED_IN with another account, or SIGNED_OUT | REBINDING (`AWAITING_SIGNAL`) | § "Identity verification" step 4: detection, kind SWITCHED or SIGNED_OUT |
| VERIFYING | `m_uRequestTimeoutMs` elapsed since entry | VERIFYING | count `online.account.verify_timeouts` once; keep the binding and the hold (§ "Identity verification" step 6); only the backend's SIGNED_OUT or another player leaves VERIFYING |
| VERIFYING | account consumer (a re-posted or test signal) | VERIFYING | the event is deferred: kept, and handled as R1 … R6 once verification decides (same account: a duplicate; otherwise the rebind) |
| SIGNED_IN | backend reports SIGNED_OUT | REBINDING (`AWAITING_SIGNAL`) | detection, kind SIGNED_OUT |
| SIGNED_IN | target account non-empty and ≠ bound account | REBINDING (`AWAITING_SIGNAL`) | detection, kind SWITCHED |
| SIGNED_IN or SIGNED_OUT | account consumer, target account = bound account, not fenced | unchanged | duplicate: count `online.account.duplicate_signals`; nothing else |
| SIGNED_IN, SIGNED_OUT or SIGNING_IN | account consumer, target account ≠ bound account | REBINDING (`AWAITING_PROFILE`) | fence (§ "Generation fencing"), then the rebind from step R4 |
| REBINDING (`AWAITING_SIGNAL`) | account consumer | REBINDING (`AWAITING_PROFILE`), or SIGNED_IN / SIGNED_OUT when step R6 runs at once | the rebind from step R1 |
| REBINDING (`AWAITING_SIGNAL`) | 60 frames without a consumer call | unchanged | re-post the signal; count `online.account.signal_reposted` |
| REBINDING (`AWAITING_PROFILE`) | `Pump`, `SetActiveProfile` accepted | SIGNED_IN or SIGNED_OUT | step R6 (the bind: generation to the next even value) |
| REBINDING (`AWAITING_PROFILE`) | `Pump`, `SAVE_ERROR_PROFILE_BUSY` | unchanged | retry next frame; count `online.account.profile_busy_retries` |
| REBINDING (`AWAITING_PROFILE`) | `Pump`, any other error, attempts < `m_uRebindMaxSaveAttempts` | unchanged | attempts += 1; retry next frame |
| REBINDING (`AWAITING_PROFILE`) | the same, attempts reached | SIGNED_IN or SIGNED_OUT (degraded) | § "Profile switch retry" step 3 |
| SIGNED_IN (degraded) | 60 frames since the last degraded attempt | unchanged, or the late switch of § "Profile switch retry" step 4 | § "Profile switch retry" step 4 |
| REBINDING (any) | the target account changes again (to another SIGNED_IN account, or to SIGNED_OUT) | REBINDING (`AWAITING_SIGNAL`) | a new detection: the fence is re-run (the generation moves to the next odd value), the pending profile is replaced |
| REBINDING (any) | backend SIGNING_IN (an unverified identity, Play resuming during a busy switch) | unchanged | keep the pending profile; hold completions and defer account events as VERIFYING does; the rebind continues when the backend reports SIGNED_IN (the same target: as before; another: a new detection) or SIGNED_OUT (a new detection) |
| any except REPLAY, SHUT_DOWN | `BeginShutdown` | SHUTTING_DOWN | `Zenith2/Docs/Design/ONLINE.md` → "Startup and shutdown" |
| SHUTTING_DOWN | account consumer, or a backend identity change | SHUTTING_DOWN | logged in `online.account`, nothing else: no fence, no rebind, nothing queued; the bound account is kept until SHUT_DOWN |
| SHUTTING_DOWN | flush finished or deadline passed, backend `Shutdown` returned | SHUT_DOWN | `IsDrained` true |
| REPLAY | `BeginShutdown` | REPLAY | the call is recorded (`IsDrained` reads it); `PumpShutdown` does nothing; `IsDrained` is true from then, because no backend exists to shut down; the destructor's check therefore passes for a replay session |
| REPLAY | any event | REPLAY | none |

Every transition is logged in the `online.account` category with the generation and the account ordinals (`#<n>` or `local`), never an account identifier, an account key or a profile key.

## Sign-in

1. Steam and the offline backend sign in during the backend's creation or immediately (Steam's identity exists when `SteamAPI_InitFlat` succeeds; the offline backend signs `online.offline.activeAccount` in when `online.offline.autoSignIn` is true). Play performs PGS v2's automatic sign-in at start (`Zenith2/Docs/Design/ONLINE/Backends.md` → "Play identity").
2. Bind at start: when `GetIdentity()` reports SIGNED_IN as soon as the backend is created, `Start` binds synchronously (§ "Bind at start"). Otherwise, in STARTING the first `Pump` reads `GetIdentity()`: SIGNED_IN goes to detection; SIGNING_IN (Play's automatic sign-in still running) waits in SIGNING_IN without submitting; SIGNED_OUT submits `ONLINE_REQUEST_SIGN_IN_SILENT` and enters SIGNING_IN.
3. A successful sign-in is reported by the backend through `OnIdentityChanged`, never by the completion's payload; the completion only ends the request.
4. A failed silent sign-in (any status but OK) moves to SIGNED_OUT and queues `ONLINE_NOTIFY_IDENTITY_CHANGED` with reason sign-in failed to every PLAY world. The save profile is left as SAVE started it (the last-profile record, `Zenith2/Docs/Design/SAVE/Formats.md` → "Last profile record"): the player of a device who last played signed in keeps playing that profile offline, and the cloud is unavailable until a sign-in succeeds. A subsequent explicit sign-out (a SIGNED_IN identity becoming SIGNED_OUT) is what switches to the local profile.
5. When Play's `online.googlePlay.interactiveSignInOnStart` is true and the silent attempt failed, the session submits one `ONLINE_REQUEST_SIGN_IN_INTERACTIVE`; otherwise an interactive sign-in happens only on request: `Online.RequestSignIn(ctx, true)` from a script, or `RequestSignIn(true)` from presentation code.
6. Silent sign-in is retried after a failure only on an `ONLINE_INVALIDATION_CONNECTIVITY` event reporting connected, at most once per 60 s.

<!-- elaboration -->
Rationale for step 4: SAVE's resume rule already binds the resume file to the profile that was active when it was written, and a device that relaunches offline must not lose its player's saves; switching to `local` on a failed sign-in would hide them, while a real sign-out (the player chose to leave the account, or the backend reports another state) is the event Z2-D-074 names.

The treatment is deliberately asymmetric. Saves made while signed out under the last profile belong to that profile, so they are attributed to the account that profile belongs to and upload at that account's next sign-in: SAVE's profile, not ONLINE, decides whose saves they are, and a different account that signs in next binds its own profile and sees none of them (I1). Achievements earned while signed out are never credited to anyone (§ "Achievement operations"): an achievement is a claim about a person, the session cannot know which person earned it while nobody was signed in, and crediting it to the next account would be a cross-account leak (I6). The game recovers its own achievements from its save state after `Online.IdentityChanged` reports `SignedIn` (the reconcile pattern of `Zenith2/Docs/Design/ONLINE/PublicAPI.md` → "Script-facing API"), so a player who signs back in loses nothing that their save records.

## Bind at start

Worlds attach at startup step 16, after `Start` (step 15), bound under the profile SAVE started in (the last-profile record, `local` on a first launch). A bind that happens only at the first `Pump` would flag every such world whose profile differs, so its requests answer `accountChanged`, its saves are refused, and the reference flow reloads it, on every first launch and on every launch whose last profile is not the signed-in account's. The session therefore binds before any world exists whenever it can:

1. In `Start`'s Session step, right after `Zenith_OnlineSession::Create`, the module calls `session.BindAtStart()` when `GetIdentity()` reports SIGNED_IN (Steam after a successful `Init`; the offline backend with `online.offline.autoSignIn`).
2. `BindAtStart` runs R4 … R6 of § "Rebind steps" with `SetActiveProfile(P′)` called directly (no world is bound yet, so no intake freeze is needed): accepted → the generation goes 0 → 2 (no fenced interval exists, because no request can have been recorded), the state becomes SIGNED_IN, the account's work is submitted, and no account signal is posted (no world exists to observe `Platform.AccountChanged`); refused (SAVE busy at step 15, or any error) → nothing changes and the first `Pump` takes the ordinary PLAT path.
3. A PLAY world that attaches is told the identity it finds, by state at its `AttachWorld`:

| State at attach | Queued to the world |
|---|---|
| SIGNED_IN, SIGNED_OUT (after a bind, a failed silent sign-in, or with auto sign-in off after the first `Pump`) | one `ONLINE_NOTIFY_IDENTITY_CHANGED` with reason attached (5), signed in true or false, the backend, its previous-profile flag (computed at attach, normally clear) and, when exposed and the flag is clear, the display name |
| VERIFYING | the same, with the bound state (signed in), because the binding holds |
| STARTING, SIGNING_IN | nothing at attach; the first settle (the bind, or the sign-in failure) queues its own notification to every PLAY world, this one included |
| REBINDING | nothing at attach; the bind's R6 queues its notification to every PLAY world, this one included |

So every world learns the identity without a query (a world attached after a failed sign-in learns signed out at once instead of waiting for the title flow's 10 s), and the reference flow re-asserts achievements on `Attached` with signed in.
4. Identities that settle after creation (Play's `nativeOnPlayer`, a silent sign-in that completes after creation, an offline backend with auto sign-in off) bind through detection and PLAT. Worlds created before such a late first bind are flagged when their binding profile differs from the bound one: on Play's first launch, the boot world. The flagship title flow therefore holds its entry into gameplay until the first IDENTITY_CHANGED, or until 10 s pass (cross-area row ON23 (b)), so a gameplay world entered before the first bind, which the late bind would flag and whose unsaved progress the flow would discard, does not arise in the reference games; a game that enters gameplay earlier accepts that reload.

## Account change detection

Detection compares `GetIdentity()` with the bound account; it is triggered by `OnIdentityChanged` and by the comparison every `Pump` makes. Inside the backend's `Pump` the sink's `OnIdentityChanged` only sets the session's `m_bIdentityDirty` flag; detection runs after the backend's `Pump` has returned and before the inbox drain of the same session `Pump` (§ "Generation fencing" ordering), so it may submit requests:

1. Classify against `GetIdentity()`: bound empty → target non-empty is `ACCOUNT_SIGNAL_SIGNED_IN`; bound non-empty → target empty is `ACCOUNT_SIGNAL_SIGNED_OUT`; both non-empty and different is `ACCOUNT_SIGNAL_SWITCHED`; a SIGNED_IN session whose backend reports SIGNING_IN enters VERIFYING instead (§ "Identity verification").
2. Fence immediately (§ "Generation fencing"): from this point until the bind, no request, transfer or cache answer of the previous account runs, and every request recorded meanwhile carries an odd generation, so it can never execute under the account bound next.
3. Post `Zenith_Platform::PostAccountSignal({ kind, ACCOUNT_SIGNAL_SOURCE_ONLINE_BACKEND, target key, 0 })` with the keyed target key (0 for an empty target) (`Zenith2/Docs/Design/PLAT/Platform.md` → "Account signal sources"). PLAT converts it into `PLATFORM_EVENT_ACCOUNT_CHANGED` at the next pump; the runtime hands that event to the account consumer, `Zenith_OnlineSession::OnAccountEvent`, before any world sees it (`Zenith2/Docs/Design/PLAT/Platform.md` → "Account event delivery"), and PLAT publishes it to every world at the next tick boundary as `Platform.AccountChanged`.
4. Enter REBINDING (`AWAITING_SIGNAL`) and record the frame index of the post.

<!-- elaboration -->
The session posts the signal rather than rebinding at detection so that every account change follows one path through PLAT: one ordering point, one recorded publication to worlds, and one consumer call that rebinds before gameplay reacts. The price is a fenced interval of one frame (the frame of the post) whose ticks may record requests; the second generation boundary at the bind (§ "Generation fencing") is what keeps those requests from running as the new account. A `PostAccountSignal` failure (`PLATFORM_ERROR_BAD_SIGNAL` is impossible for the values above; any failure is a defect) is logged and counted `online.account.post_failed`, and the session runs the consumer path itself at the end of the same `Pump`, after the backend's `Pump` has returned, so the rebind still happens.

## Identity verification

A backend whose identity can change while the game is not looking (Play: the player can switch the Play Games account in another app while the game is in the background) reports an **unverified identity** when it cannot vouch for the current player: `OnIdentityChanged` with `ONLINE_IDENTITY_STATE_SIGNING_IN`, and `GetIdentity()` answering SIGNING_IN until it has re-read the player. The window between the resume and that re-read is fenced as follows (the resume fence):

1. Entering VERIFYING (from SIGNED_IN, in the `Pump` that observed SIGNING_IN): the generation is unchanged; the session still drains the script inboxes but executes nothing: each drained record moves to the world's pending pool as a deferred record with its intake deadline (the inbox and the pool share the in-flight capacity the merge bounds, so it always fits), and runs at step 3 in drain order; no new backend request is submitted; the cloud engine pauses (no transfer starts; a running transfer step completes into the held state below); every internal read in flight (entitlement refresh, achievement load, `CLOUD_LIST`, `CLOUD_READ`) is cancelled, its completion discarded, and it is resubmitted after step 3, each only once its cancelled predecessor's completion has been delivered, because the resubmitted read reuses the buffer the cancelled one was given (`Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Transfer memory").
2. While VERIFYING, every completion delivered by the backend is **held**: the session copies the status and at most 64 payload bytes (a write's 32-byte revision, an unlock's flag, a set-steps answer) into the pending record and acts on nothing; a script record's completion is held the same way, not parked. A held completion of a script record that has meanwhile been completed (its deadline passed, or its world detached and it was completed `ABANDONED`) only frees the record when it is applied or discarded. Notifications already queued stay queued and are parked as usual (they were built before the resume).
3. The same account confirmed (`GetIdentity()` SIGNED_IN with the bound account ID): back to SIGNED_IN; every held completion is applied in the order it was delivered, exactly as if it had arrived now; the cancelled reads are resubmitted (each after its predecessor's completion); the deferred records run in drain order, each with the checks of § "Request execution" step 2. Nothing is rebound and nothing a script requested fails unless its own deadline passed.
4. Another account or no account: detection runs (kind SWITCHED or SIGNED_OUT) and fences, which completes every accepted script request `ACCOUNT_CHANGED` (the deferred records included) and discards every held completion; records pushed since the last drain, stamped with the previous generation, drain as `ACCOUNT_CHANGED` after the fence.
5. A cloud write that was already in flight when the player changed may have reached the new player's cloud (the SDK commits it under whichever player it then holds); that cloud then holds an index or envelope carrying the previous profile's key, which the new account's reconcile classifies as a foreign index (`Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Index view"), a state in which nothing is deleted, so the residual cannot destroy data. The same holds for an index commit Play made offline and the server overrides on reconnection: the cloud model treats the lost entry as a lost commit and re-uploads (`Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Three-way decision table" rows 18 and 19).
6. A long verification is not a sign-out: when the backend has not answered after `m_uRequestTimeoutMs`, the session counts it and keeps the binding and the hold (the cloud stays paused, nothing is submitted, deferred records complete `TIMEOUT` as their own deadlines pass, saves are unaffected because SAVE's profile is unchanged). Only the backend's SIGNED_OUT, or another player, rebinds; a resume with poor network therefore never returns the legitimate player to the title world. The session does not re-ask: the backend that reported the unverified identity owns re-reading it (Play repeats `RefreshIdentity(silent)` at every connectivity change and otherwise every 15 s while it reports SIGNING_IN, `Zenith2/Docs/Design/ONLINE/Backends.md` → "Play identity"; the offline backend's unverified state is the test access's and ends when the test clears it), so a lost callback cannot freeze the session for the rest of the process.
7. Play's own client also queues `unlock` and `increment` calls made while offline and replays them on reconnection under whichever player it then holds; an achievement call the session submitted before the player switched in the Play Games app can therefore reach the new player. The session cannot see or cancel the client's queue; I6 states what the session controls (§ "Cross-account isolation").

Every backend obeys the same rule from `Pump`: the session compares `GetIdentity()` with the bound account before applying each completion it receives (it may call `GetIdentity` from a sink callback), and a completion delivered while the backend does not report the bound account SIGNED_IN is held as in step 2 until detection or confirmation decides it.

## Rebind sequence

### Rebind steps

`OnAccountEvent(const Zenith_PlatformAccountPayload& xAccount)`, the process account consumer, runs on the main thread in frame-prologue step 1 (assumption pending ARCH and MOD in `Zenith2/Docs/Design/ONLINE.md` → "Assumed interfaces pending other areas": once per `PLATFORM_EVENT_ACCOUNT_CHANGED`, after `Platform.Pump`, before the frame listeners' `OnPlatformEvents`). A payload whose source is `ACCOUNT_SIGNAL_SOURCE_OS` goes to § "OS session signals" instead. For a backend-sourced payload:

| Step | Action | Failure |
|---|---|---|
| R1 | Read `GetIdentity()`; the target is its account when SIGNED_IN, else empty | none |
| R2 | When the payload's key differs from the keyed key of the target account (0 for empty), the signal is stale (a newer change is queued behind it): count `online.account.stale_signals` and continue with the target account, so the session always converges on the backend's current account | none |
| R3 | When the target account equals the bound account (full ID comparison) and the session is not fenced: a duplicate; count it and return. When the session is not fenced but the accounts differ (a signal from a test, or a change the session had not yet detected): fence now | none |
| R4 | Compute the target profile P′ (§ "Account identifiers and keys"); when P′ equals `Zenith_SaveSystem::GetActiveProfile()`, go to R6; otherwise call `Zenith_SaveSystem::BeginProfileSwitch(P′)` (SAVE freezes intake for every world not bound under P′, § "Worlds bound under the previous profile"), then `Zenith_SaveSystem::SetActiveProfile(P′)` (`Zenith2/Docs/Design/SAVE/Algorithms.md` → "Profile switching") | `SAVE_ERROR_PROFILE_BUSY` or another error: § "Profile switch retry" |
| R5 | The switch was accepted: SAVE has cleared every retained and pending checkpoint and its slot table, recovered P′'s journals, written the last-profile record and ended the intake freeze, so nothing of the previous profile is readable through SAVE | — |
| R6 | Bind: the generation moves to the next even value (§ "Generation fencing"); bound account and bound profile become the target's (the bound profile is `GetActiveProfile()`, the profile SAVE actually made active); the display name is the snapshot's; the account ordinal is assigned; the state is SIGNED_IN (target non-empty) or SIGNED_OUT; for every attached world set the previous-profile flag when `GetBindingProfile(tag)` differs from the bound profile (§ "Worlds bound under the previous profile"); for every attached PLAY world queue `ONLINE_NOTIFY_IDENTITY_CHANGED` with reason signed in, signed out or switched (empty → A, A → empty, A → B; a rebind to the account it was fenced from reports signed in), the display name when exposed and only to a world whose previous-profile flag is clear (a flagged world's notification carries an empty display name), and flag bit 0 equal to the world's previous-profile flag; then start the account's work: the entitlement refresh (§ "Entitlement refresh"), the achievement load (§ "Achievement synchronisation") and, when the cloud is enabled and the backend has the capability, the cloud reconcile (`Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Reconcile algorithm") | a refresh or load that cannot be submitted is retried with the backoff |

When SAVE is idle (no queued or running operation, no checkpoint lease), R1 to R6 complete inside the one consumer call, so the account's saves and entitlements are rebound in the same frame prologue in which PLAT delivered the change, before the tick boundary that publishes `Platform.AccountChanged` to worlds.

### Profile switch retry

<!-- assumption: pending SAVE (row ON16 (a)) -->
ONLINE assumes SAVE adds `Zenith_SaveSystem::BeginProfileSwitch(const Zenith_SaveProfileKey& xTarget) → Zenith_Result<void, Zenith_SaveError>` and `AbandonProfileSwitch()` (MAIN_THREAD; refused in replay with `SAVE_ERROR_REFUSED_IN_REPLAY`). From `BeginProfileSwitch(P′)` until `SetActiveProfile(P′)` succeeds or `AbandonProfileSwitch` is called, SAVE refuses every new request of a world whose binding profile is not P′ with `SAVE_ERROR_PROFILE_MISMATCH` (`QueueRequest`, `SubmitOutOfTick`, a due autosave, which is skipped and counted, `SubmitResumeWrite`, `SubmitExitAutosave`), lets the work already queued or running drain, and keeps the retained-checkpoint leases' existing release rule; a second `BeginProfileSwitch` replaces the pending profile; a successful `SetActiveProfile(P′)` ends the freeze.
<!-- /assumption -->

1. `SAVE_ERROR_PROFILE_BUSY` (SAVE refuses while any operation is queued or running or a retained-checkpoint lease is alive): stay in REBINDING (`AWAITING_PROFILE`) with the pending profile P′, retry `SetActiveProfile(P′)` at every `Pump`, and count each retry. Because the intake freeze refuses every new request of the previous profile's worlds, SAVE's queues only shrink: the writer finishes its job, a retry's restore job ends and releases its lease, and the switch succeeds after a bounded number of frames however often the game autosaves (SAVE's design states the runtime retries it each prologue, `Zenith2/Docs/Design/SAVE/Algorithms.md` → "Checkpoints"). A save the previous account's world attempts meanwhile fails with `SAVE_ERROR_PROFILE_MISMATCH`, published to the world as a save result, so nothing of the new account's play is written into the previous account's profile.
2. Any other error (an I/O failure while recovering P′'s journals): count the attempt and retry at the next `Pump`.
3. After `m_uRebindMaxSaveAttempts` non-busy failures: `AbandonProfileSwitch()`, then `BeginProfileSwitch(local)` and `SetActiveProfile(local)` once; on success bind (R6) with the account's identity and the `local` save profile actually made active, so every world's previous-profile flag and IDENTITY_CHANGED flag bit 0 are computed against `local`; disable the cloud engine for the session (`ONLINE_NOTIFY_CLOUD_STATUS` degraded, reason profile switch failed). When the local switch also fails, `AbandonProfileSwitch()` and keep the session in REBINDING, retrying P′ every 60 frames. In no outcome does the new account's session use the previous account's profile: SAVE's active profile is either P′, `local`, or still the previous account's while the session stays fenced (every request answered ACCOUNT_CHANGING, the cloud idle, every entitlement UNKNOWN to scripts and DENIED to packages).
4. In the degraded state, every 60 frames: `SetActiveProfile(P′)` alone, without `BeginProfileSwitch`, so no intake freeze ever refuses the current world's saves for a switch that may not happen; SAVE accepts it only at a moment it is idle (no queued or running operation, no lease), so the switch and the end of the old profile's intake are one call; a busy answer or a failure waits 60 frames again. A game that saves continuously can postpone the late switch, which only prolongs the degraded state the bind already reported. When it is accepted (the late switch): the bound profile becomes P′; every world's previous-profile flag is recomputed against P′; every attached PLAY world is queued `ONLINE_NOTIFY_IDENTITY_CHANGED` with the reason of the original bind, the display name when exposed, and flag bit 0 equal to its recomputed flag, so a world bound under `local` learns that it must return to a world bound under the new profile; the cloud engine is enabled and the cloud status queued as available after its first reconcile; the generation does not change (the account did not change). Counted `online.account.late_profile_switches`.
5. A further account change during the retry replaces P′ (state machine row "the target account changes again"); the new detection's `BeginProfileSwitch` replaces the pending profile.

### Worlds bound under the previous profile

<!-- assumption: pending SAVE (row ON1 (d)) -->
A world's state was created under the profile active when SAVE bound it (`Zenith_SaveSystem::BindWorld`). After an account switch that state still belongs to the previous account, so saving it into the new profile would leak the previous account's progress into the new account's saves. ONLINE assumes SAVE records each world binding's profile at `BindWorld`, exposes it as `Zenith_SaveSystem::GetBindingProfile(uint16 uWorldTag) → Zenith_SaveProfileKey`, and refuses every request of a world whose binding profile differs from the active profile with `SAVE_ERROR_PROFILE_MISMATCH` (a new code, 38): `QueueRequest`, `SubmitOutOfTick`, the autosave scheduler (a due autosave of such a world is skipped and counted), `SubmitResumeWrite` and `SubmitExitAutosave`.
<!-- /assumption -->

ONLINE applies the same rule to its own requests: a world whose previous-profile flag is set (R6, or the late switch of § "Profile switch retry" step 4) has every script request answered `ACCOUNT_CHANGED` at drain (§ "Request execution" step 2), so the previous account's world can neither unlock an achievement for the new account nor learn the new account's entitlements or cloud state. The game learns of the situation from `Online.IdentityChanged` with `PreviousProfileSession` true, and returns to a world created after the switch (its title or profile-select world, a GAME world transition), which binds under the new profile and whose flag is clear. The reference flow in the flagship games does exactly that (`Zenith2/Docs/Design/ONLINE.md` → "Flagship slice integration"). A save attempted before the transition fails with the SAVE error published as a save result, which the game's save UI already handles.

## Generation fencing

- The session holds a 64-bit bind generation `std::atomic<uint64>`, 0 at `Create`. The value is **odd while the session is fenced** (from a fence to the following bind) and **even otherwise**. The fence sets it to the least odd value greater than the current one (a fence while already fenced therefore advances it by 2); the bind (R6) sets it to the least even value greater than the current one. So the bind is a second generation boundary: no record stamped before the bind, and in particular none stamped during the fenced interval, can carry the bound generation. The low 32 bits are published in every result and notification header (`Zenith2/Docs/Design/ONLINE/Formats.md` → "Script result payloads").
- Every pending record (a script request, an internal request, a cloud job) stores the generation it was accepted in. A completion whose record's generation is not the current one is discarded after its record is freed; a script record was already completed at the fence.
- The fence, in order: (1) the generation to the next odd value (store-release); (2) state REBINDING; (3) `Cancel` every backend request in the pending tables; (4) complete every accepted, uncompleted script request `ACCOUNT_CHANGED` through its world's sink; (5) cancel the cloud engine's jobs and SAVE operations (`Zenith_OperationHandle::RequestCancel`), detaching their buffers (§ "Rebind state per subsystem"); (6) clear the entitlement states to UNKNOWN, switch the package answers to DENIED when a previous bind exists, and increment the entitlement revision; (7) discard the achievement cache and the display name; (8) drop the queued, unparked notifications; (9) log `online.account: fenced (generation <g>)`. Steps 3 to 8 make no backend call that can block; the whole fence is O(pending records + slots + queued notifications).
- Ordering inside `Pump`: the backend's `Pump`, then detection and its fence, then the inbox drain. A record recorded under A in the ticks before the change was detected therefore drains after the fence and answers `ACCOUNT_CHANGED`.
- The fence does not drain the script inboxes: records already in an inbox carry their intake generation and are completed when the next drain reaches them. The fence and the bind run in the frame prologue, which is not a frame-graph subgraph and runs on the main thread before the frame's ticks ([Z2-N-ARCH-437]), so no merge node is writing an inbox while the generation changes, and a record pushed by a subsequent merge node carries the new value.

<!-- informative -->
The interleaving the second boundary closes: in frame F's `Pump` the backend reports bob while alice is bound; the fence moves the generation from 2k to 2k + 1 and posts the signal. Frame F's ticks still run alice's world, whose behaviour calls `Online.UnlockAchievement("beat_boss")`; intake stamps the record 2k + 1. In frame F + 1 the consumer binds bob (SAVE idle) and the generation becomes 2k + 2 before `Pump`; `Pump` drains the record, whose odd generation answers `ACCOUNT_CHANGING`, so bob's achievement is never unlocked by alice's world. `Test_OnlineRebind_RequestInFencedFrame_NotRunForNewAccount` replays exactly this sequence.

## Entitlements

### Entitlement cache

- One `Zenith_OnlineEntitlementState` per catalogue entitlement, plus the generation the states belong to, a `uint64` revision starting at 1, and the package-answer mode (normal or fenced-deny).
- `GetEntitlementState(id)`: an ID absent from the catalogue answers DENIED (logged once per ID per session as `online: entitlement '<id>' is not in the online catalogue`); an ID in the catalogue answers its cached state.
- The revision increments whenever any state may have changed: at every fence, and at every completed refresh whose answers differ from the previous ones or that ends the fenced-deny mode. `GetEntitlementRevision()` returns it; PACK's query reads the same value (§ "Entitlement query for packages").

### Entitlement refresh

1. Submitted at bind, on `ONLINE_INVALIDATION_ENTITLEMENTS`, on a script `QueryEntitlement` while the states are UNKNOWN and no refresh is in flight, and after a failed refresh's backoff (`m_uRetryBackoffMs`, doubling to 480,000 ms). At most one refresh is in flight; a trigger during a refresh sets a flag that submits one more after it.
2. The request is `ONLINE_REQUEST_QUERY_ENTITLEMENTS` with one native ID per catalogue entitlement that has a mapping for the backend (Steam: the app ID in decimal; Play: the product ID; offline: the catalogue ID); entitlements with no mapping answer DENIED without a backend call.
3. Signed out: when the backend lacks `uONLINE_CAPABILITY_ENTITLEMENTS_WITHOUT_SIGN_IN`, every state is DENIED and no request is made; Play has the capability (ownership belongs to the device's Play Store account, `Zenith2/Docs/Design/ONLINE/Backends.md` → "Play entitlements through Play Billing"), so it refreshes while signed out.
4. On OK (generation current): copy the states, end the fenced-deny mode, increment the revision when any state changed or the mode ended, queue `ONLINE_NOTIFY_ENTITLEMENTS_CHANGED` (revision, granted count) to every PLAY world whose previous-profile flag is clear when any state changed, and complete every script `QueryEntitlement` waiting on the refresh.
5. On failure: keep the states (UNKNOWN after a fence) and the mode (fenced-deny after a fence), complete the waiting script requests with the mapped status (`UNAVAILABLE`, `BACKEND_ERROR`), schedule the backoff.

### Entitlement query for packages

<!-- assumption: pending PACK and MOD (rows ON3 (c), ON17; PACK's answer PK21) -->
From Stage 6 `Zenith_OnlinePackEntitlements` implements PACK's `Zenith_EntitlementQuery` (`Zenith2/Docs/Design/PACK/PublicAPI.md` → "Zenith_EntitlementQuery header") over the session. The module hands it over at `Start` through `Zenith_ModuleStartContext::ProvideEntitlementQuery(Zenith_EntitlementQuery&)` (MAIN_THREAD, during `Start` only, at most one per process, journaled), which MOD implements by setting it as the provider of the package bridge's `Zenith_ForwardingEntitlementQuery` (`Zenith2/Docs/Design/PACK/Algorithms.md` → "Entitlement provider"; there is no `Zenith_PackageService::SetEntitlementQuery`). The forwarder answers UNKNOWN until the provider is set and again from shutdown step 4, so ONLINE's query is never called after its module starts shutting down, and every provider change is a revision change, so the service re-evaluates every entitlement-gated unit at its next prologue.
<!-- /assumption -->

- `GetRevision()` returns `GetEntitlementRevision()`.
- `GetEntitlement(id)`: in the normal mode, the cached `Zenith_OnlineEntitlementState` mapped one to one (the values are equal); in the **fenced-deny mode**, which a fence enters only when a previous bind exists (the generation was 2 or more before the fence) and the first successful refresh of the bound account ends (§ "Entitlement refresh" step 4), DENIED for every ID. Before the first bind of the process, the first detection's fence included, the mode is normal and the states are UNKNOWN, so nothing is mounted and nothing is revoked at start-up, and no entitlement-gated pack records `ENTITLEMENT_DENIED` before the first refresh answers.
- Why DENIED rather than UNKNOWN: PACK's current revocation rule unmounts a mounted DLC when its answer becomes DENIED, and raises nothing on a change to UNKNOWN (`Zenith2/Docs/Design/PACK/Algorithms.md`, entitlement events E and G). Answering DENIED in the fenced interval makes the previous account's DLC unmount at PACK's first evaluation after the fence whatever PACK's choice about UNKNOWN, and PACK's G event (DENIED → GRANTED) remounts the DLC the new account owns once its refresh completes. Scripts keep seeing UNKNOWN, which is the truth they can act on. An offline account change therefore unmounts a DLC until the new account's refresh answers, which on the offline backend is the next frames.

The package service calls the query in its own prologue step after ONLINE's `Pump` (ONLINE runs in prologue step 1; PACK's DLC evaluation in step 1b, `Zenith2/Docs/Design/PACK.md` → "Frame-graph placement"), so a revision change made by a rebind is seen by PACK in the same frame.

## Achievements

### Achievement operations

The four operations of the script surface, after § "Request execution" accepted them (signed in, bound generation current, the world's previous-profile flag clear):

| Operation | Precondition failures (status) | Cache hit (no backend call) | Backend call |
|---|---|---|---|
| unlock | ID not in the catalogue: `UNKNOWN_ID`; no mapping for the backend (Steam name or Play ID; the offline backend needs none): `NOT_SUPPORTED`; not signed in: `NOT_SIGNED_IN` | the cache says unlocked: OK, `alreadyUnlocked` true | `ONLINE_REQUEST_UNLOCK_ACHIEVEMENT`; OK updates the cache (unlocked, steps = total for incremental) |
| set steps (n) | as unlock; a standard achievement: `REFUSED`; the cache not loaded: wait for the load | n ≤ cached steps: OK with the cached values (steps never decrease) | n is clamped to the total; `ONLINE_REQUEST_SET_ACHIEVEMENT_STEPS` with the absolute value and the total; OK stores max(cache, n) and unlocked when it reaches the total |
| increment (d) | as set steps | none | as set steps with n = min(total, cached + d), the cache updated at drain time so consecutive increments accumulate in drain order |
| query | as unlock, except a missing mapping still answers from the offline cache | always from the cache once loaded | none |

- Increments are applied in the order the session drains them (world tag ascending, then each world's merge order), and the backend receives absolute step values, which it keeps at their maximum, so a backend applying two calls out of order still ends at the larger value.
- Achievements earned while signed out are not queued for a subsequent account: a request while signed out completes `NOT_SIGNED_IN`, so progress made by one person signed out can never be credited to whichever account signs in next (I6, and the asymmetry of § "Sign-in"). The game re-asserts unlocks from its own save state after `Online.IdentityChanged` (the reconcile pattern of `Zenith2/Docs/Design/ONLINE/PublicAPI.md` → "Script-facing API"); the backends' own SDKs keep unlocks made while signed in but disconnected (Steam stores stats locally until `StoreStats` reaches the service; Play's client queues `unlock` and `increment` calls offline).
- A loaded cache that is unavailable (the load failed) makes unlock and set steps call the backend anyway (both are idempotent and monotonic), and makes increment and query complete `UNAVAILABLE`.

### Achievement synchronisation

1. At bind, the session submits `ONLINE_REQUEST_QUERY_ACHIEVEMENTS` with every catalogue achievement mapped for the backend (Steam: the API name, with the progress stat beside an incremental one; Play: the ID; offline: the catalogue ID).
2. On OK the cache holds unlocked and steps per achievement; requests waiting for the load run in their drain order.
3. On `ONLINE_INVALIDATION_ACHIEVEMENTS` the cache is reloaded the same way; operations accepted meanwhile wait for the reload.
4. A failed load schedules the backoff of § "Entitlement refresh" step 5.

## Script request processing

### Request intake

1. The `Online` bindings record a `SIDE_EFFECT_KIND_ASYNC_REQUEST` (payload `Zenith2/Docs/Design/ONLINE/Formats.md` → "Script request payloads"). A rolled-back or rejected invocation records nothing and consumes no completion ID ([Z2-N-SCRIPT-334]); a committed one is assigned its completion ID at commit in merge order.
2. The runtime's multiplexer routes the record by byte 0 to `Zenith_OnlineScriptConsumer::Consume` on the committing world's merge node (`Zenith2/Docs/Design/MOD.md` → "SCENE and SCRIPT seams of the runtime"), which calls `SubmitScriptRequest(worldTag, completionID, payload)`.
3. In replay mode the request is dropped (counted `online.replay.requests_dropped`); the replay source supplies its recorded result ([Z2-N-SCRIPT-336]).
4. Otherwise the session copies the payload (at most 80 bytes) with the completion ID, the current generation (an acquire load of the atomic generation) and the intake time (`Zenith_GetMonotonicTimeUs` ÷ 1,000) into the world's inbox, a `Zenith_SpscRing` (`Zenith2/Docs/Design/CORE/Containers.md`) of `m_uMaxRequestsPerWorld` records, whose single producer is the world's merge chain (one world's merge nodes never overlap). The inbox cannot be full when the merge accepted the request (the capacity row Z2-B-SCRIPT-026 bounds both); a full inbox is a defect, handled by completing the request `REFUSED` at once through the world's sink and counting `online.requests.inbox_full`.

### Request execution

At each `Pump`, after detection and its fence, for each attached world in ascending world tag, every record of its inbox in FIFO order (while VERIFYING, step 2 onward is replaced by deferral to the pending pool, § "Identity verification" step 1):

1. Decode (`Zenith_DecodeOnlineScriptRequest`); failure: `REFUSED`.
2. In this order: the record's generation is odd (it was recorded while fenced): `ACCOUNT_CHANGING`; it differs from the current generation: `ACCOUNT_CHANGED`; the state is REBINDING: `ACCOUNT_CHANGING`; the world's previous-profile flag is set: `ACCOUNT_CHANGED`; the state is SHUTTING_DOWN: `SHUTTING_DOWN`.
3. Execute the operation:

| Operation | Executed by |
|---|---|
| query identity | answered at once: signed in, backend kind |
| request sign-in | already signed in: answered at once; otherwise `ONLINE_REQUEST_SIGN_IN_SILENT` or `_INTERACTIVE` (`NOT_SUPPORTED` without the capability); the result is answered when the identity settles (bound, or the sign-in failed) |
| query entitlement | § "Entitlement refresh" |
| unlock, set steps, increment, query achievement | § "Achievement operations" |
| query cloud slot | answered at once from the cloud engine's slot table (`Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Slot sync state machine"); cloud off: `CLOUD_DISABLED` |
| resolve cloud conflict | `Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Resolution choices" |
| sync cloud now | `Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Polling and triggers"; answered when that reconcile and its transfers finish |
| repair cloud index | `Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Index repair"; answered when the repair commits or fails |

4. A record waiting on a backend request or an internal job moves to the world's pending pool (`m_uMaxRequestsPerWorld` records, allocated at `AttachWorld`) with its deadline: its intake time (the monotonic milliseconds `SubmitScriptRequest` stored in the inbox record) plus `m_uRequestTimeoutMs`, the same start point `online.requestTimeoutMs` names.

### Result completion

- A result is built when its operation finishes, encoded (`Zenith_EncodeOnlineResult`) and parked through the world's sink: `Park(completionID, ASYNC_SOURCE_ONLINE, PUBLICATION_KIND_GENERIC_RECORDED, bytes)`. The publication becomes visible at the world's next tick boundary in completion-ID order ([Z2-N-SCRIPT-335]) and is recorded in the replay log ([Z2-N-SCRIPT-336]).
- Every accepted request is completed exactly once (the producer obligation of cross-doc item X255): with its result, `ACCOUNT_CHANGED` at a fence, `TIMEOUT`, `SHUTTING_DOWN`, or `ABANDONED` at `DetachWorld`. A record is freed only after both its script completion and, when it made one, its backend request's completion.
- Results are presentation-independent: an OK result's body is a pure function of the session's state at completion, and the publication tick is a simulation input recorded in the log ([Z2-N-SCRIPT-338]).

### Timeouts

At each `Pump`, every pending script record (deferred records included) whose deadline, measured from intake, has passed is completed `TIMEOUT`. A record with a backend request of its own (an unlock, a set-steps call, a sign-in) has that request cancelled; a record waiting on a shared internal job (the entitlement refresh, the achievement load, a reconcile, a repair, which several records can wait on at once) only detaches from it: the job is cancelled only by a fence, by shutdown or by its own failure, so one waiter's timeout never cancels the work another waiter is owed. The deadline is wall-clock (`Zenith_GetMonotonicTimeUs` divided by 1,000), which is allowed because the outcome is recorded: a replay publishes the recorded `TIMEOUT` at its recorded tick whatever the replaying machine's speed. A record whose completion is held (§ "Identity verification" step 2) times out the same way; its held completion is then discarded when it is applied.

## Notifications

1. The session parks notifications only to worlds attached with `WORLD_PURPOSE_PLAY` (editor and preview worlds get none, I10). ENTITLEMENTS_CHANGED, CLOUD_CONFLICT, CLOUD_SLOT_REPLACED and CLOUD_STATUS are built from the bound account's state, so they are queued only to PLAY worlds whose previous-profile flag is clear; IDENTITY_CHANGED goes to every PLAY world, with an empty display name for a flagged one (I7).
2. Each world has a queue of `uONLINE_NOTIFY_QUEUE_CAPACITY` (96) encoded notifications. When it is full, the oldest ENTITLEMENTS_CHANGED or CLOUD_STATUS entry is dropped to make room; with none of those, the new notification is dropped; both count `online.notify.dropped`. IDENTITY_CHANGED, CLOUD_CONFLICT and CLOUD_SLOT_REPLACED are dropped only by a fence (§ "Rebind state per subsystem") or in that last case, and a dropped CLOUD_CONFLICT is reported again by the next reconcile.
3. At the end of each `Pump`, for each PLAY world in ascending tag: while the world's own outstanding set holds fewer than `uONLINE_NOTIFY_MAX_OUTSTANDING` (8) completion IDs and the queue is non-empty, allocate a completion ID through the world's sink on the main thread (`AllocateCompletionID(ASYNC_SOURCE_ONLINE)`, a frame-prologue allocation of a recorded kind), park the head, and add the ID to the outstanding set (8 entries, in the world record). `PUBLICATION_SINK_ERROR_FULL` stops that world for the frame (retried at the next `Pump`); `PUBLICATION_SINK_ERROR_REPLAYING` cannot occur (the session parks nothing in REPLAY); `PUBLICATION_SINK_ERROR_DETACHED` stops that world for good. The sink admits this allocation: `ASYNC_SOURCE_ONLINE` is a mixed kind (script-declared by ONLINE with `DeclareScriptAsyncSource`, with ONLINE's handler registered on each world's sink), whose one site is the prologue, and whose notifications park as `PUBLICATION_KIND_GENERIC_RECORDED` (`Zenith2/Docs/Design/MOD/RuntimeSeams.md` → "Allocation sites and acceptance" steps 1 and 2, "Parking a result" step 2; row ON18 (f), landed). `PUBLICATION_SINK_ERROR_SITE` therefore indicates a defect (a handler not registered, an allocation off the prologue) and is kept as a defensive path: a permanent refusal of the configuration, distinct from capacity: the session logs `online: notification source refused by the publication sink (site)` once, counts `online.notify.site_refused`, and stops allocating for every world for the process (queued notifications stay queued and count as dropped when the queue fills), so a refusal never turns into a retry loop.
4. The session's tick-boundary handler removes an ID from the world's outstanding set when it sees that notification published; an ID the set does not hold (a notification restored from a save, below) changes nothing, so the set can never underflow. A paused world therefore accumulates at most 8 parked notifications, which publish at its first resumed tick boundary ([Z2-N-SCRIPT-335]). A notification is a C++-allocated publication without a ticket, so SCRIPT releases its slot at that boundary, after the handler, while a script result keeps its slot until its ticket is read (`Zenith2/Docs/Design/SCRIPT/Runtime.md` → "Asynchronous result table"; the mixed-kind rule core-doc item X337 adds to [Z2-N-SCRIPT-343]), so notifications never pin the source's capacity.
5. At tick-boundary step 1, `OnPublished` receives every `ASYNC_SOURCE_ONLINE` publication of the world in completion-ID order (through the sink's module-side handler). A payload whose byte 0 is 1 (a script result) is left for its ticket. A payload whose byte 0 is 2 is decoded (`Zenith_DecodeOnlineNotification`; a failure drops it and counts `online.events.decode_failed`) and appended to the world's published buffer (16 records; beyond that, possible only from a corrupt replay, dropped and counted).
6. In phase 1, the system `Online.Events@W<tag>` (C++, `PHASE_INPUT`, `EmitsEvent` of the five event types, no component access) takes the buffer with `TakePublishedNotifications` and emits one event per record, in order, with the fields of `Zenith2/Docs/Design/ONLINE/PublicAPI.md` → "Event types"; delivery is phase 9 of the same tick.
7. A save taken while notifications are parked and unpublished (a pause-menu save) records them as SAVE records every unpublished `GENERIC_RECORDED` result (`Zenith2/Docs/Design/SAVE/Formats.md` → "Async section"); a restore publishes them into the restored world exactly as recorded, so they may describe an identity or a conflict that has since changed. They are delivered as recorded (determinism forbids rewriting them); consumers tolerate them: a resolution of a slot no longer in conflict answers `notInConflict`, an `IdentityChanged` older than the world's current binding is followed by the current state's own events, and the reference flows check `Online.QueryIdentity` and `Online.QueryCloudSlot` before acting.

## Replay mode

<!-- assumption: pending MOD (row ON5 (a)) -->
`Zenith_Module_Online_Start` learns that the process runs `--replay` from `Zenith_ModuleStartContext::IsReplaying()`, a member ONLINE requests from MOD (the world sink's `IsReplaying()` exists per world only from `AttachWorld`).
<!-- /assumption -->

In replay mode:

1. `Start` creates no backend (no factory is called, so no SDK initialises and no file of the user mount is opened), reads no catalogue asset (it creates `Zenith_OnlineCatalogue::CreateEmpty` and passes it as the session's non-null `m_pxCatalogue`), registers no console command that changes state, and creates the session with `m_bReplay` and a null `m_pxServices`.
2. The session's state is REPLAY for its whole life; `OnAccountEvent` returns at once (a replay ignores live platform events, [Z2-N-ARCH-791]); `Pump` does nothing; script requests are dropped at intake; no completion ID is ever allocated; every presentation action returns `ONLINE_ERROR_REPLAY`.
3. The session's tick-boundary handler and the `Online.Events` systems still run: the replay source supplies every recorded `ASYNC_SOURCE_ONLINE` publication, results reach their tickets, and recorded notifications become the same events at the same ticks as in the recorded run, so the replayed simulation is bit-identical ([Z2-N-ARCH-783]).
4. The replay header records no online configuration key (none is simulation-affecting), so a replay of a Steam-backed recording runs on a machine with no Steam client.

## OS session signals

`ACCOUNT_SIGNAL_SOURCE_OS` payloads (Windows session notifications, `Zenith2/Docs/Design/PLAT/Platform.md` → "Account signal sources") never rebind: the OS session's user is not the online account.

| Signal | Action |
|---|---|
| `ACCOUNT_SIGNAL_SESSION_LOCKED` | no new cloud transfer starts until unlocked; transfers in flight finish; count `online.os.session_locked` |
| `ACCOUNT_SIGNAL_SESSION_UNLOCKED` | transfers resume; a reconcile is submitted when more than `online.cloud.pollSeconds` (or 300 s when that is 0) passed since the last |
| `ACCOUNT_SIGNAL_SIGNED_OUT` (Windows logoff) | the background flush of `Zenith2/Docs/Design/ONLINE/CloudSave.md` → "Shutdown and background flush" starts, because the process is about to end |
| `ACCOUNT_SIGNAL_SIGNED_IN`, `ACCOUNT_SIGNAL_SWITCHED` from the OS | not produced by PLAT today; ignored and counted `online.os.ignored` |
