# ECS design — queries, views and change tracking

This file is part of the ECS design family; the entry document is `Zenith2/Docs/Design/ECS.md`, whose section "Chunk queries" states the worker-facing contract of iterating a query. This file specifies the algorithms behind it: query compilation, the matched-chunk cache and its invalidation, change-filtered queries, view validation, change versions and merge versions, the stage order of merge points, the version wrap sweep, row change bits and `CommitRowChanges`, the own-row rule and random access. The specification is `Zenith2/Docs/Architecture/ECSModel.md` → "Queries", "Views" and "Sync points and the structural epoch" (Z2-I-ECS-06, Z2-I-ECS-07).

## Query compilation

`Zenith_World::CompileQuery(xDesc)` runs on the sync-point node or out of tick (in practice at `Zenith_SystemRegistry::Freeze` and at each recompile, for every `Zenith_QuerySlot`); each slot compiles its own query, so no query is shared between systems and a query's cache has one owner. Steps:

1. Validate: 1 to 16 terms; every type registered with `TYPE_KIND_COMPONENT` (`ECS_ERROR_UNKNOWN_TYPE`); every named property in the type's current revision (`ECS_ERROR_UNKNOWN_PROPERTY`); a type named twice with conflicting operators, `m_bWrite` on a `WITHOUT` term, or at least one `WITH` or `CHANGED` term missing is `ECS_ERROR_INVALID_DESC`; more than `uECS_MAX_QUERIES_PER_WORLD` queries is `ECS_ERROR_CAPACITY`.
2. Normalise: expand empty property lists to every property of the type; drop container properties from the column set (they are not exposed in chunk views, [Z2-N-ARCH-699]); sort terms by (operator, type ID) and each term's properties ascending; the column set is the union of `WITH`, `CHANGED` and `OPTIONAL` properties in (type ID, property ID) order.
3. Record the required set R (`WITH` ∪ `CHANGED` types), the excluded set X (`WITHOUT`), the optional set O and the write mask per column; mark read-only the value types that chunk views never write ([Z2-N-ARCH-699]: `STRING_ID`, `ENTITY`, `ASSET`, `PERSISTENT_ID`), whatever `m_bWrite` says (a C++ write declaration of such a property is legal for commands; the view simply returns it with `m_bWritable = false`).
4. Hand the normalised query to the backend, which builds its storage-specific match structure (`Zenith2/Docs/Design/ECS/Backends.md` → "Queries" for the custom backend, the query row of `Zenith2/Docs/Design/ECS/Backends.md` → "flecs mapping", and `Zenith2/Docs/Design/ECS/Backends.md` → "Owning groups and views" for EnTT) and an empty cache marked stale.
5. Return the `Zenith_QueryID` (the index in the world's query table).

Complexity O(t log t + p log p) for t terms and p properties. `Test_Query_CompileValidation` covers every rejection.

## Matched-chunk cache and invalidation

Each compiled query caches, per matched chunk, a `Zenith_ChunkBinding` with one `Zenith_ChunkColumnBinding` per column (null data for an optional component the chunk lacks), in the backend's storage order ([Z2-N-ARCH-702]). The world's **query structure version** is incremented by playback whenever it creates or removes an archetype, table, pool page or chunk ([Z2-N-ARCH-700], ECSModel table "Sync points and the structural epoch"); a query is **stale** when its cached version differs from the world's.

Refresh rule (the lazy refresh of [Z2-N-ARCH-700]):

1. At the end of every sync point's playback (after step 9), the sync-point node refreshes, in query-ID order, every stale query whose owning system runs in a subsequent stage of the current tick instance or in the next tick instance (the schedule records each query's owner and phase), then no other. At the end of the end-of-tick playback (its step 6) it refreshes every stale query of the world, in query-ID order, whatever its owner: after a tick's last stage the next readers are phase 1 of the next tick instance and, after the frame's last tick instance (a catch-up frame runs several), the EPILOGUE stage-12 extractors and epilogue stages, whose queries no sync point's subsequent-stage set contains. A frame that runs no tick instance (paused, or no accumulated time) runs its epilogue on caches the previous end-of-tick or out-of-tick playback refreshed. `Test_ECS_ExtractorQueryFreshAfterCatchUp` runs a frame of three catch-up ticks with a spawn recorded in the last tick's phase 10 and asserts that the extractor's query sees the spawned entity in that frame's epilogue, on every backend.
2. Out of tick (tools, tests, world loading), `GetChunkCount` on a stale query refreshes it on the calling main thread first.
3. Within a phase no query is refreshed and no binding changes, so a system's chunk list is stable for the whole phase ([Z2-N-ARCH-700]); a `GetChunkCount` from a frame-graph node on a stale query is `ZENITH_ASSERT` (it cannot happen by rule 1) and returns the cached count.

A refresh walks the backend's match structure: the custom backend appends archetypes created since the last refresh to the query's archetype list (a query records the archetype count it has examined, so a refresh examines only new archetypes, O(new archetypes × terms)), then rebuilds the chunk binding array from the matched archetypes' chunk lists (O(chunks)); flecs refreshes from its cached query's table list; EnTT regathers its synthetic chunks (O(entities in the leading pool)), which is the chunk-synthesis cost the research reports ([Z2-N-ARCH-686], Z2-D-064).

Invalidation of what callers hold is by structural epoch alone (§ "Views and validation"): a refresh never changes a chunk that playback left untouched, and a chunk whose rows playback changed has a new epoch.

## Chunk iteration contract

For a system invocation:

1. `GetChunkCount(slot)` returns the number of chunks the system sees in this invocation: the cached matched-chunk count, filtered by `QUERY_TERM_CHANGED` terms (§ "Change-filtered queries"). The first call in an invocation builds the invocation's filtered ordinal list in the node arena; subsequent calls reuse it.
2. `GetChunk(slot, i)` for `i < count` returns a view of the i-th filtered chunk, scoped to the invocation (`GetScope()`), with pending change bits allocated in the calling context's arena for every writable column (one bit per row, rounded up to 64-bit words, zeroed) and a staging-weight array for every writable `WeightedBlend`-arbitrated column. Two `GetChunk` calls for the same (slot, i) in one invocation return views sharing one pending-bit block.
3. The system iterates inline or with `ParallelFor(count, grain, …)` ([Z2-N-ARCH-397], [Z2-N-ARCH-707]); each leaf calls `ForLeaf` and `GetChunk` on its own context.
4. Row order within a chunk and chunk order are storage order and never observable to simulation ([Z2-N-ARCH-702]): a system that needs an order sorts by stable simulation ID (`GetSimulationIDs`) or folds through merge order and fixed-order trees ([Z2-N-ARCH-703], [Z2-N-ARCH-704]).

`Test_ECS_QueryStableWithinPhase` records commands from every chunk of a query during a phase and asserts the count and every binding are unchanged until the sync point; `Test_Query_ChunkOrderUnobservable` runs one system under both capacities and forced compaction and asserts identical tick hashes.

## Change-filtered queries

<!-- elaboration -->
A `QUERY_TERM_CHANGED` term matches a chunk when at least one of the term's declared properties has a column version that is newer than the query slot's **last-seen version** L and is not the slot's **own version** O:

- **L** is the version of the system's **read point** in its latest completed invocation: the merge point that immediately precedes the system's node in its stage's order (§ "Stage order of merge points" item 5). Every commit of a property the system declares a read of that the schedule ran before the node is at or below L, and every such commit it ran after the node — a same-stage writer the system pre-read through `Before(<writer>)`, an arbitration node after it, the system's own merge, the stage's sync point and everything after it — is above L. The qualification is real: item 2.2 of § "Stage order of merge points" joins every same-stage commit of a property the system reads to the system's node by a direct edge, so the stage order and the executor agree on those, while a merge point that commits only properties the system does not read has no edge to the node and may sit on one side of it in the stage order and run on the other; no `CHANGED` term of the system can observe that (its terms name only properties it reads), but it means L is no watermark for other properties. So the next invocation sees exactly the committed writes of the properties it reads that the previous one did not read.
- **O** is the version the system's own merge point stamped in that invocation (0 for a system that has no merge point). A column whose version equals O was last stamped by the system's own merge and by nothing since, because every other producer stamps a different version: the system does not re-see its own in-place writes, so a system that normalises a property it filters on does not re-trigger itself. Every other write of the same property is seen, including a command the system itself recorded (applied at a sync point) and the result an arbitration node commits from the system's own staged value.
- **Comparison.** Both start at 0, so the first invocation sees every chunk: L = 0 matches every chunk (0 is never issued as a version, so it means "never seen"); otherwise a property matches when `Zenith_IsVersionNewer(uColumnVersion, L) && uColumnVersion != O`.
- **When it runs.** The filter runs once per invocation, when the invocation's ordinal list is built (step 1 above). Versions are settled by then: every commit ordered before the node has completed, because merge nodes and final continuations complete before any successor starts ([Z2-N-SCRIPT-159], [Z2-N-ARCH-395]), and every commit ordered after it is above L.
- **Update.** Where the invocation completes — its merge node's trampoline, or for a system without a merge node its final continuation (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Disabled systems") — the slot takes the invocation's (L, O): its read version and, when it has a merge point, its merge version; the system's **previous read version** P, which `Zenith_SystemContext::GetPreviousReadVersion()` returns to its next invocation, takes the same read version, so P equals the L of every slot of the system. A disabled or skipped invocation leaves all three unchanged. The version wrap sweep resets a pair whose L is more than 2^30 merge points behind the world to (0, 0), and a P that old to 0, which also bounds the stored side, so serial-number comparison never inverts (§ "Version wrap sweep"); `RestoreSimulationState` resets every pair and every P (§ "Change versions and merge versions" item 2).
- `Zenith_World::GetChunkCount` and `GetChunk` (the world-level API used by tools and tests) ignore `CHANGED` filtering: they see every structurally matching chunk.

**What the filter promises: conservative and chunk-granular.** A `QUERY_TERM_CHANGED` term never omits a chunk holding a row whose named property was committed after the read point, and it may hand the system unchanged rows and unchanged chunks: unchanged rows always, because which rows share a chunk with a changed row depends on chunk capacity and compaction (and a relocation makes a destination chunk's column version at least as new as the row it moved in, `Zenith2/Docs/Design/ECS/Backends.md` → "Change tables"); whole unchanged chunks in the first invocation after `RestoreSimulationState`, or after the version wrap sweep reset the slot (§ "Version wrap sweep" item 4). A system's committed result must therefore not depend on whether an unchanged row was handed to it: Z2-D-019 already demands results independent of chunk layout, and this is the same rule as [Z2-N-ARCH-702] for order. A system either processes every row of a matched chunk so that an unchanged row yields the value it already holds, or makes a row-level decision by comparing `Zenith_ChunkView::GetRowChangeVersions(xType, xProperty)` against `Zenith_SystemContext::GetPreviousReadVersion()`: a row is changed when its version is newer under `Zenith_IsVersionNewer` or when the previous read version is 0 (every row; a row the system itself wrote in its previous invocation also compares newer, which this rule makes harmless). A system keeps no last-seen version of its own: a copy it kept would survive `RestoreSimulationState` and the sweep, which reset only the slot pairs and previous read versions ECS holds, would then lie ahead of every re-stamped row version, and would miss writes; C++ cannot forbid such a copy, so its absence is part of the system contract (`Zenith2/Docs/Design/ECS/SystemAPI.md` → "Zenith_SystemContext header"). Under this rule an over-match changes no committed result and no tick hash, which is what makes the resumed-replay promise (§ "Change versions and merge versions" item 2) and the sweep's false positive harmless. The determinism fixture carries a row-filtered `CHANGED` system so that the capacity and compaction axes exercise the rule (`Zenith2/Docs/Design/ECS/Tests.md` → "Determinism suite").

`Test_ECS_ChangedQueryFilter` asserts that a `CHANGED` query returns exactly the chunks whose declared properties changed, across two systems and three ticks, on every backend. Four tests pin the read-point and own-version rules and the stage-ordered merge chain, each on every backend:

## Views and validation

A `Zenith_ChunkView` holds its binding pointer, its scope, the chunk's structural epoch at creation, its merge version and its private pending bits. `IsValid(xCurrent)` is `m_ulScope == xCurrent.m_ulInvocationID && *m_pxBinding->m_puStructuralEpoch == m_uEpochAtCreation` ([Z2-N-ARCH-696]): two integer compares, compiled in every configuration, because SCRIPT raises its view errors from it in every build ([Z2-N-ARCH-697], [Z2-N-SCRIPT-443]). A view outlives no invocation. Views are returned by value, so a copy a caller retains cannot be reached to clear it; instead the invocation's merge resets the node-arena block that holds the invocation's pending bits and staging weights, and validity rests on the scope compare: a retained copy fails `IsValid` in every subsequent invocation (its scope is the finished invocation's, which is never reissued), and its C++ use (`GetColumn`, `MarkRowChanged`, `CommitRowChanges`) asserts where asserts are enabled and `CommitRowChanges` returns `ECS_ERROR_STALE_HANDLE` in every build ([Z2-N-ARCH-697]). Merge versions are stamped only by the paths of `Zenith2/Docs/Design/ECS/WorldAPI.md` → "Zenith_ChunkView header" (table "Merge version stamping"): a world-level view (`Zenith_World::GetChunk`, `GetChunkOfEntity`) carries version 0 and cannot commit, a system context stamps its invocation's version, and a playback write view carries the playback's version.

`GetColumn(xType, xProperty)`:

1. Binary search the binding's columns (sorted by type then property); absent means undeclared: return a null column and `ZENITH_ASSERT` where asserts are enabled ([Z2-N-ARCH-698]); the null column's `m_pData` is null so any use faults visibly in every build rather than reading unrelated memory.
2. A declared read returns `{ m_pData, m_uStride, m_uRowCount, m_puRowIndex, nullptr, false }`.
3. A declared write of a non-arbitrated property returns the same with `m_pulRowChangeBits` pointing at the view's pending bits for that column and `m_bWritable = true`.
4. A declared write of an arbitrated property by a writer returns the writer's **staging column** for its writer source (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Arbitration merge"), with the pending bits used as the source's written bits; `GetArbitrationWeights` returns its weight array. <!-- elaboration --> The staging column is a write target: a row the writer has not written this invocation holds no meaningful value. A writer that also declared a read of the property reads the **committed** value, the property column as the previous merge left it (at the start of the tick when nothing committed it since), through `Zenith_ChunkView::GetCommittedColumn` (added by the arbitration slice), never its own or another source's staged value: staged contributions become visible only after the arbitration node has merged them, to the readers step 5 names. `GetCommittedColumn` of any other declared column returns its read form (step 2).
5. A read of an arbitrated property by a non-writer in the writers' phase reads the arbitration node's result (the real column), because the schedule orders it after the arbitration node ([Z2-N-ARCH-497]).

## Change versions and merge versions

<!-- elaboration -->
[Z2-N-ARCH-694] advances a column's version at the merge point of the writing invocation, and [Z2-N-ARCH-723] sets it to the world's change version "which the merge node has incremented once for that merge point". Merge continuations of different systems in one phase can run concurrently (only merge nodes that consume shared capacity are chained, [Z2-N-ARCH-692]), so a counter incremented at run time would hand out versions in completion order, and `QUERY_TERM_CHANGED` results would then depend on scheduling, breaking Z2-D-019. This design makes every version a **precomputed merge version**:

<!-- /assumption -->

1. **Enumeration.** At `Freeze` (and at every recompile, before `EmitInto` declares the nodes), the world simulation enumerates the **merge points** of one tick in a fixed order: ordinal 0 is the tick boundary; then, for each stage s from 1 to 11, the merge points of stage s — the merge of every system of stage s that writes any column (its merge node, or for a system without one its system node, whose final continuation commits) and every arbitration node of stage s — in the stage order of § "Stage order of merge points", then the sync point of stage s (for s = 11, the end-of-tick playback). M is the highest ordinal. Each system and each arbitration node lies in exactly one stage and is at most one merge point, and the tick boundary and the 11 sync points are the only other ordinals, so M ≤ (systems) + (arbitration nodes) + 11. Systems are bounded by `Zenith_SystemRegistryDesc::m_uMaxSystems` ≤ 65,536 (a larger value, or 0, is `ECS_ERROR_INVALID_DESC` at `Create`, `Zenith2/Docs/Design/ECS/SystemAPI.md` → "Zenith_System header") and arbitration nodes only by the declarations, so the enumeration computes M and `Freeze` fails when M ≥ 2^20: it logs `ECS_ERROR_CAPACITY` under `ecs.schedule` with the message `schedule: world <w> declares <M> merge points per tick; at most 1048575 are admitted` and returns a `Zenith_ScheduleError` whose one diagnostic is `SCHEDULE_ERROR_GRAPH` carrying that text (no specification code names the limit, and it is a property of the stage graphs `EmitInto` lowers), so startup stops with exit code 3 and a recompile keeps the previous schedule ([Z2-N-ARCH-409]). Every schedule that runs therefore has M < 2^20, which the one-boundary-per-tick sweep trigger and the 2^31 comparison bound of § "Version wrap sweep" rest on. `Test_SystemRegistry_MaxSystemsAndMergePointBound` covers both limits, the merge-point limit lowered for the test through `Zenith_WorldTestAccess::SetMergePointLimit`.
2. **Unwrapped counter.** The world simulation keeps a `uint64` tick base B. Merge point m of tick t has the unwrapped number U(t, m) = B_t + m. Before the first tick the tick index is 0 and B_0 = 0; tick-boundary step 0 of tick t, once the pause check has passed and t is determined, sets B_t = B_(t−1) + M_(t−1) + 1, where M_(t−1) is the M of the schedule tick t − 1 ran, before step 1 runs and step 3 commits at V(t, 0); so U grows by exactly one per merge point across ticks and across a recompile that changes M (a recompile takes effect at a frame boundary), and a paused boundary advances nothing (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Tick boundary and end-of-tick" step 0). `RestoreSimulationState(t, …)` (out of tick) sets B_t = t × (M + 1) for the current M and resets the change-tracking state to that point: every stored column and row version is re-stamped to V(t, M) through `SweepChangeVersions(xToken, V(t, M), 0)` (a threshold of 0 rewrites every version other than V(t, M), including one that lies ahead of the restored counter on the ring), every query slot's (L, O) becomes (0, 0) and every system's previous read version 0, and the sweep floor becomes ⌊U(t, M) / 2^29⌋ (§ "Version wrap sweep" item 1). So after a save load or a replay checkpoint every `QUERY_TERM_CHANGED` system sees every chunk in its first invocation (and every row-level filter every row), no stored version is ahead of the counter, every row the load then creates is stamped `GetChangeVersion()` = V(t, M), and the next sweep runs at the first sweep boundary above the restored counter. The cost is O(chunks × columns × (rows + 1)), once per restore. `Test_ECS_RestoreResetsChangeTracking` (conformance) runs a world for 10 ticks with three `CHANGED` systems, restores tick 3 out of tick, applies an out-of-tick load and runs two ticks: every `CHANGED` system matches every chunk in the first tick and only the chunks written since in the second; and after restoring a counter that lies past a sweep boundary to a tick below it, an `AdvanceMergeCounter` across the next boundary above the restored counter runs exactly one sweep (`ecs.version_sweeps` + 1), on every backend. **Resumed replay.** A replay resumed from a save or a replay checkpoint ([Z2-N-ARCH-789]) reproduces the recorded tick hashes' ECS part (`Zenith2/Docs/Design/ECS/Scheduling.md` → "World state hash") from the first tick after the restore, provided the restore reproduces every item that part covers at tick t and tick t's carried events (loaded as `EVENT` records, `Zenith2/Docs/Design/ECS/Scheduling.md` → "Out-of-tick playback" step 2): the resumed run's versions differ from the recorded run's (B_t = t × (M + 1) differs whenever a recompile changed M, and so may the ticks at which sweeps run), and every `QUERY_TERM_CHANGED` system and row-level filter over-matches in its first invocation, but no version is hashed and, under the conservative-filter rule of § "Change-filtered queries", no over-match changes a committed result (Z2-D-019). `Test_ECS_RestoreThenContinueMatchesUninterrupted` (conformance) runs a fixture with three row-filtered `QUERY_TERM_CHANGED` systems, property writers and structural churn and no carried events for 600 ticks, captures the world at tick 300 through `Zenith_WorldInspector` and field sets, restores it into a fresh world with `RestoreSimulationState` and `ApplyOutOfTick`, runs that world to tick 600, and asserts that its per-tick hashes equal the uninterrupted run's for ticks 301 … 600, under both chunk capacities, on every backend.
3. **Version.** V(t, m) = 1 + (U(t, m) mod (2^32 − 1)). Versions run 1 … 2^32 − 1; consecutive merge points get consecutive versions, the successor of 2^32 − 1 is 1, and **0 is never issued**: 0 means "never seen" in a query slot's last-seen version and nothing else. V(0, 0) = 1 is reserved for the state before the first tick (world loading at startup step 17 stamps it); the first tick's boundary is V(1, 0) = M_0 + 2, so no merge point of any tick shares it until the counter wraps, which § "Version wrap sweep" makes unobservable.
4. **What each producer stamps.** A system with a merge point stamps its own V(t, m) through `CommitRowChanges` (`Zenith_MergeContext::GetMergeVersion`, and the private `m_uMergeVersion` of its views); an arbitration node stamps its own; a sync point stamps its own for playback's property commands (committed from the playback write set after step 5, and stamped at once for the property writes step 6 makes: `Zenith2/Docs/Design/ECS/Backends.md` → "Playback writes") and for the rows its spawns and adds create ([Z2-N-ARCH-728]); the tick boundary stamps V(t, 0) for its handlers' property writes (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Tick boundary and end-of-tick"); out-of-tick playback stamps `GetChangeVersion()` (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Out-of-tick playback"). Every system's invocation also carries its **read version** V(t, R(N)), the version of its read point (§ "Stage order of merge points" item 5), which becomes its query slots' next last-seen version (`Zenith_MergeContext::GetReadVersion`); it is at or above every commit of a property the system declares a read of that the schedule ran before the system's node and below every such commit it ran after (§ "Change-filtered queries" explains the qualification). A system that writes no column has no merge point: its views carry the read version as their merge version and no column of theirs is writable, and its slots' own version stays 0.
5. **`Zenith_WorldSimulation::GetChangeVersion()`**, while a frame instance of the world runs, returns the version of the latest completed sync point (the end-of-tick playback is tick t's last, V(t, M)); within a phase every merge of that phase commits a version between the preceding sync point's and the next one's. Out of tick (no frame of the world running) it returns V(t, M_t) for the current tick index t — the highest version tick t can issue, below V(t + 1, 0) — whether or not tick t's end-of-tick playback completed, and 1 before the first tick. The two agree whenever tick t completed. They differ after a cancelled frame instance ([Z2-N-ARCH-412]): its latest completed sync point can be s_k inside tick t while systems of stage k + 1 whose merge node or final continuation had started completed and took read versions above V(t, s_k), so an out-of-tick write stamped V(t, s_k) would be no newer than their last-seen versions and missed, whereas V(t, M_t) is above every version tick t issued (`Zenith2/Docs/Design/ECS.md` → "Cancellation" item 6). It is well defined at every point any code may read it.

Properties: U is strictly increasing along the enumeration and across ticks, and V is a pure function of U, so every stored version is a function of the declarations and the tick index (and the restored base), never of completion order. `Test_ECS_ChangeVersionAdvancesAtMerge` asserts a written column's version equals its merge's version and a failed write advances nothing; `Test_ECS_MergeVersionsIndependentOfWorkers` asserts identical versions for every column after 60 ticks with 1, 2, 8 and all workers; `Test_ECS_VersionZeroNeverIssued` drives U across 2^32 − 3 … 2^32 + 1 with `Zenith_WorldTestAccess::AdvanceMergeCounter` and one real tick at each step, and asserts the issued versions 2^32 − 2, 2^32 − 1, 1, 2, 3 in that order and that no merge point, sync point or tick boundary is ever stamped 0. The reconciliation item for [Z2-N-ARCH-723]'s "incremented once" wording is listed in `Zenith2/Docs/Design/ECS.md` → "Reconciliation items".

Per (chunk, column) change state lives in the backend's change table: one `uint32` column version and one `uint32` row version per row, outside the chunk's 16 KiB block (`Zenith2/Docs/Design/ECS/Backends.md` → "Change tables"). Structural moves carry a row's versions with the row and leave the destination chunk's column version at least as new as the row's (`Zenith2/Docs/Design/ECS/Backends.md` → "Change tables", the relocation rule); a new row's versions are the version its creating playback stamps (item 4), so a spawn reads as changed.

## Stage order of merge points

<!-- elaboration -->
Within a stage, merge ordinals follow the order in which the schedule runs a property's writer against its readers, never registration order: `Zenith2/Docs/Architecture/CPUFrameGraph.md` → "Frame graph builder" (translation step 3) runs a same-stage reader after the writer of a property it reads, except a reader that declared `Before(<writer>)`, which runs first and reads the previous value. The executor's own order cannot be used, because it depends on cost hints ([Z2-N-ARCH-332] orders ready nodes by critical-path priority) and `GetDeclarationHash` excludes costs; so the world simulation computes, at `Freeze` and at every recompile, its own cost-independent order per stage from the declarations alone:

1. **Nodes.** The stage graph G_s holds every TICK node `EmitInto` declares in stage s of the world: each system node, each merge node M(S) and each arbitration node A_P (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Node and resource naming").
2. **Edges.** G_s holds every ordering between two nodes of stage s that the graph core derives from the declarations, except the merge chain, which is read off the result (item 7); so G_s is acyclic exactly when the stage's declarations are:
   1. S → M(S) (rule 1 of `Zenith2/Docs/Design/ECS/Scheduling.md` → "Merge nodes and the merge chain"); no chain edge.
   2. For each property P the stage writes, with committing writer W (the writer's merge node; the writer's system node when it has no merge node; A_P when P is arbitrated): W → N for every other node N of the stage that reads P, except N → W when N declared `Before` naming the system whose merge W is (by merge rule 3 such a declaration orders N before that system's merge node too). "Other" excludes the nodes that read P before its commit by construction: the system whose merge W is (its own reads are pre-reads, merge rule 3) and, for an arbitrated P, P's writers (each writer that also reads P declares `Before` the arbitration node, `Zenith2/Docs/Design/ECS/Scheduling.md` → "Arbitration nodes").
   3. S → A_P for every writer S of an arbitrated property P (through its staging resource), so every writer, reading P or not, is before A_P and every other reader of P after it (item 2.2).
   4. Every explicit `Before`/`After` between two nodes of the stage, resolved by name ([Z2-N-ARCH-401]).
   5. For each world resource and each event queue the stage accesses (translation step 3 applied to them): every node declaring a write of it → every other node of the stage that declares only a read of it, reversed (reader → writer) for a reader that declared `Before` the writer's system. Two writers of one resource or queue (event emission appends, so every emitting merge node read-writes its queue) get no edge from this item: the chain orders them.
   Item 2.5 never orders a property's committing writer against its reader, which is all the version enumeration needs; it is in G_s because the chain is read off the order, and a chain edge running against any ordering the graph core derives would close a cycle.
3. **Kahn's algorithm with a registration-order tie-break.** Repeatedly remove, from the nodes whose predecessors are all removed, the one with the smallest key, and append it to the stage order. The key of a system node is (0, registration index, 0), of its merge node (0, registration index, 1) and of an arbitration node (1, type ID, property ID). A min-heap makes the pass O((n + e) log n) for n nodes and e edges. Neither the keys nor the edges depend on `m_uCostHint`, user data or the worker count, so the order is a pure function of the declarations and `GetDeclarationHash` covers it.
4. **Ordinals.** The stage's merge points take consecutive ordinals in the order's sequence, after the previous stage's sync point; the stage's sync point takes the next ordinal. A system node that is its own merge point (no merge node, writes columns) takes its ordinal at its own position.
5. **Read points.** Every system node N gets its read point R(N): the ordinal of the last merge point strictly before N in the stage order or, when none precedes N in its stage, the ordinal of the previous stage's sync point (the tick boundary, ordinal 0, for stage 1). The invocation record carries V(t, R(N)) beside its merge version V(t, m_N) (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Disabled systems" step 2).
6. **Cycles.** A cycle in G_s is a genuine cycle among the stage's own declarations — two systems each reading a property the other's merge commits with no `Before` between them, or contradictory explicit orderings — and leaves nodes unordered; the pass appends them in key order so the table stays defined, and the same cycle fails the graph compile (`GRAPH_ERROR_CYCLE`, reported as `SCHEDULE_ERROR_GRAPH`; a recompile keeps the previous schedule, [Z2-N-ARCH-409]), so a schedule with that order never runs. Neither the merge chain (item 7) nor any cross-stage ordering can add a cycle, so ECS has no cycle diagnostic of its own (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Merge nodes and the merge chain").
7. **Merge chain.** Rule 2 of `Zenith2/Docs/Design/ECS/Scheduling.md` → "Merge nodes and the merge chain" orders each merge node of the stage after the merge node that precedes it in this order. Every chain edge points forward in a topological order of G_s, so G_s with the chain is acyclic exactly when G_s is, and the executor runs the stage's merges in this order whatever its cost hints; a merge-node reader registered before the merge-node writer of a property it reads merges after the writer instead of closing a cycle.

Why the order is exact for `QUERY_TERM_CHANGED`: every same-stage merge point X that commits a property N reads is joined to N by a direct edge of item 2.2 (X → N, or N → X for a pre-read), so X precedes N in the stage order exactly when the schedule runs X before N; by item 5, V(t, m_X) ≤ V(t, R(N)) exactly when X committed before N read, and every merge point of an earlier stage, every earlier sync point and the tick boundary are at or below V(t, R(N)), every subsequent one above. The merge chain is read off the stage order (item 7), so the two agree by construction. The three cases the rule exists for — a pre-reader declared `Before(<writer>)`, a writing reader without a merge node registered before its writer, and a merge-node reader registered before its merge-node writer — are `Test_ECS_ChangedQueryPreReaderSeesWriteNextTick`, `Test_ECS_ChangedQueryNoSpuriousMatchAfterSameStageWriter` and `Test_ECS_ChangedQueryReaderRegisteredBeforeWriter` (§ "Change-filtered queries"); `Test_EmitInto_MergeEnumerationTopological` builds one phase with a pre-reader, a writing reader without a merge node registered before its writer, an arbitrated property with two writer sources and a three-node merge chain whose first-registered system reads a property the last-registered one's merge commits (so the chain runs against registration order), and asserts the ordinals and read points equal the hand-computed stage order and are identical under two different cost-hint sets.

## Version wrap sweep

<!-- elaboration -->
`Zenith_IsVersionNewer` compares versions in serial arithmetic, which is meaningful only while the two versions are fewer than 2^31 merge points apart. A query slot's last-seen side is kept close by its reset rule (§ "Change-filtered queries"); the stored side is not kept close by writes, because a column stamped at spawn and never written again ages without bound. Without a sweep, once the world is more than 2^31 merge points past such a column (≈ 10.7 M ticks with M ≈ 200, ≈ 50 hours at 60 Hz) the column compares as newer than every last-seen version and every `QUERY_TERM_CHANGED` system re-processes the unchanged chunk: deterministic and never a missed change, but a false positive. The sweep removes it:

1. **Trigger.** A sweep boundary is every multiple of 2^29 of U. The world simulation keeps the **sweep floor** F, the value of ⌊U / 2^29⌋ at the latest sweep check (0 at creation; set by `RestoreSimulationState` and by `Zenith_WorldTestAccess::AdvanceMergeCounter`). The end-of-tick playback of tick t (its step 7) runs the sweep when ⌊U(t, M) / 2^29⌋ > F and then sets F to it; a tick crosses at most one boundary, because M < 2^20 < 2^29. The trigger depends on U alone, so every run of the same replay sweeps at the same ticks.
2. **Distance.** For the current version c = V(t, M) and a stored version s, the distance is d(c, s) = c − s when c ≥ s, else c − s + (2^32 − 1): the number of merge points from s to c on the ring 1 … 2^32 − 1.
3. **Re-stamp.** Through `Zenith_World::SweepChangeVersions(xToken, c, 2^30)` every backend visits every change block and sets every column version and row version with d(c, s) > 2^30 to the version 2^30 merge points before c (the V of U(t, M) − 2^30). The simulation resets every query slot's pair (L, O) with d(c, L) > 2^30 to (0, 0), and every system's previous read version P with d(c, P) > 2^30 to 0 (P equals the L of the system's slots, § "Change-filtered queries").
4. **What the sweep guarantees: never a missed change, and a false positive only in a reset slot's next invocation.**
   - A slot with d(c, L) ≤ 2^30 is not reset. A version s the sweep re-stamps had d(c, s) > 2^30 ≥ d(c, L), so it is older than L under unbounded versions and did not match; its re-stamped value, exactly 2^30 behind c, is not newer than L either, and it cannot equal O (O is newer than L). Every result of such a slot is unchanged.
   - A slot with d(c, L) > 2^30 is reset to (0, 0) and matches every chunk in its next invocation, which then sets a fresh L. Under unbounded versions it would have matched only the chunks changed after L, so the reset adds matches and removes none: a false positive, confined to that slot's next invocation. The sweep has lost the order among versions more than 2^30 behind c, so no exact result is possible for that slot; this is the only divergence from unbounded versions.
   - Only a slot whose system completed no invocation for more than 2^30 merge points can be reset, because an enabled system refreshes L every tick: in practice a system disabled (`Zenith_SystemRegistry::SetEnabled`, or a script system disabled after a failure, [Z2-N-SCRIPT-189]) for more than 2^30 merge points (≈ 5.4 M ticks with M ≈ 200, ≈ 25 hours at 60 Hz) and then re-enabled.
5. **Bound.** After a sweep no stored version and no non-zero last-seen version is more than 2^30 behind c; the next sweep runs within 2^29 + M merge points; so no comparison ever spans more than 2^30 + 2^29 + 2^20 < 2^31 merge points.
6. **Cost.** O(chunks × columns × (rows + 1)) once per 2^29 merge points (≈ 2.7 M ticks with M ≈ 200, ≈ 12 hours at 60 Hz), inside the zone `ECS.VersionSweep`, counted in `ecs.version_sweeps`; it never runs in a phase.

`Test_ECS_VersionWrapSweep` (conformance, 16 seeds) stamps columns of a small world with three `QUERY_TERM_CHANGED` systems, then advances the counter with `Zenith_WorldTestAccess::AdvanceMergeCounter` in 64 random steps of 2^27 to 2^29 merge points each, running one real tick with random writes after each step (the checkpoints; the steps sum to more than 2^33, so the property is exercised across more than 2^31 merges and at least one full wrap of the version ring). One of the three systems is disabled across consecutive checkpoints whose steps sum to more than 2^30 + 2^29 + M, so at least one sweep resets its slot, and is then re-enabled. The oracle applies the same matching rules (L, O, own version) to 64-bit unwrapped versions. At each checkpoint the test asserts, on every backend: every chunk the oracle matches is matched (no missed change); every slot's matched set equals the oracle's, except the re-enabled system's first invocation after re-enabling, which matches every structurally matching chunk; no stored version and no non-zero last-seen version is more than 2^30 + 2^29 + M merge points behind; and `ecs.version_sweeps` equals the number of multiples of 2^29 the counter has crossed since creation, with no sweep in a tick or an advance that crossed none.

## Row change bits and CommitRowChanges

- `Zenith_RawColumn::MarkRowChanged(uRow)` sets bit `uRow` of `m_pulRowChangeBits` (`m_pulRowChangeBits[uRow >> 6] |= 1ull << (uRow & 63)`, a plain store: the bits are private to one invocation and one leaf writes one chunk) and changes nothing else ([Z2-N-ARCH-720]). `MarkAllRowsChanged` sets bits 0 … m_uRowCount − 1. Both assert `m_bWritable` and the row bound.
- `Zenith_ChunkView::CommitRowChanges(xScope, xType, xProperty, pulAccepted)`:
  1. Return `ECS_ERROR_STALE_HANDLE` if `!IsValid(xScope)`; `ECS_ERROR_UNKNOWN_PROPERTY` if the column is not declared writable; nothing is changed on either failure.
  2. For each word w, `uBits = pulAccepted[w]`; for each set bit r: `puRowVersions[rowIndex(r)] = m_uMergeVersion` (through the row-index table on backends that have one).
  3. If any bit was set, `*puColumnVersion = m_uMergeVersion`.
  4. For a staging column (arbitrated), the bits are the source's written bits and no version is stamped; the arbitration node stamps the property's version at its own merge version.
- The caller passes only accepted entities' bits: SCRIPT passes the pending bits masked by its accepted rows ([Z2-N-SCRIPT-245]); the ECS default merge passes the pending bits unchanged, because C++ systems do not roll back column writes (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Commit and collection"); a rejected script entity's bits leave no trace ([Z2-N-ARCH-720]).
- One call per written (chunk, column) per merge ([Z2-N-ARCH-723]): the merge deduplicates the invocation's view list by (binding, column) and ORs the bit sets of duplicates before calling.

`Test_ECS_CommitRowChangesAdvancesVersionOnce`, `Test_ECS_ChangeVersionAdvancesAtMerge` and `Test_ChunkView_CommitRejectsStaleScope` cover these rules on every backend.

## Own-row and any-row reads

[Z2-N-ARCH-711] and [Z2-N-SCRIPT-179] … [Z2-N-SCRIPT-181]: a chunk system reads a column it writes in the same phase for its own row only, and other rows only in columns no node of the phase writes.

1. At `Freeze`, for each system and each column its queries bind, the schedule compiler marks the binding `m_bOwnRowOnly = true` when any system of the same phase and world declares a write of that property (including the system itself).
2. A system's `ReadAnyRow(xType, axProperties)` declaration of a property that some system of the same phase writes is `SCHEDULE_ERROR_CROSS_ENTITY_READ` (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Messages").
3. Enforcement at run time: script views check `m_bOwnRowOnly` on every cross-row access and raise ZS1204 in every build; C++ systems cannot be checked per pointer access, so the rule is enforced for them by the declaration check of step 2 and by `GetChunkOfEntity`, which returns a view whose own-row-only columns are null for any entity other than the invocation's current one (a C++ system that reads other entities declares `ReadAnyRow`). The current entity is the context's current simulation ID C of `Zenith2/Docs/Design/ECS/SystemAPI.md` → "The current logical invocation": the simulation ID of the logical invocation most recently opened through `Commands(sim)`, `Commands(sim, ordinal)`, `Events(sim)`, `Events(sim, ordinal)` or `Contributions(sim)`, or, while none has named an entity, the entity of the context's first `GetChunkOfEntity*` call. When the resolved entity's simulation ID equals C, the returned view's own-row-only columns are the entity's chunk columns, non-null; for any other entity they are null columns in every build, and every column the slot does not mark reads normally.

`Test_Query_OwnRowOnlyMarking` and `Test_Schedule_CrossEntityReadOfWrittenColumn_IsError` cover both steps.

## Resolve and random access

- `Zenith_World::Resolve(xEntity)` validates the handle through the entity table (null, wrong world, stale — [Z2-N-CONTRACT-062], [Z2-N-ARCH-761]) and returns the location, the simulation ID and the destroy-pending flag. O(1).
- `Zenith_SystemContext::GetChunkOfEntity(slot, xEntity, uRowOut)` resolves the entity, checks the entity's archetype, table or pools against the slot's query (O(terms)), and returns a view of the entity's chunk with the query's columns and the invocation's scope; it is how behaviours reach their own row and how scripts read another entity's row in a different chunk (`Zenith2/Docs/Scripting/Bindings.md` → "Field access algorithm"). A write through such a view to another entity's row is refused by the own-row marking for scripts and is a programmer error for C++.
- A handle resolved in the wrong world fails with `ECS_ERROR_WRONG_WORLD` in every configuration ([Z2-N-CONTRACT-073]); `Test_ECS_ForeignWorldHandle_Fails` asserts it on every backend.
