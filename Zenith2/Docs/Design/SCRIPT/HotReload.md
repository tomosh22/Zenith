# SCRIPT design — behaviour state, recovery and hot reload

Companion to `Zenith2/Docs/Design/SCRIPT.md`: the implementation of the declared behaviour state (schemas, registration, the state proxy, the checkpoint serializer and slot pools, restore), quarantine recovery and last-good restore, the hot-reload staging area, `ApplyPendingReloads`, the schedule commit in the prologue, go-live, rollback, chunk-system generations, migration execution, the schema migration script host, behaviour state in saves and the development reload sources. It elaborates `Zenith2/Docs/Scripting.md` → "Behaviour state model and recovery" and "Quarantine and hot reload", and restates none of their bullets. Files are under `Zenith2/Engine/ZenithScript/Internal/`.

## Scope of this file

Everything that serializes, restores or replaces a behaviour's state or a module's code. The checkpoint format is Scripting.md → "Checkpoint format"; the declared kinds are Scripting.md → "Declared state schema"; the recovery policy values are Design/SCRIPT/PublicAPI.md → "Zenith_ScriptRecovery header".

## State schema internals

`Zenith_ScriptStateSchema` (per behaviour module generation, in the world's module state):

| Member | Contents |
|---|---|
| `m_xType` | the registered `Behaviour.<Name>.State` type ID (`TYPE_KIND_BEHAVIOUR_STATE`) |
| `m_uVersion` | `StateVersion` |
| `m_axFields` | `Zenith_ScriptStateField { uint32 m_uID; uint32 m_uParent; uint8 m_uKind; uint8 m_uElementKind; uint16 m_uMaxCount; uint16 m_uMaxBytes; Zenith_StringID m_xName; Zenith_ByteSpan m_xDefault; uint16 m_uEnumFirst; uint16 m_uEnumCount; }` in declaration order, nested fields after their parent; `m_uKind` and `m_uElementKind` hold the index of a kind in the table of Scripting.md → "Declared state schema" (0 = Bool), the encoding of the manifest's field records |
| `m_xNameIndex` | a perfect-hash table from interned Luau field name (per VM, as views) to field index, for the proxy |
| `m_uMaxSerializedBytes` | computed from the maxima: header 32 + Σ over fields (4-byte ID + maximum encoded size) + 8 × `uSCRIPT_MAX_CHECKPOINT_FIXUPS`, with unknown-field preservation bounded by the same slot |
| `m_ulShapeHash` | Compiler.md → "Declaration extraction" |
| `m_aiMigrateRefs` | `Zenith_Array<int>`: the main-VM registry references of the `Migrate[n]` functions, index n − 1 |

Encoded sizes per kind follow the "Serialized as" column of Scripting.md → "Declared state schema"; nested `Table` fields serialize their fields in declaration order; `Array` a u16 count then elements; `Map` a u16 count then (key, value) pairs sorted by key (string keys by UTF-8 byte order, enum keys by index, integer keys numerically).

## State registration at startup

Registration is split across two startup steps, conforming to ECS's ruling (`Zenith2/Docs/Design/ECS.md` → "Behaviour-state type registration"; cross-area note E12(a), which supersedes E5's step-6 reading):

| Step (`Zenith2/Docs/Architecture/CompositionRoot.md` → "Startup sequence") | Call | Registers |
|---|---|---|
| 6, the Script slot of the engine types, registry DECLARING | `Zenith_ScriptRegisterEngineTypes(xTypes)` | `Zenith_BehaviourComponent` (C++ registration, stable name `Zenith.Behaviour`, authority `PHASE_COMMANDS_ONLY` on both properties) |
| 10, after `RegisterSchemaBlob` and before `Freeze` | `Zenith_ScriptRegisterBehaviourStateTypes(xTypes, xManifest)` | one behaviour-state type per state-schema record of the cooked manifest |

At step 10 the composition root loads `content:/Scripts/scripts.zlmf` from the mounted virtual filesystem with `Zenith_ScriptModuleManifest::Load` (a failure is startup exit code 3), then calls `Zenith_ScriptRegisterBehaviourStateTypes`, which, for each state-schema record of the manifest in module-ID order:

1. `xTypes.BeginRuntimeType(TYPE_KIND_BEHAVIOUR_STATE, "Behaviour.<Name>.State", "<Name>State", StateVersion)`;
2. one `AddField` per top-level field with its kind mapped to a `Zenith_PropertyValueType` (Bool → `PROPERTY_TYPE_BOOL`, I32 → `I32`, … String → `STRING_ID`, Enum → `U16` with the value names as editor info, Entity → `ENTITY`, Asset → `ASSET`, Table → `STRUCT` (a nested runtime struct type `Behaviour.<Name>.State.<Field>`), Array and Map → `CONTAINER`), `m_uFlags = PROPERTY_FLAG_SERIALIZED`, authority `PHASE_COMMANDS_ONLY`;
3. `Origin(TYPE_ORIGIN_SCHEMA)`; `End()`.

A registration failure is `SCRIPT_ERROR_LOAD` naming the module; the composition root stops with exit code 3 (a cooked state schema the registry refuses is a cook defect). The same manifest object is then passed to the script runtime at step 14 (`Zenith_ScriptRuntimeDesc::m_pxModules`), so the registered types and the loaded modules come from one manifest. A behaviour-state type added or changed afterwards registers only inside the hot-reload window of frame-prologue step 6 (§ "ApplyPendingReloads procedure").

At world load, `LoadModules` computes the live declaration's shape hash and compares it with the record's (ZS1806 on a mismatch), so the registered type always describes the loaded code ([Z2-N-SCRIPT-382]). The registered type is how the inspector shows state and how saves name it; the checkpoint payload is SCRIPT's own encoding, not a reflected field set, because it must carry provisional fixups and preserved unknown fields (Z2-D-038 holds either way: neither depends on C++ layout).

## State proxy implementation

The `state` argument is a tag-6 userdata (Design/SCRIPT/Bindings.md → "Userdata tags and view objects") over the instance's live state, which is kept in C++ memory rather than in the Luau heap, so the state is never part of the non-transactional Luau heap and a quarantine loses nothing the checkpoint does not also hold:

| Storage | Where |
|---|---|
| live state values | a per-instance `Zenith_ScriptLiveState` block in the checkpoint pool (fixed size: the schema's decoded maximum), laid out field by field |
| `Array`/`Map` elements and strings | inside the block, bounded by the declared maxima |

`__index(field)`: resolve the field through `m_xNameIndex` (unknown name: ZS1901); read the value and push it (a nested `Table` returns a child proxy; an `Array` or `Map` returns a container-like proxy with the `Container<T>` method set bounded by the maximum). `__newindex(field, v)`: validate kind, range, length and count (ZS1902, ZS1903, ZS1904, ZS1905, ZS1906), copy by value (a Luau table assigned to a `Table`, `Array` or `Map` field is copied element by element, [Z2-N-SCRIPT-388]), set the dirty flag ([Z2-N-SCRIPT-387]). Writes to live state are part of the entity transaction: the first write of an invocation snapshots the instance's live-state block into the transaction's retention arena (Design/SCRIPT/Transactions.md → "Invocation layout in the arenas"; charged to the entity like a column snapshot), and a failure or rejection restores it; this is how a failed invocation leaves state at its previous committed value even before any checkpoint is involved.

## Checkpoint serializer

At the end of the instance's final invocation of the tick (Runtime.md → "Behaviour node body", the checkpoint flag), when the dirty flag is set ([Z2-N-SCRIPT-389]):

1. Take the inactive slot of the instance's pair.
2. Write the 32-byte header (magic `ZBST`, format version 1, `StateVersion`, source ID, tick, payload bytes, fixup count).
3. For each field in declaration order: u32 field ID, then the value encoded per kind; an `Entity` field holding a provisional handle writes tag 3 and records a fixup `{ payload offset u32, provisional index u32 }`.
4. Append preserved unknown fields verbatim (restore algorithm step 4 of Scripting.md).
5. More than 16 fixups, or a payload larger than the slot, raises ZS1404 (`SCRIPT_ERROR_KIND_CHECKPOINT`) inside the transaction ([Z2-N-SCRIPT-392], [Z2-N-SCRIPT-390]).

The whole serialization runs as a limit-0 `NATIVE_BODY` protected call on the main VM (it reads Luau values only for the unknown-field block, which is C++ data; the protected call is required because `lua_tolstring` of string fields may allocate). Commit flips the active index (Transactions.md → "Commit implementation"). At the next sync point, fixups of the active slot are rewritten from the spawn results (tag 3 → tag 2 with the stable simulation ID) in place, which is why the Entity encoding is always 17 bytes.

## Checkpoint slot pools

`Zenith_ScriptCheckpointPools` (per world, main thread): one CORE `Zenith_Pool` (`Zenith2/Docs/Contracts/Memory.md` → "Zenith_Pool") per behaviour module generation, element size `2 × m_uMaxSerializedBytes + live-state block size`, rounded to 64 bytes, blocks of 64 elements. An element — the instance's slot pair and its live-state block — is reserved from the current generation's pool when an instance is created in the directory refresh (Runtime.md → "Behaviour instance directory"), outside any transaction, and released at instance destruction; a pool growth failure is the fatal `SCRIPT_ERROR_KIND_RESERVATION` world halt (general-heap state is scheduling-dependent, as for transaction arenas). A reload of the module creates the new generation's pool and reserves every instance's new element in the prologue (§ "ApplyPendingReloads procedure" step 2.4); go-live installs the new elements and retires the old ones into the world's `m_axRetired`, and `CommitPendingReloads` step 1 returns each to its pool on the main thread and destroys a generation's pool when its last element has returned. So the pools are touched only on the main thread, and at a tick boundary every instance's slot pair belongs to the current generation and holds a blob of the current `StateVersion`. The pools' bytes are reported under `MEMORY_SUBSYSTEM_SCRIPTS` and bounded per instance by Z2-B-SCRIPT-015 ([Z2-N-SCRIPT-391]).

## Restore implementation

Scripting.md → "Restore algorithm" steps 1–6 over a source blob (the active slot, or a save's blob):

1. Bounds-check the header against the blob length; magic, format version and source ID must match; a mismatch leaves the instance quarantined with the diagnostic `SCRIPT_STATE_RESTORE_FAILED` (module, simulation ID, the mismatched field; a restore failure, not a Luau error), a row of `Zenith2/Docs/Scripting/MisuseCatalogue.md` → "Diagnostics that are not Luau errors" added with cross-doc row X121 ([Z2-N-SCRIPT-843]).
2. If `StateVersion` is older (only in the prologue's `ApplyPendingReloads` and out of tick in `RestoreSavedStates`; a last-good restore at a tick boundary decodes the active slot of the current generation, which holds a blob of the current version — the slot pair a go-live installs was serialized at the new version in the prologue, § "ApplyPendingReloads procedure" step 2.4, and every subsequent checkpoint is written at the current version — so this step never runs there): decode into a plain Luau table keyed by field name (the old version's field IDs map to names through the cooked schema history of the manifest's state record for that version; a version absent from the history fails the restore), run `Migrate[n]` … `Migrate[current − 1]` each as a `FUNCTION` protected call under Z2-B-SCRIPT-018, and validate the result against the current schema (ZS1907 on failure).
3. Decode each field by ID into the live-state block; an unknown ID is appended to the unknown-field block with a warning (Scripting.md → "Restore algorithm" step 4, Z2-D-048).
4. Resolve references: entity fields tagged 1 by persistent ID (out of tick and in the prologue through the world's inspector lookup, at a tick boundary through `Zenith_TickBoundaryAccess::FindByPersistentID`, `Zenith2/Docs/Design/ECS/WorldAPI.md` → "Zenith_ECSObservers header"), tagged 2 by stable simulation ID within the session; unresolvable → nil with `SCRIPT_STATE_REFERENCE_UNRESOLVED` ([Z2-N-SCRIPT-397]); asset fields through the asset registry by GUID (`Zenith_AssetRegistry` lookups are `ANY_THREAD`). Steps 1, 3 and 4 are C++ over the blob and the live-state block and touch no Luau object, which is what lets a last-good restore run on the tick-boundary node.
5. Create a fresh `self` and state proxy — immediately when the restore runs on the main thread out of tick (`RestoreSavedStates`) or in the prologue (`ApplyPendingReloads`), and at the module's next behaviour node when it runs at a tick boundary (Design/SCRIPT/Runtime.md → "Tick-boundary handler") — and schedule `OnRecover` for the first tick of the instance's declared phase (`PENDING_RECOVER`).
Only an instance whose behaviour declares `OnRecover` is scheduled, and `RestoreSavedStates` schedules it only for an entry whose flags call for a recovery; every other restored instance returns to ACTIVE or DORMANT with no recovery invocation (§ "Recovery invocations and exact restore" steps 4 and 6; [Z2-N-SCRIPT-929], [Z2-N-SCRIPT-930]; Z2T-SCRIPT-114).

Every length, count and offset is checked against the schema's maxima and the blob before it is read; the decoder allocates nothing beyond the live-state block, which is exactly the slot's size ([Z2-N-SCRIPT-485]). `Zenith_Fuzz_Script_CheckpointDecode` (Scripting.md's `Fuzz_Script_CheckpointDecode`) drives this decoder with arbitrary bytes under a fixed test schema set.

## Quarantine and recovery scheduling

| Event | Action |
|---|---|
| an instance's transaction fails | quarantine (Transactions.md → "Quarantine store"); the module's `m_bDisableAtNextTickBoundary`; `m_ulLastFailureTick = tick` |
| the tick boundary after the failure | the module is disabled (Runtime.md → "Tick-boundary handler") |
| policy `AUTOMATIC` and `tick − m_ulLastFailureTick ≥ m_uDelayTicks` and `m_uRecoveries < m_uMaxRecoveriesPerModule` | last-good restore of the module at this tick boundary (step 3 of the handler), `m_uRecoveries += 1`, the listener's `OnModuleRecovered` |
| policy `AUTOMATIC` and the recovery count reached | the module stays disabled for the session; `SCRIPT_MODULE_DISABLED` with detail `recovery limit reached` ([Z2-N-SCRIPT-423]) |
| policy `MANUAL` | the module stays disabled until `RequestModuleReload` or a hot reload of the module |
| `RequestModuleReload(module)` (editor command, console) | first runs the out-of-tick go-live of a `COMMITTED` generation of the module's world (§ "Go-live at the tick boundary"), then queues a last-good restore for the next tick boundary |

## Last-good restore

At a tick boundary (step 3 of the handler, on the tick-boundary node, any frame thread), for a module being recovered, in C++ alone: for every instance of the module (quarantined or not), append its non-zero `self`, state-proxy and coroutine references to the world's main-VM release list `m_aiMainVMReleases` (a quarantined instance's references were already released at quarantine), restore from its active slot with § "Restore implementation" steps 1, 3 and 4 (an instance with no committed checkpoint restores its declared defaults; step 2 cannot run, the slot being of the current `StateVersion` even right after a version-raising reload, whose go-live installed slots holding the migrated state), and mark it `PENDING_RECOVER`; clear the module's `m_bDisabled` (also request ECS's re-enable through `Zenith_TickBoundaryAccess::RequestSystemEnabled`, Design/SCRIPT/Runtime.md → "Tick-boundary handler"); clear the module's quarantine entries ([Z2-N-SCRIPT-424]). The module's next behaviour node, on the main thread, drains the release list and creates each instance's fresh `self` and state proxy before its first invocation, and `OnRecover` runs in the first invocation of the instance's declared phase ([Z2-N-SCRIPT-394]). An `OnRecover` that fails re-quarantines its instance only and counts as a new failure of the module ([Z2-N-SCRIPT-396], [Z2-N-SCRIPT-429]).

## Hot-reload staging area

`Zenith_ScriptPendingReload` (runtime queue entry): world tag, module ID, the `Zenith_ScriptBytecode` copied into the runtime's reload arena, the request's source (`EDITOR_COMPILE`, `COOKED_FILE`), and the time it was queued (for the W-Editor latency measurement). `RequestHotReload(module, bytecode)` (main thread, any time outside the prologue window):

1. Refuse `SCRIPT_ERROR_WORLD_HALTED`, `SCRIPT_ERROR_UNKNOWN_MODULE`, and `SCRIPT_ERROR_NOT_STATELESS_VERIFIED` when the header's flag bit 3 is clear on a simulation module ([Z2-N-SCRIPT-356]).
2. Verify the header against the build (Compiler.md → "Load-time verification procedure"); a mismatch is `SCRIPT_ERROR_BYTECODE_MISMATCH`.
3. Copy the bytecode into the reload arena and insert or replace the (world, module) entry.

The two requests also carry the reloaded module's load-time name references (`Zenith_Span<const Zenith_ScriptNameRefRecord> axNameRefs = {}`, [Z2-N-SCRIPT-927]; Scripting/LibraryLayout.md → "Public API of Zenith_ScriptWorld" and Scripting/PublicTypes.md → "Zenith_ScriptRuntime"), copied into the reload arena with the bytecode, so `ApplyPendingReloads` step 2.1 resolves them as the loader does at world load (Design/SCRIPT/Bindings.md → "Load-time name references"). The editor fills `RequestHotReload`'s from the `Zenith_ScriptExtractNameRefs` run it already makes; `RequestCookedReload`'s caller, the development Player's `Zenith_FileWatcher` on `content:/Scripts/` (§ "Development reload sources"), re-reads the re-cooked `content:/Scripts/scripts.zlmf` with `Zenith_ScriptModuleManifest::Load` and passes `GetNameRefs(xModule)`; the cook's watch mode only writes the files, the manifest after the changed `.zlbc` files.

`Zenith_ScriptStagedGeneration` (built in the window): the module's new generation number, the new module table's registry reference on the main VM, the validated declaration, the new state schema and its registered type ID, the new generation's checkpoint pool (a behaviour module), the generation's bytecode buffer (a chunk-system module, § "Chunk-system generations"), its breakable-line array (Design/SCRIPT/Debugger.md → "Breakpoint storage and fan-out"), and per instance a staged record `Zenith_ScriptStagedInstance { int m_iSelfRef; int m_iStateProxyRef; void* m_pLiveState; uint32 m_uCheckpointSlot; bool m_bMigrated; }`, where `m_uCheckpointSlot` is the instance's element in the new generation's pool, whose live-state block `m_pLiveState` points into and whose slot 0 holds the staged state serialized at the new `StateVersion`.

## ApplyPendingReloads procedure

`Zenith_ScriptRuntime::ApplyPendingReloads(xRegistry)`, prologue step 6, inside the window ZenithRuntime opened ([Z2-N-SCRIPT-903]):

1. Record `m_ulRevisionOnEntry = xRegistry.GetRevision()` in the runtime.
2. For each queued entry in (world creation order, module ID) order — except an entry whose (world, module) still holds a `COMMITTED` generation that has not gone live (the world ran no tick boundary step 3 since its commit, for example while paused), which stays queued for the next frame's prologue:
   1. Load the bytecode into a staging generation on the world's main VM (the loader of Design/SCRIPT/Bindings.md → "Module loader implementation" with the staged generation number; the old generation stays cached and current).
   2. Validate the declaration (the same checks as at world load).
   3. For a behaviour module: register the new state type with `xRegistry.BeginRuntimeType(TYPE_KIND_BEHAVIOUR_STATE, …)` (the window admits it, same type ID, version may rise).
   4. For a behaviour module, create the new generation's checkpoint pool (element size from the new schema, § "Checkpoint slot pools"); then for each live instance of the module, quarantined ones included: take its active slot (for a non-quarantined instance with dirty state, serialize a fresh checkpoint into the inactive slot first and use it); reserve the instance an element of the new pool (`m_uCheckpointSlot`); run the `Migrate` chain when `StateVersion` increased; restore into staging objects built from the new module (§ "Restore implementation" steps 1–4 into the new element's live-state block, and a staged `self` and state proxy created on the main VM); and serialize that staged, migrated live state into the new element's slot 0 at the new `StateVersion` (§ "Checkpoint serializer" steps 2–5, a limit-0 `NATIVE_BODY` protected call on the main VM). A ZS1404 from that serialization, or a failure to create the pool or reserve an element, fails the reload with its rollback. The staged slot is the instance's committed checkpoint from go-live on, so a last-good restore and a phase-11 save of the go-live tick both see the migrated state at the new version.
   5. For a chunk-system module: copy the staged bytecode into a general-heap buffer owned by the world for this generation (a failure is `SCRIPT_ERROR_OUT_OF_MEMORY` with rollback); the staged generation records the new declaration and the buffer.
   6. When the staged declarations raise the retention-set size of a slot, grow that slot's retention set (Design/SCRIPT/Transactions.md → "Transaction arena partition" rule 1); every entry is idle in the prologue.
   7. Mark the generation `STAGED`.
3. If any step failed: roll back every entry of this call (§ "Rollback procedure"), return the first error (recorded in the runtime's diagnostic ring naming world, module and instance); ZenithRuntime calls `AbandonHotReload()` ([Z2-N-SCRIPT-425]).
4. Otherwise return success; ZenithRuntime calls `EndHotReload()`, and then, in every outcome, `CommitPendingReloads()` (§ "Schedule commit in the prologue").

The queue is emptied by step 2 in every outcome, except the entries step 2 leaves for the next frame; a failed reload is not retried until a new request arrives.

`Zenith_ScriptRuntime::CommitPendingReloads()` runs on the main thread in prologue step 6 of every frame, called by ZenithRuntime after the hot-reload window closed (published or abandoned), or in the window's place when no change was queued. It opens the system reload scope where ECS allows it — `Zenith_SystemReloadScope` is `MAIN_THREAD`, frame-prologue steps 6 to 8 only (`Zenith2/Docs/Design/ECS/SystemAPI.md` → "Zenith_System header") — so the recompile it triggers runs in step 8 of the same frame ([Z2-N-ARCH-408]) and the go-live at the frame's first tick boundary only swaps generations:

1. Drain every world's main-VM release list (`lua_unref` of each reference on the world's main VM; Design/SCRIPT/Runtime.md → "Script world internals").
2. If this frame's `ApplyPendingReloads` left `STAGED` generations and `m_pxTypes->GetRevision() == m_ulRevisionOnEntry` (the window did not publish: abandoned, or `EndHotReload` failed validation), roll back every `STAGED` generation (§ "Rollback procedure") and return.
3. For each world with `STAGED` generations, in creation order: when any of them changes an access set, the phase, the ordering or the system set of its module, open `Zenith_SystemReloadScope xScope = m_pxSimulation->GetSystems().BeginReload()` on the world desc's simulation; for each changed module in module-ID order build the staged `Zenith_ScriptSystemRecord`s (the staged declaration index; the retention-set sizes of Design/SCRIPT/Transactions.md → "Transaction arena partition" rule 1) and call `ReplaceSystem` (same system name), `RemoveSystem` or `AddSystem` with them as user data; then `Commit()`. On success the registry marks the recompile trigger. On failure ECS keeps the previous declarations and schedule ([Z2-N-ARCH-409]); every `STAGED` generation of that world is rolled back (§ "Rollback procedure"), the schedule error (`SCHEDULE_ERROR_GRAPH` or the error `Commit` returned, with ECS's diagnostics) is recorded in the runtime's diagnostic ring naming the world and its first changed module and logged under `script.reload`; other worlds are unaffected.
4. For each world with surviving `STAGED` generations, reserve the capacity go-live appends into: `m_aiMainVMReleases` for every old `self`, state-proxy, coroutine, module-table and `Migrate` reference it will queue, and `m_axRetired` for every old checkpoint element, old bytecode buffer and old breakable-line array it will retire (a failure rolls back that world's `STAGED` generations, § "Rollback procedure", with the diagnostic of step 3). Then mark every surviving `STAGED` generation `COMMITTED`. It goes live at the world's next tick boundary that runs step 3 (§ "Go-live at the tick boundary"), which allocates nothing and cannot fail.

Between prologue step 8 and that tick boundary no script node of the world runs — the tick-boundary node is the first node of every tick ([Z2-N-ARCH-383]) — so the new schedule never runs the old generation, and the new generation never runs under the old schedule: a staged declaration that adds a `Write` is ordered against the systems it now conflicts with from its first invocation. A world destroyed while it holds a `COMMITTED` generation releases the staged objects with the world, before `lua_close`.

## Go-live at the tick boundary

At step 3 of the world's first tick boundary that runs step 3 after the commit (the frame's first tick boundary, unless the world is paused), after the disables, in C++ alone (the tick-boundary node may run on any frame thread and touches no Luau object):

1. For each `COMMITTED` behaviour generation: the new generation becomes current (the module's declaration and system records swap to the staged ones); for each instance, append its old `self`, state-proxy and coroutine references (the non-zero ones) to the world's main-VM release list `m_aiMainVMReleases` — the one place old objects are queued — install the staged `self` and proxy references (created on the main VM in the prologue), install the staged checkpoint element — the instance's `m_uCheckpointSlot` becomes the staged element of the new pool, `m_uActiveSlot` 0, `m_bDirty` false, so the staged live-state block is current — and append the old element (old generation, element index) to `m_axRetired`, and mark the instance `PENDING_RECOVER` so `OnRecover` runs in its next invocation (Scripting.md's step 3); a quarantined instance of the module leaves quarantine (a hot reload is a recovery).
2. For each `COMMITTED` chunk-system generation: the world's module generation advances, the declaration and system records swap and the module's bytecode pointer is set to the generation's buffer copied in the prologue (a pointer store; nothing is allocated or copied here); the previous generation's buffer, when it was itself a reload's, is appended to `m_axRetired`; each worker VM reloads the module before its next invocation of it (Runtime.md → "Chunk-system node body" step 3, [Z2-N-SCRIPT-428]).
3. Append the old generation's module-table reference and its `Migrate` references (`m_aiMigrateRefs`) to `m_aiMainVMReleases`; in development builds publish the generation's breakable-line array (Design/SCRIPT/Debugger.md → "Breakpoint storage and fan-out") and append the replaced one to `m_axRetired` with the epoch the publication advanced to.
4. Clear the module's `m_bDisabled` if it was set (the re-enable of [Z2-N-SCRIPT-429]; also request ECS's re-enable through `Zenith_TickBoundaryAccess::RequestSystemEnabled`, Design/SCRIPT/Runtime.md → "Tick-boundary handler").
5. <!-- elaboration --> For each generation that went live in steps 1 and 2, in ascending module ID, call the world listener's `OnModuleReloaded(uWorldTag, ulTick, xModule, uGeneration)` (A3 cross-area row ED16), where `ulTick` is the tick about to start and `uGeneration` the generation now current. The call records and returns, as every listener call does. An out-of-tick go-live makes the same calls on the main thread, with `ulTick` the world's current tick index. A rolled-back generation never went live and is never reported.

Every append lands in capacity reserved by the schedule commit (§ "Schedule commit in the prologue" step 4), so go-live allocates nothing, copies no bytecode and has no failure path. The module's next behaviour node drains the release list on the main thread (Runtime.md → "Behaviour node body" step 1), and CommitPendingReloads drains it, and returns every retired block (`m_axRetired`: checkpoint elements to their pools, bytecode buffers freed, breakable-line arrays freed once the DAP thread has seen their epoch), in the next prologue whether or not a behaviour node ran. A reload therefore takes effect at a tick boundary and never mid-tick ([Z2-N-SCRIPT-426]); the only registry types it changes are `TYPE_KIND_BEHAVIOUR_STATE` ([Z2-N-SCRIPT-430]).

Out-of-tick go-live: a `COMMITTED` generation can wait across frames (a paused world runs no tick boundary). `RestoreSavedStates`, and `RequestModuleReload` of a module that holds a `COMMITTED` generation, therefore first run go-live (steps 1–4 above) for every `COMMITTED` generation of the world on the main thread — out of tick, where no node runs, so the frame structure orders it against every node exactly as a tick boundary does — and then act: the save is restored into the new generation's instances and slots, and a new instance created by the load reserves its element from the new generation's pool; the retired blocks and released references drain at the next prologue as usual.

## Rollback procedure

Every failure path of a reload — load, declaration, state registration, `Migrate`, restore (`ApplyPendingReloads` step 3), a window that did not publish and a schedule commit that failed (`CommitPendingReloads` steps 2 and 3) — runs in prologue step 6 on the main thread before anything of the reload went live, and does exactly one thing: it releases the staged objects of each rolled-back generation once — each staged `self` and state-proxy reference, the staged module table and its `Migrate` references with `lua_unref` on the world's main VM, each staged checkpoint element back to the new generation's pool, which is then destroyed because nothing else uses it, a staged chunk-system bytecode buffer and breakable-line array freed — and discards the staged records. It releases nothing else: the previous generation's objects are queued only by go-live, which runs only for a `COMMITTED` generation and cannot fail, so no failure path releases a reference an instance still uses.

The end state is the same on every path: the previous generation current on every VM, every instance's Luau objects, live state and checkpoint slots exactly as before the request, the registry revision unchanged (window abandoned) or advanced with the new state type registered but unused (a schedule failure after publication: harmless, because types are read only through the current generation), the previous schedule in effect, and one diagnostic naming the first failure ([Z2-N-SCRIPT-425], [Z2-N-SCRIPT-428]). `Test_Script_HotReload_RollbackOnError` checks the instances' heap state by comparing each instance's `self` and proxy registry references and a hash of its live-state block before and after; `Test_Script_HotReload_ScheduleCommitFailureRollsBack` checks that every instance's references still resolve on the main VM after a schedule failure and that every staged reference was released exactly once.

## Chunk-system generations

Per world, per chunk-system module: `m_uCurrentGeneration`; per worker VM, per module: the loaded generation. At each invocation of a module on a worker VM, a loaded generation below the current one reloads the module from the current generation's bytecode — the world's bytecode arena for the generation loaded at world load, or the world-owned buffer `ApplyPendingReloads` copied the staged bytecode into for a reloaded generation (§ "ApplyPendingReloads procedure" step 2.5), which go-live only publishes — before the invocation; a superseded reload buffer is read by no worker VM after the go-live that replaced it, because every worker VM reloads from the current generation, so `CommitPendingReloads` frees it in the next prologue, and the world frees the rest at destruction; the reload is a lazy load (Design/SCRIPT/Bindings.md → "Module loader implementation") and a failure halts the world as an internal inconsistency, because the main VM validated the same bytecode ([Z2-N-SCRIPT-428]).

## Migration execution

`Migrate[n]` runs on the main VM in the behaviour environment with no world access (the call's invocation kind is `LOAD`, so every world-reading binding raises ZS1705), under Z2-B-SCRIPT-018 per step ([Z2-N-SCRIPT-399]). Inputs are plain Luau tables decoded from the checkpoint by field name; the output table is validated against the version n+1 schema (unknown keys, wrong kinds and exceeded maxima are ZS1907). Migration fixtures: `Games/<Name>/Scripts/Tests/Migration/<Behaviour>/v<n>.zbst` files, one per version, loaded by the game's `Game_<Name>_ScriptMigrations` test, which boots the game's development Player headless with the gametest option `--script-migration-fixtures <dir>` (MOD; A5 cross-area row SB30) so the fixtures meet the game's own sealed binding table, types and cooked manifest, and restores them through `Zenith_ScriptRestoreMigrationFixtures` (Design/SCRIPT/PublicAPI.md → "Zenith_ScriptWorld header"), that is through `Zenith_ScriptWorld::RestoreSavedStates`, asserting every fixture restores and, where the behaviour declares `Run`, runs `OnRecover` ([Z2-N-SCRIPT-400]).

## Schema migration script host

SCRIPT implements ZenithReflect's `Zenith_MigrationScriptHost` (`Zenith2/Docs/Design/ECS/Schemas.md` → "Script ops"; cross-area note E6(e)) as `Zenith_ScriptMigrationHost` (`Internal/Zenith_ScriptMigrationHost.cpp`), created by the composition root in the editor and at save loading:

1. On first use, create a dedicated sandboxed VM (role MAIN, TOOLS environment without any world binding; memory cap Z2-B-SCRIPT-009).
2. `RunScriptOp(szModule, szFunction, xOld, xNew)`: load the cooked `migrate` bytecode of `Schemas/<Component>.migrate.luau` (cooked by the schema cook with this library's compiler), convert `xOld` and `xNew` field sets to Luau tables keyed by field name, call the function under Z2-B-SCRIPT-018, convert `new` back into `xNew`.
3. A raised error, a budget trip or a conversion failure returns `MIGRATION_ERROR_SCRIPT`; the input is unchanged (the contract of `Zenith_MigrationScriptHost` in `Zenith2/Docs/Design/ECS/Schemas.md` → "Script ops").

The host's VM belongs to no world and never runs simulation code.

## Recovery invocations and exact restore

Orchestrator ruling Q82 (b) (`C:/dev/Zenith2-drafts/findings/OPEN_QUESTIONS_FOR_HUMAN.md`, 2026-10-03) changes two Scripting.md rules so that a restore with captured behaviour state can continue bit-identically: the recovery invocation consumes no invocation ordinal of [Z2-N-SCRIPT-274] and records under a reserved recovery namespace, and an instance needing no recovery gets none ([Z2-N-SCRIPT-394]). Cross-doc row X267 carried the Scripting.md wording, applied by core-doc patch e: [Z2-N-SCRIPT-274] and [Z2-N-SCRIPT-394] are reworded, [Z2-N-SCRIPT-928] (the recovery ordinal and acceptance order), [Z2-N-SCRIPT-929] (no recovery invocation without `OnRecover`) and [Z2-N-SCRIPT-930] (snapshot entries, restore lifecycle and fidelity) are new, and `Zenith2/Docs/Scripting.md` → "Restore algorithm" step 6 follows them. This section is the design form, implemented by Z2T-SCRIPT-114.

1. **Reserved recovery ordinal.** `inline constexpr uint32 uSCRIPT_RECOVERY_ORDINAL = 0xFFFFFFFFu;` (`Zenith_ScriptTypes.h`, Design/SCRIPT/PublicAPI.md → "Zenith_ScriptTypes header"). A recovery invocation (`OnRecover`) is an entity transaction whose logical invocation ID is (stable simulation ID, `uSCRIPT_RECOVERY_ORDINAL`). It consumes no ordinal: the behaviour node does not advance the instance's `m_uNextOrdinal` for it, so the instance's `OnCreate`, event handlers, `OnUpdate` call or `Run` segment and checkpoint-only transaction of that tick carry exactly the ordinals they carry in a tick without a recovery. No ordinary invocation reaches the value: an instance runs at most 3 + V invocations in a node (Design/SCRIPT/Transactions.md → "Retention ceiling derivation"), V bounded by the tick's event capacity.
2. **Recovery namespace keys.** The recovery transaction obtains its ECS command buffer with `xLeaf.Commands(ulSimulationID, uSCRIPT_RECOVERY_ORDINAL)`, its SCRIPT records carry the same logical invocation ID, and its random draws key `Zenith_ScriptRandomKey` with the recovery ordinal (Design/SCRIPT/Runtime.md → "Random draws"), so a recovery's commands, events, side effects and draws never share a merge key or a draw sequence with an ordinary invocation. Playback applies them in merge-key order (system order, simulation ID, ordinal, sequence), where they follow the same instance's ordinary records of the node.
3. **Acceptance order.** The merge's candidate sort (Design/SCRIPT/Transactions.md → "Merge node body" step 3) uses the ordinal digit `uOrdinal + 1` modulo 2^32, so an instance's recovery transaction is accepted, rejected or counted as failed before its ordinary invocations of the node: it ran first, and the earliest-failure rule of [Z2-N-SCRIPT-252] treats it as the earliest, so a rejected recovery rejects the instance's later invocations and no committed invocation builds on an uncommitted recovery. Capacity is consumed in that candidate order.
4. **Who gets a recovery invocation.** Only an instance whose behaviour declares `OnRecover` — exactly the behaviours that declare `Run` ([Z2-N-SCRIPT-141]) — is ever marked `PENDING_RECOVER`. Every other instance a last-good restore, a hot-reload go-live or `RestoreSavedStates` restores returns to ACTIVE (DORMANT while its `Zenith.Behaviour` component's `Enabled` is false) with no recovery invocation, so its first invocation after the restore is the one a run without the restore would make. For `RestoreSavedStates` the entry's flags decide (step 6).
5. **Snapshot entries.** `GetStateSnapshot` holds one `Zenith_ScriptSavedState` per instance past NEW (ACTIVE, DORMANT, PENDING_RECOVER, QUARANTINED), in ascending (source ID, simulation ID). An instance with no committed checkpoint carries an empty `m_xCheckpoint`, which restores its declared defaults, so a restored instance is never mistaken for a new one that runs `OnCreate` again. Each entry carries three flags, read in phase 11 after every checkpoint of the tick committed: `m_bRunSuspended` — the instance holds a `Run` coroutine that has yielded without returning (at phase 11 every existing coroutine has: a coroutine is resumed by the invocation list of the node that created it); `m_bRecoveryPending` — the instance is `PENDING_RECOVER`; `m_bQuarantinedOrDisabled` — the instance is QUARANTINED, or its module is disabled or flagged to disable at the next tick boundary.
6. **Restore lifecycle.** `RestoreSavedStates`, per entry after § "Restore implementation" steps 1–4 (an empty blob writes the declared defaults and decodes nothing): when the behaviour declares `OnRecover` and the entry carries `m_bRunSuspended`, `m_bRecoveryPending` or `m_bQuarantinedOrDisabled`, the instance becomes `PENDING_RECOVER` and its `OnRecover` runs under the recovery ordinal in the first tick of its declared phase; otherwise it becomes ACTIVE (or DORMANT) with no recovery invocation and no coroutine — a `Run` that had returned stays ended, as in the uninterrupted run.
7. **Fidelity.** A restore of a snapshot none of whose entries carries `m_bRunSuspended` or `m_bQuarantinedOrDisabled` continues bit-identically to the uninterrupted run (same build, backend and inputs): every instance resumes with that run's state, lifecycle and ordinals, and a pending recovery runs at the same tick under the same keys. An entry with `m_bRunSuspended` restores consistently only, because the coroutine restarts from the phase its state records ([Z2-N-SCRIPT-393], [Z2-N-SCRIPT-395]); an entry with `m_bQuarantinedOrDisabled` restores as a recovery the uninterrupted run did not make at that tick (module disables and recovery counters are not saved). SAVE's `Zenith.Script.States` participant reads the flags for its capture fidelity (cross-area rows SV23 and SC25).
