# SCRIPT design — the DAP debugger and the sampling profiler

Companion to `Zenith2/Docs/Design/SCRIPT.md`: the Debug Adapter Protocol server of `Zenith2/Docs/Scripting.md` → "DAP server design", its transport over PLAT's development listener, request handling, breakpoint fan-out, the stop protocol and the stop loop, stepping, variables, the attach workflows and the sampling profiler. D-LUAUDBG (open, Stage 1) selects the client; the server is client-neutral. Everything here exists only in configurations other than Shipping ([Z2-N-SCRIPT-461], [Z2-N-SCRIPT-488]). Files are under `Zenith2/Engine/ZenithScript/Internal/Debug/`.

## Scope of this file

The server is `Zenith_ScriptDap` (Internal). It is created by `Zenith_ScriptRuntime::Create` inside `if constexpr (!Zenith_IsShippingBuild())` when `Zenith_ScriptDebuggerDesc::m_bEnabled` is set (the Player's `--script-dap-port <port>` argument, default 27851; ZenithEditor always), so the composition root owns it through the script runtime. A listener that cannot be created leaves the runtime without a debugger (`IsDebuggerAvailable()` false, diagnostic `SCRIPT_DEBUGGER_UNAVAILABLE`) unless `m_bRequired` is set, which only the DAP tests' harness does; then `Create` fails with `SCRIPT_ERROR_DEBUGGER_UNAVAILABLE` (Design/SCRIPT/Runtime.md → "Script runtime internals" step 3). The Luau debug callbacks (`debugbreak`, `debugstep`, `debuginterrupt`) are installed on a VM only when the runtime has a debugger. In Shipping the construction is a discarded statement and no `Zenith_ScriptDap` symbol is referenced, which libgraph's link-surface check asserts ([Z2-N-SCRIPT-461]).

`Zenith_ScriptRuntime::PollDebugger()` (frame-loop step 3, main thread, out of tick) refreshes the `loadedSources` path mapping after a hot reload and serves a queued sample-dump request. The DAP `thread` events are the DAP thread's own: at every poll it compares, under the DAP mutex, each slot's `m_bLive` with the value it last reported (`m_bLiveReported`, written only by the DAP thread), copies the changed thread IDs into an array it reserved before locking, unlocks, and sends one `thread` event per change (reason `started` or `exited`). Nothing in the stop protocol depends on either.

## DAP service ownership and lifetime

| Object | Owner | Thread |
|---|---|---|
| `Zenith_ScriptDap` | `Zenith_ScriptRuntime` (`m_pxDebugger`) | created and destroyed on the main thread |
| `Zenith_DevListener` (`Zenith2/Docs/Design/PLAT/Platform.md` → "Loopback socket") | `Zenith_ScriptDap` | polled by the DAP thread |
| the DAP thread `Zenith.ScriptDap` | `Zenith_ScriptDap` (a CORE `Zenith_Thread`) | parses requests, answers what it can, forwards VM work |
| per-world breakpoint sets | each `Zenith_ScriptWorld` (`m_xBreakpoints`) | written only by the DAP thread, which builds each array outside any lock and publishes it with a release store (§ "Breakpoint storage and fan-out"); read by VMs |
| the stop mailbox | `Zenith_ScriptDap` | one `Zenith_ScriptStopBlock` per world (§ "Stop protocol"), linked into the service's `m_axWorldBlocks` (`Zenith_FixedArray<Zenith_ScriptStopBlock*, uSCRIPT_WATCHDOG_MAX_WORLDS>`: every world registers with the watchdog, so no more worlds exist), the DAP mutex (`Zenith_MutexNoProfiling` at `uLOCK_LEVEL_SCRIPT_DAP`, 710, not short-hold; acquired by a frame thread only inside the stop bracket of § "Stop protocol"; row added with the DAP ticket, [Z2-N-CONTRACT-320], its exemption with cross-doc row X120; it is unprofiled because the debugger stop reports its own named wait, and a development-only debugger lock is not a performance subject) and a CORE `Zenith_ConditionVariableNoProfiling` per slot |
| each world's stop block | allocated by `Zenith_ScriptDap::AttachWorld` in `Zenith_ScriptRuntime::CreateWorld` and freed by `DetachWorld` in `DestroyWorld` (below) | its slots as § "Stop protocol" states; the block itself is reached by the DAP thread only through `m_axWorldBlocks`, under the DAP mutex |
| each world's breakable-line arrays | the world's module states (§ "Breakpoint storage and fan-out") | built by the main VM's loader on the main thread, published with a release store, read by the DAP thread under the DAP mutex |
| each world's debugger gate | the world (`Zenith_ScriptDebugGate`, Design/SCRIPT/Runtime.md → "Script world internals") | the stopped count, a `Zenith_ConditionVariableNoProfiling` (`m_xGate`) paired with the DAP mutex |
| each VM's debugger fields | the VM (`Zenith_ScriptVMDebugState`, § "Stop protocol") | the VM's thread; the stop flag read by the watchdog |

World attach and detach, on the main thread out of tick:

1. `AttachWorld(xWorld)` (from `CreateWorld`, after `Zenith_ScriptWorld::Create` and before any VM of the world runs an invocation): allocate, outside any lock, one `Zenith_ScriptStopBlock` with `Zenith_TryNew` — the world tag, the world's breakable-line table pointer (null until `LoadModules` publishes it, release store), and `Zenith_FixedArray<Zenith_ScriptStopSlot, 1 + uSCRIPT_MAX_WORKER_VM_SLOTS> m_axSlots` of which the first `1 + m_uFrameThreadCount` are used, indexed by VM index — then lock the DAP mutex, append the pointer to `m_axWorldBlocks` (a fixed array: no allocation under the mutex), unlock, and store the block pointer in the world (`m_pxStopBlock`). A failed allocation is `SCRIPT_ERROR_OUT_OF_MEMORY` from `CreateWorld` (fault point `uFAULT_POINT_SCRIPT_RUNTIME_DAP_SLOTS`), which then destroys the world it created. Every VM of the world, the main VM and each worker VM including one created lazily inside a sub-job, uses slot `vmIndex` of its world's block with no registration, no allocation and no lock.
2. `DetachWorld(xWorld)` (from `DestroyWorld`, after the tick drained and every VM of the world was destroyed, so no slot is `STOPPED` and every `m_bLive` is false): lock, remove the pointer from `m_axWorldBlocks` (order kept), unlock, then free the block and the world's breakable-line arrays outside any lock. The DAP thread's next poll reports the exited threads it had not yet reported.

Destruction order of the service: stop the DAP thread (stop flag, wake, join), release every stopped VM (none can remain once every world tick drained), destroy the listener.

## Transport and framing

1. The DAP thread creates the listener with `m_szServiceName = "dap"`, `m_uPort` from the descriptor, `m_uMaxConnections = 1` (one client session; a second connection is closed with a log line), `m_uReceiveBufferBytes = 262144`.
2. PLAT's handshake applies: the first message of a connection must be `ZENITH2-TOKEN <token>\n` within 5 s (the token is printed to the local log); the client configuration of D-LUAUDBG passes it, on Windows from the log line, on the S24 from `adb logcat`.
3. After the handshake, messages are DAP base-protocol frames: `Content-Length: <n>\r\n\r\n<n bytes of JSON>`. A frame above 1 MiB, a missing or malformed header, or JSON rejected by CORE's reader under `Zenith_JsonLimits` for untrusted input (`Zenith2/Docs/Design/CORE/Text.md` → "JSON reader") closes the connection with a log line; the bytes are untrusted input and never reach an assert ([Z2-N-CONTRACT-472]). `Zenith_Fuzz_Script_DapMessage` fuzzes the framer and request parser.
4. Responses and events are written with CORE's JSON writer and sent with `Send`; the thread polls every 5 ms.

## Session state machine

| State | Event | Next state and action |
|---|---|---|
| LISTENING | a connection passes the handshake | CONNECTED |
| CONNECTED | `initialize` | INITIALIZED; respond with capabilities: `supportsConfigurationDoneRequest`, `supportsEvaluateForHovers` (locals only), `supportsLoadedSourcesRequest`; no conditional or function breakpoints in v1 |
| INITIALIZED | `attach` (the only launch kind: the process is already running) | ATTACHED; send `initialized` event |
| ATTACHED | `setBreakpoints`, `configurationDone` | RUNNING |
| ATTACHED, RUNNING or STOPPED | a VM of any world stops (breakpoint, step, pause, error with the error breakpoint enabled) | STOPPED; `stopped` event with the thread ID and reason |
| ATTACHED, RUNNING or STOPPED | `continue` for a thread whose slot is `STOPPED` | release that thread's world (§ "Stop protocol" rule 5); then recompute the state |
| ATTACHED, RUNNING or STOPPED | `next`, `stepIn`, `stepOut` for a thread whose slot is `STOPPED` | the thread steps (§ "Stop protocol" rule 6); then recompute the state |
| ATTACHED, RUNNING or STOPPED | `continue`, `next`, `stepIn`, `stepOut` for a thread whose slot is not `STOPPED` | error response `thread not stopped`; nothing changes |
| RUNNING or STOPPED | a slot turns `STEP_COMPLETED` | `continued` event for the world; release the world (rule 5); then recompute the state |
| any | `disconnect` or the connection closes | LISTENING; release every stopped VM of every world, then clear every breakpoint set |

STOPPED is a summary, not a gate: after every stop and every release the DAP thread recomputes it under the DAP mutex as "at least one slot of any linked world is `STOPPED`" (else RUNNING), so a release of one world never hides another world's stop. With the editor's edit and play worlds both stopped, `continue` on a play-world thread releases the play world only, the session stays STOPPED, and `continue` on an edit-world thread is accepted and releases the edit world.

## Request handling

| Request | Handled on | Behaviour |
|---|---|---|
| `initialize`, `attach`, `configurationDone`, `disconnect` | DAP thread | as the state machine |
| `threads` | DAP thread | every live VM of every world: `id = worldTag × 256 + vmIndex`, name `<World>/main` or `<World>/worker<N>`; under the DAP mutex the DAP thread walks `m_axWorldBlocks` and copies the ID of every slot whose `m_bLive` is set (acquire) into an array it reserved before locking for the linked blocks' slot total, then builds the response after unlocking; it holds no VM pointer and reads no VM's state. `Zenith2/Docs/Scripting.md` → "DAP server design" step 2 says "world index"; the world tag is used because it is the one world identifier every SCRIPT and ECS interface carries (4,095 × 256 + 64 fits a DAP integer), and the specification's wording changes with cross-doc row X121 |
| `setBreakpoints` | DAP thread | replace the source's line set in every world's breakpoint set, bump each world's generation (§ "Breakpoint storage and fan-out"); respond with each breakpoint `verified` when the line is in the breakable-line array of the module's current generation in any world (a binary search under the DAP mutex, § "Breakpoint storage and fan-out"), else `verified: false` with message `not yet loaded` (it is applied when the module loads); the DAP thread never reads a VM's Luau state |
| `setExceptionBreakpoints` | DAP thread | one filter `error` (stop on any script error before rollback); off by default |
| `stackTrace`, `scopes`, `variables` | the stopped VM's thread, through the stop mailbox | § "Variables and scopes"; for a VM that is not stopped (running, or parked at the gate between invocations) `stackTrace` returns `totalFrames: 0` |
| `evaluate` | the stopped VM's thread | § "Evaluate restrictions" |
| `continue`, `next`, `stepIn`, `stepOut` | DAP thread posts to the stop mailbox | accepted in ATTACHED, RUNNING and STOPPED for a thread whose slot is `STOPPED`, whichever world it belongs to; the stopped thread resumes (`continue` releases its world, § "Stop protocol" rule 5); for any other thread the error response `thread not stopped` |
| `pause` | DAP thread | under the DAP mutex, set `m_bPauseRequested` in every slot of the thread's world's stop block; each VM stops at its next safepoint inside an invocation (§ "Stop protocol" rule 1); the release of rule 5 clears the flag in every slot of the world, so a VM that was parked or idle does not stop after `continue` |
| `loadedSources` | DAP thread | the manifest's module paths mapped to host source paths (development builds carry the source roots in the loose mount's metadata) |
| anything else | DAP thread | error response `unsupported request` |

The set above is the minimum Scripting.md's D-LUAUDBG entry requires ([Z2-N-SCRIPT-463]); the ruling may add requests, never remove them.

## Breakpoint storage and fan-out

`Zenith_ScriptBreakpointSet` per world: an array of `Zenith_ScriptBreakpoint { Zenith_ScriptModuleID m_xModule; uint32 m_uLine; }` sorted by (module, line), a `std::atomic<uint32> m_uGeneration`, written only by the DAP thread and read by VM threads through a copy-on-write swap: the DAP thread (the single writer, so no lock) builds a new array outside any lock and publishes it with a release store of the pointer and then of the generation; readers acquire the generation, then the pointer; the DAP thread frees an old array, outside any lock, once every VM of the world has applied a newer generation.

Fan-out, as Scripting.md → "DAP fan-out" steps 1–4:

1. The main VM applies a new generation at the next point no invocation runs on it: at the start of each behaviour node and between instances (a check of one atomic).
2. A worker VM compares its applied generation at the start of each sub-job (Runtime.md → "Chunk-system node body" step 3).
3. Applying: for every loaded function prototype of the VM's modules (the loader keeps, per module, the registry references of its function prototypes, enumerated with `lua_getinfo` at load), call `lua_breakpoint(L, funcIndex, line, enabled)` for every added or removed line of that module, inside a limit-0 `NATIVE_BODY` protected call ([Z2-N-SCRIPT-089]).
4. A module loaded afterwards applies the current set for its own lines after `luau_load` ([Z2-N-SCRIPT-087]): on the main VM before its module scope runs (a module-scope line then stops the out-of-tick load, § "Stop protocol" rule 8); on a worker VM only after its module scope returned, because a lazy load runs inside a leaf but outside any invocation (Runtime.md → "Chunk-system node body" step 3), where no stop is allowed (§ "Stop protocol" rule 8).

Breakable lines, the only source of `setBreakpoints`' `verified`: per world and module generation, the main VM's loader (world load in `LoadModules`, or the prologue's staging in `ApplyPendingReloads`, both on the main thread) builds an immutable `Zenith_ScriptBreakableLines { uint32 m_uCount; uint32 m_auLines[]; }` — the sorted, de-duplicated lines of every function prototype of the module, read with `lua_getinfo` while it enumerates the prototypes for step 3 — in one general-heap block (a failure is the load's `SCRIPT_ERROR_OUT_OF_MEMORY`, or the reload's failure with rollback). The world keeps one `std::atomic<const Zenith_ScriptBreakableLines*>` per manifest module, allocated with the module table at `LoadModules` and recorded in the world's stop block with a release store. A generation's array is published there with a release store — by the loader at world load, and by go-live for a reloaded module (the array was built in the prologue, so go-live only stores a pointer, Design/SCRIPT/HotReload.md → "Go-live at the tick boundary") — followed by an increment of the world's `std::atomic<uint64> m_ulBreakableEpoch` (release). The DAP thread reads the arrays only under the DAP mutex (binary searches, no allocation); before each read it loads the epoch (acquire) and afterwards stores that value into `m_ulBreakableEpochSeen` (release), and at every poll with no read in progress it stores the current epoch there. A replaced array is retired with the epoch its replacement published and freed on the main thread by `Zenith_ScriptRuntime::CommitPendingReloads` step 1 once `m_ulBreakableEpochSeen` has reached that epoch — so no read that could hold it is in progress, the rule of old breakpoint arrays — or at `DetachWorld`. No thread reads another thread's VM, and a hot reload that frees prototypes on the main VM frees nothing the DAP thread reads.

Per world, in development builds, `Zenith_ScriptDebugGate` (`Internal/Debug/Zenith_ScriptDapStop.cpp`) holds `std::atomic<uint32> m_uStoppedCount` — the world's VMs that are stopped or stepping, changed only under the DAP mutex and read without it only by the gate's fast path of rule 2 — and a CORE `Zenith_ConditionVariableNoProfiling` `m_xGate` paired with the DAP mutex (`Zenith2/Docs/Design/CORE/Threading.md` → "Condition variables and semaphores"). Each VM carries, in development builds, a `Zenith_ScriptVMDebugState`:

| Field | Type | Written by | Read by |
|---|---|---|---|
| `m_bDebuggerStopped` | `std::atomic<bool>` | the VM's thread: true (release) before it blocks, false (release) after the watchdog rebase of rule 5 | the watchdog poll (acquire; Design/SCRIPT/Runtime.md → "Watchdog internals") |

| `m_bCounted` | `bool` | the VM's thread, under the DAP mutex | the VM's thread, under the DAP mutex |
| `m_xStep` | `Zenith_ScriptStepState { uint8 m_uKind; int m_iStartDepth; bool m_bActive; }` | the VM's thread: armed by rule 6, consumed by rule 1 at the VM's next stop, cleared by rule 6's exit after a return and kept per instance coroutine after a `Run` yield (§ "Stepping") | the step callback and the protected-call exit |

The stop block of a world (`Zenith_ScriptStopBlock`, § "DAP service ownership and lifetime") holds one `Zenith_ScriptStopSlot` per VM of the world, indexed by VM index and allocated with the world, so a VM's slot exists before the VM does:

| Slot field | Type | Written by | Read by |
|---|---|---|---|
| `m_bLive` | `std::atomic<bool>` | the VM's thread, with no lock: true (release) at the end of VM creation, after its debug callbacks are installed; false (release) at its destruction, before `lua_close` | the DAP thread, under the DAP mutex (acquire), for `threads` and the `thread` events |
| `m_bLiveReported` | `bool` | the DAP thread | the DAP thread |
| `m_bPauseRequested` | `std::atomic<bool>` | the DAP thread, under the DAP mutex: set by `pause` (relaxed), cleared by the release of rule 5 (relaxed) | the VM's interrupt, with no lock (relaxed; a stale read moves the stop by one safepoint) |
| `m_uState` | `uint8`: `NONE`, `STOPPED`, `RESUME`, `STEP`, `STEP_COMPLETED` | the VM's thread and the DAP thread, under the DAP mutex | the same, under the DAP mutex |
| `m_bStopPending` | `bool` | the VM's thread, set under the DAP mutex by rule 1; the DAP thread, cleared under the mutex when it takes the stop record | the DAP thread, under the DAP mutex |
| `m_xStop` | `Zenith_ScriptStopRecord { uint32 m_uThreadID; uint32 m_uLine; uint8 m_uReason; char m_acFunction[64]; }` | the VM's thread, under the DAP mutex, copied from the record it computed before locking | the DAP thread, under the DAP mutex |
| `m_uStepKind` | `uint8` | the DAP thread, under the DAP mutex | the VM's thread, under the DAP mutex |
| `m_xRequest` | `Zenith_ScriptStopRequest { uint8 m_uKind; uint32 m_uSequence; uint32 m_uFrame; uint32 m_uVariablesReference; char m_acExpression[256]; }` (a pending stack, scopes, variables or evaluate request; kind 0 = none) | the DAP thread, under the DAP mutex | the VM's thread, under the DAP mutex |
| `m_pxResponse` | `Zenith_ScriptStopResponse*` (a general-heap block: the request's sequence, the byte count and the response JSON) | the VM's thread, under the DAP mutex, posting a block it allocated before locking; the DAP thread, under the DAP mutex, taking it (the slot's pointer becomes null) | the same |
| `m_xWake` | `Zenith_ConditionVariableNoProfiling` paired with the DAP mutex | — | the stopped VM waits on it |

**The DAP mutex rule.** A thread holding the DAP mutex (710) reads and writes only the fields of this section, the stop blocks, the breakable-line arrays and the session state, signals condition variables, and unlocks; it allocates nothing, frees nothing, takes no other lock and calls no other subsystem — including Luau: `lua_getinfo` runs before a stopping thread locks (rule 1). In particular it never calls PLAT's listener (levels 600 … 630), the watchdog (700) or a heap while holding 710, because each of those locks is below 710 and [Z2-N-CONTRACT-319] admits acquisition upward only. Every transition below therefore does its bookkeeping under the mutex and its other work — computing a stop record, serving a request and allocating or freeing its response, writing or sending a message, building or freeing a breakpoint array, rebasing the watchdog — before it locks or after it unlocks.

1. **Which invocations stop, the one increment, and the step a stop consumes.** A VM stops only inside an invocation (or inside one of the out-of-tick calls of rule 8), at a point Luau reports through `debugbreak` (a breakpoint), `debugstep` (a step target, § "Stepping") or the interrupt callback's pause branch — its slot's `m_bPauseRequested`, which the branch honours only while the VM is inside an invocation or a rule-8 call (elsewhere the flag stays set and the next invocation's first safepoint stops), or the `error` exception filter before rollback. Before taking any lock the stopping thread: (a) consumes any armed step: when `m_xStep.m_bActive` is set — a `debugstep` stop at the step target, or a breakpoint, pause or error stop reached while stepping — it clears `m_xStep.m_bActive` (and the copy kept for the instance's `Run` coroutine) and calls `lua_singlestep(L, 0)`, so a step never outlives the stop it produced and only a new `next`, `stepIn` or `stepOut` arms one (rule 6); (b) computes its stop record — thread ID, reason, line and the function name from `lua_getinfo(L, 0, "sln", &ar)`, truncated at a code-point boundary to 63 bytes; (c) sets `m_ulStopStartTicks = now` and `m_bDebuggerStopped.store(true, std::memory_order_release)`. It then enters the bracket (rule 4), locks the DAP mutex and, when `m_bCounted` is false, sets it and increments `m_uStoppedCount` (`fetch_add(1, std::memory_order_release)`). This is the only increment of the count: a VM that stops while stepping is still counted from its earlier stop (rule 6) and does not increment again. Still under the mutex it copies the record into its slot's `m_xStop`, sets the slot to `STOPPED` and sets its `m_bStopPending` — a flag of the slot, not a list, so nothing is allocated — from which the DAP thread, at its next poll, copies the record out under the mutex, clears the flag, and after unlocking sends `stopped` for this thread with `allThreadsStopped: false`; the thread continues at § "Stop loop" step 2, still holding the mutex.
2. **Which invocations park, and on which condition.** Every script node body of the world passes the gate before each invocation it starts: a chunk-system leaf before each invocation of its range, a behaviour node before each invocation of its list (`OnRecover`, `OnCreate`, handlers, `OnUpdate` or the `Run` segment, a checkpoint-only transaction). The fast path is `m_uStoppedCount.load(std::memory_order_acquire) == 0`: the invocation starts. Otherwise the thread parks: it enters the bracket (rule 4), locks the DAP mutex, runs `while (m_uStoppedCount.load(std::memory_order_relaxed) != 0) m_xGate.Wait(xDapMutex);` — so the predicate is re-checked under the mutex before the first wait and after every wake — unlocks, leaves the bracket and starts the invocation. A parked thread therefore holds no open transaction and no Luau frame. Invocations already running on other VMs of the world when the first stop happens continue to their end, or to their own stop when they reach a breakpoint or the pause flag; a thread that passed the fast path just before a stop is such an invocation. Script nodes of the world whose bodies have not started start normally when the executor reaches them and park at their first invocation. Merge nodes, the tick-boundary node and engine (C++) nodes never park: they run no script and run only when the graph's edges allow, exactly as in an undebugged frame. The gate is per world, so other worlds are unaffected.
3. **How the tick commit is held.** By the graph alone: a stopped or parked node's body has not returned, so its merge node — which starts only after every sub-job and continuation of the node has finished ([Z2-N-ARCH-395]) — has not started; every subsequent merge node of the phase is ordered after it by the merge chain ([Z2-N-SCRIPT-249], `After(required)`); the phase's sync point follows every merge of the phase. So no transaction of a stopped or parked node commits, no subsequent merge of the phase commits, the tick does not advance and `RunFrame` does not return. A merge node earlier in the chain whose system node completed may commit during the stop; it commits the same values in the same order as in an undebugged frame, because commit order is the chain order and a node that reads what it writes starts only after it ([Z2-N-SCRIPT-159]).
4. **The bracket.** Every frame thread that takes the DAP mutex does so inside the same bracket, and nothing else in ZenithScript blocks or takes 710 inside a node body: `const bool bWasJobBody = Zenith_IsJobWorkerThread();` (`Zenith2/Docs/Design/CORE/Threading.md` → "Debug thread state"); `Zenith_MarkThreadAsJobWorker(false)`; lock the DAP mutex (710, acquired by a frame thread only here); wait on its slot's `m_xWake` (a stopped thread) or on `m_xGate` (a parking thread) until released, or, for a stepping thread leaving the count (rule 6), do its bookkeeping without waiting; unlock; then, only when the thread waited, report the wait once through `Zenith_DispatchBlockingWait("debugger-stop", ulStoppedNs)`, where `ulStoppedNs` is the time from the thread's start to its release (a stopped thread measures from `m_ulStopStartTicks`, rule 1; a parking thread from a `Zenith_GetMonotonicTimeNs()` reading taken before it locks), in the nanoseconds the profiler hook table defines. A parking thread that finds the count already zero waited for nothing and reports nothing; so does a stepping thread (rule 6) and a thread that does not wait under the detached session of rule 5. The report is made before the flag is restored, so the hook runs with the job-worker flag false: `Zenith_MarkThreadAsJobWorker(bWasJobBody)`. The bracket restores the flag it found: true inside a job body, false on the main thread outside one (rule 8), so an out-of-tick stop never leaves the main thread flagged as running a job body and the prologue's subsequent blocking waits pass CORE's [Z2-N-CONTRACT-315] check. The debug callbacks, and so the bracket, exist only when the runtime has a debugger, which is never in Shipping ([Z2-N-SCRIPT-461]).
5. **Release.** The DAP thread releases a world on `continue` for one of its threads, on `disconnect`, when the connection closes, and when a step completes without reaching its target (rule 6). Under the DAP mutex it scans the world's whole stop block — every slot, whether or not its VM is live, so a worker VM created lazily in the stopped tick (whose first invocation is often the one that hit the breakpoint) is released like any other — sets every slot in state `STOPPED` to `RESUME` and signals that slot's `m_xWake`, and stores false into every slot's `m_bPauseRequested`. Each resumed thread wakes holding the mutex, sees `RESUME` and leaves the count: it holds no step state (rule 1 consumed it; `ZENITH_ASSERT(!m_xStep.m_bActive)`), and when `m_bCounted` is true it clears it, checks `ZENITH_CHECK(m_uStoppedCount.load(std::memory_order_relaxed) > 0)`, decrements `m_uStoppedCount` (`fetch_sub(1, std::memory_order_release)`) and calls `m_xGate.NotifyAll()` when its decrement reached 0 (still holding the mutex); it frees nothing under the mutex (a response block it still owns is freed after unlocking, § "Stop loop" step 3), sets its slot to `NONE`, unlocks and leaves the bracket. Every decrement of the count, here and in rule 6, is so guarded: the count never goes below zero, and a thread that is not counted never decrements. Then, outside any lock, it rebases its watchdog time: `D = now − m_ulStopStartTicks`; `m_ulWatchdogRebaseTicks += D`; when `m_ulWatchdogStartTicks` is non-zero it stores `start + D` (release); only then `m_bDebuggerStopped.store(false, std::memory_order_release)`. The rebase precedes the flag, so no watchdog poll sees the VM unflagged with its pre-stop start time, and the time a VM spends stopped never counts towards its limit, however long the stop. Every parked thread wakes, re-checks the predicate under the mutex, finds 0 and starts its invocation; because the decrement, the notify and the parker's predicate check all happen under the mutex, no wake-up is lost. Only the stopped VM itself sets and clears its own watchdog flag, so a VM that stops again while others are being released (rule 1 during rule 5) cannot have its exemption cleared by another thread. A `disconnect` or a lost connection releases every world this way and marks the session detached under the mutex; after unlocking, the DAP thread clears every world's breakpoint set by publishing an empty array as § "Breakpoint storage and fan-out" does, so no new breakpoint stop arises. A VM that reaches rule 1 while the session is detached — a stepping VM at its target, or a breakpoint or pause racing the disconnect — does not wait: its step was already consumed before it locked; under the mutex it leaves the count when it is counted (the guarded decrement, notifying at 0), clears its slot's pause flag, unlocks, leaves the bracket, rebases and clears its watchdog flag, and returns into Luau.
6. **Stepping.** `next`, `stepIn` and `stepOut` resume only the named VM: under the DAP mutex the DAP thread sets its slot to `STEP` with the step kind and signals it. The VM wakes holding the mutex, keeps `m_bCounted` (the count does not change, so the world stays gated while one of its VMs steps), sets its slot to `NONE`, unlocks, leaves the bracket, rebases its watchdog time and clears `m_bDebuggerStopped` exactly as in rule 5, arms the step — `m_xStep = { kind, lua_stackdepth(L), m_bActive = true }` — enables `lua_singlestep(L, 1)` and returns into Luau. Its next stop, at the step target or at a breakpoint, pause or error before it, goes through rule 1, which consumes the step and does not increment. When the stepping invocation returns or yields with the step still armed, the outermost protected call's exit on that VM (Design/SCRIPT/Runtime.md → "Protected call implementation") finds `m_xStep.m_bActive` and leaves the count: it enters the bracket without calling the blocking-wait hook (it will not wait), locks the DAP mutex, and when `m_bCounted` is true clears it and decrements with the guard of rule 5 (`ZENITH_CHECK` that the count is positive; `m_xGate.NotifyAll()` at 0), sets its slot to `STEP_COMPLETED`, unlocks and leaves the bracket; it then calls `lua_singlestep(L, 0)` and clears `m_xStep` after a return, or keeps it for the instance's coroutine after a `Run` yield, so the coroutine's next segment stops at its first line (§ "Stepping"). A VM that is not counted at that exit — which the protocol never produces, and which a detached session's rule 1 would otherwise risk — does not decrement. The DAP thread observes `STEP_COMPLETED` at its next poll (within 5 ms), sends a `continued` event for the world and releases every other stopped VM of the world (rule 5), so stepping out of an invocation continues the world. The stepping thread's decrement and notify are under the mutex and it never waits, so a parker between its predicate check and its wait cannot miss the wake-up, and a job body acquires 710 only inside the bracket.
7. **Why it cannot deadlock.** Every blocked thread waits for a condition that only the DAP thread's release (rule 5), or a stepping VM's completion (rule 6) after the DAP thread resumed it, makes true, and a release reaches every stopped VM of its world because it scans the world's whole stop block, which exists from world creation. The DAP thread is a dedicated `Zenith_Thread`, never a frame thread: it depends on no job, no frame and no worker; it takes the DAP mutex only for the bookkeeping of the mutex rule — no thread holds 710 across a wait, because a condition-variable wait releases it, and no thread holding 710 waits for anything else — and it reads PLAT's listener and writes and sends its messages with no lock held, so it always reaches its next request. No blocked thread holds any other lock: a node body holds none across an invocation boundary, and no binding holds one across a call into Luau, because a short-hold lock is never held across a callback ([Z2-N-CONTRACT-316]) and a job acquires no other kind ([Z2-N-CONTRACT-315]). A client that vanishes closes the connection, which is a release. So every stopped and parked thread resumes after one release, whatever their number: every frame thread of the process may be parked or stopped at once, the main thread included, and the frame then completes after the release. What waits besides the world's script is work queued behind the blocked threads — other worlds' jobs, the render subgraph's CPU jobs of frame k − 1, the next frame's prologue — which is why a stopped Player stops repainting until `continue`; no value depends on that timing, so no result changes.
8. **Out-of-tick stops and module scope.** A stop during `LoadModules`, `ApplyPendingReloads` (a `Migrate` step, or a staged module's scope on the main VM) or `ConsoleEvaluate` happens on the main thread outside any job body; it uses the same bracket, which then finds and restores a false job-worker flag (rule 4), and no node parks, because no tick runs. A worker VM never stops outside an invocation: its lazy module load (Design/SCRIPT/Runtime.md → "Chunk-system node body" step 3) runs module scope inside a leaf but outside any invocation, breakpoints reach that module only after its scope returned (§ "Breakpoint storage and fan-out" step 4), the pause branch does not enter there (rule 1), and the `error` filter does not apply there (a load failure on a worker VM halts the world as an internal inconsistency). The same module scope ran on the main VM at world load or in the reload prologue, where a breakpoint in it stops under this rule; a lazy worker load holds no scratch or retention state, so none could be held across a stop anyway.

## Stop loop

When `debugbreak`, `debugstep` or the interrupt's pause branch fires on a VM thread (§ "Stop protocol" rule 1):

1. Take the stop of rule 1: consume an armed step, compute the stop record, record the stop start and set the watchdog flag — all before locking — then enter the bracket, lock the DAP mutex, count the VM once, copy the record into the slot, set the slot to `STOPPED` and its `m_bStopPending`; the DAP thread sends `stopped` for this thread with `allThreadsStopped: false` at its next poll; the world's other VMs finish their running invocations and park at the gate (§ "Stop protocol" rule 2).
2. Wait on the slot's `m_xWake` while the slot is `STOPPED` and holds no pending request (the wait releases the mutex and re-acquires it on wake).
3. A pending request (stack, scopes, variables, evaluate): copy `m_xRequest` out of the slot and clear its kind, unlock, and serve it outside the mutex as a limit-0 `NATIVE_BODY` protected read that never blocks, writing the response JSON into a `Zenith_ScriptStopResponse` block allocated from the general heap (legal: no lock is held); then lock and, when the slot is still `STOPPED`, store the block's pointer into `m_pxResponse` and signal the DAP thread's poll, which takes the pointer under the mutex, sends the response after unlocking and frees the block after sending. When the slot is no longer `STOPPED` (a release came first), the VM keeps ownership, unlocks after handling the release of step 4, and frees the block itself outside any lock. Either way every block has exactly one owner and is freed outside 710. Return to step 2; the thread stays inside the bracket throughout.
4. `RESUME` (a release, including a session reset): rule 5 — no step state survives, because rule 1 consumed it; leave the count with the guarded decrement, notify at 0, unlock, leave the bracket, free a response block still owned, rebase the watchdog time and clear the flag. `STEP`: rule 6 — stay counted, unlock, leave the bracket, rebase and clear the flag, arm the step and start stepping. Then return from the callback; Luau continues exactly where it stopped.

A stop changes no safepoint count (the interrupt counts before it checks the pause, and the stop consumes no safepoint), no watchdog outcome (the stopped time is excluded, rule 5) and no committed value, so a debugged replay has the same world-state hashes as an undebugged one ([Z2-N-SCRIPT-462]).

## Stepping

`lua_singlestep(L, 1)` enables the step callback; at each callback compare `lua_stackdepth(L)` with the depth recorded when the step was armed (§ "Stop protocol" rule 6): `next` stops at the next line with depth ≤ start, `stepIn` at the next line at any depth, `stepOut` at the next line with depth < start. A step lasts until the VM's next stop, which consumes it (rule 1: `m_bActive` cleared and `lua_singlestep(L, 0)` before the thread locks), so after `next` reaches its line a `continue` runs the invocation free to its end with no further stop, and the invocation's end does not touch the count, which the release already left. A breakpoint reached before the step target consumes the step in the same way. A behaviour's `Run` coroutine that yields while its step is armed keeps the step for the instance's coroutine (rule 6's exit, which leaves the count); when the runner resumes that coroutine's next segment it re-arms the kept step with `lua_singlestep(L, 1)`, and the segment's first line stops through rule 1 — which counts the VM again, because the exit left the count — and consumes it. This is how the client steps "across yields" (D-LUAUDBG's acceptance rule). Stepping out of the outermost function of an invocation continues the world until the next breakpoint (rule 6).

## Variables and scopes

On the stopped thread: `stackTrace` walks `lua_getinfo(L, level, "sln", &ar)` up to 64 frames (source = the module path mapped to the host path, line); `scopes` gives, per frame, `Locals` (`lua_getlocal`), `Upvalues` (`lua_getupvalue`) and, for behaviour frames, `State` (the declared state through the state proxy's fields) and `Self` (`Entity`); `variables` expands tables up to 256 entries per request (variables references are per stop, invalidated at resume), engine userdata through their tag's describe function (an entity shows its simulation ID and persistent ID; a component view its fields read through the view, which is valid because the stop is inside the invocation). Reading never calls a metamethod (raw access only) and never allocates Luau objects except strings for the response, inside a limit-0 protected call.

## Evaluate restrictions

`evaluate` accepts an expression that is a local, upvalue or state field name, optionally followed by `.field` or `[integer]` segments; it is resolved with the same raw reads as `variables`. Anything else — calls, operators, assignments, globals — returns an error response `evaluate reads locals only` ([Z2-N-SCRIPT-463]); no script code runs from the debugger, so the debugger cannot change simulation state.

## Debugger and simulation dispatch

| Effect | Mechanism |
|---|---|
| the stopped world starts no new script invocation | the gate of § "Stop protocol" rule 2, passed before every invocation |
| invocations already running finish | the gate is checked between invocations, never inside one |
| other worlds and non-script nodes continue while unblocked threads remain | the gate is per world; merge, tick-boundary and engine nodes never park |
| the watchdog ignores a stopped VM, and its stopped time never counts | the VM's own `m_bDebuggerStopped`, set before it blocks and cleared after it rebased its start time (§ "Stop protocol" rule 5; Design/SCRIPT/Runtime.md → "Watchdog internals"); running VMs of the world stay watched |
| safepoint counts, random draws and commits are unchanged | a stop sits between safepoints inside the transaction, a park between invocations; commit order is the merge chain's |
| the world's tick cannot complete while stopped | the stopped and parked nodes' merge nodes have not started (§ "Stop protocol" rule 3) |
| no deadlock, whatever the number of blocked threads | § "Stop protocol" rule 7 |
| no lost wake-up | the count changes, the notify and every parker's predicate check happen under the DAP mutex (§ "Stop protocol" rules 2, 5 and 6) |

## Sampling profiler implementation

Development builds: `script.profiler.sample` (a runtime toggle, a development-only configuration key) enables sampling on every VM. Each VM owns a ring of `uSCRIPT_SAMPLE_RING_ENTRIES` (65,536) samples, allocated from the general heap when sampling is first enabled; a sample is up to 32 `Zenith_ScriptSampleFrame { uint32 m_uModule; uint32 m_uLine; uint32 m_uFunctionNameOffset; }` frames read with `lua_getinfo` from the interrupt every `uSCRIPT_SAMPLE_PERIOD` (997) safepoints ([Z2-N-SCRIPT-467]). A dump request (the console command `script.profiler.dump <path>` or a DAP custom request `zenithSampleDump`) collapses the rings of every VM of a world into stack-count pairs and writes a flame-graph JSON (`{ "schema": "zenith2.script-samples", "schemaVersion": 1, "stacks": [ { "frames": ["@game/Combat/Stamina:Each:42", …], "count": n } ] }`) through the development file grant; sampling reads the stack only and never changes a safepoint count or a result.
