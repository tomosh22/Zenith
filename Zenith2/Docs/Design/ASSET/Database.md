# ASSET design: the asset database

This file is part of the ASSET design family; the entry document is `Zenith2/Docs/Design/ASSET.md`. It specifies asset identity (GUIDs, sub-asset identity), the `.meta` importer-settings sidecar as a document, the tool-side asset database `Zenith_AssetDatabase`, scan and reconcile, the dependency graph, and provenance records. The database lives in `Zenith2/Tools/ZenithCook/Internal/Database/`; the byte formats are `Zenith2/Docs/Design/ASSET/Formats.md`.

## Asset identity

### GUIDs

- Every asset source and every sub-asset has one `Zenith_AssetGUID` (a `Zenith_PersistentID`, RFC 9562 version 4), written in the source's `.meta` sidecar, which is tracked in source control beside the source ([Z2-N-CONTRACT-065], [Z2-N-CONTRACT-066]).
- A GUID is generated by `Zenith_GeneratePersistentID` over a `Zenith_RandomSource` created by `Zenith_RandomSource::CreateFromEntropy()` in the tool; a worker that adds a source in a diff writes the `.meta` by hand with a fresh version-4 GUID in the 36-character form.
- **Preset at creation** (`AssignMissingGuidsWithPresets`, `--assign-guids` and the server's `assignGuids` from Stage 4; cross-area rows CT3 (c), CT24 (e)): the cook services build CONTENT's `Zenith_ImportPresetSet` (`Zenith2/Tools/Authoring/Zenith_AuthoringContent.h`) from every live `*.importpreset.json` record of the scan, game and engine roots; for each source receiving a new `.meta`, `Select(importer ID, lower-case extension with the dot, content-root-relative path)` gives the preset GUID written into `preset` and the labels merged into `labels`; `Zenith_AssetPresetChoice { Zenith_StringView m_strSource; Zenith_AssetGUID m_xPreset; Zenith_StringView m_strGlob; }` lists the choice in source byte order (`--assign-guids` prints one line `preset: <source> <guid or none> <glob>` per new `.meta`). The preset is chosen once, at creation, and never inferred afterwards. `AssignMissingGuids` without a set writes `"preset": null`.
- A GUID is never reused: a GUID seen once in a game's database stays reserved in the tracked tombstone list of its content root even after its source is deleted ("Orphaned meta files and tombstones"), and assignment rejects a candidate found in the live index or in any tombstone list the scan read (a second draw; with 122 random bits a collision is a defect report, not a loop).
- The GUID is the only identity of an asset: cooked file names, catalogue keys, references in scenes, prefabs, materials and schemas' `asset<K>` fields, the DDC's asset-scoped inputs and provenance records name the GUID, never a path. Renaming or moving a source together with its `.meta` changes nothing but the logical path.

### Sub-asset identity

- A source that produces several assets (a glTF file with meshes, materials, skeletons and clips; a font with several faces) declares each product with an importer-defined key, stable across reimports of the same content: `<kind prefix>:<name>` (for example `mesh:Body`, `material:Skin`, `anim:Walk`), built by the importer from the source's own names, with the rules of Import.md "Identity preservation on reimport" when names collide or change.
- The `.meta`'s `subAssets` array maps each key to its GUID and kind. On import, a key already present keeps its GUID; a new key gets a new GUID; a key no longer produced stays in the array with `"orphaned": true` (its GUID stays reserved, references to it report a missing sub-asset rather than silently re-binding) until a reference-repair operation (CONTENT's) or a human removes it.
- The source's own GUID names its primary product (the importer declares which key is primary, or none, in which case the source GUID names no cooked asset and is only the identity of the source).
- A **derived product** (Import.md "Derived products") has a GUID its importer computes and no `subAssets` entry; its record is a sub-asset record like any other, removed (never orphaned) when an import no longer declares it (cross-area row WD4).
- An entry may carry owner members beside `key`, `guid`, `kind` and `orphaned` (Formats.md "Sub-asset entries"); they belong to the entry, so they follow its GUID (Import.md "Product members and fingerprints").

### What is an asset source

Every file under a content root (entry document "Content root mapping") is classified by the first matching rule:

| Rule | Classification | `.meta` |
|---|---|---|
| name ends `.meta` | a sidecar | — |
| name begins with `.` (`.zenith-tombstones`, `.migration/`) | skipped: never content ("Scan algorithm" step 1) | — |
| under `Config/` of a game's `Assets` root, or `Internal/Config/` of a library | configuration, merged or copied by PLAT's validators (Cook.md "Configuration merge") | none |
| `*.schema.json` under a `Schemas` root | a schema, compiled by ECS's step into `schemas.zreg` | none (identity is the schema's `stableName`) |
| `*.luau` under a `Scripts` root or a module's `Scripts/` | a script module, compiled by SCRIPT's step (identity is its module path) | none |
| `*.bindings.json`, `tiers.<platform>.json` | PLAT data, validated and copied | none |
| `*.generator.json`, `*.lightbake.json`, `*.lightpage.json` (WORLD's) and `*.terraintile.json` (ENV's), anywhere in a content root | an input-only document: read only through its owner's importer (`OpenInputDocument`, `OpenInputDocumentRelativeTo`), never imported itself, never `COOK_WARNING_UNRECOGNISED_FILE` (cross-area row WD3) | none |
| `*.scene.json` under `Worlds/<W>/Regions/` or `Worlds/<W>/Generated/` of a game's storage root, when `Worlds/<W>/<W>.world.json` exists | an input-only document of that world's importer (row WD21 (a)); this row precedes the importer-suffix row, so `zenith-doc` never claims a region scene | none |
| a file the previous import of a live source recorded as one of its import inputs (`Inputs/<GUID>.txt`: a `.gltf`'s `.bin` buffer, a terrain's tile files) | an import input: hashed by the scan for the reimport check and never imported itself, never warned (cross-area row CT24 (b)); this row follows the importer-suffix row, so a file an importer claims stays an asset source | none |
| `*.importpreset.json` (CONTENT's) | an asset source of the `zenith-doc` importer with no product (Import.md "Importer registry", row CT3 (b)); presets also ship in `Zenith2/Engine/ZenithAssets/Internal/Content/ImportPresets/`, a CONTENT-owned subdirectory of ZenithAssets' engine content root (row CT3 (d)) | required |
| an extension an importer claims (Import.md "Importer registry") | an asset source | required |
| anything else | ignored, with one `COOK_WARNING_UNRECOGNISED_FILE` per file in the report | — |

A `.meta` without its source is an orphaned sidecar ("Orphaned meta files and tombstones").

### Reading and writing meta documents

- A `.meta` is opened with the framework's `Zenith_DocumentMigrator::Open` over its content storage root (`Zenith2/Docs/Design/ASSET/Migration.md → "Reading and writing meta documents through the framework"`): the framework parses it under the JSON limits (the 1 MiB `.meta` cap is ASSET's, checked on the file size first, Formats.md "Meta sidecar schema"), migrates an older envelope and older importer settings in memory, and records the digest. `Zenith_ReadAssetMeta` then checks every key of the schema and keeps every member it does not recognise in place ([Z2-N-CONTRACT-543]).
- Writing an older document back is a migration (preview, backup, journaled write through `PlanMigration` and `ApplyPlan`), never an incidental rewrite; an ordinary sidecar write (a new `.meta`, a settings change) is `Zenith_DocumentMigrator::SaveDocuments` with the canonical bytes and the opened digest.
- A document whose `schemaVersion` or `importer.settingsVersion` is newer than the tool's opens read-only: the cook uses it only if every key it needs parses (`bAllowReadOnly`), and no tool writes it ([Z2-N-CONTRACT-537]).

### Canonical meta form

`Zenith_WriteAssetMetaCanonical` first sorts `subAssets` by key byte order and `labels` by byte order in the meta's document, then calls the framework's `Zenith_WriteCanonicalJson(document, root, Zenith_GetAssetMetaCanonicalSchema(), out)` (`Zenith2/Docs/Design/SCENE/DocumentFramework.md → "Zenith_CanonicalJson header"`; the rule table is `Zenith2/Docs/Design/ASSET/Migration.md → "The meta document type"`). The result: the byte format of `JSON_WRITE_STYLE_PRETTY` (`Zenith2/Docs/Design/CORE/Text.md → "Byte format"`), the envelope keys in the order of Formats.md "Keys", `settings` and each platform object's members in byte order of key, one sub-asset object per element in key order, unknown members re-emitted at their anchored positions ([Z2-N-CONTRACT-543]), `x-` members byte for byte, LF line endings, one trailing LF. Writing a document that was read and not changed reproduces its bytes exactly when they were canonical (`Test_AssetMeta_CanonicalRoundTripIsIdentity`).

### Build cooks never write sources

- The build's cook (`ZenithCook --game … --platform … --out …`, the `<Name>_Content` command) reads the source tree and writes only under `--out`, `${ZENITH_OUT}/AssetDB/` and the DDC root ([Z2-N-ARCH-025]); it never creates or rewrites a `.meta`.
- An asset source without a `.meta` fails the build's cook with `COOK_ERROR_META_MISSING`, naming the file and the command that creates it: `ZenithCook --game <Name> --assign-guids`.
- `.meta` files and tombstone lists are created or changed only by `--assign-guids`, `--fix-duplicate-guids`, `--migrate`, the cook server's `assignGuids`, `setSettings`, `import` and `migrateApply` requests, and a ticket's diff; every tool write of a `.meta` goes through the framework's journaled write (`Zenith2/Docs/Design/SCENE/DocumentFramework.md → "Journaled write"`).

### Zenith_AssetDatabase API

### Records

```cpp
/// @contract enum Zenith_AssetRecordState
/// Ownership: Plain value.
/// Thread affinity: IMMUTABLE.
/// Invalidation: None.
/// Units: None.
/// Errors: None; a value outside the enumerators read from assetdb.zdb discards the file (a rebuild).
/// Version: since Z2 Stage 2. Serialized as uint8 in assetdb.zdb and by name without prefix in the cook server's records.
/// @endcontract
enum Zenith_AssetRecordState : uint8
{
	ASSET_RECORD_STATE_NEW = 1,        // found by this scan, never imported
	ASSET_RECORD_STATE_CURRENT,        // imported; source hash, settings hash and importer version match
	ASSET_RECORD_STATE_DIRTY,          // an import input changed
	ASSET_RECORD_STATE_MISSING_SOURCE, // the .meta exists, the source does not (orphaned sidecar)
	ASSET_RECORD_STATE_TOMBSTONE,      // deleted; GUID reserved
	ASSET_RECORD_STATE_ERROR,          // the last import or scan failed; the error is recorded
};

/// @contract value Zenith_AssetRecord
/// Ownership: Owned by the database; returned by pointer from its Find functions and GetRecords.
/// Thread affinity: OWNER_THREAD of the database; cook workers read the plan's immutable snapshot copies instead.
/// Invalidation: A record pointer and its strings are valid until the next Scan, UpdateAfterImport or Save.
/// Units: Bytes.
/// Errors: None.
/// Version: since Z2 Stage 2. Tool-side; Formats.md "Asset database file" is its serialized form.
/// @endcontract
struct Zenith_AssetRecord
{
	Zenith_AssetGUID m_xGUID;
	Zenith_AssetGUID m_xSourceGUID;             // itself for a source; the source's GUID for a sub-asset
	Zenith_String m_strSubAssetKey;             // empty for a source
	Zenith_AssetKind m_eKind;                   // ASSET_KIND_NONE for a source without a primary product
	Zenith_String m_strSourcePath;              // Zenith2-relative: "Games/Hero/Assets/Characters/Hero.gltf"
	Zenith_String m_strLogicalPath;             // "content:/Characters/Hero.gltf#mesh:Body"
	Zenith_String m_strImporterID;
	uint32 m_uImporterVersion;
	Zenith_Hash128 m_xSourceHash;               // Zenith_Hash128Of the source bytes
	Zenith_Hash128 m_xSettingsHash;             // of the canonical resolved settings (Import.md "Settings resolution")
	Zenith_Hash128 m_xImportKey;                // the import's DDC key (DDC.md "Key inputs")
	uint64 m_ulSourceBytes;
	uint64 m_ulStatCookie;                     // size, modification time and file ID folded: a cache hint only
	Zenith_AssetRecordState m_eState;
	uint32 m_uLastError;                       // Zenith_ImportError when ERROR
	// A source's last successful import's diagnostics (Import.md "Stored diagnostics"), in Report order, at most 256; strings in
	// the database's arena; empty for a sub-asset, a record never imported and a record in ERROR.
	Zenith_Span<const Zenith_StoredImportDiagnostic> m_axImportDiagnostics;
	uint32 m_uImportDiagnosticsDropped = 0;    // that import's Report calls beyond the cap
};
```

| State | Event | Next |
|---|---|---|
| — | scan finds a source with a `.meta` whose GUID is unknown | NEW |
| NEW, DIRTY | import succeeds | CURRENT |
| CURRENT | scan finds the source hash, settings hash, importer version or a declared import input changed | DIRTY |
| any live | import fails | ERROR |
| ERROR | an input changes | DIRTY |
| any live | the source disappears, `.meta` stays | MISSING_SOURCE |
| any live | both source and `.meta` disappear | TOMBSTONE |
| MISSING_SOURCE | the source reappears (or a move is detected) | DIRTY |

### Database file location and rebuild

- The database file is `${ZENITH_OUT}/AssetDB/<Name>/assetdb.zdb` per game (the engine content is scanned into each game's database), written atomically (write `assetdb.zdb.<pid>.tmp`, flush, rename) by `Save` after every scan and import batch, and only by the holder of `assetdb.lock`, which a process tries once at start and, having taken it, holds until exit (the server: for its session); a process that finds the lock held opens the database with `m_bReadOnlyFile`, works on its in-memory copy and never saves it (`Zenith2/Docs/Design/ASSET/Cook.md → "Output tree and database locks"`).
- It is a cache: deleting it loses nothing but time, because every GUID, importer choice and setting is in the tracked `.meta` files, every tombstone is in the tracked tombstone lists, and every hash is recomputed.
- The tombstone lists are tracked files `.zenith-tombstones` at the top of each content storage root — `Zenith2/Games/<Name>/<R>/.zenith-tombstones` for each content root `R`, `Zenith2/Engine/<Lib>/Internal/Content/.zenith-tombstones` for an engine library — in the format of Formats.md "Tombstone list". They live inside content-root directories, so `Games/<Name>/` gains no top-level entry ([Z2-N-ARCH-246]); the scan skips them because their names begin with `.`. `WriteTombstoneLists` (sidecar-writing modes only) re-reads, under the root's writer lock (`Zenith2/Docs/Design/ASSET/Cook.md → "Output tree and database locks"` item 5), the list of every root that gained a tombstone, merges the new lines (sorted, deduplicated) and rewrites it through the storage, whether or not this process holds the database lock; `Save` never writes a list, and a build cook never writes one.
- A file whose magic, version, check or bounds fail is discarded with a warning and rebuilt by a full scan (`Test_AssetDatabase_CorruptFileRebuilds`).

## Scan and reconcile

### Scan algorithm

1. Read every content root's `.zenith-tombstones` (Formats.md "Tombstone list"). Walk every content root (games' roots and the engine content roots of the libraries the game links, Cook.md "Content selection"), depth first, entries in byte order of name, skipping every directory named `Tests`, `Workload`, `Acceptance` or `.migration` at any depth and every `.`-prefixed name (so the `Scripts` content root's `Scripts/Tests/`, which holds SCRIPT's behaviour-state migration fixtures, is never visited, core-doc item X194, while a directory such as `Scripts/Testing/` is); reject a name that is not NFC Unicode (`COOK_ERROR_NAME_NOT_NFC`, checked with the host OS's normalisation test in the tool) or whose logical path fails the virtual-path rules (`COOK_ERROR_BAD_SOURCE_NAME`).
2. Pair each source with `<source>.meta`; classify by "What is an asset source".
3. For each pair, compare the stat cookie with the record's; on any difference, or when the record is new, read the source and compute `Zenith_Hash128Of` of its bytes (the cookie only decides whether to re-hash; a hash decides everything else), and open (`Zenith_DocumentMigrator::Open`) and validate the `.meta` (`Zenith_ReadAssetMeta`).
4. Build the new record set; mark states per "Records"; detect moves ("Rename and move detection"), duplicates ("Duplicate GUIDs") and orphans.
5. Rebuild the logical-path index and check collisions (entry document "Content root mapping").
6. Update the graph's import edges from the records' declared import inputs (read files recorded by the last import) and mark dependents dirty ("Graph maintenance").
7. Return a `Zenith_ScanSummary` (counts per state, the diagnostics list) and `Save`.

The scan is O(files) stats plus O(bytes) hashing of changed files; with no change it hashes nothing.

### Rename and move detection

- A `.meta` whose GUID was recorded at another source path, and whose old path no longer exists, is a move: the record keeps its GUID, takes the new source and logical paths, and becomes DIRTY only if the source hash changed (a pure move re-cooks nothing; the catalogue's logical path changes).
- A source that appears without a `.meta` while a MISSING_SOURCE record has the same source hash is reported as a probable move of a file whose `.meta` was left behind (`COOK_WARNING_PROBABLE_MOVE`, naming both paths); the build's cook fails on the missing `.meta` as always; `--assign-guids` offers to move the orphaned `.meta` onto it (the cook server's `assignGuids` returns the suggestion for EDIT to confirm).
- Reference repair across other documents is CONTENT's (Z2-I-CONTENT-19 … -21); the database supplies the old and new paths and the referrer edges.

### Duplicate GUIDs

- Two `.meta` files (or two sub-asset entries) with one GUID are `COOK_ERROR_DUPLICATE_GUID`, naming both files; the build's cook fails.
- `--fix-duplicate-guids` keeps the GUID on the path the database recorded for it before this scan and gives every other holder a new GUID; with no prior record it keeps the GUID on the byte-order-smallest source path. It reports every change, because references to the copy may now need repair.
- A GUID found in the tombstone list on a live `.meta`, or on a sub-asset entry of a live `.meta`, is accepted (a restored file, or a batch rollback's `restoreSubAssets`) and leaves the tombstones (cross-area row CT22 (f)).

### Orphaned meta files and tombstones

- An orphaned `.meta` (no source) is a warning in the report, never an error: its GUID stays reserved and its dependents report a missing reference at validation.
- Deleting both source and `.meta` moves the record to TOMBSTONE; its GUID (with its last logical path) is added to the `.zenith-tombstones` of the content root the source lived under by the next sidecar-writing tool run, and is never reissued. The build cook keeps the tombstone in its untracked database until then, so it never reissues the GUID either.
- Because the database is untracked, "the next sidecar-writing run" happens only on a machine whose database knew the GUID; a fresh checkout never learns of a deletion made elsewhere. So the tracked list is written where the deletion is made: a diff that deletes an asset source's `.meta` appends, in the same diff, one line `<GUID>` TAB `<last logical path>` to the `.zenith-tombstones` of the content root the source lived under, in the sorted form of Formats.md "Tombstone list" — the rule for every worker ticket and every person deleting assets by hand, checked in review; the editor's deletions go through the cook server, whose `WriteTombstoneLists` writes the line. Deleting a sub-asset (an importer key that disappears from a `.meta`) needs no line: its GUID stays recorded in the `.meta` as an orphaned sub-asset entry until the whole `.meta` goes.
- A cook whose database knew a GUID that is now TOMBSTONE, and whose tracked list lacks it, reports `COOK_WARNING_TOMBSTONE_NOT_TRACKED` naming the list and the exact line to add, so a missed line is visible on the machine that made the deletion; `--assign-guids` writes it (`Test_AssetDatabase_TombstoneLists`).

## Dependency graph

### Edge kinds

`Zenith_AssetEdgeKind` (in "Queries") gives each edge its value, which `assetdb.zdb` stores in an edge's kind byte and the cook server names in its `edges` strings:

| Edge | Value, enumerator, server name | From → to | Recorded by | Used for |
|---|---|---|---|---|
| import input | 1, `ASSET_EDGE_KIND_IMPORT_INPUT`, `importInput` | source → a file it read (a glTF's `.bin`, an image it references) | `Zenith_ImportContext::ReadInput` | import keys; dirty propagation on file change |
| reference (hard) | 2, `ASSET_EDGE_KIND_HARD_REFERENCE`, `hardReference` | asset → asset it needs ACTIVE before its own load | `Zenith_CookContext::DeclareReference(guid, ASSET_DEPENDENCY_FLAG_HARD)` | the catalogue's hard dependencies; runtime load order; reference validation |
| reference (soft) | 3, `ASSET_EDGE_KIND_SOFT_REFERENCE`, `softReference` | asset → asset it names but loads on demand | `DeclareReference(guid, ASSET_DEPENDENCY_FLAG_SOFT)` | the catalogue; reference validation; CONTENT's repair |
| cook input | 4, `ASSET_EDGE_KIND_COOK_INPUT`, `cookInput` | asset → another asset's intermediate or output property its cook reads (a mesh cook reads its materials' texture resolutions) | `Zenith_CookContext::ReadDependencyOutput` | the cook key (the upstream key hash is a key input); ordering |
| settings input | 5, `ASSET_EDGE_KIND_SETTINGS_INPUT`, `settingsInput` | asset → the preset document its settings resolve through | settings resolution | the import key; dirty propagation |

The graph is a DAG for hard references and cook inputs (a cycle is `COOK_ERROR_DEPENDENCY_CYCLE` naming the cycle in GUID order); soft references may form cycles.

### Graph maintenance

- Edges are stored in adjacency arrays sorted by (from GUID, edge kind, to GUID) and rebuilt for a node whenever that node's import or cook runs; edges to unknown GUIDs are kept (and reported by validation).
- Dirty propagation: when a node's import key or cook key changes, every node with a cook-input or settings-input edge to it is marked for key recomputation; propagation walks in topological order and stops at a node whose recomputed key is unchanged, so a change that produces identical output invalidates nothing downstream (Cook.md "Dependency-driven invalidation").

### Queries

```cpp
/// @contract enum Zenith_AssetEdgeKind
/// Ownership: Plain value.
/// Thread affinity: IMMUTABLE.
/// Invalidation: None.
/// Units: None.
/// Errors: None; a kind byte outside 1 … 5 in assetdb.zdb discards the file (a rebuild); an unknown server edge name is
///   COOK_ERROR_PROTOCOL.
/// Version: since Z2 Stage 2. Serialized as uint8 in assetdb.zdb; a value keeps its meaning forever; the edge mask of
///   GetTransitiveDependents has bit (value − 1) per kind.
/// @endcontract
enum Zenith_AssetEdgeKind : uint8
{
	ASSET_EDGE_KIND_IMPORT_INPUT = 1,
	ASSET_EDGE_KIND_HARD_REFERENCE = 2,
	ASSET_EDGE_KIND_SOFT_REFERENCE = 3,
	ASSET_EDGE_KIND_COOK_INPUT = 4,
	ASSET_EDGE_KIND_SETTINGS_INPUT = 5,
};

/// @contract value Zenith_AssetEdge
/// Ownership: A view element of the graph's adjacency arrays.
/// Thread affinity: OWNER_THREAD of the database.

/// Units: None.

/// @endcontract
struct Zenith_AssetEdge { Zenith_AssetGUID m_xFrom; Zenith_AssetGUID m_xTo; Zenith_AssetEdgeKind m_eKind; uint8 m_uFlags; };

/// @contract type Zenith_AssetDependencyGraph
/// Ownership: Owned by Zenith_AssetDatabase; reached through GetGraph.
/// Thread affinity: OWNER_THREAD of the database.

/// Units: None.
/// Errors: TopologicalOrder returns ASSET_DATABASE_ERROR_DEPENDENCY_CYCLE naming the cycle in GUID order and
///   ASSET_DATABASE_ERROR_OUT_OF_MEMORY; the other queries cannot fail (unknown GUIDs give empty spans).
/// Version: since Z2 Stage 2. Tool-side.
/// @endcontract
class Zenith_AssetDependencyGraph
{
public:
	Zenith_Span<const Zenith_AssetEdge> GetOutgoing(const Zenith_AssetGUID& xFrom) const;
	Zenith_Span<const Zenith_AssetEdge> GetIncoming(const Zenith_AssetGUID& xTo) const;
	Zenith_Result<Zenith_Span<const Zenith_AssetGUID>, Zenith_AssetDatabaseError> TopologicalOrder(

		Zenith_Arena& xArena) const;
};
```

## Provenance records

### Provenance record content

Every cooked output (an asset file, a non-asset cooked file) gets one record, written by the cook when it publishes the output (Formats.md "Provenance record lines"):

| Field | Content |
|---|---|
| output | cooked path, output Hash128, bytes |
| asset | GUID, kind, logical path (asset outputs) |
| sources | each source and import-input file: Zenith2-relative path and Hash128 |
| import | importer ID and version, settings Hash128, import key |
| cook | cook step ID and version, cook key, platform |
| toolchain | `uZENITH_ENGINE_COOK_VERSION`, the manifest versions of fastgltf, meshoptimizer, KTX-Software, zlib, zstd and the step's declared tools, the ZenithCook build identity |
| DDC | hit or miss, the store that served a hit (local, shared) |
| content origin | the `.meta`'s `provenance` object verbatim (CONTENT's schema) |

No field carries a time, host name or user name, so provenance is deterministic like the outputs; the cook log carries times.

## Reference defaults in the cook

The cook's scratch type registry holds the game's schemas; an `asset<K>` default must name an asset of kind K the cook will cook, and a default naming none must fail the cook (`Zenith2/Docs/Design/ECS/Schemas.md → "Default values"`). After the scratch registry's `Freeze`, the cook services call `ResolveReferenceDefaults(PROPERTY_TYPE_ASSET, &Zenith_ResolveCookAssetReferenceDefault, &xDatabase)`:

```cpp
// Zenith2/Tools/ZenithCook/Internal/Database/Zenith_AssetDatabase.h
// A Zenith_PfnConstructFromPersistentID over the database (pUserData is the const Zenith_AssetDatabase*).
bool Zenith_ResolveCookAssetReferenceDefault(void* pElement, const uint8* pPersistent, Zenith_TypeID xKind,
	void* pUserData);
```

It decodes the 16 bytes, maps `xKind` with `Zenith_FindAssetKindByTypeID`, and returns true when the database holds a live record (state NEW, CURRENT or DIRTY) of that GUID and kind, false otherwise; in both cases it writes the null handle into `pElement`, because the cook has no asset registry and no cook step dereferences an asset handle (steps read a default's persistent ID from `Zenith_PropertyInfo::m_xDefault`). A false result is ECS's `SCHEMA_ERROR_BAD_DEFAULT` for that field, which the cook reports as `COOK_ERROR_STEP_FAILED` of the `ecs.schemas` step naming the schema, the field and the GUID.

## Database errors

```cpp
// Zenith2/Tools/ZenithCook/Internal/Database/Zenith_AssetDatabase.h
/// @contract enum Zenith_AssetDatabaseError
/// Ownership: Plain value.
/// Thread affinity: IMMUTABLE.
/// Invalidation: None.
/// Units: None.
/// Errors: None; the cook error each maps to is the paragraph below this block.
/// Version: since Z2 Stage 2. Tool-side; values are appended, never renumbered.
/// @endcontract
enum Zenith_AssetDatabaseError : uint8
{
	ASSET_DATABASE_ERROR_IO = 1,
	ASSET_DATABASE_ERROR_META_PARSE,             // the key path and message are logged
	ASSET_DATABASE_ERROR_META_SCHEMA,
	ASSET_DATABASE_ERROR_META_NEWER_VERSION,
	ASSET_DATABASE_ERROR_META_MISSING,
	ASSET_DATABASE_ERROR_DUPLICATE_GUID,
	ASSET_DATABASE_ERROR_NAME_NOT_NFC,
	ASSET_DATABASE_ERROR_BAD_SOURCE_NAME,
	ASSET_DATABASE_ERROR_LOGICAL_PATH_COLLISION,
	ASSET_DATABASE_ERROR_DEPENDENCY_CYCLE,
	ASSET_DATABASE_ERROR_UNKNOWN_IMPORTER,
	ASSET_DATABASE_ERROR_READ_ONLY,              // a sidecar write without m_bWriteSidecars
	ASSET_DATABASE_ERROR_FILE_CORRUPT,
	ASSET_DATABASE_ERROR_OUT_OF_MEMORY,
	ASSET_DATABASE_ERROR_JOURNAL_PENDING,        // an unrecovered framework journal at a storage root (Migration.md "Recovery before a cook")
	ASSET_DATABASE_ERROR_STALE_DOCUMENT,         // the .meta changed since it was opened (DOCUMENT_ERROR_STALE_PLAN)
	ASSET_DATABASE_ERROR_DOCUMENT,               // any other Zenith_DocumentError; its code is logged and carried in the cook error's detail
	ASSET_DATABASE_ERROR_TOMBSTONES_INVALID,     // a tombstone list line does not parse
	ASSET_DATABASE_ERROR_UNKNOWN_OUTPUT,         // a provenance query matched no output
};
constexpr const char* Zenith_ToString(Zenith_AssetDatabaseError eError);
```

Each maps onto a `COOK_ERROR_*` (Cook.md "Cook errors") at the cook's boundary ([Z2-N-CONTRACT-463]): one to one by name where a cook error of the same name exists; `READ_ONLY`, `FILE_CORRUPT` and `UNKNOWN_OUTPUT` to `COOK_ERROR_IO`-class internal failures logged with the database code; `JOURNAL_PENDING` and `TOMBSTONES_INVALID` to `COOK_ERROR_GAME_INVALID` (exit 3); `STALE_DOCUMENT` to `COOK_ERROR_META_CHANGED`; `DOCUMENT` to `COOK_ERROR_IO` with the document error code in the detail.
