# CINE playback

## Scope of this file

This file specifies how a cinematic plays inside a world: the world record, the systems and their declared access, every command playback, the instance state machine, asset binding and preparation, the pre-cinematic snapshot and its restore, the evaluation of each track kind, blending, seeking, the determinism rules, the save participant, the lifecycle listener, the tick-boundary handler, world transition and shutdown, and the memory consumer. It also specifies the two per-world structures that carry work across a sync point or a tick boundary: the **outbox** (events and caption cues, with the tick and phase that decide when they are emitted) and the **side work** of an instance (records a playback cannot make itself, which the next `Cinematics.Evaluate` makes). The public types are in `Zenith2/Docs/Design/CINE/PublicAPI.md`; the cooked data the evaluation reads is in `Zenith2/Docs/Design/CINE/Formats.md`. The lifecycle contract this file implements is `Zenith2/Docs/Architecture/LifecycleCommands.md` → "Cinematic start, interrupt and skip"; the phases are `Zenith2/Docs/Architecture/FramePhases.md` → "The twelve phases".

## Playback model

A cinematic is a cooked sequence (`Zenith_Cinematic`) played by an **instance** in one world. An instance binds up to 64 entities to the sequence's named binding slots, keeps a sequence time and a blend weight, and every tick from the tick after Begin writes the outputs of its tracks into the world: local transforms and the physics weight through arbitrated writes in phase 6 with `WRITER_SOURCE_CINEMATIC`, ANIM slots and AUDIO, VFX and other module commands through command records, ECS events and caption cues through the event queue, and lens, lighting and other reflected properties through `SetProperty` commands. Nothing a cinematic does reaches the world except through those four channels, so every effect is a recorded, replayed and saved value (Z2-D-019).

Time is integer. A sequence time is a count of microseconds; the instance keeps it scaled by the tick rate so that a tick at any rate advances it exactly ("Time arithmetic"). A weight is the ratio of two integers, computed once per tick in IEEE single precision.

Worked tick timeline of a skip (the start of `Zenith2/Docs/Design/GAME/PhaseContract.md` → "Scenario SkipCinematicMidBlend", 60 Hz, sequence resident and prepared by an earlier `Cinematics.Preload`):

| Tick, point | What happens |
|---|---|
| 10, phase 2 | a script records `Cinematics.Start` (bindings A, B, camera C; blend-in 0.25 s) |
| 10, sync after phase 2 | "Start playback": the sequence is resident and prepared, so "Begin" runs inline: snapshot of A, B, C; state `BLENDING_IN`, time 0, weight 0, `m_ulBeginTick = 10`; `LIFECYCLE_EVENT_CINEMATIC_START` once with a null entity and once per bound entity; `Zenith.Cinematics.Started` queued in the outbox (queue tick 10, queue point 2, so emitted in tick 10) |
| 10, phase 6 | the Begin tick: `Cinematics.ApplyTransforms` writes nothing for the instance (tracks write from the tick after Begin, `Zenith2/Docs/Architecture/LifecycleCommands.md` → "Cinematic start, interrupt and skip"), so the gameplay writers keep A, B and C this tick |
| 10, phase 8 | `Cinematics.EmitEvents` emits `Started`; delivered in phase 9 of tick 10 |
| 11, phase 1 | `Cinematics.Evaluate`: time 16,666 µs (scaled 1,000,000 / 60), weight 1/15; ANIM `PlaySlot` for sections starting in [0, 16,666]; events of keys in [0, 16,666] queued |
| 11, phase 6 | transforms at weight 1/15 |
| 12, phase 1 | weight 2/15 |
| 12, phase 2 | the script records `Cinematics.Skip` |
| 12, sync after phase 2 | "Skip playback": end state evaluated; `fireOnSkip` events queued (queue point 2); the fire-on-skip command keys and the audio stops become side work; `LIFECYCLE_EVENT_CINEMATIC_SKIP` dispatched; state `ENDED` (reason SKIPPED), `m_ulEndTick = 12` |
| 12, phase 6 | the end state is written at weight 1 (skip-applied bit; it wins phase 6's arbitration this one tick) |
| 12, phase 8 | the `fireOnSkip` events and `Ended` are emitted; delivered in phase 9 of tick 12 |
| boundary 12→13, step 2 | "Tick-boundary handler": restore-flagged properties written back from the snapshot; snapshot block freed; state `RELEASED`; the side work and the instance record stay |
| 13, phase 1 | `Cinematics.Evaluate` records the side work of the released instance into its side buffer: the fire-on-skip command keys in timeline order, `Audio.StopInstance` for every audio instance it posted, and a caption cancel for every caption it queued; the side work is cleared at the merge |
| 13, phase 6 onwards | no CINE writer writes any row |

Worked timeline of a natural end (tick e − 1 wrote weight 1/15; blend-out 0.25 s):

| Tick, point | What happens |
|---|---|
| e, phase 1 | `Cinematics.Evaluate`: blend elapsed reaches the blend-out, weight 0; it records `Cinematics.End` (reason `COMPLETED`) |
| e, sync after phase 1 | "End playback": state `ENDED`, `m_ulEndTick = e`; `LIFECYCLE_EVENT_CINEMATIC_END` with a null entity and per bound slot; side work STOP_AUDIO and CANCEL_CAPTIONS set; `Ended` queued (queue point 1) |
| e, phase 6 | **the end tick is written** ("End tick"): restore-flagged properties at their snapshot bits, unflagged properties at the held value; no gameplay writer of those rows wins in tick e |
| e, phase 10 | `Cinematics.ApplyLate` records the end-tick values of lens, lighting and property tracks |
| boundary e→e+1, step 2 | the restore writes the snapshot bits, identical to what tick e wrote; state `RELEASED` |
| e + 1, phase 1 | `Cinematics.Evaluate` records the side work |

### Instance block

One block of the snapshot pool per begun instance, allocated by "Begin" and freed by the restore, holding five runs in this order, each 16-byte aligned:

| Run | Count field | Entry | Read by |
|---|---|---|---|
| snapshot entries | `m_uSnapshotEntries` | "Pre-cinematic snapshot" step 3 | blending (the base B), the restore |
| take-over bases | `m_uTakeOverBases` | `{ u32 snapshot entry index; u32 value bytes; value }` | blending during the blend-in of a taken-over entity only (an active holder's, or an ended holder's, "Take-over of a bound entity") |
| late cache | `m_uLateEntries` | `{ u16 track; u16 property slot; u16 value bytes; u8 valid; u8 reserved; 16 value bytes }` (24 bytes), one per (track, written late property) the sequence declares (`Zenith_Cinematic::GetLatePropertyCount`) | `Cinematics.ApplyLate` ("Cinematics.ApplyLate") |
| end state | `m_uEndStateEntries` | `{ u32 snapshot entry index; u32 value bytes; value }`, one per arbitrated written entry | tick-boundary step 2.1 (a skip played after phase 6) |
| prefetch bits | `m_uPrefetchBits` | one bit per section of the sequence (≤ `uCINE_MAX_SECTIONS`, 65,536, so ≤ 8 KiB) | "Cinematics.Evaluate" step 7 |

The block's size is computed before it is allocated, so a limit breach fails the start before any allocation ("Pre-cinematic snapshot" step 5).

### Outbox

`Zenith_CinematicOutbox` holds the events and caption cues CINE emits, in storage order. Storage is `uOutboxCapacity` entries of 288 bytes: queue tick (8), queue point (1), source (1: 0 `Cinematics.Evaluate`, 1 playback, 2 tick-boundary handler), payload bytes (2), reserved (4), event type ID (8), instance ID (8; 0 for a start outcome with no instance), payload (256, the reflected event value). Entries are appended at the end and removed only by `Cinematics.Evaluate`'s step 0 (compacting in order), so an entry's storage position is stable from `Cinematics.EmitEvents` of tick t until the removal at the next Evaluate: between them only appends happen (the playbacks after phases 8 to 10 and the tick-boundary handler).

- **Queue point.** 0 for an entry `Cinematics.Evaluate` queues in phase 1 (committed by its merge), k for an entry a playback queues at the sync point after phase k (1 … 10). The tick-boundary handler queues with queue tick = the tick starting and queue point 0.
- **Emission tick.** An entry is due in the tick `queue tick` when its queue point is ≤ 7, and in `queue tick + 1` when its queue point is 8, 9 or 10, because `Cinematics.EmitEvents` runs in phase 8 ([Z2-N-ARCH-478]).
- **Emission.** `Cinematics.EmitEvents` of tick t emits every entry whose emission tick is ≤ t and that is still stored, in emission groups ("Cinematics.EmitEvents"); an entry whose group the merge rejected stays stored and is emitted again at t + 1, before any later entry of its instance.
- **Removal.** `Cinematics.Evaluate` of tick t, before anything else, removes exactly the entries whose acceptance bit `Zenith.Cinematics.Emission` holds for tick t − 1 ("Emission acceptance"), and compacts the storage in order. An entry queued after phase 7 of tick t − 1 has emission tick t, was not emitted at t − 1, so it stays and is emitted in tick t; an entry emitted and accepted is removed exactly once; an entry emitted and rejected is neither removed nor lost.
- **Instance reservation.** Every instance record holds `m_uOutboxReserve` reserved entries for the entries a playback or the handler may still queue for it: set to 10 at the instance's allocation (start playback step 3) — one start outcome (`Started` or `StartFailed`), one `Ended` and at most `uCINE_MAX_FIRE_ON_SKIP_KEYS` (8) fire-on-skip events, the only entries a playback or the handler queues for an instance (the cook and load limit L9 bounds the fire-on-skip keys). Each such queue moves one entry from the reservation into the store (decrement, then append). **Order rule:** a playback that moves an instance to `ENDED` or `RELEASED` (the skip, the End playback, a take-over's end of P, a cancel in `BINDING` or `PREPARING`, a binding failure in the start playback or the publication handler, the restore's cancel of re-cooked content) first queues every entry it owes from the reservation, in the order its steps list them, and sets `m_uOutboxReserve = 0` as its last action, because no further playback entry can follow; a queue that finds the reservation at 0 is a `ZENITH_ASSERT` that the order rule makes unreachable.
- **Admission.** With S the stored count and Q the sum of every record's `m_uOutboxReserve`:
  1. `Cinematics.Evaluate` stages an entry (a track item, a side-work caption event, a seek's caption event; "Side work", "Seeking and scrubbing") only while S plus the entries it staged this run is below `uCINE_MAX_EVENTS_PER_TICK` (256). A track item it cannot admit stops the instance's item processing for the tick ("Cinematics.Evaluate" step 8); a side buffer whose staged events do not all fit is not built this tick and its side work stays (`cine.events.deferred_delta` + 1).
  2. The start playback, once it holds a ticket entry, admits a start only when `uOutboxCapacity − S − Q` ≥ 10 while the pool has a free record (the start may allocate an instance), or ≥ 1 while it is full (the start can only fail `CINEMATIC_ERROR_INSTANCE_LIMIT`, one `StartFailed`); otherwise the start is dropped at step 0 exactly like a ticket-table overflow ("Start playback" step 0), its ticket entry released, counted in `cine.commands.outbox_full_delta`.
  3. Every other playback and handler entry comes from its instance's reservation.
- **Proof of the bound.** The claim is the invariant **S + Q ≤ `uOutboxCapacity`, holding after every append and every reservation change**; then every append finds a free entry, so the store's append is a `ZENITH_ASSERT` that no input can reach. It holds initially (S = Q = 0) and is preserved by each of the only four changes: (i) an Evaluate admission appends only while S plus the run's staged entries is below 256, so after Evaluate's merge S ≤ 256 and, because Q ≤ 10·M (at most M records, each reserving at most 10), S + Q ≤ 256 + 10·M < `uOutboxCapacity`; (ii) a playback or handler entry moves one unit from Q to S (the order rule keeps Q ≥ 0), leaving S + Q unchanged; (iii) admission rule 2 admits a start only when it leaves room for what the start may add (10 for an allocation, 1 for a failure before allocation), so S + Q ≤ `uOutboxCapacity` after it; (iv) removals and the zeroing of a reservation only decrease S + Q. The restore rebuilds the store with the running configuration's capacity, which is at least the saved one ("Save and restore"), so the invariant holds from the first tick after a load. **No drop without rejection:** while no emission group is rejected, every stored start outcome without an instance is emitted and removed within two ticks of its queue, inside its ticket's three-tick window, so when a start holding its own ticket entry reaches rule 2, F (those outcomes) ≤ 63, belonging to the other ticket entries; with a free record I ≤ 10·(M − 1) (I: the records' reservations plus their stored entries), so `uOutboxCapacity − S − Q` ≥ 256 + 10·M + 64 − 256 − 10·(M − 1) − 63 = 11 ≥ 10, and with a full pool ≥ 64 − 63 = 1. Because step 0 takes the ticket entry first, a 65th start in the window is a ticket overflow, never an outbox drop, so only consecutive emission rejections can make rule 2 drop a start, and the drop is counted and deterministic. `Test_CinematicPlayback_OutboxBound_SixtyFourSkipsOneTick` (M = 64, 64 instances each skipped in one tick with 8 fire-on-skip keys) asserts no assert, every event delivered once and S + Q ≤ 960.
- **Bound and progress.** The world's event queue row `Z2-B-GAME-003` bounds what `EmitEvents` emits per tick; CINE emits at most `uOutboxCapacity` entries in one tick (480 at the default M). Progress needs that row's value to admit at least one emission group, `uCINE_EMISSION_GROUP_ENTRIES` (64) events, beyond the peak of the other phase-8 emitters; otherwise an instance's first group could be rejected in every tick. CINE states this condition as its requirement on the pending row (`Zenith2/Docs/Design/CINE.md` → "Rows CINE is measured against"), for GAME's producer to measure against.

### Emission acceptance

`Zenith.Cinematics.Emission` is a second CINE world resource (owned by `PHASE_TRANSFORM_PROPAGATION`, phase 8), so that the main world record keeps its single phase-1 owner while `Cinematics.EmitEvents`' merge function records what it accepted:

```cpp
struct Zenith_CinematicEmission        // internal; Internal/World/Zenith_CinematicOutbox.h
{
	uint64 m_ulTick = 0;              // the tick whose EmitEvents merge wrote the bits; 0 none
	uint64 m_aulAccepted[15] = {};    // bit p: the entry at storage position p was emitted and its group accepted
};                                     // 128 bytes: 960 bits cover uOutboxCapacity at M = 64
```

`Cinematics.EmitEvents`' merge writes it at tick t ("Cinematics.EmitEvents"); `Cinematics.Evaluate` reads it at step 0 of tick t + 1 and acts only when `m_ulTick` is t (otherwise it removes nothing). The resource is not saved: a save in phase 11 of tick t first applies to its copy what step 0 of t + 1 would do with the bits — every caption list entry whose cue has its bit set is written with expiry `t + duration ticks` (the last accepted cue of that source ID, in storage order, sets it) — and then writes only the entries whose bit is clear ("Save and restore"); a restore sets `m_ulTick = 0`. The restored world therefore expires those captions at the same tick as the uninterrupted run (`Test_CinematicSave_AcceptedCueExpiry_Applied`).

### Bound set

`m_axBound` is the single source of "the sequence is bound in this world": an entry `Zenith_CinematicBoundSequence { Zenith_PersistentID m_xGUID (16); uint64 m_ulContentHash (8); Zenith_CinematicTemplate* m_pxTemplate (8); uint32 m_uHolders (4); uint32 m_uReserved (4) }` (40 bytes) exists for every sequence GUID whose binding was published successfully in this world and that something still holds. Its holders are the instance records holding the GUID's handle (`RELEASED` records included) and the preload entry of the GUID (one holder however many pins it has). The publication handler adds the entry with one holder per current waiter ("Asset binding" step 3); a start playback of a bound GUID adds a holder; a freed record and a preload entry whose last pin drops each remove one, and the entry, with its template, is freed at 0. Capacity 96 = 64 records + 32 preloads, the most distinct GUIDs that can be held at once, so the table never fills. A failed publication creates no entry (a later start of the GUID collects a new need). The entry is saved with its GUID, content hash and holder count, and `RestoreSection` rebuilds its template from the resident asset ("Save and restore"), so a start after a load begins inline exactly when the uninterrupted run's did (`Test_CinematicSave_BoundSet_StartBeginsInlineAfterLoad`).

### Side work

A playback cannot record commands ("Command playback"), and the restore releases an instance at the tick boundary before the next `Cinematics.Evaluate`. Records that a playback or a restore needs are therefore described in the instance record (outside the instance block, so they survive the restore) as side work, and the next `Cinematics.Evaluate` makes them, whatever the instance's state, `RELEASED` included:

| Bit of `m_uSideWork` | Set by | Records and events made by the next Evaluate (in this order) |
|---|---|---|
| `SKIP_KEYS` (0) | "Skip playback" | every command key with `fireOnSkip` whose time is in `(m_ulSideSkipFromUs, D]`, in timeline order (fire-item key order, "Cinematics.Evaluate"), each built from its template |
| `STOP_AUDIO` (1) | "Skip playback", "End playback", "Interrupt playback", "Take-over of a bound entity" (P ends) | for every audio list entry of the instance: `Audio.StopInstance` (`AUDIO_STOP_MODE_FADE`, `m_uSideAudioFadeMs`) when the entry is live (flag bits 2 and 3 clear); then the entry is removed (staged) |
| `CANCEL_CAPTIONS` (2) | the same | one `Zenith.Runtime.CaptionCancelEvent` per caption list entry whose expiry tick is above t and that is not cancelled by presentation; the list is emptied, marked entries included (staged) ("Subtitle tracks") |
| `STOP_TAKEN_OVER_SLOTS` (3) | "Take-over of a bound entity" | `Zenith_RecordStopSlot` (blend-out = the taking instance's blend-in) for every animation section of the instance active on a slot flagged stop-slots pending |
| `PAUSE_PRESENTATION` (4) | "Rate pause and resume playback" (`Pause`, or a rate that leaves 1) | `Audio.StopInstance` (50 ms fade) for every live time-locked audio list entry, which keeps its entry with flag bit 2 set (staged); for every caption list entry whose expiry tick is above t and that is not already marked, a cancel, and the entry is kept marked cancelled by presentation (source-ID bit 63 set, expiry 0; staged) |
| `RESUME_PRESENTATION` (5) | "Rate pause and resume playback" (`Resume` or a rate returning to 1, while the rate is 1); "Save and restore" (bit 16) | skipped whole when `STOP_AUDIO` is also set, when content-changed is set, or when the instance is `ENDED` or `RELEASED`; while the instance is `PAUSED` only step (1) for flag-bit-3 entries runs; otherwise: (1) for every audio list entry with flag bit 3, and, when `m_uRateQ16 == uCINE_RATE_ONE_Q16`, every entry with flag bit 2: a fresh post serial, `Audio.PostEvent` or `Audio.PlayDialogue` with the fresh deterministic ID, then `Audio.SeekInstance` of that ID to `(s_cur − sectionStart) / 1,000` ms when it is above 0, the entry's native ID, serial and flag bits 2 and 3 updated (staged) ("Audio tracks"); rate-presentation-stopped is cleared by the acceptance of the side buffer that re-posted the bit-2 entries; (2) the caption re-queue of "Subtitle tracks" |
| `REQUEUE_CAPTIONS` (6) | "Rate pause and resume playback" (a rate change between two rates both above 0, a `Resume` at a rate above 0 other than 1) | skipped when `CANCEL_CAPTIONS` is also set or the instance is `PAUSED`, `ENDED` or `RELEASED`; otherwise the caption re-queue of "Subtitle tracks" |

**Consumption.** A side-work bit is consumed — cleared — by the acceptance of the side buffer that ran it, whether the bit acted fully, partly (`RESUME_PRESENTATION` while `PAUSED`) or not at all (a skip rule); it is never left set by a skip rule, so a `RELEASED` record's side work always empties and the record is freed. A content-changed instance's `SKIP_KEYS` is discarded unbuilt (the template it would read is gone, "Save and restore"), consumed like any other bit and counted with the instance's `cine.save.content_changed` log.

The side records and events of instance index i are recorded into `Commands(0, uCINE_SIDE_ORDINAL_BASE + i)` (`uCINE_SIDE_ORDINAL_BASE` = 1), so every side buffer merges before every tick buffer (`Commands(0, uCINE_TICK_ORDINAL_BASE + i)`, `uCINE_TICK_ORDINAL_BASE` = 65) and both in instance order. Everything a side buffer changes in the world record is staged with it and committed only when the merge accepts that side buffer: the cleared side-work bits, the side events appended to the outbox in order, the audio list removals of `STOP_AUDIO` and `STOP_TAKEN_OVER_SLOTS` and the flag, ID and serial updates of `PAUSE_PRESENTATION` and `RESUME_PRESENTATION`, the post serial, the caption list changes, presentation-resume and rate-presentation-stopped cleared. A rejected side buffer commits none of it and keeps the bits for the next tick ("Cinematics.Evaluate" merge), and the next tick rebuilds the same records from the same state. A side buffer holds at most 8 command keys + 256 stops + 256 posts + 256 seeks for one instance (776 records, within `uCINE_MAX_COMMANDS_PER_INSTANCE_TICK` × 2) and at most 80 events (16 cancels of `PAUSE_PRESENTATION` or `CANCEL_CAPTIONS`, 16 cancels and 16 cues of each of `RESUME_PRESENTATION` and `REQUEUE_CAPTIONS`, with caption overlap at most 16 by the cook rule `cine.cook.caption_overlap`), within the outbox admission of 256.

A `RELEASED` instance's record is freed only when its ticket window has passed, its side work is empty **and** no outbox entry carries its instance ID; until then it holds its sequence handle (the side records are built from the sequence's templates) and its holder in the bound set.

Memory: with the defaults the fixed part of the record is 72 KiB of instances, 135 KiB of outbox, 32 KiB of audio list and about 14 KiB of tables (tickets, player starts, preloads, needs, the bound set), about 253 KiB, plus the 1 MiB snapshot pool and the templates; at M = 64 it is about 632 KiB. All of it counts toward `Z2-B-CINE-001`.

Each system is added with `Zenith_SystemDesc` and declared through `Zenith_SystemBuilder` (`Zenith2/Docs/Design/ECS/SystemAPI.md` → "Zenith_System header"); the name carries the world suffix `@W<tag>` that the registry adds. **Own-row writes.** A CINE system writes a component row it reaches by handle (a bound entity, a player row of a pending autostart) only as the invocation's current entity, because those columns are own-row-only for it (`Zenith2/Docs/Design/ECS/Queries.md` → "Own-row and any-row reads" step 3: `Zenith.LocalTransform` 1–3 is also written in phase 6 by `Physics.SyncTransforms`, and `Zenith.Cinematics.Player` 8–10 by `Cinematics.Evaluate` itself, so `GetChunkOfEntity` returns those columns null for any entity other than the current one). For each such entity E, in the order given below, the system first opens E's logical invocation with `xContext.Commands(E's simulation ID, uCINE_CURRENT_ORDINAL)` (`uCINE_CURRENT_ORDINAL` = 0), which makes E current, then calls `GetChunkOfEntity(slot, E, uRow)` with the slot that declares the write and writes row `uRow` only. A `GetChunkOfEntity` error (a stale handle, an entity outside the slot's query) skips that entity's write for the tick and counts `cine.commands.no_row_delta`.

The call that makes an entity current is ECS's (`Zenith2/Docs/Design/ECS/SystemAPI.md` → "The current logical invocation", row CN24 answered): the logical invocation most recently opened through `Zenith_SystemContext::Events(ulSimulationID)` or `Commands(ulSimulationID[, uInvocationOrdinal])` is current, and `GetChunkOfEntity` returns that entity's own-row-only columns non-null. CINE opens `Commands(sim, 0)` and records nothing into it for `Cinematics.ApplyTransforms` (an empty buffer has zero demand at the merge); `Cinematics.Evaluate`'s `Commands(playerSimID, 0)` is the autostart buffer it already uses.

Declared access:

| `Query` | `m_xPlayerSlot`: `Zenith_QueryDesc{ "Cinematics.Players", { { Zenith.Cinematics.Player, QUERY_TERM_WITH, {1, 2, 3, 4, 5, 6, 11}, false }, { Zenith.Cinematics.Player, QUERY_TERM_WITH, {8, 9, 10}, true } } }` (one type named twice with the same operator, which "Query compilation" step 1 admits; property 7 is a container and never a view column, so the start playback reads it with `ReadContainer`) |

| `ConsumesMergeCapacity` | its merge function allocates completion IDs, issues asset loads and applies capacity acceptance |

Buffers: the side buffer `Commands(0, 1 + i)` and the tick buffer `Commands(0, 65 + i)` of the instance with index i in ascending instance ID ("Side work"), and the autostart buffer `Commands(playerSimulationID, 0)` of each player row it writes or autostarts. The merge order of CINE's records is therefore every side buffer in instance order, every tick buffer in instance order, then the autostarts in ascending player simulation ID (`Zenith2/Docs/Design/ECS/SystemAPI.md` → "Zenith_SystemContext header").

Body, per tick t (complexity O(I · (N log T + R)) for I instances, N fire items, T tracks and R records written):

0. **Housekeeping.** Write `GetSystemOrder()` to `m_uEvaluateSystemOrder` and t to `m_ulCurrentTick`. If `Zenith.Cinematics.Emission`'s `m_ulTick` is t − 1: for every stored caption cue entry whose acceptance bit is set, in storage order, set the expiry tick of its caption list entry (matched by instance ID and source ID; when two accepted cue entries carry one source ID, the later one in storage order sets it, and a marked entry is not touched) to `(t − 1) + duration ticks` (UI set the cue's start tick when it was delivered in phase 9 of t − 1); then remove every entry whose bit is set and compact ("Outbox"). Remove every caption list entry whose expiry tick is ≤ t.
1. **Player autostart.** For every `Zenith.Cinematics.Player` row of `m_xPlayerSlot` in ascending simulation ID with `PlayOnStart`, a non-null `Sequence`, `State == NONE`, `Instance == 0` and no player-start entry for its entity, while `m_axPlayerStarts` has a free entry: open the row's autostart buffer `Commands(simID, 0)` (the row is current, so its columns are its own row), record `Cinematics.Start` into it with `uCINE_START_FLAG_FROM_PLAYER`, the row's entity in `m_xPlayer`, its blends, rate, loop flag and `VoiceLocale` (property 11) (the bindings are read by the start playback, "Start playback" step 4), and stage the player-start entry {entity, simulation ID, returned ticket, t} with that buffer. The node writes no column here: the entry is committed only when the merge accepts the autostart buffer, so a rejected buffer leaves the row `NONE` with no entry, and it autostarts again at t + 1 (`Test_CinematicPlayback_PlayerComponent_AutostartsOnce`). A row beyond the 64 entries waits for the next tick.
2. **Player outcomes.** For every player-start entry in ascending player simulation ID: make the player current (`Commands(simID, 0)`), `GetChunkOfEntity(m_xPlayerSlot, player, uRow)`, then — when the start's ticket entry exists and succeeded, write `Instance` = the instance ID and remove the entry; when it exists and failed, write `State = CINE_STATE_ENDED`, `LastError` = the error code and remove the entry; when it does not exist and t > record tick + `uCINE_TICKET_WINDOW_TICKS` (the start was dropped at its step 0, so no ticket entry will ever exist), write `State = CINE_STATE_ENDED`, `LastError = CINEMATIC_ERROR_TICKET_EXPIRED` and remove the entry; otherwise leave it. A player whose entity no longer resolves has its entry removed. Then, for every row of `m_xPlayerSlot` whose `Instance` names an instance record of the world, write `State` = the instance's state (`RELEASED` once released); `State` therefore mirrors the instance from the Evaluate after the start's playback. A row with `State != NONE` never autostarts again, so a failed or expired autostart is never retried, and no entry can wait for ever.
3. **Drain asset completions** of the loads issued by earlier merges, and complete abandoned needs ("Asset binding" steps 2 and 4).
4. **Side work.** For each instance with `m_uSideWork ≠ 0`, in ascending ID, whatever its state: build its side records and events ("Side work") into its side buffer, staging every world-record change with it; a side buffer whose events do not fit the outbox admission is not built and its bits stay.
5. **Per instance by state** ("Instance state machine"), in ascending ID: `BINDING` collects its needs; `PREPARING` checks readiness and either records `Cinematics.Begin` into its tick buffer or counts the wait; `BLENDING_IN`, `PLAYING`, `BLENDING_OUT` advance (step 6); a content-changed instance records `Cinematics.End` with reason `FAILED` and evaluates nothing else; `PAUSED`: (a) a pending seek is applied with "Seeking and scrubbing" steps 1 to 6 in their paused form (slots, the audio list, the caption list, fire-on-seek keys, the cut, the time) into the tick buffer, with no advance; (b) for every animation section active at s_cur, `Zenith_RecordSetSlotTime` to `offset + (s_cur − sectionStart) × section rate` seconds, so ANIM's slot holds the paused (or just sought) time instead of advancing; (c) `m_iVideoPauseOffsetUs` advances by `(1,000,000 + H / 2) / H` µs ("Video tracks"); it evaluates no other fire item; `ENDED` and `RELEASED` are skipped (their side work was handled in step 4).
6. **Advance** (an instance in `BLENDING_IN`, `PLAYING` or `BLENDING_OUT`). An instance in `BLENDING_OUT` whose end reason is `INTERRUPTED` or `FAILED` advances its time and weight and its continuous tracks (transform, camera, property, physics weight) are evaluated at the advancing s_cur by ApplyTransforms and ApplyLate, but it processes no fire item: step 6.6 sets `m_ulNextItemKey = (s_cur + 1) << 26` (staged) and records nothing, so no section starts or ends, no key fires, no caption is queued and no prefetch is made (step 7 skips it too). The interrupt has already stopped its audio and captions and ANIM blends its cinematic slots out on INTERRUPT (`Zenith2/Docs/Design/ANIM/Runtime.md` → "Lifecycle listener"), so a fire item there would restart what the interrupt ended (`Test_CinematicPlayback_InterruptedBlendOut_FiresNothing`). A `COMPLETED` blend-out is unaffected: its time is clamped at D, past every item.
   1. A pending seek is applied first ("Seeking and scrubbing"), then the advance continues from the seek target.
   2. `m_iPrevTimeScaled = m_iTimeScaled`; advance `a = (1,000,000 × m_uRateQ16 + 32,768) >> 16`; `m_iTimeScaled += a`.
   3. Duration D (µs) scaled `D·H`. If `m_iTimeScaled ≥ D·H`: with `uCINE_START_FLAG_LOOP`, wrap (`m_iTimeScaled −= D·H`; the item window becomes `[next, D] ∪ [0, s_cur]`, wrap-pending set until the pre-wrap part is processed); without it, clamp to `D·H` and, unless already `BLENDING_OUT`, enter `BLENDING_OUT` with reason `COMPLETED` (`m_fHoldWeight = m_fWeight`, `m_iBlendElapsedScaled = 0`). One subtraction suffices, because a looping instance has `D·H ≥ 8,000,000` ("Start playback" step 1), the largest advance a (rate 8), so after one wrap `m_iTimeScaled < D·H`.
   4. Weight. `BLENDING_IN`: `m_iBlendElapsedScaled += 1,000,000`; `w = min(1, float(double(e) / double(b)))` with e the elapsed and b `m_iBlendInScaled`; at w = 1 the state becomes `PLAYING`. `PLAYING` holds w = 1. `BLENDING_OUT`: `m_iBlendElapsedScaled += 1,000,000`; `w = float(double(w₀) · max(0.0, 1.0 − double(e) / double(b)))` with w₀ = `m_fHoldWeight` and b `m_iBlendOutScaled` (b = 0 gives w = 0 at once); at w = 0 record `Cinematics.End` with the reason into the tick buffer, unless end-recorded is set. The time, the weight and the state change above are written to the instance by the node itself, whatever the merge decides, because they are a function of committed state and t alone.
   5. Time: `s_cur = m_iTimeScaled / H` (integer division, floor) in µs. When this run applied a seek (step 6.1, or step 5 (a) for a `PAUSED` instance), the new `m_iTimeScaled`, `m_iPrevTimeScaled`, `m_ulNextItemKey`, the cleared prefetch bits and the clearing of seek-pending and seek-fire-events are **staged** with the tick buffer, together with this tick's advance, instead of being written by the node: a rejected tick buffer leaves the pre-seek time and the pending seek, so the next tick re-applies the whole seek from the same committed s_cur (and a rejected seek tick does not advance). Without a seek, the advance's time, weight and state are written by the node as step 6.4 says.
   6. **Fire items** of the window `[m_ulNextItemKey, s_cur]` (the fire items of "Cinematics.Evaluate"), processed into the tick buffer and staged outbox entries.
7. **Prefetch** for instances in `BLENDING_IN` and `PLAYING`: the clip and dialogue needs of sections that start in `(s_cur, s_cur + lookahead]` and whose prefetch bit is clear are fire items of kind prefetch (time = section start − lookahead, clamped to ≥ 0), so they are recorded once, in timeline order, by step 6.6: `Animation.PrefetchClip`, and `Audio.PrepareDialogue` with the lead `cine.audioLeadSeconds` (recording a prepare record with tick t).
8. **Cap.** An instance whose tick buffer reaches `uCINE_MAX_COMMANDS_PER_INSTANCE_TICK` (512) records, or whose next item is refused by the outbox's admission, stops processing items for the tick; `m_ulNextItemKey` then names the first unprocessed item, so the next tick's window starts there and no item is lost (`cine.commands.instance_cap_delta` or `cine.events.deferred_delta` + 1, logged once per instance).

**Fire items.** Every point-in-time effect of a track is a fire item with the 64-bit key `K = time µs << 26 | track index << 17 | item index`, where the item index is the key index for keyed tracks (event, marker, command; < 2¹⁷) and `section index × 32 + {0 prefetch, 1 prepare, 2 start, 3 end, 4 + w window-end of lip-sync window w}` for sectioned tracks (w < 16, so the largest index is 4,095 × 32 + 19 < 2¹⁷); the track index is < 512 (9 bits) and a time ≤ 3.6 × 10⁹ µs fits the remaining 38 bits. Each track's items are sorted by key in the cooked file, so the window's items in key order are a k-way merge over the instance's tracks (a binary heap of ≤ 512 track cursors, O(N log T)). Processing an item records its commands or stages its outbox entry; after the last processed item, `m_ulNextItemKey` = the next item's key, or `(s_cur + 1) << 26` when the window is exhausted. The first advance after Begin starts with `m_ulNextItemKey = startUs << 26`, so items at the start time fire. Each fired item's sub-tick offset is "Time arithmetic"'s.

**Merge function** (`m_pfnMerge`, `Zenith2/Docs/Design/ECS/SystemAPI.md` → "Zenith_MergeContext header"), single-threaded, reaching the world record through `GetUserData`:

1. For each buffer in base-key order (every side buffer, every tick buffer, every autostart buffer): `Zenith_ECSCapacityDemand d = xMerge.ComputeDemand(xBuffer)`; when `xMerge.GetCapacity().TryAccept(d)` succeeds, `AcceptBuffer` it and commit what the node staged with it (for a side buffer: everything "Side work" lists; for a tick buffer: `m_ulNextItemKey`, the staged outbox entries in order, audio list additions and removals with the post serial, caption list additions, prepare records, prefetch bits, end-recorded when the buffer holds `Cinematics.End`, first-advance cleared, a paused seek's clearing of seek-pending; for an autostart buffer: its player-start entry; for a tick buffer whose run applied a seek, also the seek's staged time fields and flags of step 6.5); otherwise `RejectBuffer` it, discard everything staged with it, count `cine.commands.capacity_deferred_delta` and log once per instance (`cine: instance <id> deferred by merge capacity`). A rejected tick buffer's items are re-run from the same `m_ulNextItemKey` at the next tick, and a rejected paused seek stays pending, so a buffer is never partly applied (`Test_CinematicPlayback_MergeCapacityRejection_RerunsWhole`). The default merge's capacity rule applies to CINE's buffers exactly as to any other system's (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Commit and collection").
2. Then, in the collected order of `m_axNeeds` (ascending GUID), for each collected need while the in-flight count is below `uCINE_MAX_LOADS_IN_FLIGHT` (64): `m_pxPublicationSink->AllocateCompletionID(ASYNC_SOURCE_CINEMATICS)` (`Zenith2/Docs/Design/MOD/RuntimeSeams.md` → "Allocation sites and acceptance"; this is the merge-chain site the source declared) and, on success, issue the load ("Asset binding" step 1). `PUBLICATION_SINK_ERROR_FULL` changes nothing: the need stays collected for the next tick, allocates no ID and counts `cine.binding.deferred_delta`; this need and every later one in the order wait, so the deferral is in CINE's deterministic order. `PUBLICATION_SINK_ERROR_DETACHED` (the world's table was retired) allocates nothing for any need this run, and the needs stay collected. `PUBLICATION_SINK_ERROR_SITE` and `PUBLICATION_SINK_ERROR_REPLAYING` cannot occur at a declared merge-chain site (the sink asserts them as engine defects); CINE treats either as `FULL`.

### Cinematics.ApplyTransforms

Declared access: `ReadResource` `Zenith.Cinematics.World`; `Write` `Zenith.LocalTransform` 1 Position, 2 Rotation, 3 Scale and `Zenith.Animation.Pose` 1 PhysicsWeight, each with `WRITER_SOURCE_CINEMATIC` (`Zenith2/Docs/Architecture/FramePhases.md` → "Writer sources and default precedence"); `Query` `m_xTransformSlot` = `Zenith_QueryDesc{ "Cinematics.Transforms", { { Zenith.LocalTransform, QUERY_TERM_WITH, {1, 2, 3}, true } } }` and `m_xPoseSlot` = `Zenith_QueryDesc{ "Cinematics.Poses", { { Zenith.Animation.Pose, QUERY_TERM_WITH, {1}, true } } }`; `ReadAnyRow` `Zenith.WorldTransform` 1, 2, 3 (the committed world transforms of anchor slots and of bound entities' parents, written by phase 8 of the previous tick, so no system of phase 6 writes them); `EmitsCommands` (the empty current-entity buffers of "Own-row writes"; it records nothing). It reads no committed `Zenith.LocalTransform`: every blend base is stored in the instance block (the snapshot or the take-over base, "Blending"). It visits only bound entities, never iterating a chunk, so its cost is O(bound entities × tracks per entity) and independent of world size.

For each instance in ascending ID, for each bound, not dropped slot whose taken-over tick is 0 or ≥ t (a slot taken over at tick t is still written in tick t, "Take-over of a bound entity") in slot order, the slot's entity E is made current (`Commands(E's simulation ID, 0)`) and its rows reached with `GetChunkOfEntity(m_xTransformSlot, E, uRow)` and, when it has a physics-weight channel, `GetChunkOfEntity(m_xPoseSlot, E, uRow)` ("Own-row writes"); then, for each transform or camera track and each animation track with a physics-weight channel of that slot, in track order:

| Instance condition | Written |
|---|---|
| `m_ulBeginTick == t` | nothing (the Begin tick) |
| `BLENDING_IN`, `PLAYING`, `PAUSED`, `BLENDING_OUT` | the track evaluated at `s_cur` ("Transform tracks"), blended at the current weight with the rule of the state (for `PAUSED`, of `m_ePausedFromState`; "Blending") |
| `ENDED` with skip-applied and not skip-after-phase-6 | the end state at weight 1 |
| `ENDED` with `m_ulEndTick == t` and reason `COMPLETED`, `INTERRUPTED` or `FAILED` | the **end tick**: weight 0 ("End tick") |
| `ENDED` with taken-over-end and `m_ulEndTick == t` | the slots taken over this tick, at the weight the instance had when it ended |
| any other | nothing |

Values are written into the staging column of the cinematic source with the row's written bit, through the view of the current entity only. Two instances never write one row in one tick: "Take-over of a bound entity" hands a row from P to N at a tick boundary (P writes it through tick t, N from tick t + 1), and two tracks of one instance driving the same component of one entity is a cook error (`cine.cook.duplicate_driver`, Authoring.md "Cook validation rules").

### End tick

The tick whose `End` playback moved an instance to `ENDED` (reason `COMPLETED`, `INTERRUPTED` or `FAILED`) is written by `Cinematics.ApplyTransforms` and `Cinematics.ApplyLate` at weight 0: every restore-flagged written property at its snapshot value B, bit for bit, and every unflagged written property at its held value `lerp(B_in, C, w₀)` ("Blending"); a content-changed instance writes only the restore-flagged properties. The boundary restore that follows writes the same snapshot bits, so a flagged property arrives at its pre-cinematic value in the end tick and does not move again, and no gameplay writer of those rows wins in the end tick (`Test_CinematicBlend_OutFlaggedReachesSnapshot`). One exception keeps the end tick single-writer for commands: `Cinematics.ApplyLate` records no lens or lighting channel of a slot flagged `uCINE_BINDING_FLAG_CAMERA` in the end tick, because END, dispatched at the sync point after phase 1 of that tick, resumes GAME's camera director, which records the camera's `Zenith.Render.Camera` and `Zenith.Lighting.CameraLighting` properties in phase 10 of the same tick (`Zenith2/Docs/Design/GAME/Cameras.md` → "Cinematic suspension"); the camera's restore-flagged properties still reach their snapshot at the boundary restore, and its pose (an arbitrated phase-6 write) is written as above (`Test_CinematicTracks_Camera_EndTickLensLeftToDirector`).

### Cinematics.EmitEvents

Declared access: `ReadResource` `Zenith.Cinematics.World`; `WriteResource` `Zenith.Cinematics.Emission` (the owner, phase 8); `EmitsEvent` for `Zenith.Cinematics.Started`, `Ended`, `Marker`, `StartFailed`, `Zenith.Runtime.CaptionCueEvent`, `Zenith.Runtime.CaptionCancelEvent`, and every `TYPE_KIND_EVENT` type in the registry at attach (an event track may name any of them; the registry's event set is frozen at attach, so a schedule compiled once covers every sequence); `ConsumesMergeCapacity` (its merge function accepts groups).

**Emission groups.** The entries due in tick t (emission tick ≤ t, still stored) are partitioned in storage order: first by instance ID (entries with instance ID 0 form the group of ID 0), then each instance's run into consecutive chunks of at most `uCINE_EMISSION_GROUP_ENTRIES` (64). The groups are numbered g = 0, 1, … in (instance ID ascending, chunk order), and group g is emitted with `Zenith_EventWriter::Emit(xType, axValues)` into `Events(0, uCINE_EMISSION_ORDINAL_BASE + g)` (`uCINE_EMISSION_ORDINAL_BASE` = 1), so the groups merge in that order and the entries of one group in storage order. The node stages, per group, the list of storage positions it emitted; it writes no world state.

`Zenith_SystemContext::Events(uint64 ulSimulationID, uint32 uInvocationOrdinal)` (`Zenith2/Docs/Design/ECS/SystemAPI.md`, row CN23 answered) is the event writer of the logical invocation `Commands(ulSimulationID, uInvocationOrdinal)` opens, so a system can emit into several independently accepted buffers that carry no entity.

**Merge function.** In group order: a group whose instance had an earlier group rejected in this merge is rejected with `RejectBuffer` without `TryAccept`, so an instance's entries are never accepted out of order; otherwise `TryAccept(ComputeDemand(group))` decides `AcceptBuffer` or `RejectBuffer`. Then the merge writes `Zenith.Cinematics.Emission` once: `m_ulTick = t` and a set bit for every storage position of every accepted group. A rejected group writes no bit and counts `cine.events.emit_rejected_delta` (logged once per world per cause); its entries are still stored, so `Cinematics.EmitEvents` of t + 1 emits them again, first among that instance's due entries, and they are removed only after a merge accepted them. Everything that consumes "what was emitted" — the caption expiry of step 0, the capture's subtitle list (`Zenith2/Docs/Design/CINE/Video.md` → "Capture algorithm" step 5) — reads the acceptance bits, never the emission itself, so a re-emitted entry is counted once (`Test_CinematicPlayback_EmitRejected_ReEmittedOnce`: the phase-8 capacity forced below one group's demand in tick t; every entry of that instance is delivered exactly once, in phase 9 of t + 1, in queue order, and no other instance's entry is lost or duplicated).

Events queued by `Cinematics.Evaluate` in phase 1 and by playbacks at the sync points after phases 1 to 7 are delivered in phase 9 of the same tick ([Z2-N-ARCH-478]) when their group is accepted; entries queued at the sync points after phases 8, 9 and 10 or by the tick-boundary handler are emitted in phase 8 of the next tick and delivered in its phase 9, exactly once (`Test_CinematicPlayback_OutboxLateEntries_EmittedNextTickOnce`). Delivery order within phase 9 is the merge order: the group of instance ID 0, then the instances in ascending ID, each in queue order.

### Cinematics.ApplyLate

Declared access: `ReadResource` `Zenith.Cinematics.World`; `ReadAnyRow` `Zenith.Render.Camera` 10 CutRequest (the cut counter's committed value; property 10 is written only by commands, so no phase-10 system writes it); `EmitsCommands` (`SetProperty` records); `ConsumesMergeCapacity`. It declares no read of the components property tracks name, because which components a sequence names is not known at attach. Buffers `Commands(0, 65 + i)`.

For each instance under the same conditions as `Cinematics.ApplyTransforms` (the Begin tick writes nothing; the end tick writes at weight 0, except a camera slot's lens and lighting, "End tick"), each camera track's lens and lighting channels and each property track record `SetProperty(entity, type, property, value)` for the blended value ("Blending"), applied at the sync point after phase 10 and so visible to phase 11 and to extraction. ## Command playback

Every CINE playback runs on the world's sync-point node at the sync point after the recording phase, in merge order ([Z2-N-ARCH-489] through `Zenith2/Docs/Architecture/FramePhases.md` → "Playback at a sync point", step 7 for module records). It receives `Zenith_WorldPlaybackAccess`, the payload and the merge key; it reaches the world record through the module's world table by `GetWorldTag()`. Lifecycle events are dispatched through `m_pxSceneState->GetLifecycleDispatcher()` with the follow-up buffer the playback receives. A playback records no command of its own: what it needs recorded becomes side work.

### Start playback

0. **Ticket entry and outbox.** First take a free entry of `m_axTickets` (entries whose ticket window has passed are free); then the outbox admission of "Outbox" rule 2 (at least 10 free entries beyond the stored count and every reservation while the pool has a free record, at least 1 while it is full), which releases the entry when it refuses. When either fails (an outbox held full by rejected emission groups; 64 starts within three ticks), the start is dropped before any other step: `cine.commands.outbox_full_delta` or `cine.commands.ticket_overflow_delta` + 1, logged once per world; no event is queued, and the ticket resolves `CINEMATIC_ERROR_TICKET_EXPIRED` from the next tick ("Zenith_CinematicsWorld header").
1. Validate the payload as untrusted data: a looping start (`uCINE_START_FLAG_LOOP`) of a sequence whose `D × H` is below `ulCINE_MIN_LOOP_SCALED` (8,000,000: the advance of rate 8, `uCINE_RATE_MAX_Q16 × 1,000,000 / 65,536`: about 133 ms at 60 Hz) is refused with `CINEMATIC_ERROR_INVALID_ARGUMENT`, checked once D is known (here when resident, otherwise at the binding resolution), because one wrap per advance must suffice whatever rate `SetRate` sets later; binding count ≤ 64 and the overflow bit clear; every flag bit in `uCINE_START_FLAG_KNOWN_MASK`, and `uCINE_START_FLAG_FROM_PLAYER` only when the merge key's system order is `m_uEvaluateSystemOrder`; rate ≤ `uCINE_RATE_MAX_Q16`; blends ≤ `ulCINE_MAX_BLEND_US`; no field equal to the rejected sentinel 0xFFFFFFFF (a NaN or infinite float at record); start time ≤ the duration once resident; sequence GUID non-null. A failure writes the ticket entry with the error and queues `Zenith.Cinematics.StartFailed`; nothing else happens.
2. Instance limit: live instances (not `RELEASED`) < `cine.maxInstancesPerWorld`, else `CINEMATIC_ERROR_INSTANCE_LIMIT` as step 1. A `RELEASED` record still holding side work or its ticket window occupies a pool entry; a full pool is the same error.
3. Allocate the instance: ID = `m_ulNextInstanceSerial++`; ticket entry {ticket → ID, playback tick}; state `BINDING`; `m_uOutboxReserve = 10` ("Outbox"); copy blends, rate, start time, flags, tag, the voice-locale tag (`m_xVoiceLocale`, payload property 12) and `m_xPlayer`; take a handle to the sequence (`Zenith_AssetRegistry::Acquire` by GUID, no load issued here). Every `StartFailed` and `Started` this instance queues later comes from its reservation; a failure at steps 1 and 2, before an instance exists, queues one `StartFailed` from the free entry step 0 checked.
4. Bindings. From the payload (sorted by name hash by the recorder), or, with `uCINE_START_FLAG_FROM_PLAYER`, from the player's `Bindings` container (`Zenith_WorldPlaybackAccess::ReadContainer(m_xPlayer, Zenith.Cinematics.Player, 7, uCount)`; each element's `Name` is hashed with `Zenith_Hash64` of its text, then sorted) plus the player's entity for the slot `Self` when the sequence has one. Held by name hash until the sequence is resident.
5. If the GUID has an entry in the bound set `m_axBound` ("Bound set") and the resident sequence's content hash equals the entry's, add this record as a holder and resolve the bindings now ("Binding resolution", with the playback access); a failure ends the instance with `CINE_END_REASON_FAILED`, writes the error into the ticket entry, queues `StartFailed` and releases the instance (no lifecycle event). Otherwise the instance waits in `BINDING` for `Cinematics.Evaluate` to collect its need, and its bindings are resolved by the publication handler ("Asset binding" step 3).
6. If bound, check preparation ("Preparation"); when ready, run "Begin" inline (this is the case of every test and every authored sequence that is preloaded); otherwise the state becomes `PREPARING`.

### Binding resolution

Binding resolution runs in exactly two contexts, each with the world access it is given: the start playback of a sequence already in the bound set (step 5, `Zenith_WorldPlaybackAccess`) and the publication handler at tick-boundary step 1 for every instance that waited for the publication ("Asset binding" step 3, `Zenith_TickBoundaryAccess`, `Zenith2/Docs/Design/ECS/WorldAPI.md` → "Zenith_ECSObservers header"). Both accesses provide what it uses: entity resolution through `GetEntityTable().Resolve` and `HasComponent`. No system resolves bindings, because no system holds a world access ("Systems").

For each binding in the recorded order (ascending name hash): find the slot by name hash (`Zenith_Cinematic::FindBinding`), `CINEMATIC_ERROR_BINDING_UNKNOWN` when absent; a second binding of the same slot is `CINEMATIC_ERROR_BINDING_DUPLICATE`; resolve the entity through the access (a stale, null or wrong-world handle leaves the slot unbound); check that the entity carries every component the slot's tracks require (`HasComponent`), `CINEMATIC_ERROR_BINDING_TYPE` naming the slot otherwise. Then every slot flagged `uCINE_BINDING_FLAG_REQUIRED` must be bound, else `CINEMATIC_ERROR_BINDING_REQUIRED`. The detail field of `StartFailed` names the binding's index in the recorded order or the slot index. Complexity O(B log S).

### Begin

Runs inline in the start playback, or as the playback of `Cinematics.Begin` recorded by `Cinematics.Evaluate` when preparation finished in a subsequent tick (then at the sync point after phase 1). t is the playback tick.

1. **Take-over admission.** For each bound entity E held by another instance P (`FindByEntity`) in `BLENDING_IN`, `PLAYING`, `PAUSED` or `BLENDING_OUT`: with `uCINE_START_FLAG_NO_TAKEOVER`, the start fails with `CINEMATIC_ERROR_BINDING_DUPLICATE` (ticket entry, `StartFailed`, no event) and nothing else changes. A P in `ENDED` (its end tick is t) or `RELEASED` is not taken over; an `ENDED` P still gives N a captured base ("Take-over of a bound entity", ended holder).
2. **Snapshot into a staging block** ("Pre-cinematic snapshot"), merging the entries of every P of step 1 and of every `ENDED` holder ("Take-over of a bound entity", merge rule). `CINEMATIC_ERROR_SNAPSHOT_LIMIT` (or `CINEMATIC_ERROR_OUT_OF_MEMORY` from the pool) frees the staging block and fails the start as step 1 does; every P is untouched.
3. **Commit the take-over** ("Take-over of a bound entity", commit) for every P of step 1, and set base-capture pending on N's slot of every entity an `ENDED` P holds.
4. State `BLENDING_IN` at weight 0; or `PAUSED` at weight 1 with `uCINE_START_FLAG_PAUSED` (`m_ePausedFromState = PLAYING`, `m_fPausedWeight = 1`); or `PLAYING` **at weight 1** when the blend-in is 0. `m_iTimeScaled = startUs × H`; `m_iPrevTimeScaled = m_iTimeScaled`; `m_ulNextItemKey = startUs << 26`; first-advance set; `m_ulBeginTick = t`.
5. Dispatch `LIFECYCLE_EVENT_CINEMATIC_START` with a null entity, then once per bound slot in slot order with `m_xEntity` = the slot's entity (row GA4); the payload is a `Zenith_CinematicLifecyclePayload`.
6. Queue `Zenith.Cinematics.Started`.
7. **Spawnable bindings** (Stage 5): for each binding with `uCINE_BINDING_FLAG_SPAWNABLE`, record `Zenith_RecordInstantiatePrefab` of the prefab its spawn-prefab dependency record names (`Zenith2/Docs/Design/CINE/Formats.md` → "Binding table section") at the anchor binding's transform, or the world origin without one, into the playback's follow-up buffer; the boundary handler binds the slot to the spawn result at t → t + 1, so the slot's tracks write from t + 1 like every other slot's; the slot takes no snapshot entry; the instance's release records `Destroy` of the spawned entity, and a spawn the prefab could not produce (not resident, too large: a null ticket) fails the start with `CINEMATIC_ERROR_BINDING_REQUIRED` (detail the slot index).

Tracks write from tick t + 1: `Cinematics.ApplyTransforms` and `Cinematics.ApplyLate` skip an instance with `m_ulBeginTick == t`, and the first advance runs in the Evaluate of t + 1. An instance that begins at weight 1 (zero blend-in, `PLAYING` or `PAUSED`) therefore writes the full track value from tick t + 1 (`Test_CinematicPlayback_ZeroBlendIn_FullWeightFromFirstAdvance`).

### Take-over of a bound entity

When a beginning instance N binds an entity E that an earlier instance P holds:

**Merge rule (step 2 of Begin).** N's snapshot entries for E are N's own union of written and restore sets for E ("Pre-cinematic snapshot" steps 1–2), in (type ID, property ID) order. For each (type, property) of that union, the value is P's entry for E when P has one (its pre-cinematic value), otherwise the committed value read now; the flags are N's (bit 0 from the type's restore flag, bit 1 from N's driver list). P's entries for E that N's union lacks are not carried: a restore-flagged one cannot be missing (the restore set depends on E's components alone), and a written-only one keeps P's last value ([Z2-N-ARCH-555]). When P is `ENDED` (its end tick is t), N takes P's values the same way, but P keeps its own entries and restores them at the boundary; both restores then write the same pre-cinematic bits.

**Ended holder (the chained cutscene).** `Ended` is delivered in phase 9 of P's end tick t, so a script that starts the next sequence N there begins it inline in tick t, while the world holds P's end-tick output, not P's pre-cinematic values: an unflagged position at P's held `lerp(B_in, C, w₀)`. N's blend-in must start from that output, so for every entity E an `ENDED` P holds, Begin step 3 sets base-capture pending on N's slot for E without marking P. Tick-boundary step 2.2, which runs before step 2.3 restores P, then reads E's committed value of every property in N's written set (P's end-tick output: the snapshot bits for flagged properties, the held value for unflagged ones) into N's take-over base run. N blends in from what was on screen in tick t, and its restore uses the merged snapshot (P's pre-cinematic values). `Test_CinematicPlayback_TakeOver_EndedHolder_NotTakenOver` asserts that P is not marked, that both restores write the same bits, and that an unflagged position does not move between ticks t and t + 1 by more than the track's own per-tick change.

**Commit (step 3 of Begin), for a P in `BLENDING_IN` … `BLENDING_OUT`.**

1. P's slot for E gets taken-over tick = t and the stop-slots-pending flag; P's snapshot entries and take-over bases for E are released from P's block (marked free; P's block is compacted at P's restore). P writes E through tick t (its transforms in phase 6, its late values in phase 10) and never from t + 1 on; its tracks of that slot evaluate no fire item from t + 1. P's side work `STOP_TAKEN_OVER_SLOTS` makes P's next Evaluate stop P's animation sections on that slot.
2. N's slot for E gets base-capture pending. At the boundary t → t + 1 (tick-boundary step 2.2) the handler reads E's committed value of every property in N's written set with `Zenith_TickBoundaryAccess::ReadProperty` (that is P's tick-t output) into N's take-over base run, and clears the bit. N's blend-in base for E is that run ("Blending"); its restore uses the moved snapshot, so the final restore returns E to its state before the first cinematic.
3. E receives `LIFECYCLE_EVENT_CINEMATIC_START` from N and no event from P.
4. When P has no slot left that is bound, not dropped and not taken over, P ends through the End path at once, in this order: `Ended` queued from P's reservation; reason `INTERRUPTED`, `m_ulEndTick = t`, taken-over-end set; `LIFECYCLE_EVENT_CINEMATIC_END` dispatched once with a null entity (its entities were handed to N); side work `STOP_AUDIO` (fade 50 ms) and `CANCEL_CAPTIONS`; state `ENDED` and `m_uOutboxReserve = 0` last ("Outbox", order rule). Its end tick writes only its slots taken over at t, at its current weight ("Cinematics.ApplyTransforms"); its restore has no entry left and only releases it.

The base capture, the per-slot taken-over tick and the pending bits are saved ("Save and restore"), so a save taken between the take-over and its boundary restores the take-over exactly (`Test_CinematicSave_TakeOverMidBlend_RoundTrip`). `Test_CinematicPlayback_TakeOver_SnapshotFailure_LeavesHolderIntact` fills the pool so that N's snapshot fails and asserts that P still holds and writes E and that P's final restore returns E to its pre-cinematic value.

|---|---|

### Skip playback

| Instance state | Effect |
|---|---|
| `BINDING`, `PREPARING` | cancel exactly as an interrupt does |
| `BLENDING_IN`, `PLAYING`, `PAUSED`, `BLENDING_OUT` | the steps below |
| `ENDED`, `RELEASED`, unknown ID | counted, dropped |

1. **Fire-on-skip events.** Every event, marker and subtitle key and section with the `fireOnSkip` flag whose time is in `(s_cur, D]`, in key order (the fire items of "Cinematics.Evaluate"), queues its outbox entry now from the instance's reservation (at most `uCINE_MAX_FIRE_ON_SKIP_KEYS`, 8, per sequence, a cook and load limit); a skip-fired caption cue carries bit 51 in its source ID ("Subtitle tracks"), so the skip's own `CANCEL_CAPTIONS` does not remove it. The fire-on-skip command keys become side work `SKIP_KEYS` with `m_ulSideSkipFromUs = s_cur`. Keys without the flag do not fire; skipped dialogue and audio sections do not start.
2. **End state.** For every bound, not dropped slot, evaluate every transform, camera and property track at D. The non-arbitrated values (lens, lighting, property tracks) are written now through `Zenith_WorldPlaybackAccess::SetProperty`. The arbitrated values (transforms, physics weight) are written by `Cinematics.ApplyTransforms` in phase 6 of this tick (skip-applied set) when the skip played at a sync point before phase 6; when it played after phase 6 (skip-after-phase-6 also set), they are stored in the instance block's end-state run and written by tick-boundary step 2.1. Either way the end-state value is in the world before the next tick begins.
3. **Audio, captions and animation.** Side work `STOP_AUDIO` (fade 50 ms) and `CANCEL_CAPTIONS`; ANIM handles its slots from the lifecycle event (empty plus a 0.15 s inertial take, `Zenith2/Docs/Design/ANIM/Runtime.md` → "Lifecycle listener").
4. Queue `Ended` with `SKIPPED` from the reservation (after step 1's fire-on-skip entries); reason `SKIPPED`, `m_ulEndTick = t`, time `D`; dispatch `LIFECYCLE_EVENT_CINEMATIC_SKIP` with a null entity and per bound slot; then state `ENDED` and `m_uOutboxReserve = 0` as the last action ("Outbox", order rule). No `LIFECYCLE_EVENT_CINEMATIC_END` follows a skip: SKIP is terminal for the listeners (GAME resumes its director on SKIP or END, `Zenith2/Docs/Design/GAME/Cameras.md` → "Cinematic suspension").
5. The restore runs at the next tick boundary; the side work is recorded by the next `Cinematics.Evaluate` whatever the instance's state then (`Test_CinematicPlayback_SkipSideTable_RecordedAfterRestore`: a skip with one fire-on-skip command key and one playing audio section; in tick t + 1 both records are played back, and the instance is `RELEASED`).

### End playback

Recorded by `Cinematics.Evaluate` when the blend-out weight reaches 0 (reason `COMPLETED` or `INTERRUPTED`), when a slot flagged `uCINE_BINDING_FLAG_REQUIRED` is dropped and no other slot with that flag is bound (reason `FAILED`), or for a content-changed instance (reason `FAILED`). The playback, in this order: queues `Ended` from the reservation; sets `m_ulEndTick = t` and `m_fHoldWeight` = the current weight when the instance was not blending out; dispatches `LIFECYCLE_EVENT_CINEMATIC_END` with a null entity and per bound slot (the payload carries the reason); sets side work `STOP_AUDIO` (fade 50 ms) and `CANCEL_CAPTIONS`; and as its last action sets `ENDED` and `m_uOutboxReserve = 0` ("Outbox", order rule). Tick t is the end tick ("End tick"); the restore runs at the boundary t → t + 1, so in the interrupt test the marked property equals its snapshot from the end tick on.

### Seek playback

Valid in `BLENDING_IN`, `PLAYING`, `PAUSED`, `BLENDING_OUT`; elsewhere counted and dropped. The target is clamped to [0, D] and stored with the seek-pending bit and the fire-events flag; `Cinematics.Evaluate` applies it at its next run, in step 6.1 for a playing instance and in step 5 (a) for a `PAUSED` one ("Seeking and scrubbing"). Two seeks before an Evaluate keep the second one.

### Rate pause and resume playback

`SetRate`: a rate above `uCINE_RATE_MAX_Q16` or equal to the sentinel is rejected and counted; otherwise the next advance uses it. Rate 0 holds time like a pause but keeps the state (tracks keep writing at the current time). For a change from r₀ to r₁ ≠ r₀ the playback sets, in addition to the rate: when r₀ = 1, side work `PAUSE_PRESENTATION` and rate-presentation-stopped (time-locked voices stop, captions are cancelled); when r₁ = 1, `RESUME_PRESENTATION` (stopped voices re-post, captions re-queue at rate 1); when r₁ > 0 and r₁ ≠ 1, `REQUEUE_CAPTIONS` (captions re-queue with the duration at r₁; no voice re-posts while the rate is not 1). Rate 0 cancels captions and does not re-queue them, because the duration divides by the rate. `Pause`: `BLENDING_IN`, `PLAYING`, `BLENDING_OUT` → `PAUSED`, `m_ePausedFromState` = the state left, `m_fPausedWeight` = the current weight (time and weight held), side work `PAUSE_PRESENTATION`. `Resume`: `PAUSED` → `m_ePausedFromState` (`PLAYING` when it was begun with `uCINE_START_FLAG_PAUSED`), the weight continues from `m_fPausedWeight`, side work `RESUME_PRESENTATION` at rate 1, `REQUEUE_CAPTIONS` at another rate above 0, none at rate 0. The records these produce are made by the first `Cinematics.Evaluate` after the playback ("Side work"); a seek is handled by that Evaluate's seek step. A pause and a resume, or two rate changes, before one Evaluate run both their side work in table order with fresh audio IDs, so a voice stopped and re-posted within AUDIO's 50 ms stop fade is never refused as a live ID (`Test_CinematicTracks_Audio_PauseResumeWithinFade_Replays`).

## Asset binding

Sequences and the video assets they reference load asynchronously through ASSET, and a load's completion must reach the simulation at a deterministic tick: CINE is an asynchronous source, in ANIM's pattern (`Zenith2/Docs/Design/ANIM/Runtime.md` → "Asset bindings").

The sink is MOD's single module publication sink of the Q76 (a) ruling, specified in `Zenith2/Docs/Design/MOD/RuntimeSeams.md` → "Zenith_ModulePublication header", "Source declaration and handler registration", "Allocation sites and acceptance" and "Parking a result"; CINE uses it as follows.

`Zenith_WorldAttachContext::GetPublicationSink()` (`Zenith2/Docs/Architecture/CompositionRoot.md` → "Module interfaces", [Z2-N-ARCH-879]: MAIN_THREAD during `AttachWorld`) returns the world's `Zenith_ModulePublicationSink&`; CINE stores the pointer in `m_pxPublicationSink` and calls `Park` through it until every completion ID it allocated is completed, even after its `DetachWorld` returned, as the sink's contract allows. The source kind is `ASYNC_SOURCE_CINEMATICS` (12), the value SCRIPT assigned in `Zenith2/Docs/Scripting.md` → "Asynchronous source kind registry" (row CN2, answered).

- **Declaration (AttachWorld step 1).** `xSink.DeclareSource(ASYNC_SOURCE_CINEMATICS, Zenith_ModuleSourceDesc{ uCINE_MAX_LOADS_IN_FLIGHT (64), 24, MODULE_SOURCE_SITE_MERGE_CHAIN })`, then `xSink.SetSourceHandler(ASYNC_SOURCE_CINEMATICS, *m_pxPublicationHandler)`. Both are registrations: a rejection (a kind already declared, an out-of-range value, the arena bound) is logged by the sink and fails CINE's `AttachWorld` with `MODULE_ERROR_REGISTRATION` once it returns; the module host also refuses a declared kind left without a handler, which CINE never does. 64 × 24 = 1,536 bytes count toward the world's `ulMODULE_PUBLICATION_MAX_ARENA_BYTES`.
- **Handler.** `Zenith_CinematicsPublicationHandler` (`Internal/Playback/Zenith_CinematicHandlers.cpp`) implements `Zenith_ModulePublicationHandler::OnPublished(const Zenith_ModulePublication& xPublication, Zenith_TickBoundaryAccess& xWorld)`; MOD's forwarder calls it on the tick-boundary node, step 1, once per publication of the kind in completion-ID order, live and in replay. Because the contract requires the handler to outlive the world's table (which a swap may retire after `DetachWorld`), the handler objects live in the module instance: one per world tag ever attached, kept in the module's world table (a `Zenith_Array` grown on the main thread at `AttachWorld`) and freed with the module instance; `DetachWorld` sets the entry's record pointer to null, and a handler with a null record returns at once (a retired table never publishes, so this is a guard, not a path).
- **Allocation** on the merge chain only (CINE's merge function, "Cinematics.Evaluate" merge step 2), with the sink's `Zenith_PublicationSinkError` handling stated there. **Parking** with `Park(ulCompletionID, ASYNC_SOURCE_CINEMATICS, uPublicationKind, xPayload)` from the Evaluate node (step 3) and from `DetachWorld`.

1. **Request.** `Cinematics.Evaluate` collects one need per sequence GUID that an instance in `BINDING` or a preload entry waits for and that has no record in `m_axNeeds`; once a sequence is resident, a second need per video GUID its video tracks reference. The merge function (step 2 of "Cinematics.Evaluate" merge) allocates the completion ID from the sink and issues `Zenith_AssetLoader::RequestLoad` with the world's completion queue `cine.loads.w<tag>` (capacity 128, below) and the completion ID as the user tag. Clips, sounds and dialogue are not bound by CINE: ANIM and AUDIO load their own through the commands CINE records. **The allocation gate counts a need from its allocation until its publication only** — both are ticks fixed by recorded state (the merge chain and the logged publication), so which needs allocate in a tick is a function of committed state in record, replay and after a load. The need's `m_axNeeds` entry is freed at its publication; the drain looks a completion record up by completion ID and drops one whose need is gone (an abandoned need's late `CANCELLED` record). The completion queue `cine.loads.w<tag>` therefore has capacity 128 (`2 × uCINE_MAX_LOADS_IN_FLIGHT`): at most 64 records of gate-counted needs plus the late records of operations CINE cancelled with `RequestCancel` (`Zenith2/Docs/Design/ASSET/RuntimeAPI.md` → "Zenith_AssetLoader header"); the drain half sizes only that queue and never gates an allocation.
2. **Drain.** `Cinematics.Evaluate` step 3 drains the completion queue into its node arena and parks each completion of a live need with the sink: success as `PUBLICATION_KIND_GENERIC_RECOMPUTED` with no payload, failure as `PUBLICATION_KIND_GENERIC_RECORDED` with ASSET's 24-byte load result record. The completion record of an abandoned need is dropped (its ID was completed at abandonment); only its drain half of the in-flight count is released.
3. **Publication.** At tick-boundary step 1, `Zenith_CinematicsPublicationHandler::OnPublished` receives each publication in completion-ID order and does all of the following itself, through its `Zenith_TickBoundaryAccess` (no CINE playback runs for a waiting instance, and no system holds a world access): it releases the need's publication half; on success it adds the GUID's bound-set entry ("Bound set") with the resident sequence's content hash, builds the entry's template ("Reflected payloads"), and then, for every instance in `BINDING` that waits on the GUID, in ascending instance ID, adds the record as a holder and runs "Binding resolution" with `xWorld`: a success moves the instance to `PREPARING`, and a binding error writes the ticket entry, queues `StartFailed` from the instance's reservation (queue tick = the tick starting, queue point 0) and releases the instance (no lifecycle event). On failure (an abandoned zero-length payload included) every waiting instance fails with `CINEMATIC_ERROR_INVALID_ASSET` in the same way, and no bound-set entry is made. Preparation is then checked by the next `Cinematics.Evaluate` (step 5), which records `Cinematics.Begin` when ready, so a binding published at the boundary t → t + 1 begins at the sync point after phase 1 of tick t + 1 at the earliest (`Test_CinematicPlayback_StartNotResident_BindsThenBegins`). A preload entry waiting on the GUID becomes bound (or failed) in the same call. A video need never fails a start: a failed video asset makes its sections draw nothing (`cine.video` log once, "Video failure handling" of `Zenith2/Docs/Design/CINE/Video.md`), and an instance's preparation does not wait for a video need beyond its publication. A replay reproduces the publication tick from the log (`PUBLICATION_KIND_GENERIC_RECOMPUTED` re-runs the load and waits for it at that tick).
4. **Abandonment.** A need whose waiters are all gone (cancelled, failed, released) is abandoned in the next `Cinematics.Evaluate` run (step 3), in ascending completion ID: `RequestCancel` on its operation handle, then `Park(id, ASYNC_SOURCE_CINEMATICS, PUBLICATION_KIND_GENERIC_RECORDED, empty)` (the zero-length "abandoned" payload, SAVE's convention, `Zenith2/Docs/Design/SAVE/Formats.md` → "Async section"). The need stays in `m_axNeeds`, marked abandoned, until its publication releases it; CINE never re-issues an abandoned need under its ID and counts no discard itself ([Z2-N-SCRIPT-931]). A need that is already parked when its waiters go is complete: it is only marked abandoned and its publication is dropped.
5. **Preload pins.** `Cinematics.Preload` adds a pin (count ≤ 65,535) to the preload entry of the GUID and collects the need if absent; with 32 preload entries in use, a preload of a new GUID is refused and counted (`cine.binding.preload_refused_delta`). `Cinematics.Release` drops one pin. An instance holds its own handle; the sequence leaves memory when no instance and no pin holds it.

## Preparation

An instance is **prepared** when every animation clip of the sections active at its start time or starting within `cine.prepareLookaheadSeconds` after it is ready (`Zenith_AnimationWorld::IsClipReady(simID, clip)` for its bound entity, the previous tick's state), and every dialogue line of the sections in the same window has a prepare record whose recorded tick is at least `ceil(cine.audioLeadSeconds × H)` ticks before t (CINE cannot observe AUDIO's residency: it waits a deterministic tick count after recording `Audio.PrepareDialogue`). Video sections do not gate preparation. On entry to `PREPARING`, `Cinematics.Evaluate` records `Animation.PrefetchClip` and `Audio.PrepareDialogue` for the window once (a prepare record per line, at most `uCINE_MAX_PREPARES_PER_INSTANCE`, 32; lines beyond are prepared when the window advances). Each tick in `PREPARING` counts `m_uPrepareTicks`; reaching `cine.prepareTimeoutTicks` begins the instance anyway with `cine.prepare.timeout_delta` counted (default), or fails it with `CINEMATIC_ERROR_PREPARE_TIMEOUT` when `cine.prepareTimeoutFails` is true. A sequence with nothing in the window is prepared at once.

## Pre-cinematic snapshot

Taken at Begin into a staging block, for every bound slot in slot order:

1. The **written set**: every (component type, property) a track of the slot writes, from the cooked binding's driver list (Formats.md "Binding table section"): transform tracks give `Zenith.LocalTransform` 1–3 (only the driven channels), camera tracks also give the lens and lighting properties their channels drive, animation tracks with a physics-weight channel give `Zenith.Animation.Pose` 1, property tracks give their property.
2. The **restore set**: every property of every component the entity carries that its type marks `PROPERTY_FLAG_RESTORE_AFTER_CINEMATIC` (the schema's `restoreAfterCinematic`), found by walking the entity's archetype component list and each type's property flags (`Zenith2/Docs/Design/ECS/Reflect.md` → "Zenith_TypeInfo header").
3. For each property in the union, in (type ID, property ID) order, take the value by the take-over merge rule ("Take-over of a bound entity") or read the committed value with `Zenith_WorldPlaybackAccess::ReadProperty` (`ReadContainer` for container properties), and append an entry `{ u64 simulation ID; Zenith_TypeID type (8); Zenith_PropertyID property (4); u32 flags (bit 0 restore, bit 1 written, bit 2 arbitrated, bit 3 released); u32 value bytes; value }`, 16-byte aligned.
4. A slot's entries are contiguous (`m_axBindings[i]` first entry and entry count).
5. Limits: the block's whole size ("Instance block": entries, take-over bases sized as the written entries of taken-over slots, late cache, end state, prefetch bits) is computed first; more than `uCINE_MAX_SNAPSHOT_ENTRIES` entries, more than `uCINE_MAX_SNAPSHOT_BYTES` bytes, or a pool that cannot hold it fails the start with `CINEMATIC_ERROR_SNAPSHOT_LIMIT` before any allocation (no partial snapshot) and counts `cine.snapshot.limit_delta`.

Complexity O(P log P) for P snapshot properties. The block is saved ("Save and restore"), so a save taken mid-cinematic restores correctly after load.

`Zenith_TickBoundaryAccess::SetContainer` (`Zenith2/Docs/Design/ECS/WorldAPI.md`, row CN22 answered): it reserves the container's block with `Zenith_ContainerHeap::Reserve(GetBlockBytes(elementBytes, uCount))` itself (the boundary node is single-threaded and no merge is running, so the reservation is an out-of-tick request that fails with `ECS_ERROR_CAPACITY`, changing nothing), then forwards to `Zenith_WorldPlaybackAccess::SetContainer`, which allocates within the reservation and frees the replaced block deferred; property-only and structure-free like `SetProperty`. Row CN22.

**Restore** ("Tick-boundary handler" step 2.3): for every entry with the restore bit and without the released bit, in entry order, `Zenith_TickBoundaryAccess::SetProperty(entity, type, property, value)`, or, for a container property, `Zenith_TickBoundaryAccess::SetContainer(entity, type, property, elements, count)` with the element bytes and count the snapshot holds; a container whose block the heap cannot serve at the boundary (`ECS_ERROR_CAPACITY`) is skipped and counted like a removed component. A `SetProperty` that fails (the entity no longer carries the component, `ECS_ERROR_NO_COMPONENT`) skips that entry and counts `cine.snapshot.restore_skipped_delta`; a component added to the entity after Begin is not restored, because the pre-cinematic snapshot holds only what existed at Begin ([Z2-N-ARCH-554]) (`Test_CinematicSnapshot_RestoreSkipsRemovedComponent`). Entries of dropped slots were already released. Entries with only the written bit are not restored ([Z2-N-ARCH-555]): those properties keep the cinematic's final value. Then the block is freed and the instance becomes `RELEASED`.

## Track evaluation

### Time arithmetic

| Quantity | Representation | Formula |
|---|---|---|
| tick rate H | `uint32` Hz | `sim.tickHz`, read once at Start from `Zenith_Config` (`Zenith2/Docs/Design/JOBS/PublicAPI.md` → "Zenith_SimulationClock header"; recorded in the replay header) |
| scaled time | `sint64` µs·Hz | one tick at rate 1 adds exactly 1,000,000 |
| advance per tick a | `sint64` | `(1,000,000 × rateQ16 + 32,768) >> 16` (round half up; rate 8 gives 8,000,000; rate 0 gives 0 and fires no item) |
| sequence time s | `uint64` µs | `scaled / H` (floor) |
| key time k | `uint64` µs | authored integer microseconds |
| tick start S₀ | `sint64` µs·Hz | the scaled time at the start of this tick's advance: `m_iTimeScaled − a` (after a seek, the target × H). For the post-wrap part of a loop it is `S₀ − D·H`, which is `m_iTimeScaled − a` evaluated after the wrap's subtraction, so the general formula covers it and the unwrapped axis continues (S₀ is then negative) |
| sub-tick fraction f | `double` | `f = double(k·H − S₀) / double(a)`, clamped to [0, 1]; k·H and S₀ are `sint64` products (≤ 3.6 × 10¹² fits with a margin of 10⁶); one `double` division |
| `m_fTimeIntoTick` | `float` s | `float(f / double(H))`, clamped to `[0, nextafter(float(1.0 / H), 0.0f)]`: the offset of AUDIO's command header, in seconds into the tick |

Worked rows, which `Test_CinematicTime_SubTickOffset_InRange` asserts: at 60 Hz, rate 1, S₀ = 0, a key at 10,000 µs gives k·H = 600,000, f = 0.6, `m_fTimeIntoTick` = 0.6 / 60 = 0.010 s; at rate 2 (a = 2,000,000) the same key gives f = 0.3 and 0.005 s; a key at the tick start gives 0; a key at the tick end (f = 1) gives the largest float below 1/60 s; an item carried from an earlier tick by the cap ("Cinematics.Evaluate" step 8) has k·H < S₀ and gives 0; and the post-wrap row: 60 Hz, D = 1 s (D·H = 6 × 10⁷), S₀ = 5.95 × 10⁷ before the wrap, a = 10⁶, so the post-wrap S₀ is −5 × 10⁵ and a key at 0 µs gives f = 0.5 and 0.5 / 60 = 0.0083 s.

At 60 Hz and rate 1, 15 ticks advance exactly 250,000 µs, so a 0.25 s blend lasts exactly 15 ticks and the weight after k ticks is exactly the float nearest k/15 — the values `Zenith2/Docs/Design/GAME/PhaseContract.md` asserts. The largest scaled value, one hour at 1,000 Hz, is 3.6 × 10¹² and fits `sint64` with a margin of 10⁶.

### Curve channels and interpolation

A channel is a sorted array of keys `{u64 time µs; f32 value; f32 in tangent; f32 out tangent; u8 interpolation; u8 reserved[3]}` (Formats.md "Key table section"). Sampling at s: binary search for the last key with time ≤ s (O(log K)); before the first key the first value, after the last the last value; between keys i and i+1 with u = (s − tᵢ) / (tᵢ₊₁ − tᵢ) as `double` then `float`:

| Interpolation (`Zenith_CinematicInterpolation`) | Value |
|---|---|
| `CINE_INTERP_CONSTANT` (0) | vᵢ |
| `CINE_INTERP_LINEAR` (1) | vᵢ + (vᵢ₊₁ − vᵢ)·u |
| `CINE_INTERP_CUBIC` (2) | cubic Hermite with tangents scaled by the interval: h00·vᵢ + h10·Δt·mᵢ⁺ + h01·vᵢ₊₁ + h11·Δt·mᵢ₊₁⁻, Δt in seconds |

Rotations are four channels (x, y, z, w) sampled per channel and normalised (a cook-time sign alignment makes consecutive keys lie within 90° of each other, so per-channel interpolation never takes the long way; Authoring.md "Cook validation rules"); a rotation channel group may instead be marked `slerp`, which interpolates the two neighbouring key quaternions with spherical linear interpolation at u (constant and cubic are refused for slerp groups at cook). Colour channels interpolate in linear space.

**Slerp.** Every slerp in CINE — slerp channel groups, the instance blend of a rotation ("Blending") and nothing else, because section blending uses a normalised sum — is one function, `Zenith_CinematicSlerp(a, b, u)`, computed in binary64 from the binary32 inputs: if a·b < 0, b = −b; d = a·b; c = |a × b| (the vector parts' cross product combined as `sqrt(|a|²|b|² − d²)` clamped at 0); θ = `Zenith_Atan2(c, d)`; when `Zenith_Sin(θ)` < 10⁻⁶ the result is the normalised linear blend `normalise(a + u·(b − a))`, otherwise `(Zenith_Sin((1 − u)·θ)·a + Zenith_Sin(u·θ)·b) / Zenith_Sin(θ)`, normalised; then each component is rounded to binary32. `sqrt` and the four arithmetic operations are correctly rounded IEEE operations; no CRT transcendental is called (the X314-FMA3 ruling).

`Zenith_Atan2` and `Zenith_Sin` are CORE's deterministic transcendental functions (`Zenith2/Docs/Design/CORE/Maths.md` → "Deterministic transcendental functions": the binary64 overloads, declared in `Zenith_Transcendental.h` and included by `Zenith_Maths.h`, bit-identical on every CPU and platform); CINE calls these two only (row CN25, answered).

### Section blending

A section is `{start µs; end µs; ease-in µs; ease-out µs; payload index; flags}`. Its weight at s is `smoothstep(clamp((s − start)/easeIn))` × `smoothstep(clamp((end − s)/easeOut))` (an ease of 0 is a step). Overlapping sections on one track blend: for transform and property tracks the outputs of the active sections are combined as a normalised weighted sum (quaternions sign-aligned to the first then normalised with `sqrt`, no transcendental); for animation tracks each section maps to its own ANIM slot play with the section ease as the slot's blend-in and blend-out ("Animation tracks"); for audio, dialogue and video tracks overlapping sections play independently. `Zenith_GetActiveCinematicSections` returns at most 8 active sections per track; the cook refuses more than 8 overlapping sections at any time (`cine.cook.overlap_limit`).

### Transform tracks

A transform track drives some of position (3 channels), rotation (4) and scale (3) of a bound slot's `Zenith.LocalTransform`, in one of three spaces (`Zenith_CinematicTransformSpace`):

| Space | Value written |
|---|---|
| `CINE_TRANSFORM_SPACE_PARENT` (0) | the sampled value is the local transform |
| `CINE_TRANSFORM_SPACE_WORLD` (1) | the sampled world transform converted into the entity's parent space with the parent's committed `Zenith.WorldTransform` (the previous propagation's value, the declared `ReadAnyRow`); an entity with no parent writes the world value |
| `CINE_TRANSFORM_SPACE_ANCHOR` (2) | the sampled value is relative to the anchor slot's committed `Zenith.WorldTransform` (an anchor is another binding slot, so a sequence authored around "Hero" plays wherever Hero stands), then converted as for world space |

Undriven components are not written. The parent of a bound entity is resolved at Begin through `Zenith_WorldPlaybackAccess` and kept in the slot's parent handle (`Zenith_CinematicBoundSlot`, saved as an entity reference) for the instance's life, so a reparent during a cinematic, a structural change the cinematic does not follow, changes no world-space write before or after a load. A transform track of a slot whose entity is a physics character controller writes the local transform; PHYS's controller adopts any other source's write ("Character move algorithm" step 1 of `Zenith2/Docs/Design/PHYS/CharacterRagdollVehicle.md`), with velocity 0.

### Camera tracks

A camera track is a transform track of the camera slot plus lens, cut and lighting channels:

| Channel group | Property written (by `Cinematics.ApplyLate`, `SetProperty`) |
|---|---|
| FovY, Near, Far | `Zenith.Render.Camera` 4 FovYDegrees, 6 NearMetres, 7 FarMetres |
| cut keys | `Zenith.Render.Camera` 10 CutRequest: committed value + 1 when the cut index changes between the previous and current tick (a seek that crosses a cut also counts one), so the camera extractor resets histories (`Zenith2/Docs/Design/RPROD/Extractors.md` → "Camera cuts") |
| FocalLength, SensorWidth, FocusDistance, FocusRange, Aperture, ShutterSeconds, ISO, ExposureCompensation, MaxCoCPixels | `Zenith.Lighting.CameraLighting` 8 FocalLengthMm, 9 SensorWidthMm, 10 FocusDistanceMetres, 11 FocusRangeMetres, 3 Aperture, 4 ShutterSeconds, 5 ISO, 6 ExposureCompensation, 12 MaxCoCPixels |
| step channels DepthOfField, MotionBlur, ExposureMode, GradingLUT, GradingLUTB, LUTBlend, VignetteIntensity, GrainIntensity | `Zenith.Lighting.CameraLighting` 7, 13, 1, 16, 17, 18, 19, 20 |

The driven CameraLighting properties are exactly 1, 3–13 and 16–20: camera tracks drive neither ManualEV100 (2), ShutterFraction (14) nor MaxBlurPixels (15). The pose is written in phase 6 like any transform track. The properties are found by stable name at attach (`Zenith_TypeRegistry::FindTypeByStableName` and the property name table), so CINE includes no Flux or LIGHT component header; a missing type (a build without the renderer) makes the group a no-op counted once (`cine.track.missing_type`). A camera track whose first section is flagged `cutIn` requests one cut at the first evaluated tick after Begin and writes the track pose at full weight from that tick (the sequence opens on a hard cut from the gameplay camera); without the flag the camera blends in from its snapshot pose like any transform track, and no cut is requested.

### Animation tracks

An animation track's sections each name a clip (`Zenith_PersistentID` of an ANIM clip), a slot (`cine.body` by default, `cine.face` for facial performance, or any slot hash the target graph declares), a clip start offset, a play rate and optionally a physics-weight channel and a forced state (machine hash, state hash). At a section's start item inside the window, `Cinematics.Evaluate` records `Zenith_RecordPlaySlot(buffer, entity, {slot hash, clip, blend-in = section ease-in or the instance blend-in for a section at the start time, blend-out = section ease-out, rate = section rate × instance rate, start time = offset + (s_cur − sectionStart), tag = ANIM_SLOT_TAG_CINEMATIC | track index, flags})`; at its end item `Zenith_RecordStopSlot` with the ease-out; a forced state is `Zenith_RecordForceAnimState` at the start (`Zenith2/Docs/Design/ANIM/Runtime.md` → "Zenith_AnimationCommands header"). Because the record is in phase 1, ANIM evaluates it in phase 3 of the same tick ([Z2-N-ARCH-489]). The slot's clip time then advances in ANIM at the slot's rate; drift between ANIM's clip time and CINE's sequence time is zero while the rates match, and `Cinematics.Evaluate` re-sends `Zenith_RecordSetSlotTime` whenever the instance rate changes, after a seek, and on resume. The physics-weight channel is written in phase 6 to `Zenith.Animation.Pose` 1 ("Blending").

Every time CINE passes to ANIM's float-second recorders (`Zenith_AnimSlotPlayDesc::m_fStartTime`, `Zenith_RecordSetSlotTime`) is converted once from integer µs with `float(double(us) / 1e6)`, so record, replay and load pass identical bits.

ANIM owns the slot semantics (`Zenith2/Docs/Design/ANIM/Graph.md` → "Slots"): CINE never re-specifies how a slot blends, binds or emits notifies. On interrupt ANIM blends the cinematic-tagged slots out with their own blend-out; on skip it empties them with an inertial take; on end it blends them out ("Lifecycle listener" there).

### Audio tracks

An audio section names an AUDIO event (`Zenith_AudioEventID` value, the 64-bit hash of the event path, carried as a number because CINE cannot include AUDIO's header), an attachment (a binding slot to follow, a fixed position, or 2D), volume dB, pitch cents and flags (`timeLocked`, default true; `stopAtEnd`, default true; `fireOnSkip`). At the section's start item CINE writes a `Zenith.Audio.PostEventPayload` by reflection ("Reflected payloads") and records `Audio.PostEvent`: header tick = t, `m_fTimeIntoTick` = the item's sub-tick offset with `uAUDIO_POST_FLAG_SCHEDULE_SUBTICK`, `uAUDIO_POST_FLAG_TIME_LOCKED` when `timeLocked`, follow-entity or at-position, and a deterministic native instance ID: `v = Zenith_Hash64` of the 16 little-endian bytes (`ulCINE_AUDIO_DOMAIN ^ instance serial` as u64, `track index << 16 | section index` as u32, the post serial as u32), `v & ~(1 | 1<<63)`, `v = 2` when 0 — AUDIO's native-ID rule (`Zenith2/Docs/Design/AUDIO/PublicAPI.md` → "Identifiers"; row CN9 asks AUDIO to confirm the domain constant `ulCINE_AUDIO_DOMAIN = 0xC1E0000000000000` keeps CINE's IDs disjoint from other native recorders). The post serial is the instance's `m_uAudioPostSerial`, incremented (staged, committed with the buffer) by every post and re-post of the instance, so every post — the first, and every re-post after a stop — carries an ID no earlier post of the instance used; AUDIO refuses a post of a live ID (`Zenith2/Docs/Design/AUDIO.md` → "Handle and identifier kinds": "a post with a live ID is refused and counted"), and a voice still fading out from a stop is still live, so reusing an ID would lose the re-post. The entry, with its serial, joins the audio list at the merge. At the section's end item, `stopAtEnd` records `Audio.StopInstance` with the section's ease-out as the fade and removes the entry; a `stopAtEnd = false` entry stays in the list (its voice may outlive the section) until the instance's `STOP_AUDIO`.

Time-locked voices follow simulation time with AUDIO's drift correction (`Zenith2/Docs/Design/AUDIO/Mixer.md` → "Time-locked voices"), which assumes the voice advances with simulation time at rate 1. CINE therefore keeps the locked relation itself, driven by the **audio list**, never by section activity (a `stopAtEnd = false` voice outlives its section, and a voice a stop removed must not come back):

| Event | Audio list and records |
|---|---|
| pause, or the rate leaving 1 (`PAUSE_PRESENTATION`) | every live time-locked entry: `Audio.StopInstance` (50 ms fade) and flag bit 2 (stopped by presentation); non-time-locked voices play on |
| resume at rate 1, or the rate returning to 1 (`RESUME_PRESENTATION`) | every entry with bit 2 while `m_uRateQ16 == uCINE_RATE_ONE_Q16` and the instance is not `PAUSED`: a fresh post serial, `Audio.PostEvent` or `Audio.PlayDialogue` with the new ID, then `Audio.SeekInstance` of the new ID to `(s_cur − sectionStart) / 1,000` ms; bit 2 cleared. Skipped when `STOP_AUDIO` is pending in the same side work (an instance saved in its interrupt tick carries both, and the stop wins) and for a content-changed instance; the bit is consumed either way ("Side work", consumption) |
| a time-locked audio or dialogue section's start item while `m_uRateQ16 ≠ uCINE_RATE_ONE_Q16` | the entry joins the audio list with bit 2 and posts nothing (staged); the next `RESUME_PRESENTATION` at rate 1 posts it with a fresh serial and seeks it to `(s_cur − sectionStart) / 1,000` ms, so a section that starts during a 0.5× preview plays in sync after the return to 1. A non-time-locked section posts as at rate 1 |
| a load (`RestoreSection`) | AUDIO saves no voice ("audio state is presentation and never saved", `Zenith2/Docs/Design/AUDIO.md` → "Areas that consume AUDIO", row SAVE): every time-locked entry gets bit 2 (re-posted by a `RESUME_PRESENTATION` at rate 1 outside `PAUSED`, so a paused or rate-changed instance re-posts it only at its resume), every other entry gets bit 3 (lost: re-posted by the first `RESUME_PRESENTATION`, even while `PAUSED` and whatever the rate, because non-time-locked voices play through a pause) |
| `STOP_AUDIO`, `STOP_TAKEN_OVER_SLOTS` | a live entry (bits 2 and 3 clear) records `Audio.StopInstance`; a stopped or lost one records nothing (its voice no longer exists); the entry is removed |
| a seek ("Seeking and scrubbing" step 2) | `Audio.SeekInstance` alone for a live entry whose section stays active |

The 50 ms stop fade therefore never collides with a re-post: pause and resume in one tick, or a rate 1 → 2 → 1 within 50 ms, stop the voice with its old ID and re-post it with a new one (`Test_CinematicTracks_Audio_PauseResumeWithinFade_Replays`). AUDIO pauses time-locked voices with the world clock (sim pause), which needs no CINE action.

### Event tracks

An event key names an event type by stable name, a payload (property name → value, values typed by the registry), a `fireOnSkip` flag and a `fireOnSeek` flag. Property values may be the literal `$binding:<Slot>`, replaced at queue time by the slot's entity handle (null when unbound), `$instance` (the instance ID) or `$time` (the key's time in µs). The key's payload is built into a template by reflection when the sequence's template-cache entry is built ("Reflected payloads"), and at fire time the template is copied and the `$` fields patched. Keys in the window are queued in the outbox in key order; `Cinematics.EmitEvents` emits them.

### Dialogue tracks

A dialogue section names an AUDIO dialogue line (`Zenith_AudioDialogueLineID` value, the hash of the line ID text), the speaker slot (the entity the line follows), an optional face clip (a CHAR lip-sync clip, played in slot `cine.face` by the lip-sync rule below), the caption keys (the subtitle localization key, the speaker localization key, the speaker colour index) and flags (`fireOnSkip` for its caption, never for its audio). At its prepare item, `start − cine.audioLeadSeconds` (or at Begin when that is earlier), CINE records `Audio.PrepareDialogue` and a prepare record with the recording tick; at its start item it records `Audio.PlayDialogue` with the header's `uAUDIO_POST_FLAG_TIME_LOCKED` and sub-tick offset and a deterministic instance ID as for audio sections, and queues its caption cue ("Subtitle tracks").

**Lip-sync face clips** (CHAR's rows CH3 and CH19, answered by row CN26; `Zenith2/Docs/Design/CHAR/Facial.md` → "Lip-sync playback contract"). One face clip serves every voice locale: window w of the clip starts at its marker `char.lipsync.<tag>` (time T_w) and ends at its first `char.lipsync.windowEnd` event after T_w (time e_w) ("Window markers and events" there). CINE follows CHAR's contract without reading a clip at run time:

1. **Cooked window table.** The `cine.sequence` step reads the face clip's markers and instant events from the `anim.clip` step's published property `anim.clip.markers` (row CN27) and writes, after the section's dialogue payload ("Section table section" of `Zenith2/Docs/Design/CINE/Formats.md`), one record `{ u64 marker name hash (Zenith_Hash64 of "char.lipsync.<tag>"); u64 T_w µs; u64 e_w µs }` per window, in the clip's marker order, at most 16 (`uCINE_MAX_LIPSYNC_WINDOWS`; cook rule `cine.cook.lipsync_windows`). A face clip with no `char.lipsync.*` marker gets an empty table and plays from 0 for the section's duration, as an animation section does.
2. **The voice locale.** `Zenith_CinematicStartDesc::m_xVoiceLocale` and the start payload's property 12 carry the simulation voice-locale tag (a `Zenith_StringID`; the empty ID means window 0), which a script fills from AUDIO's recorded dialogue locale (`Zenith.Audio.DialogueLocale` `EffectiveTag`, `Zenith2/Docs/Design/AUDIO/Mixer.md` → "Recorded dialogue locale", ruling GmB33-DIALOGUE-LOCALE; `Cinematics.Start` option `voiceLocale`, a player autostart from `Zenith.Cinematics.Player` property 11 `VoiceLocale`). The start playback stores it in `m_xVoiceLocale`; it is saved with the instance as text, so the window a restored instance plays is the window the uninterrupted run played.
3. **Choosing the window.** At the section's start item CINE resolves w by CHAR's order: the table record whose hash equals `Zenith_Hash64` of `"char.lipsync." + text(m_xVoiceLocale)` (the text read once per evaluation with `Zenith_StringTable::GetText`, ANY_THREAD), else the record of the language subtag (the text before the first `-`: `fr-CA` → `char.lipsync.fr`), else window 0 (T = 0 and e = the first window's end, or the section end for an empty table). The choice is a pure function of the cooked table and the saved tag, so it is recomputed, never stored, wherever it is needed.
4. **Start.** `Zenith_RecordPlaySlot(buffer, speaker entity, { slot `cine.face`, clip, blend-in = section ease-in, blend-out 0.1 s, rate 1 × instance rate, start time = T_w + (s_cur − sectionStart), tag = `ANIM_SLOT_TAG_CINEMATIC | ANIM_SLOT_TAG_FULL_RATE`, flags 0 })`, in the same tick buffer as the section's `Audio.PlayDialogue` (time-locked). A seek into the section, a paused hold (step 5 (b) of "Cinematics.Evaluate") and a rate change use `T_w + (time − sectionStart)` as the slot time likewise.
5. **Stop.** Every window record w also produces a fire item of the section, of kind window-end w, at sequence time `sectionStart + (e_w − T_w)` (written by the cook only when that time is below the section's end; see the fire-item key layout). Processing it records `Zenith_RecordStopSlot(buffer, speaker, cine.face, 0.1)` when w is the window step 3 chooses for the instance, and nothing otherwise. Because CINE records the stop in phase 1 at the tick whose advance crosses e_w, ANIM applies it in phase 3 of the same tick, one tick earlier than a script's notify-driven stop, so CHAR's window bound ("Why the stop never crosses the window" there) holds with a tick to spare; the section's end item still stops the slot when the section ends first.

CHAR's lip-sync contract is the one `Zenith2/Docs/Design/CHAR/Facial.md` → "Lip-sync playback contract" states, with CINE's cooked table replacing the run-time marker read and CINE's window-end fire item replacing the `char.lipsync.windowEnd` notify (row CN26). ANIM's slot tag bit 14 `ANIM_SLOT_TAG_FULL_RATE` (row CH16) and the `anim.clip.markers` property of the `anim.clip` step (row CN27; `Zenith2/Docs/Design/ANIM/Formats.md` → "Clip published properties") are ANIM's. The tag scripts pass is AUDIO's recorded `Zenith.Audio.DialogueLocale` `EffectiveTag` (ruling GmB33-DIALOGUE-LOCALE).

### Subtitle tracks

A subtitle section is a caption cue without audio: localization key, speaker key, kind (`subtitle` or `sound` for a sound caption), priority (default 128), speaker colour index, start and duration. Every caption CINE shows (subtitle sections and dialogue lines) carries a source identity, so UI can remove exactly the cue CINE queued:

- **Source ID.** `(1 << 52) | (k << 51) | ((instance serial mod 2²⁸) << 21) | (track index << 12) | section index` (track < 512, section < 4,096; k = 1 for a cue a skip fired, "Skip playback" step 1, else 0; bits 49 and 50 are 0), a value below 2⁵³ that a script reads exactly.
- **Queue.** At the section's start item CINE queues one `Zenith.Runtime.CaptionCueEvent` with the fields of `Zenith_UICaptionCue` (`Zenith2/Docs/Design/UI/Accessibility.md` → "Caption cues"): key and speaker key as `Zenith_StringID` (interned at load, "Reflected payloads"), kind, priority, speaker colour, duration ticks and the source ID. UI sets the cue's start tick when it receives it (`Zenith_UICaptionCue::m_ulStartTick`, no event property). The duration in ticks is `ceil(remaining µs × H × 65,536 / (1,000,000 × rateQ16))` in `uint64` (≤ 3.6 × 10⁹ × 1,000 × 65,536 ≈ 2.4 × 10¹⁷), the remaining sequence time of the section scaled by the rate; at the section start the remaining time is the section's duration.
- **Caption list.** Each instance keeps what it queued in `m_axCaptions` (16 entries `{ u64 source ID; u64 expiry tick }`, saved): an entry is added (staged, committed with the buffer that carries the cue) with expiry `UINT64_MAX`; when `Cinematics.Evaluate` removes the cue's outbox entry as accepted, it sets the expiry to the acceptance tick + duration ticks, which is UI's `m_ulStartTick + duration` (UI sets the start tick when it receives the cue in phase 9 of the emission tick); an entry is expired, and removed, once t ≥ its expiry; a cancel removes it. The cook bounds simultaneous caption sections (`cine.cook.caption_overlap`: at most 16 subtitle and dialogue sections active at any time), so the list fills only while rejected emission groups hold expiries back; a cue that finds it full first cancels the entry with the smallest expiry tick (lowest source ID among equals), counted `cine.captions.evicted_delta`.
- **Cancel.** `Zenith.Runtime.CaptionCancelEvent { SourceID }` removes the cue with that source ID from UI's queue. CINE queues a cancel for every caption list entry that has not expired (expiry > t) when the instance pauses or its rate leaves 1 (`PAUSE_PRESENTATION`), when a seek leaves the section, when the rate changes between two rates above 0 (followed by a re-queue, `REQUEUE_CAPTIONS`), and on skip, interrupt and end (`CANCEL_CAPTIONS`). A cue whose outbox entry is not yet emitted is cancelled the same way: its cancel follows it in the same instance's emission order, so UI receives the cue and then its cancel.
- **Re-queue (list-driven).** The caption re-queue of `RESUME_PRESENTATION` (a resume at rate 1, a rate back to 1, after a load) and `REQUEUE_CAPTIONS` (a resume at another rate above 0, a rate change between rates above 0) acts on the caption list, never on section activity, so a caption an interrupt, skip or end removed (`CANCEL_CAPTIONS` removes entries outright) never comes back: it cancels every listed, unexpired, unmarked caption and marks it, then, for every marked entry whose section is active at s_cur, queues the cue again with the remaining duration at the current rate and clears the mark (the entry's expiry returns to `UINT64_MAX` until the new cue is accepted); a marked entry whose section is no longer active at s_cur is removed. A load marks every listed entry ("Save and restore"). Only a seek re-queues by section activity ("Seeking and scrubbing" step 3): it cancels and removes every listed entry and queues a cue per subtitle and dialogue section active at the target, except in a `BLENDING_OUT` instance whose end reason is `INTERRUPTED` or `FAILED`, where it queues none (its captions ended with the interrupt). Rate 0 cancels and never re-queues (the duration divides by the rate), and a `PAUSED` instance re-queues nothing until it resumes (`Test_CinematicCaptions_InterruptThenPauseResume_NoResurrection`).

So the caption on screen follows the sequence time in every non-linear case (`Test_CinematicTracks_Subtitle_PauseSeekSkipKeepsCaptionInSync`). UI presents the cue; CINE never formats or localizes text.

### Property tracks

A property track names a component type and property by stable name (`"Zenith.Render.Light"`, `"Intensity"`), interpolation (curve for `f32`, `vec*`, `quat`, `colour`; step for `bool`, integers, enums, asset references and strings), and keys. When the template-cache entry is built, CINE resolves the type and property IDs and checks the value type against the channel layout (`CINEMATIC_ERROR_PAYLOAD` disables the track, counted once). `Cinematics.ApplyLate` records the blended value. A property that is arbitrated (any rule) is refused at cook (`cine.cook.arbitrated_property`): arbitrated properties are written only by transform, camera and animation tracks through the phase-6 writer.

### Command tracks

A command key names a registered module command kind by name (`"VFX.Spawn"`, `"Gameplay.ApplyEffect"`), its payload type by stable name, a payload by property name with the same `$` substitutions as event tracks, and `fireOnSkip`. CINE resolves the kind ID and the payload layout per sequence, when its template-cache entry is built, from the process command kind table (immutable after Start); a kind absent from the build disables the track (`CINEMATIC_ERROR_KIND_MISSING`, counted and logged once per world). The kind's `m_uAllowedPhaseMask` must include phase 1; otherwise the cook (with the kind table of the game's build) and the template build refuse it. `VFX.Spawn` (`Zenith.VFX.SpawnPayload`) is the Stage 5 case: VFX lands in Stage 5, so command tracks naming it evaluate from Stage 5, and a Stage 4 CinematicSlice uses no VFX keys.

### Overlay tracks

Channels: fade colour (RGB linear), fade alpha [0, 1], letterbox fraction [0, 0.5] of the output height. `Cinematics.ExtractRender` writes them as one overlay record; the VideoComposite pass draws the fade and the letterbox bars after the video layers (Video.md "VideoComposite pass"). The overlay is presentation: it is extracted, not written into the world, and a headless run evaluates it but writes nothing.

### Video tracks

A video section names a video asset, a media start offset, a layer, a placement (full screen with a fit mode, or a normalised rectangle) or a texture surface name, opacity and `pauseWithInstance`. The section's media time is `offset + (s_cur − sectionStart)` plus, when `pauseWithInstance` is false, `m_iVideoPauseOffsetUs`, which `Cinematics.Evaluate` step 5 advances by `(1,000,000 + H / 2) / H` µs for every tick the instance spends `PAUSED` and keeps after the resume (the video plays on while the sequence is held). `Cinematics.ExtractRender` writes a `Flux_VideoDrawDesc` with the media time each frame, interpolated by the extraction alpha (`s_cur + alpha · a / H`, where alpha is the simulation clock's interpolation alpha, 0 in external-ticks mode) so the video advances smoothly between ticks; a paused instance with `pauseWithInstance` true writes the same media time every frame. The video's audio is a separate AUDIO sound cooked from the container (Formats.md "Cooked video file"), posted by CINE as a time-locked audio section generated at cook, so its sync obeys "Audio tracks". Because that audio stops with the instance's pause while a `pauseWithInstance = false` video plays on, the cook refuses `pauseWithInstance: false` on a section whose video has an audio sound (`cine.cook.video_pause_audio`), so video and its audio are never offset by a pause. Decoding and presentation are `Zenith2/Docs/Design/CINE/Video.md`; no decode state reaches the instance (`m_uVideoPlayerMask` stays 0 in simulation).

### Marker tracks

A marker key queues `Zenith.Cinematics.Marker` with the marker's interned name (`Zenith_StringID`), index, time and tag. Markers are also seek targets: the editor and `Cinematics.Seek` callers find them with `Zenith_Cinematic::FindMarker` and `Cinematics.GetMarkerTime` (`Zenith2/Docs/Design/CINE/PublicAPI.md` → "Luau surface").

### Reflected payloads

A payload by property name (events, command keys, audio payloads) is built without the C++ struct: CINE takes the type's `Zenith_TypeLayout` (`Zenith2/Docs/Design/ECS/Reflect.md` → "Zenith_TypeLayout header"), and for each authored property writes the value in the property's reflected value encoding at its offset into a template of the type's size (zero-initialised, then the type's defaults applied by `Zenith_TypeRegistry`). A property name the type lacks, a value of the wrong kind, or a payload above `uCINE_MAX_EVENT_PAYLOAD_BYTES` disables the key (`CINEMATIC_ERROR_PAYLOAD`, counted). Templates live in the sequence's bound-set entry ("Bound set"), built once when the binding is published in the world (by the publication handler) or rebuilt by `RestoreSection`, together with the sequence's command-track kind IDs; they are freed with the entry, when its last holder goes. String-valued fields (marker names, caption keys, speaker keys, string properties) are `Zenith_StringID`s interned by the kind loader at load ("Runtime layout" of `Zenith2/Docs/Design/CINE/Formats.md`), so building a template interns nothing.

## Blending

The instance weight w ∈ [0, 1] combines the cinematic's value C (the track evaluated at s_cur) with a base per written value. B_in is the blend-in base: the snapshot value, or for a taken-over entity the take-over base. w₀ is `m_fHoldWeight`, the weight the blend-out started from (1 for a natural end; the current weight for an interrupt or a FAILED end).

A `PAUSED` instance is written with the rule of the state it left (`m_ePausedFromState`) at the paused weight, so neither a pause nor a resume changes a written value: paused from `BLENDING_IN` or `PLAYING` it uses the first column, paused from `BLENDING_OUT` the second (with w₀ kept).

| Value | Written during `BLENDING_IN`, `PLAYING` (and `PAUSED` from them) | Written during `BLENDING_OUT` (and `PAUSED` from it) | Written in the end tick |
|---|---|---|---|
| a restore-flagged property (any channel) | `lerp(B_in, C, w)` (slerp for rotations, "Curve channels and interpolation"; per-channel for colours) | `lerp(B, X, w / w₀)` with B the snapshot value and X = `lerp(B_in, C, w₀)`; B when w₀ = 0 (slerp for rotations, both lerps) | B |
| a written, not restore-flagged property | `lerp(B_in, C, w)` | `lerp(B_in, C, w₀)` (held) | `lerp(B_in, C, w₀)` |
| `Zenith.Animation.Pose` 1 PhysicsWeight | as a restore-flagged property | as a restore-flagged property | B |
| camera CutRequest, step channels | C (never blended) | C | C |

The flagged blend-out rule is continuous at both ends for every entity: at the blend-out's start (w = w₀) it equals X, the value the blend-in rule wrote at w₀, including for a taken-over entity whose B_in (P's output) differs from B (the pre-first-cinematic value), so an interrupt during the blend-in of a taken-over entity does not jump by `(1 − w₀)·(B − B_in)`; at w = 0 it equals B. When B_in = B it reduces to `lerp(B, C, w)`, the linear fall GAME's interrupt test asserts.

A non-flagged property never jumps when the blend-out ends: it holds `lerp(B_in, C, w₀)`, which is also its value after the restore ([Z2-N-ARCH-555]); for a natural end w₀ = 1 and the held value is C. An interrupt during the blend-in starts the blend-out from w₀ < 1, so an unflagged property keeps the weight it had and does not jump to C (`Test_CinematicBlend_InterruptDuringBlendIn_UnflaggedNoPop`: an interrupt at 2/15, where every tick's unflagged value differs from the previous one by no more than the track's own per-tick change). A flagged property falls linearly from w₀ to its snapshot value, arrives at it in the end tick and the boundary restore writes the identical bits; this is the linear fall `Zenith2/Docs/Design/GAME/PhaseContract.md` → "Per-command tests" asserts for `Test_Lifecycle_Cinematic_InterruptBlendsOut`. For a restore-flagged property of a taken-over entity, the blend-in base is the take-over base and the blend-out base the moved snapshot, so the entity blends in from P's last output and blends out to its pre-cinematic state (`Test_CinematicBlend_TakeOverInterruptDuringBlendIn_FlaggedNoPop`). A pause during the blend-out holds the blend-out's value and the resume continues it (`Test_CinematicBlend_PauseDuringBlendOut_NoPop`); an interrupt of an instance paused from a completed blend-out is ignored, so w₀ = 1 stays.

Instance blending composes with section blending: a section weight multiplies the section's contribution inside the track; the instance weight applies to the track's result.

## Seeking and scrubbing

A pending seek to target g is applied by `Cinematics.Evaluate`: for an instance in `BLENDING_IN`, `PLAYING` or `BLENDING_OUT` at step 6.1, before the advance; for a `PAUSED` instance at step 5 (a), with no advance (the paused form below). Every record goes into the instance's tick buffer and every world-record change is staged with it:

1. For every animation section active at g: `Zenith_RecordPlaySlot` if the section was not active at s_cur (blend-in 0), else `Zenith_RecordSetSlotTime` to `offset + (g − start)`; for every section active at s_cur and not at g: `Zenith_RecordStopSlot` with blend-out 0. ANIM fires no notifies for the jumped interval. Paused form: the same records (step 5 (b) then holds the slots at g).
2. Audio and dialogue, by the audio list ("Audio tracks"): an entry whose section is not active at g is removed, recording `Audio.StopInstance` (`AUDIO_STOP_MODE_IMMEDIATE`) when it is live; a live entry whose section is active at both s_cur and g records `Audio.SeekInstance` of its ID to `(g − sectionStart) / 1,000` ms alone (no re-post: its ID is live); a section active at g and not at s_cur posts with a fresh post serial, then `Audio.SeekInstance` to `(g − sectionStart) / 1,000` ms when above 0, and joins the list; in a `BLENDING_OUT` instance whose end reason is `INTERRUPTED` or `FAILED` an entering section posts nothing and does not join (its audio ended with the interrupt). Paused form, and while the rate is not 1: a live time-locked entry whose section stays active gets `Audio.StopInstance` (50 ms fade) and flag bit 2 instead of a seek, an entering section joins the list with bit 2 and posts nothing, and stopped or lost entries (bits 2, 3) only stay or leave; the re-post at the resume then starts every such voice at the resume's s_cur.
3. Captions: a cancel for every listed, unexpired, unmarked caption, the list emptied, then a cue per subtitle and dialogue section active at g with the remaining duration, each listed — none in a `BLENDING_OUT` instance whose end reason is `INTERRUPTED` or `FAILED` ("Subtitle tracks", the seek is the one section-driven re-queue). Paused form: the cancels, keeping each cancelled entry marked cancelled by presentation, and for every caption section active at g and not listed a marked entry with its source ID; the resume re-queues the marked entries whose section is active at the then-current time.
4. Events, markers and command keys in the jumped interval fire only with the seek's fire-events flag and the key's `fireOnSeek` flag, in key order of the interval (backwards seeks fire none); the same for the paused form.
5. Camera: nothing here; the cut a seek crosses is detected by `Cinematics.ApplyLate`, which compares the camera track's cut index at the new s_cur with the index stored in the cut channel's late-cache entry ("Cinematics.ApplyLate").
6. `m_iTimeScaled = g × H`, `m_iPrevTimeScaled = g × H`, `m_ulNextItemKey = (g + 1) << 26` (so the next advance evaluates (g, g + a]); the prefetch bits of sections starting after g are cleared; seek-pending and seek-fire-events are cleared. All of step 6 is staged with the tick buffer and committed at its acceptance ("Cinematics.Evaluate" step 6.5), for both forms, so a rejected buffer leaves the seek pending and the pre-seek time, and the next tick re-applies the whole seek from the same s_cur (`Test_CinematicPlayback_MergeCapacityRejection_RerunsWhole`).

**Scrubbing** is seeking a paused instance: the editor's sequencer preview ("Sequencer panel" of `Zenith2/Docs/Design/CINE/Authoring.md`) records `Cinematics.Seek` (through `Zenith_RecordSeekCinematicUs`) into its preview world each time the playhead moves, with the instance started `uCINE_START_FLAG_PAUSED`; the Evaluate of the next tick applies it while paused (step 5 (a)), and `Cinematics.ApplyTransforms` and `Cinematics.ApplyLate` then write the paused instance's values at the new s_cur and the paused weight every tick, so a scrubbed pose is the same value a played tick at that time writes. A paused seek re-posts no audio and queues no caption: both wait for the resume, which re-posts and re-queues at the time it resumes from (`Test_CinematicScrub_PausedMatchesPlayedTick`). The pure evaluator ("Zenith_CinematicEvaluator header") gives the same values for the timeline widget's curve previews without a world.

## Determinism rules

- Every CINE output is a function of the cooked sequence, the start payload, the commands applied to the instance, the tick index, the tick rate and the committed world values read through declared access; CINE reads no wall clock, no device time, no asset residency outside published completions, no memory-pressure level, and no decode state (Z2-D-019).
- Instance IDs are a per-world serial; tickets hash the recording merge key; audio instance IDs and caption source IDs derive from the instance serial and the section; iteration is in ascending instance ID, then fire-item key order.
- Time is integer ("Time arithmetic"); weights are a single division per tick of exact integers; curve sampling is the same code in `Cinematics.Evaluate`, the playbacks and the evaluator.
- No simulation-affecting CINE code calls a CRT transcendental (`std::sin`, `std::acos`, `std::atan2` and the rest): slerp uses CORE's deterministic `Zenith_Atan2` and `Zenith_Sin` ("Curve channels and interpolation"), and every other operation is arithmetic or `sqrt`, so a replay recorded on one machine reproduces on another of the same build (the X314-FMA3 ruling).
- Capacity outcomes (the record cap, the outbox admission, the merge's `TryAccept`, the load bound) depend only on committed state, so a deferral happens at the same tick in every run. The load bound counts a need from its allocation to its publication only, both fixed by recorded state; the drain of ASSET's completion record, whose tick depends on I/O, sizes only the completion queue (capacity 128) and never gates an allocation ("Asset binding" step 1).
- Video decoding, presentation interpolation by the extraction alpha, memory shedding and capture never write simulation state; they read the instance's state from the render world only.
- A seek, a skip and a restore are all recorded commands or deterministic boundary work, so `--replay` reproduces them; the replay determinism tests run the CinematicSlice playthrough under the replay matrix (`Zenith2/Docs/Design/CINE/Tests.md` → "Determinism and save tests").

## Save and restore

CINE registers one `Zenith_SaveParticipant` per world named `Zenith.Cinematics.Playback`, section version 1, implementing every member of `Zenith2/Docs/Design/SAVE/PublicAPI.md` → "Zenith_SaveParticipant header" (row SV17), registered at `AttachWorld` step 3 through `Zenith_WorldAttachContext::RegisterSaveParticipant` (`Zenith2/Docs/Architecture/CompositionRoot.md` → "Module interfaces").

| Member | CINE's answer |
|---|---|
| `GetName` | `"Zenith.Cinematics.Playback"` |
| `GetSectionVersion` | 1 |
| `GetFlags` | 0 (included in every image kind, resume images among them) |
| `DeclareAccess` | reads `Zenith.Cinematics.World` |
| `CollectExcludedEntities` | none |
| `CaptureSection` | Formats.md "Save section": every part, every field of every live and `RELEASED` instance record and its block, every entity reference through `Zenith_SaveSectionWriter::WriteEntityReference`; before writing the caption lists it applies step 0's expiry rule for tick t ("Emission acceptance"): every entry whose cue's outbox entry has its acceptance bit set for t is written with expiry `t + duration ticks` |
| `GetCaptureFidelity` | EXACT |
| `GetReissuedSourceKinds` | the bit of `ASYNC_SOURCE_CINEMATICS` |
| `RestoreSection` | rebuild the world record with the **running** configuration's M′ (the pool of M′ records and the outbox of 256 + 10·M′ + 64 entries; the saved M, carried in the world prologue, is used only to refuse a section with M > M′, so the saved S + Q ≤ 256 + 10·M + 64 fits and the outbox proof holds from the first tick); re-acquire every sequence handle; re-issue exactly the needs in state 1 (issued) with their recorded completion IDs, `Zenith_SaveReissueSet::MarkReissued` first, and restore states 2, 3 and 4 (parked success, parked failure, abandoned) as completed records whose publications SAVE's async section puts back, never re-issued (X255: an ID is completed once); count every restored need, abandoned ones included, in the allocation gate until its publication only ("Asset binding" step 1); entity references through `ReadEntityReference`; rebuild every bound-set entry's template from the resident asset (an entry whose content hash differs from the resident asset's is dropped, its holders released, and a preload holding it returns to requested with a fresh need; a content-changed instance's pending `SKIP_KEYS` is then discarded, "Side work"); set `Zenith.Cinematics.Emission`'s `m_ulTick` to 0; mark the audio list as "Audio tracks" states for a load (bit 2 on time-locked entries, bit 3 on the others) and every caption list entry cancelled by presentation (UI saves no caption); set presentation-resume (and side work `RESUME_PRESENTATION`) on every instance in `BLENDING_IN`, `PLAYING`, `PAUSED` or `BLENDING_OUT` that has audio list or caption list entries, because AUDIO and UI save no voice and no caption (the side work's own rules then re-post and re-queue at once or at the resume) |
| `IsRestoreReady` | true when every sequence a live instance or a bound-set entry holds is resident, every preload entry's GUID is resident, and every parked-success need's GUID is resident (its `PUBLICATION_KIND_GENERIC_RECOMPUTED` publication at t + 1 reads the resident asset, `Zenith2/Docs/Design/SAVE/Formats.md` → "Async section") |
| `ListRestoreWaits` | the GUIDs of those three sets not yet resident |

A save runs in phase 11 of tick t; the restored world continues with the boundary t → t + 1 and tick t + 1, exactly as the uninterrupted run did. What the section therefore carries, beyond the obvious time and weight fields: the outbox entries not removed by the next Evaluate (every entry whose acceptance bit for tick t is clear: those queued after phase 7 of tick t and those whose emission group the merge rejected); each instance's outbox reservation, post serial, voice-locale tag and caption list, the caption list with tick t's acceptances already applied to its expiries (the restore zeroes the acceptance resource, so step 0 of t + 1 would otherwise never apply them); the bound set; the end-state run of a skip played after phase 6 of tick t (written by boundary step 2.1); every take-over base and base-capture pending bit; each slot's taken-over tick; `m_ePausedFromState` and `m_fPausedWeight`; every prepare record with its recorded tick; `m_xPlayer`; the side work; the audio list; the late cache; the prefetch bits; `m_ulNextItemKey`; the player-start entries and the ticket entries. Because the participant is EXACT and every value is integer or a float stored bit for bit, a restore followed by N ticks equals the original run's N ticks (Q70 (a), Q82 (b)), one test per field in `Zenith2/Docs/Design/CINE/Tests.md` → "Determinism and save tests".

**Re-cooked content.** A restore whose sequence content hash differs from the resident asset's (the content was re-cooked between save and load) does not evaluate the new content against the saved times:

| Saved state | Restored as |
|---|---|
| `BINDING`, `PREPARING` | cancelled at restore: ticket entry `CINEMATIC_ERROR_CANCELLED`, `Ended` with `CANCELLED` queued, released; no lifecycle event (none was dispatched) |
| `BLENDING_IN`, `PLAYING`, `PAUSED`, `BLENDING_OUT` | the saved state with content-changed set: the first `Cinematics.Evaluate` records `Cinematics.End` with `FAILED` and evaluates nothing else; the End playback dispatches `LIFECYCLE_EVENT_CINEMATIC_END` with a null entity and per bound slot (so GAME's director resumes and ANIM blends its cinematic-tagged slots out), queues `Ended`; the end tick writes only restore-flagged properties at their snapshot values; the boundary restores the snapshot |
| `ENDED`, `RELEASED` | as saved (END or SKIP was dispatched before the save; the restore of an `ENDED` instance runs at the first boundary, `m_ulEndTick` ≤ the tick just finished) |

`cine.save.content_changed` is logged once per instance (`Test_CinematicSave_ContentChanged_EndsFailedRestores` asserts END dispatched once and the director resumed).

## Lifecycle listener

`Zenith_CinematicsLifecycleListener`, registered per world with `AddLifecycleListener`, interest mask `LIFECYCLE_EVENT_DESTROY_PENDING | LIFECYCLE_EVENT_TELEPORTED`, runs on the sync-point node and writes only CINE's world record (`Zenith2/Docs/Design/SCENE/SceneAPI.md` → "Zenith_LifecycleListener header").

| Event | Effect |
|---|---|
| `LIFECYCLE_EVENT_DESTROY_PENDING` of a bound entity | drop the slot in the instance holding it ([Z2-N-ARCH-556]); release its snapshot entries; the instance ends `FAILED` when a slot flagged `uCINE_BINDING_FLAG_REQUIRED` is dropped and no other slot with that flag is bound: the next Evaluate records `Cinematics.End` with `FAILED` |
| `LIFECYCLE_EVENT_TELEPORTED` of a bound entity | none for the cinematic's values; an anchor slot's teleport moves anchor-space tracks with it at the next phase 6 (their base is the committed world transform) |

The listener ignores the four cinematic events it dispatches itself.

## Tick-boundary handler

`Zenith_CinematicsTickBoundaryHandler` (`Zenith2/Docs/Design/ECS/Scheduling.md` → "Tick boundary and end-of-tick"), registered per world at AttachWorld step 3:

`Zenith_WorldAttachContext::AddTickBoundaryHandler(Zenith_TickBoundaryHandler&)` (`Zenith2/Docs/Architecture/CompositionRoot.md` → "Module interfaces", X313 (c)) forwards to `Zenith_WorldSimulation::AddTickBoundaryHandler` (`Zenith2/Docs/Design/ECS/WorldAPI.md` → "Zenith_WorldSimulation header"), journaled and undone with the module.

| Step | Work |
|---|---|
| `TICK_BOUNDARY_STEP_PUBLISH_ASYNC` (1) | none in this handler: CINE's publications reach `Zenith_CinematicsPublicationHandler` at this step through MOD's forwarder, which resolves bindings there ("Asset binding" step 3) |
| `TICK_BOUNDARY_STEP_RESTORE_CINEMATICS` (2) | 2.1 for every instance with skip-after-phase-6, write its end-state run with `SetProperty`; 2.2 for every slot with base-capture pending (a take-over of an active holder, or of an `ENDED` holder), read N's take-over base run (`ReadProperty` of each written property of the slot, `ReadContainer` for a container) and clear the bit — before 2.3, so an ended holder's end-tick output is what N captures; 2.3 for every instance in `ENDED` with `m_ulEndTick` ≤ the tick just finished, in ascending instance ID: restore the snapshot ("Pre-cinematic snapshot", restore), free the block, set `RELEASED`; 2.4 clear every skip-applied and skip-after-phase-6 bit; 2.5 free the records of `RELEASED` instances whose ticket window passed, whose side work is empty and of whose instance ID no outbox entry remains, removing each one's bound-set holder; 2.6 free the ticket entries whose window passed |

The handler records nothing ([Z2-N-ARCH-508]; `Zenith_TickBoundaryHandler` "never records commands"): what follows a restore is side work. Property writes through `Zenith_TickBoundaryAccess` are property-only and change no structure (`Zenith2/Docs/Design/ECS/WorldAPI.md` → "Zenith_ECSObservers header"). The step-2 order between modules is registration order; only CINE restores cinematics.

## World transition and shutdown

`DetachWorld` (world transition or shutdown, `Zenith2/Docs/Architecture/LifecycleCommands.md` → "World transition"), on the main thread. A detaching world dispatches no cinematic lifecycle event: `DetachWorld` runs outside every tick and has neither a `Zenith_WorldPlaybackAccess` nor a follow-up buffer, and SCENE's dispatcher runs only on the world's sync-point node (`Zenith2/Docs/Design/SCENE/SceneAPI.md` → "Zenith_LifecycleListener header"); every listener's per-world state is destroyed with the world in the bulk teardown, so there is nothing for an event to release. Every instance is freed without event and without restore:

1. Complete every completion ID CINE allocated and has not completed, in ascending ID: `RequestCancel` on the need's operation handle, then `Park(id, ASYNC_SOURCE_CINEMATICS, PUBLICATION_KIND_GENERIC_RECORDED, empty)` through the sink ([Z2-N-SCRIPT-931]; the sink accepts parks after `DetachWorld`, and a retired table discards them); then wait (as an operation drain) for each load to report complete before freeing the completion queue.
2. Unregister the participant, the tick-boundary handler and the listener; set the publication handler entry's record pointer to null; free the record.

Video players are presentation and belong to the module, not to the world ("Video players" of `Zenith2/Docs/Design/CINE/Video.md`): once the world detaches, its extractor writes no draw record, so its players close by draw-record absence within two consumed render worlds; `DetachWorld` touches nothing on the render-submit thread. A carry-over entity of a transition is never bound across worlds: an instance belongs to one world.

## Memory consumer

The module's `Zenith_MemoryConsumer` `Cinematics` reports, for `MEMORY_SUBSYSTEM_ASSETS`, the resident bytes of every `Zenith_Cinematic` and the resident sections of every `Zenith_VideoAsset`, the world records with their snapshot pools and templates, and the decoder's frame buffers (CPU) — the CPU side of `Z2-B-CINE-001` — and, through the renderer's GPU accounting, the video textures (the VRAM side of the dual-resident row).

The Cinematics row of `Zenith2/Docs/Architecture.md` → "Shedding per subsystem" (X313 (a)) is presentation only: at WARNING every video player's decode-ahead trims to 2 frames; at CRITICAL the video players of sections not visible this frame stop; never a cinematic sequence, a preload pin or any state simulation reads (memory pressure is not a recorded input, Z2-D-019).

CINE implements that row ([Z2-N-ARCH-814], [Z2-N-ARCH-822]) and adds only this implementation detail: the render-submit thread applies the level within one frame of the governor's change ([Z2-N-ARCH-821]) by storing the decode-ahead limit (2 at WARNING, `cine.video.decodeAheadFrames` otherwise) into each player's atomic limit read by the video thread ("Video thread" of `Zenith2/Docs/Design/CINE/Video.md`), and at CRITICAL by closing every player whose key had no draw record with `m_fOpacity > 0` inside the output in the last consumed render world. The counters proving it ran are `cine.video.shed_trimmed_delta` (players trimmed) and `cine.video.shed_stopped_delta` (players stopped). `Test_CinematicMemory_PressureLevels_Shed` forces WARNING and CRITICAL and asserts both counters and that every world hash is unchanged.
