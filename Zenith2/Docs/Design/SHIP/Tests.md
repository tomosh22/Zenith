# SHIP design — tests

Companion to `Zenith2/Docs/Design/SHIP.md`. Every SHIP test: its file, its registration, the case it asserts and the gate step that runs it. SHIP has no C++ library, so its tests are CMake script-mode checks, PowerShell checks and one compile-fail test, registered in the SHIP block of the test registry `Zenith2/CMake/Tests/ZenithCMakeTests.cmake` ([Z2-N-ARCH-252]) through the registration forms of `Zenith2/Docs/Design/SHIP/CMakeHelpers.md` → "Registry functions"; the registry tail additionally registers every unlisted death case of every executable (§ "Test registration"). Every test is pass/fail only ([Z2-N-ARCH-228]), lands in the ticket of the code it tests, fails rather than skips when a pinned tool it needs is absent, generates its binary inputs at test time (the orchestrator's ruling Q55), and never needs a worker to compute or record a digest (§ "Fixture digests"); committed fixtures are small text files (JSON, expected-output `.txt`, hand-written recorded tool outputs).

<!-- elaboration -->
- `RunShipFixture.cmake` sets `ZENITH_SCRIPT_MODE`, sets `ZENITH_THIRD_PARTY_CACHE_ROOT` to the case's `cache/` directory under `${ZENITH_OUT}/test-fixtures/SHIP/<Case>/` (the committed `cache/` tree copied there first), expands the case's `*.json.in` templates (§ "Fixture digests"), includes `ZenithThirdParty.cmake`, `ZenithAddLibrary.cmake`, `ZenithAddTool.cmake` or `ZenithFlags.cmake` as the case's `case.cmake` names (the include defines functions only: the script-mode main of `ZenithThirdParty.cmake` runs only when `CMAKE_SCRIPT_MODE_FILE STREQUAL CMAKE_CURRENT_LIST_FILE`), runs the case, and compares the collected message and recorder lines with `<Case>/expect.txt` line by line (the scaffold runner's contract, `Zenith2/Docs/Design/MOD/GameBuild.md` → "CMake fixture tests"); a difference prints both lists and ends in `FATAL_ERROR`.
- Each `*.Tests.ps1` script takes `-Case <name>`, creates its working directory under `${ZENITH_OUT}/test-fixtures/SHIP/<Case>/` (emptied first), writes any archive, keystore, PFX, key file or git repository it needs there at test time, runs the case, and exits 0 on pass and 1 on failure with one `FAIL <Case>: <reason>` line.
- A PowerShell check that needs a built executable uses the `Minimal` game of the same tree (`Zenith2/Docs/Design/MOD.md` → "Repository games"), passed as `-Exe $<TARGET_FILE:Minimal>` and `-Pdb $<TARGET_PDB_FILE:Minimal>` in its `ARGS`; the `Build` step builds `Minimal` before the `Test` step runs (a CTest entry cannot depend on a build), and a check that needs one configuration's binary is registered with `CONFIGURATIONS <Config>` (`Zenith2/Docs/Design/SHIP/CMakeHelpers.md` → "zenith_register_script_test").

### Fixture digests

No committed SHIP fixture contains a SHA-256 of real bytes that a person or worker would have to compute (the worker-evidence and digest-refresh rulings; A5 brief clarification 2026-10-03 (d) item 1). Every digest a case needs is produced one of four ways:

| Way | Used by | How |
|---|---|---|
| computed at test time from the fixture bytes, by a function that is not under test | every case whose manifest names a licence file, a patch or an archive (`CMake_Ship_LicenceInventory_*`, `CMake_Ship_LicenceNoticesFormat`, `CMake_Ship_PatchedEntryDirectoryName`, `CMake_Ship_StampMismatch`, the `Pwsh_Ship_DigestVerify_*` cases) | a template `*.json.in` (and `expect.txt`) writes `@SHA256:<path relative to the case>@`; `RunShipFixture.cmake` replaces each token with CMake's built-in `file(SHA256)` of that file before the case runs, and the PowerShell cases build their archives and manifests at test time and hash them with .NET `[System.Security.Cryptography.SHA256]::HashData`; a cache stamp in a fixture is a template the same way |
| arbitrary literal | digests compared only with each other (the V-rule fixtures, a stamp that must mismatch, a recorded `apksigner` output whose signer digest is compared with a fixture profile's `releaseCertSha256`) | a repeated-character string such as 64 `a` or 64 `b`, written by hand |
| relations instead of values | `Pwsh_Ship_ManifestHashes_FingerprintFixtures`, `Pwsh_Ship_CheckoutHashMatchesSpec`, `Pwsh_Ship_ReleaseManifest_TwoSigningsSameReproducibleDigest` | the case asserts which hashes change and which stay equal, and recomputes each value with an independent implementation (CMake versus PowerShell, or .NET's SHA-256 over text the case builds from the specification), never against a committed value |
| hand-written specification text | `canonical-small.expected.txt` | the canonical JSON form of a small fixed value is derivable from § "Canonicalisation and hashing" of `Zenith2/Docs/Design/SHIP/Manifest.md` by hand (the GOLDEN-FILES ruling for spec-derivable outputs); its digest is never committed |
| published test vector | `Pwsh_Ship_Ed25519PublicKeyCheck_Rfc8032`, `Pwsh_Ship_UpdateSigningKey_Decrypts` | RFC 8032 § 7.1 TEST 1's seed and public key, copied by hand from the RFC (`Zenith2/Docs/Design/SHIP/Release.md` → "Update manifest signing hand-off"); the test derives nothing it then compares against itself |

The committed `Zenith2/ThirdParty/manifest.json` carries real digests, but a human writes them in the `needs-human` pinning tickets (Roadmap Stage 0 deliverable 14 and the per-consumer pinning tickets), never a worker; SHIP's tests only validate its structure.

## Integration suites

SHIP adds no integration suite under `Zenith2/Tests/`: its runtime-visible behaviour (the build ID, the Shipping exclusions, the licence assets) is exercised by the owning areas' suites and by the release verification.
