# RHI design: the Vulkan backend

This file is part of the RHI design family. The entry document is `Zenith2/Docs/Design/RHI.md`. It specifies `ZenithRHI_Vulkan`: how it realises every member of `Zenith2/Docs/Design/RHI/PublicAPI.md` on Vulkan 1.3 with volk, Vulkan-Profiles and VMA, on Windows and Android. Every Vulkan, volk, VMA and Vulkan-Profiles header is included from `Zenith2/Engine/ZenithRHI_Vulkan/Internal/` alone ([Z2-N-CONTRACT-043], Z2-D-026).

## Scope of this file

The specification this file elaborates is `Zenith2/Docs/Rendering.md → "GPU baseline and profiles"` (the Vulkan profile, capability negotiation, format features), `Zenith2/Docs/Rendering.md → "Binding model"` (the Vulkan heap realisation, push constant, draw ID), `Zenith2/Docs/Rendering/RenderGraph.md → "Barrier emission"`, `Zenith2/Docs/Rendering/GpuResources.md → "Queues and timelines"` and "Swapchain recreation", and `Zenith2/Docs/Rendering/ShaderSystem.md → "Persistent pipeline caches"`. It adds the backend's internal structure, the exact API calls, the mapping tables and the failure behaviour.

## Baseline profile check

### Profile file and generated tables

`VP_ZENITH2_baseline.json` holds exactly the rows of `Zenith2/Docs/Rendering.md → "GPU baseline and profiles"` (table "Vulkan baseline profile"), the formats section of the format-feature table ([Z2-N-REND-036]; the `platform=` rows of `FormatFeatures.table` appear in two platform-specific capability blocks, `baseline_windows` and `baseline_android`, which the profile's two `profiles` entries `VP_ZENITH2_baseline_windows` and `VP_ZENITH2_baseline_android` combine with the common block), and the heap-capacity limits as `maxDescriptorSetUpdateAfterBind*` minimums at the tier capacities of `Zenith_GetDefaultHeapCapacities` (desktop in the Windows profile, mobile in the Android profile). The Android device is checked against `VP_ZENITH2_baseline_android`, the Windows device against `VP_ZENITH2_baseline_windows`; both are the one `VP_ZENITH2_baseline` of [Z2-N-REND-020] specialised by platform.

`Zenith_VulkanBaselineTable.inl` is a `constexpr` array of `Zenith_VulkanRequirement { kind, name, structure type, member offset, minimum, platform mask }` rows with kinds `FEATURE`, `EXTENSION`, `LIMIT`, `FORMAT` and `VERSION`, one per requirement of the JSON.

### Refusal message

<!-- elaboration -->
For each physical device, in enumeration order:

1. `vpGetPhysicalDeviceProfileSupport(instance, physicalDevice, &xProfile, &bSupported)`.
2. When unsupported, walk the requirement table: query `VkPhysicalDeviceFeatures2` with the chained 1.1, 1.2, 1.3 and extension feature structures, `VkPhysicalDeviceProperties2` with the chained limit structures, `vkEnumerateDeviceExtensionProperties`, and `vkGetPhysicalDeviceFormatProperties2` for each format row; collect every failed row.
3. Format the refusal line:

```text
rhi: Vulkan device '<deviceName>' (vendor 0x<VVVV> device 0x<DDDD> driver <major.minor.patch>) does not support profile VP_ZENITH2_baseline_<platform>: missing <item>[, <item>…]
<item> := feature <name> | extension <name> | limit <name> <have> < <need> | format <VK_FORMAT_name> <letters missing> | version <have> < 1.3
```

4. Log the line at `LOG_LEVEL_ERROR` in category `rhi.vulkan`, append it to `Zenith_RHIDeviceReport::m_acRefusal`, and continue with the next device.

When no device passes, the factory returns `ZENITH_RHI_ERROR_PROFILE_UNSUPPORTED`; the report holds every device's line in enumeration order, which the composition root prints before exiting with code 4. Items are listed in table order, so the message for a given device and driver is byte-identical on every run, which `Test_VulkanProfile_RefusalListsEveryMissingItem` asserts against a mocked capability report.

## Physical device selection

| Rank | Rule |
|---|---|
| 1 | discard devices that fail the profile (the refusal message above) |
| 2 | `m_eAdapterPreference == SOFTWARE`: keep devices of type `VK_PHYSICAL_DEVICE_TYPE_CPU` (lavapipe) only |
| 3 | `m_szAdapterFilter`: keep devices whose `deviceName` contains the filter, case-insensitively |
| 4 | order by type (discrete, integrated, virtual, CPU), then by device-local heap size descending, then by enumeration index |
| 5 | take the first; none left: `ZENITH_RHI_ERROR_NO_ADAPTER` with the filter and preference in the message |

CI selects lavapipe by `rhi.adapter=software` with the loader's `VK_DRIVER_FILES` set to the pinned lavapipe ICD manifest by the shared gate environment (`Zenith2/Docs/Contracts.md → "Tests and code hygiene gates"`, heading "Shared gate environment").

The capability fill reads, once: vendor, device and driver version from `VkPhysicalDeviceProperties`; `pipelineCacheUUID`; `m_bDepthD24S8` from `vkGetPhysicalDeviceFormatProperties2(VK_FORMAT_D24_UNORM_S8_UINT)` having `DEPTH_STENCIL_ATTACHMENT` and `SAMPLED_IMAGE`; `m_bMeshShaders` from `VK_EXT_mesh_shader` with `meshShader` and `taskShader`; the queue flags of "Queue families"; `timestampValidBits` per chosen family; the optional extensions of the specification's list; `subgroupSizeControl` minimum and maximum; `m_ulDeviceLocalBytes` as the largest `DEVICE_LOCAL` heap; `m_ulHostVisibleDeviceLocalBytes` as the largest heap with a `DEVICE_LOCAL | HOST_VISIBLE` memory type; the tier from the platform (desktop on Windows, mobile on Android); `m_bSoftwareAdapter` for type CPU.

## Queue families

| Queue | Family chosen | Queue index |
|---|---|---|
| graphics | the first family with `GRAPHICS \| COMPUTE \| TRANSFER` that `vkGetPhysicalDeviceSurfaceSupportKHR` reports can present to the main window (on Android the family presenting to the current `ANativeWindow`) | 0 |
| async compute | the first family with `COMPUTE` and without `GRAPHICS`; else, when the graphics family has two or more queues, the graphics family | 0; or 1 in the graphics family |
| copy | the first family with `TRANSFER` and neither `GRAPHICS` nor `COMPUTE` | 0 |

A class with no family is aliased to the graphics queue: `HasDedicatedQueue` returns false, `GetTimeline` returns the graphics timeline, and the capability flags `m_bAsyncComputeQueue` and `m_bCopyQueue` are false ([Z2-N-REND-485] table). Every resource whose `m_uQueueMask` names more than one distinct family is created `VK_SHARING_MODE_CONCURRENT` over exactly those families; graph textures stay `EXCLUSIVE` and move between families by release/acquire pairs (`Zenith2/Docs/Design/RHI/RenderGraphBackend.md → "Queue-family ownership transfers"`).

## Logical device and volk

`vpCreateDevice(physicalDevice, &xVpDeviceCreateInfo, nullptr, &device)` with the chosen queues and the optional extensions present on the device (`VK_EXT_mesh_shader`, `VK_EXT_memory_budget`, `VK_EXT_calibrated_timestamps`, `VK_KHR_present_id`, `VK_KHR_present_wait`, `VK_EXT_device_fault`, `VK_NV_device_diagnostic_checkpoints`, `VK_AMD_buffer_marker`, `VK_GOOGLE_display_timing`, `VK_EXT_hdr_metadata` (recorded as `Zenith_RHICapabilities::m_bHdrMetadata`; an elaboration for LIGHT's HDR10 metadata until Rendering's optional-extension list names it, entry document "Reconciliation items" R20), and `VK_EXT_mutable_descriptor_type` under D-SLANG (open, Stage 1) alternative 1). `volkLoadDeviceTable(&m_xTable, device)` fills a `VolkDeviceTable` member of `Zenith_VulkanDevice`; every device-level call in the backend goes through `m_xTable.<fn>`, never through a global volk pointer or a loader trampoline ([Z2-N-REND-021]), which also keeps the device's dispatch state out of mutable globals ([Z2-N-CONTRACT-141]; volk's own instance-level globals live in its third-party root, outside the writable-data scan's scope).

## Memory through VMA

`vmaCreateAllocator` with `vulkanApiVersion = VK_API_VERSION_1_3`, `pVulkanFunctions` from `vmaImportVulkanFunctionsFromVolk` over the device table, `VMA_ALLOCATOR_CREATE_EXT_MEMORY_BUDGET_BIT` when `VK_EXT_memory_budget` is present ([Z2-N-REND-022]), `VMA_ALLOCATOR_CREATE_KHR_MAINTENANCE4_BIT`, and `pAllocationCallbacks` routing every host allocation VMA makes to `Zenith_Heap` through `Zenith2/Engine/ZenithRHI_Vulkan/Internal/Zenith_VulkanHostAllocator.cpp`.

| `Zenith_RHIMemoryClass` | VMA usage | Flags |
|---|---|---|
| `DEVICE_LOCAL` | `VMA_MEMORY_USAGE_AUTO_PREFER_DEVICE` | none; suballocated from VMA's default blocks |
| `DEVICE_DEDICATED` | `VMA_MEMORY_USAGE_AUTO_PREFER_DEVICE` | `VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT` |
| `UPLOAD` | `VMA_MEMORY_USAGE_AUTO_PREFER_DEVICE` | `HOST_ACCESS_SEQUENTIAL_WRITE_BIT \| MAPPED_BIT`; a memory type that is `DEVICE_LOCAL \| HOST_VISIBLE \| HOST_COHERENT` wins (ReBAR, the S24's unified memory), otherwise `HOST_VISIBLE \| HOST_COHERENT` system memory |
| `READBACK` | `VMA_MEMORY_USAGE_AUTO_PREFER_HOST` | `HOST_ACCESS_RANDOM_BIT \| MAPPED_BIT` |

- Heaps (`CreateHeap`) are `vmaAllocateMemory` calls with `VkMemoryRequirements{ size, alignment = 64 KiB, memoryTypeBits = 1 << (placementGroup >> 1) }`; placed resources are `vmaCreateAliasingImage2` / `vmaCreateAliasingBuffer2` at the offset ([Z2-N-REND-435]).
- `GetTextureMemoryRequirements` and `GetBufferMemoryRequirements` use `vkGetDeviceImageMemoryRequirements` and `vkGetDeviceBufferMemoryRequirements` (maintenance4) on the create-info the create call would use, and return `placementGroup = (vmaFindMemoryTypeIndexForImageInfo(…) << 1) | (tiling == LINEAR ? 1 : 0)`, so optimal-tiled images and buffers never share a group and `bufferImageGranularity` never applies inside one ([Z2-N-REND-503] table).
- `QueryHeapBudgets` is `vmaGetHeapBudgets` over the memory heaps, `m_bDeviceLocal` from `VK_MEMORY_HEAP_DEVICE_LOCAL_BIT`; without `VK_EXT_memory_budget` the budget is 80% of the heap size and the usage VMA's own statistics.

## Descriptor heap realisation

Exactly one descriptor set layout, one pool and one set exist ([Z2-N-REND-053]); their bindings follow the D-SLANG (open, Stage 1) alternative table of `Zenith2/Docs/Rendering.md → "Binding model"` (heading "Vulkan heap realisation").

| Object | Creation |
|---|---|
| set layout | `vkCreateDescriptorSetLayout` with `VK_DESCRIPTOR_SET_LAYOUT_CREATE_UPDATE_AFTER_BIND_POOL_BIT`; binding flags `PARTIALLY_BOUND \| UPDATE_AFTER_BIND \| UPDATE_UNUSED_WHILE_PENDING` on every array binding through `VkDescriptorSetLayoutBindingFlagsCreateInfo`; the static samplers as `pImmutableSamplers` of the sampler binding |
| pool | `vkCreateDescriptorPool` with `UPDATE_AFTER_BIND_BIT`, `maxSets = 1`, one pool size per binding equal to the space capacity |
| set | `vkAllocateDescriptorSets`, once, at device creation |
| null substitutes | slot 0 of each space is written at creation with the 1×1 magenta texture and the 256-byte zero buffer ([Z2-N-REND-031]) |

`Zenith_RHIDescriptorHeap::Write` builds one `VkWriteDescriptorSet` (image view for texture spaces with layout `SHADER_READ_ONLY_OPTIMAL` or `GENERAL`, `VkDescriptorBufferInfo` for buffer spaces) and calls `vkUpdateDescriptorSets` under `uLOCK_LEVEL_RHI_DESCRIPTOR_WRITE` (460), because the specification requires external synchronisation of the destination set even when the updated elements differ. Image views are created at the write (`vkCreateImageView` with the view desc) and stored in the slot's record, destroyed at the slot's retirement.

## Pipeline layout and pipelines

- One global `VkPipelineLayout`: the set layout plus `VkPushConstantRange{ VK_SHADER_STAGE_ALL, 0, 8 }` ([Z2-N-REND-053]); every pipeline uses it. The range is the push-constant block Slang reflects for every entry point's `uniform Flux_PushConstants` parameter (no shader carries a `vk::` attribute), and `ZenithShaderCompiler` refuses a program whose reflected block differs with `ZSC_ERROR_PUSH_CONSTANTS` (`Zenith2/Docs/Design/RPROD/PSO.md → "Compiler pipeline"`, step 6).
- Graphics pipelines: `VkGraphicsPipelineCreateInfo` chained with `VkPipelineRenderingCreateInfo` (colour formats, depth and stencil format from `m_eDepthFormat`), dynamic state `VIEWPORT`, `SCISSOR`, `STENCIL_REFERENCE`; vertex input from the desc's streams and attributes; `frontFace = VK_FRONT_FACE_COUNTER_CLOCKWISE` ([Z2-N-REND-198]); `rasterizationSamples = VK_SAMPLE_COUNT_1_BIT` always ([Z2-N-REND-010]); write masks per attachment from the raster state.
- Shader modules are not created: blobs are passed through `VkPipelineShaderStageCreateInfo` chained with `VkShaderModuleCreateInfo` (maintenance5 is not assumed; where it is absent the module is created and destroyed around the pipeline creation). A blob whose first word is not the SPIR-V magic `0x07230203` is `ZENITH_RHI_ERROR_SHADER_BLOB_INVALID`.
- Compute pipelines: `vkCreateComputePipelines`. Mesh pipelines: task, mesh and pixel stages with `VK_EXT_mesh_shader`; without it `CreateMeshPipeline` returns `ZENITH_RHI_ERROR_FEATURE_UNAVAILABLE`.
- `VkPipelineCreationFeedbackCreateInfo` is chained on every create; `VK_PIPELINE_CREATION_FEEDBACK_APPLICATION_PIPELINE_CACHE_HIT_BIT` sets `Zenith_RHIPipelineCreateResult::m_bCacheHit` and increments `RHI.Pipelines.CacheHits`, its absence `RHI.Pipelines.CacheMisses`; Flux's PSO code derives `Flux.PSO.CacheHits`/`CacheMisses` ([Z2-N-REND-212] table) from the returned flag (pending X71(f)).

## Barrier translation

`Zenith_Vk_ToStage`, `Zenith_Vk_ToAccess` and `Zenith_Vk_ToLayout` in `Internal/Zenith_VulkanBarriers.cpp` are the one mapping of the neutral vocabulary onto `VkPipelineStageFlags2`, `VkAccessFlags2` and `VkImageLayout`; with `Flux_ToRHIBarrier` (`Zenith2/Docs/Design/RHI/RenderGraphBackend.md → "Neutral barrier translation"`) they realise the Vulkan columns of `Zenith2/Docs/Rendering/RenderGraph.md → "Barrier state machine"` (table "Access states") exactly.

| Neutral | Vulkan |
|---|---|
| stage bits | `DRAW_INDIRECT`, `INDEX_INPUT`, `VERTEX_ATTRIBUTE_INPUT`, `VERTEX_SHADER`, `TASK_SHADER_EXT`, `MESH_SHADER_EXT`, `FRAGMENT_SHADER`, `EARLY_FRAGMENT_TESTS`, `LATE_FRAGMENT_TESTS`, `COLOR_ATTACHMENT_OUTPUT`, `COMPUTE_SHADER`, `COPY`, `CLEAR`, `ALL_COMMANDS` (`_BIT` of `VK_PIPELINE_STAGE_2_`) |
| access bits | `INDIRECT_COMMAND_READ`, `INDEX_READ`, `VERTEX_ATTRIBUTE_READ`, `SHADER_SAMPLED_READ`, `SHADER_STORAGE_READ`, `SHADER_STORAGE_WRITE`, `COLOR_ATTACHMENT_READ`, `COLOR_ATTACHMENT_WRITE`, `DEPTH_STENCIL_ATTACHMENT_READ`, `DEPTH_STENCIL_ATTACHMENT_WRITE`, `TRANSFER_READ`, `TRANSFER_WRITE` (`_BIT` of `VK_ACCESS_2_`) |
| layouts | `UNDEFINED` → `UNDEFINED`; `GENERAL` → `GENERAL`; `SHADER_READ` → `SHADER_READ_ONLY_OPTIMAL`; `COLOUR_ATTACHMENT` → `COLOR_ATTACHMENT_OPTIMAL`; `DEPTH_STENCIL_WRITE` → `DEPTH_STENCIL_ATTACHMENT_OPTIMAL`; `DEPTH_STENCIL_READ` → `DEPTH_STENCIL_READ_ONLY_OPTIMAL`; `TRANSFER_SRC`/`DST` → `TRANSFER_SRC_OPTIMAL`/`DST_OPTIMAL`; `PRESENT` → `PRESENT_SRC_KHR`; `COMMON` → `GENERAL`; `PERSISTENT_READ` → `SHADER_READ_ONLY_OPTIMAL` |

`DoRecordBarriers` builds one `VkDependencyInfo` holding one `VkImageMemoryBarrier2` per texture barrier (queue family indices equal, or the release or acquire family pair for a transfer half, with `srcStageMask`/`srcAccessMask` zero on an acquire and `dstStageMask`/`dstAccessMask` zero on a release), one `VkBufferMemoryBarrier2` per buffer barrier and at most one `VkMemoryBarrier2` for the global barrier, and records `vkCmdPipelineBarrier2` once ([Z2-N-REND-389]). A texture barrier with `m_bDiscard` uses `oldLayout = UNDEFINED`. `DoBeginSplit` (elaboration: the pool sizing below) takes a `VkEvent` from the frame slot's event pool (grown in blocks of 64, reset at `BeginFrameSlot`) and records `vkCmdSetEvent2` with the batch's dependency info; `DoEndSplit` records `vkCmdWaitEvents2` with the same info ([Z2-N-REND-393]).

## Submission and timelines

- Each physical queue has one `VkSemaphore` of type `VK_SEMAPHORE_TYPE_TIMELINE` (initial value 0). `Submit` takes the queue's `uLOCK_LEVEL_RHI_QUEUE_SUBMIT` lock (400), assigns `value = last + 1`, and calls `vkQueueSubmit2` with the command buffers, one `VkSemaphoreSubmitInfo` wait per `Zenith_RHITimelineWait` (stage `ALL_COMMANDS`), the swapchain's acquire binary semaphore when `m_pxWaitAcquire` is set (stage `COLOR_ATTACHMENT_OUTPUT`), the timeline signal (stage `ALL_COMMANDS`), and the image's render-complete binary semaphore when `m_pxSignalPresentReady` is set ([Z2-N-REND-487]).
- `GetCompletedValue` is `vkGetSemaphoreCounterValue`. `WaitCPU` is `vkWaitSemaphores` with the timeout; `VK_TIMEOUT` returns `ZENITH_RHI_WAIT_STATUS_TIMEOUT`, after which the caller (`Flux_FrameLifetime`) checks for loss with a zero-timeout `vkGetFenceStatus` on the queue's loss-probe fence, which a lost device reports as `VK_ERROR_DEVICE_LOST` ([Z2-N-REND-486]).
- `WaitIdle(timeout)` reads each physical queue's last-signalled value and calls `vkWaitSemaphores` on that queue's timeline for it, one queue at a time, each with the timeout and the loss check above; it never calls `vkDeviceWaitIdle` or `vkQueueWaitIdle` (elaboration, pending X89).
- `VK_ERROR_DEVICE_LOST` from any submit, wait or present moves the device to `ZENITH_RHI_DEVICE_STATUS_LOST` (entry document "Device status state machine").

## Swapchain and presentation

| Element | Rule |
|---|---|
| surface | `Zenith_Window::CreateVulkanSurface(instance)` returns the `VkSurfaceKHR` value; `DestroyVulkanSurface` on destroy and on `ReleaseSurface` |
| format and colour space | SDR: `B8G8R8A8_SRGB` with `SRGB_NONLINEAR_KHR`; HDR10: `A2B10G10R10_UNORM_PACK32` with `HDR10_ST2084_EXT`; scRGB: `R16G16B16A16_SFLOAT` with `EXTENDED_SRGB_LINEAR_EXT` ([Z2-N-REND-985]); a pair the surface does not list falls back to SDR, `rhi.swapchain: <output> unavailable, using sdr` |
| present mode | FIFO → `FIFO_KHR`; FIFO_RELAXED → `FIFO_RELAXED_KHR`; MAILBOX → `MAILBOX_KHR`; IMMEDIATE → `IMMEDIATE_KHR`; an unsupported mode falls back to FIFO and `GetInfo().m_ePresentMode` reports it |
| image count | the device's `GetFramesInFlight()` + 1, clamped to `[minImageCount, maxImageCount]` |
| usage | `COLOR_ATTACHMENT \| TRANSFER_DST` |
| transform | `preTransform = currentTransform`; `m_eTransform` reports it, and Flux's present pass rotates the final image (Recovery.md "Swapchain model") |
| sync objects | an acquire binary semaphore per frame slot; a render-complete binary semaphore per swapchain image |
| present ID | with `VK_KHR_present_id` each present carries `m_ulPresentID` (strictly increasing); `WaitForPresent` is `vkWaitForPresentKHR` with `VK_KHR_present_wait` |
| timings | `vkGetPastPresentationTimingGOOGLE` on Android with `VK_GOOGLE_display_timing`; empty elsewhere |
| desired present time | `SetDesiredPresentTime` chains `VkPresentTimesInfoGOOGLE` into the matching present's `pNext` with `VK_GOOGLE_display_timing`, else `FEATURE_UNAVAILABLE` (Recovery.md "Frame pacing hooks") |
| swap interval | `SetSwapInterval` validates 1 to 4 and records it in `GetInfo().m_uSwapInterval`; FIFO presents are unaffected |
| colour-space report | `vkGetPhysicalDeviceSurfaceFormatsKHR` at every creation and recreation fills `m_uOutputColourSpacesSupported` from the three pairs above; `m_bDisplayHdr` is whether `HDR10_ST2084_EXT` is listed; `m_fDisplayMaxLuminanceNits` is 0 |
| HDR metadata | `SetHDRMetadata` calls `vkSetHdrMetadataEXT(device, 1, &swapchain, &xMetadata)` through the device table with `VkHdrMetadataEXT` filled member for member (`displayPrimaryRed/Green/Blue`, `whitePoint`, `maxLuminance`, `minLuminance`, `maxContentLightLevel`, `maxFrameAverageLightLevel`) when `VK_EXT_hdr_metadata` is enabled, else `FEATURE_UNAVAILABLE` |
| recreation | `vkCreateSwapchainKHR` with `oldSwapchain` set; the old images (texture-table entries) are enqueued on the retirement queue from the main thread at the render-idle point of the recreation, with the graphics value of the last frame that used them ([Z2-N-REND-983]); the old `VkSwapchainKHR` is destroyed by the backend when the last of its image entries retires; no `vkDeviceWaitIdle` for any trigger (a frames-in-flight change idles through `WaitIdle`'s timeline waits) |
| surface release | `ReleaseSurface` destroys the image entries, the `VkSwapchainKHR` and, through `Zenith_Window::DestroyVulkanSurface`, the `VkSurfaceKHR` at once, in that order, after the wait of Recovery.md "Android surface loss" (a named immediate destruction, entry document "Rules across the API"), calling the retirement listener for each image |

`AcquireNextImage` calls `vkAcquireNextImageKHR` with timeout `rhi.gpuWaitTimeoutMs` in nanoseconds: `VK_ERROR_OUT_OF_DATE_KHR` returns `ZENITH_RHI_ERROR_SWAPCHAIN_OUT_OF_DATE`, `VK_SUBOPTIMAL_KHR` succeeds and sets the recreate recommendation, `VK_TIMEOUT` returns `ZENITH_RHI_ERROR_TIMEOUT`, `VK_ERROR_SURFACE_LOST_KHR` returns `SURFACE_UNAVAILABLE`. While the platform marks the surface lost ([Z2-N-ARCH-916]), acquire and present return `SWAPCHAIN_OUT_OF_DATE` without calling Vulkan. `Present` calls `vkQueuePresentKHR` on the graphics queue under its submit lock with the image's render-complete semaphore.

## Pipeline cache

`CreatePipelineCache(payload)` validates the payload's `VkPipelineCacheHeaderVersionOne` (header size, `VK_PIPELINE_CACHE_HEADER_VERSION_ONE`, vendor, device and UUID against the capabilities) before passing it as `pInitialData`; a mismatch creates an empty cache and sets `WasLoadRejected`. `Serialize` calls `vkGetPipelineCacheData` twice (size, then data into the arena). The Zenith2 file header around the payload, the file name and the invalidation triggers are `Zenith2/Docs/Design/RHI/Recovery.md → "Pipeline cache store"`.

## Debug utils and validation

- Object names: `vkSetDebugUtilsObjectNameEXT` for images, buffers, pipelines, command buffers, queues and semaphores, from the desc's `m_szName`, when `m_bDebugNames`.
- Queue labels: `vkQueueBeginDebugUtilsLabelEXT` around each submission batch with the frame index, so captures and validation messages name the frame.
- Synchronization validation reports hazards through the messenger; each is a `Zenith_RHIValidationMessage` of severity error.

## Device loss and fault reports

`CollectDeviceFaultReport` fills the breadcrumb reports (Recovery.md "Breadcrumbs"), `m_acReason` (`VK_ERROR_DEVICE_LOST`), the driver version and, with `VK_EXT_device_fault`, calls `vkGetDeviceFaultInfoEXT` twice (counts, then data into a 64 KiB stack-independent arena owned by the device, allocated at creation so that no allocation happens after loss), copying the description, the first address info's `reportedAddress` and the first vendor info's `vendorFaultCode`.

## Timestamps and calibration

`CreateTimestampPool` creates a `VK_QUERY_TYPE_TIMESTAMP` pool; `ResetTimestampPool` is `vkResetQueryPool` (host query reset, in the profile). `ReadTimestamps` is `vkGetQueryPoolResults(… VK_QUERY_RESULT_64_BIT)` without `WAIT_BIT`, called after the frame's timeline value completed. `GetTimestampPeriodNs` is `timestampPeriod`. `GetClockCalibration` uses `vkGetCalibratedTimestampsEXT` over `VK_TIME_DOMAIN_DEVICE_EXT` and `QUERY_PERFORMANCE_COUNTER_EXT` (Windows) or `CLOCK_MONOTONIC_EXT` (Android), converted to monotonic nanoseconds.

## RenderDoc capture on Vulkan

When `rhi.capture=renderdoc` (development builds only), before instance creation: `GetModuleHandleW(L"renderdoc.dll")` (the tool already injected), else `LoadLibraryW(L"renderdoc.dll")` from the path in the `RENDERDOC_PATH` environment variable; on Android `dlopen("libVkLayer_GLES_RenderDoc.so", RTLD_NOW | RTLD_NOLOAD)`. `RENDERDOC_GetAPI(eRENDERDOC_API_Version_1_6_0)` gives the API table, stored in the device's `Zenith_VulkanRenderDocTool`. `BeginFrameCapture` calls `StartFrameCapture(RENDERDOC_DEVICEPOINTER_FROM_VKINSTANCE(instance), nullptr)`, `EndFrameCapture` `EndFrameCapture(…)`. A missing library leaves `GetCaptureTool()` null and logs `rhi.capture: RenderDoc not found; captures unavailable`.

## Android specifics

- The loader is the system `libvulkan.so`, reached through SDL; volk resolves it the same way as on Windows.
- `VP_ZENITH2_baseline_android` requires `textureCompressionASTC_LDR` and the mobile heap capacities; the Stage 1 S24 profile ticket confirms it on the Adreno 750 ([Z2-N-REND-023]).
- The swapchain is created with `VK_COMPOSITE_ALPHA_INHERIT_BIT_KHR` when supported, else `OPAQUE`.
- Surface loss follows the platform handshake exactly as `Zenith2/Docs/Design/RHI/Recovery.md → "Android surface loss"` specifies it: `Flux_SwapchainManager::OnReleaseSurface` waits on the graphics timeline with the handshake's remaining budget as its one timeout, calls `ReleaseSurface` when the wait completed, and enters `SURFACE_STALE` without releasing when it ran out; the device and every resource stay alive ([Z2-N-ARCH-914]).
- HWASan builds use the same backend; the Vulkan driver is not instrumented, and host allocations the driver makes through the callbacks go to `Zenith_Heap`, which HWASan instruments.
