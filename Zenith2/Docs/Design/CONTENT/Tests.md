# CONTENT design: tests

This file is part of the CONTENT design family; the entry document is `Zenith2/Docs/Design/CONTENT.md`. It lists every named CONTENT test with its file and the case it asserts, the fixture generation, the fuzz targets, the needs-human recordings and the gate step that runs each group. Test names follow `Zenith2/Docs/Contracts.md → "Tests and code hygiene gates"` (doctest name `"<Library>/<Type>/<Behaviour>"`, ID `Test_<Type>_<Behaviour>`); every name is prefixed with a CONTENT type, so none collides with another area's. Expectations are derived from the specifications (the probe asset and its bitangent table, the format tables, the algorithms, the fixed SHA-256 vectors), never recorded by a worker; no test uses a double of a `final` class: importers run in ASSET's `Zenith_MakeImportTestContext` contexts and steps in `Zenith_MakeCookTestContext` contexts (`Zenith2/Tools/ZenithCook/Internal/Cook/Zenith_CookTestContexts.h`, settings from `Zenith_MakeTestImportSettings`; `Zenith2/Docs/Design/GEOM.md → "Fixtures"`), batches over real `Zenith_HostDocumentStorage` roots in temporary directories and a recording `Zenith_ContentCookChannel` (an implementation of CONTENT's own interface, selected by the test), and every time-dependent case through the `Zenith_ContentClock` seam with a scripted clock.

The recording cook channel `Zenith_RecordingContentCookChannel` (`Zenith2/Tools/Authoring/Tests/CONTENT/Support/Zenith_RecordingContentCookChannel.h`, header-only, [Z2-N-ARCH-255]) records every request, answers from a scripted table, can fail the n-th request, and can hold any answer PENDING for a scripted number of polls; integration tests use the real channel over a `ZenithCook --serve` child. The scripted clock `Zenith_ScriptedContentClock` (`Zenith2/Tools/ContentCore/Tests/Support/Zenith_ScriptedContentClock.h`, header-only) returns times a test sets and advances. No CONTENT unit test starts a helper process: a writer lock held "by another process" is held by a second `Zenith_HostDocumentStorage` over the same root, whose open handle denies writers exactly as another process's would (`Zenith2/Docs/Design/SCENE/DocumentFramework.md → "Storage-root writer lock"`), and the multi-process store cases run real `ZenithCook` processes in the integration suite.

## Fixture generation

- glTF sources: `Zenith_TestGltfBuilder` writes `.gltf` JSON with base64 data URIs from a C++ description (nodes as TRS or `matrix`, meshes with any attribute set, skins, morphs, animations, materials, images as in-memory PNG, cameras, lights, extensions, `extras.zenithId`); `.glb` by its `WriteGlb`; meshopt-compressed views by calling meshoptimizer's encoder in the test; `ApplyInverseConversion(desc)` re-expresses a description in another convention (positions, normals, tangents with w × det Q, rotations, scales) for the conversion cases, and when det Q = −1 it also writes every triangle (a, b, c) of the description as (a, c, b), because the importer reverses every triangle under a mirror conversion (`Zenith2/Docs/Design/CONTENT/DccMatrix.md → "Winding and the negative-determinant rule"`), so a correct import restores the description's outward winding.
- Images: `Zenith_TestPngWriter` (stored-deflate PNG, 8- and 16-bit, grey, RGB, RGBA, palette), TGA and BMP writers in the same header; JPEG from stb_image_write is not used (no encoder dependency): the JPEG cases decode the recorded fixture of "Needs-human recordings".
- Audio: `Zenith_TestWavWriter` (PCM 8/16/24/32, float 32/64, extensible, `smpl`, `cue `, `LIST/adtl`), an AIFF writer in the same header, `Zenith_TestFlacWriter` (verbatim subframes, CRC-8 and CRC-16, STREAMINFO and VORBIS_COMMENT blocks); Ogg Vorbis and MP3 decode the recorded fixtures.
- Merge schemas: `Zenith_TestMergeSchemas.h` (`Zenith2/Tools/ContentCore/Tests/Support/`, header-only) builds ContentCore test canonical schemas that use every node kind SCENE's scene schema uses (OBJECT, ID_MAP, KEYED_MAP, FIELD_SET, ORDERED_ARRAY with KEYED and SET rules, INLINE_ARRAY, VALUE, OPAQUE), so the merge tests and the fuzz target need no SCENE link.
- Recorded fixtures are read through `Zenith_LoadRecordedFixture(path, bytesOut)` (`Zenith2/Tools/ContentCore/Tests/Support/Zenith_RecordedFixtures.h`, header-only), which fails the calling test with `<path> is a git-lfs pointer, not the recorded file: install git-lfs and run git lfs pull (Setup-Zenith2.ps1 does both)` when the file begins `version https://git-lfs.github.com/spec/v1` (`Zenith2/Docs/Design/CONTENT/SharedCache.md → "Storage policy check"`); ZenithCook's DCC tests read their recorded exports through the same check in `Zenith2/Tools/ZenithCook/Tests/Importers/Support/Zenith_DccFixtures.h` (header-only).
- The fixture game: `Zenith_WriteContentGameFixture(Zenith_StringView strDirectory)` (`Zenith2/Tests/ContentPipeline/Support/Zenith_ContentGameFixture.h`, header-only) writes it into a directory; the case `Fixture_ContentGame_Generate` of `Zenith_Integration_ContentPipeline` (suite `z2-fixture-setup`) calls it to write `${ZENITH_OUT}/test-fixtures/CONTENT/ContentGame/` (variable `ZENITH2_CONTENT_FIXTURES`; CTest entry `CONTENT_GameFixtures`, fixture `ContentGameFixtures`; consuming suite `z2-content-cooked`, [Z2-N-ARCH-257]); nothing of it is committed (Q55). Its contents grow by stage, each stage's set written by the generator as the tickets of that stage extend it:

  | Stage | Contents the generator writes |
  |---|---|
  | 3 (the ticket that creates the suite) | `game.json`; the probe as `.gltf`; a 60-joint character with 3 clips and no `zenithId` and no morph target; a prop set of 8 `.gltf` props; 20 PNGs of at most 256 × 256 texels; 4 WAVs of at most 1 s each (48,000 Hz, 2 channels, 16-bit); one FLAC of 1 s; a `.meta` file for every source, each image's with an explicit `texture.usage` (no preset exists yet); scenes whose entities reference the imported `mesh:` products directly |
  | 4 (added by the tickets that deliver presets, the generated model prefab and ANIM's clip documents) | 12 morph targets and `zenithId`s on the character's bones; presets, with `.meta` files naming them; an ANIM clip annotation document; scenes instancing the generated model prefabs, and a prefab variant |

  The 15 s cold-cook bound of "Integration suite" rests on these sizes: the PNGs are the bulk of the cook (20 × 256² texels), and no source exceeds 1 MiB.
